# Studium · agent 工作约定

> 本文件是会话开场上下文，只回答「怎么在这个仓库干活」。项目结论不写在这里，一律以权威文件为准。

## 交流方式（硬要求，每次回复都适用）

文档变大后 agent 的上下文注意力会下降：长总结会变乱、变杂、夹黑话，甚至出错。所以：

- **一次只讲一条**：按 1.1 / 1.2 / 1.3 往下讲，一条讲清楚、等你回应，再讲下一条；**不要并列铺开多个主题**。
- **不做大总结**：不要把刚谈过的内容再汇总成表；你要的是继续往下谈。
- **先人话、后术语**：能不用黑话就不用；必须用的，第一次出现时用一句话解释。
- **不确定就说不确定**：拿不准的直接标出来，不要用推断把话填满。
- **讨论期不落盘**：你没说「写 / 落盘」之前，不改仓库文件、不提前做交付物。
- **默认短**：确实必须长的时候（例如完整代码、完整清单），先说清为什么必须长。

## 第一步

每次会话先读 `任务线路.md`：它记录当前位置、下一步、该开哪个文件。不要从本文件或目录结构反推进度。

| 层 | 文件 | 能不能当结论 |
| --- | --- | --- |

## 待裁决项

新增待裁决项的顺序：先写入 `docs/实现基线/模块检查点.md` 的§未决项登记，再在 `任务线路.md` §4 加一行。汇总索引见 `docs/Harness设计/待确认项.md`（§一 待我方主张 · §二 暂缓 / 待设计 · §三 别处登记的待拍板项）。

**举手问产品负责人之前先过筛子**：① 这真是产品决策吗？② 是不是组合层关系（谁读谁、谁用谁、缺料怎么办）——那由设计侧自己定，不问；③ 是不是实现细节（编号形态、性能阈值）——登记到实现期，不问。犯过的错：把②③混进待拍板清单，浪费产品负责人的时间。

## 文档规范（`docs/` 下面向 agent 阅读，不面向人类）

- 单文件上限 **400 行**；超出则拆分为多文件 + 索引 README。
- 优先结构化：**表格 > 列表 > 段落**，避免长段落叙事。
- 每个子目录的 README 必须列出全部文件 + 一行描述。
- 同一信息只在一处定义，其他地方引用，不重复。
- 文件头部标注状态：待定 / 已决 / 已归档。
- **内容偏了就删**：方向错误或已废弃的文档、段落、结论一律直接删除——不改名、不加括号、不留「已删除」占位、不保留旧版本。留在文档里的错误内容总会把后续 agent 带偏。

## 维护 `任务线路.md`

它是**定位页**，不承载结论。推进后只更新：顶部「最后更新」、§1 一句话、§3 队列状态；阶段切换时更新 §2 状态词。结论一律指向权威文件，避免双写冲突。
