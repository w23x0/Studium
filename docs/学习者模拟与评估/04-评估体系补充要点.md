## 1 词汇（B）

| 词 | 意思 | 在我们这里 |
| --- | --- | --- |
| 任务 | 一条测试：输入加成功标准 | 一个人设 + 一段知识链 + 开场 |
| 试次 | 对一个任务的一次尝试；输出每次不同，所以要多跑几次 | 同一任务跑一整段对话算一次 |
| 打分器 | 给表现某一方面打分的逻辑；一个任务可以有多个 | 例如“是否代做学习者的一步”“讲解是否对着误解” |
| 记录 | 一次试次的全部过程 | `runs/<名>/transcript.md` 加每轮的调用记录 |
| 结果 | 试次结束时环境里的最终状态；和“嘴上说做完了”不同 | 模拟学习者人设卡里的知识状态变化（见 §4） |
| 评估外壳 | 跑评估的那套程序 | 待建 |
| agent 外壳 | 让模型成为 agent 的那套程序；评一个 agent，评的是外壳加模型 | `proto/` 的教学循环 |

## 2 评估的两种用途（B）

| 种类 | 问的是 | 通过率 | 在我们这里 |
| --- | --- | --- | --- |
| 能力评估 | 这件事能不能做好？ | 从低处开始，留出往上爬的空间 | 交互契约里还做不好的行为，例如回复停在该停的地方 |
| 回归评估 | 以前能做的，现在还能做吗？ | 接近 100% | 已经解决的问题，例如“不开场考前置”（me-8）、“不出谜题”；每次改提示词都跑，防止倒退 |

能力评估做到接近满分后，就“毕业”转成回归评估。

B 的一个说法和本项目的设计取向相合：**先写评估，再做能力**。新模型发布时跑一遍，就知道哪些押注已经兑现。这正好用来检验“做模型进步替代不了的部分”（产品总览「设计取向」）。

## 3 打分器怎么选（A、B）

| 类型 | 适合 | 在我们这里 |
| --- | --- | --- |
| 代码检查 | 能机械判断的：轮数、字数、格式、是否调用了某个工具 | 每轮字数、系统与学习者字数比、一轮里问了几个问题、是否读了教材 |
| 模型评委 | 开放输出、标准清楚的 | 教学行为（是否代做、是否说明提问目的、是否对着误解讲） |
| 人 | 金标准；用来校准模型评委 | 产品负责人给少量对话打分 |

模型评委要注意的偏差（A §4）：

| 偏差 | 做法 | 我们要特别注意的 |
| --- | --- | --- |
| 位置偏差 | 两两比较时每条都随机 A / B | `compare.py` 已做 |
| **偏爱长回答** | 明确告诉评委不因为长而给高分 | **me-9 的核心问题就是回复过长**，评委偏爱长回答会把问题掩盖掉 |
| 偏爱同家族模型 | 不用被测模型给自己打分；最好换家族，或用几个评委投票 | Sonnet 与 Opus 同属 Claude 家族，只能部分避开；以后接入 DeepSeek 等再考虑换家族评委 |
| 看标签打分 | 不告诉评委哪份是基线、哪份是人写的 | — |
| 标准含糊 | 写成可逐条核对的陈述；每个维度单独一次评委调用 | 一条行为一个评委，不要一个评委管所有项 |
| 没有退路 | 允许评委回答“无法判断” | 防止评委编理由 |
| 没校准 | 在几十条人工标注上核对；清楚的案例一致率明显低于约 90% 就先改评委 | 需要产品负责人标注 |
| 没测反例 | 给评委空回复、“我不知道”、答非所问三种，确认都判不通过 | — |

其他打分原则：

| 原则 | 出处 | 在我们这里 |
| --- | --- | --- |
| 看结果，不看路径 | A §4、B | 不要求“先讲再问”这类固定顺序，只看学习者最后是否自己走通 |
| 给部分分 | B | 对话推进到链上第几步，而不是只看闭没闭合 |
| **两个方向都要测** | A §1、B | 既测“该让学习者输出时有没有让”，也测“学习者已经会了时有没有停止追问”；只测一边，会把系统推向另一个极端（me-8 就是一直要证据） |
| 罕见的严重行为用“出现即不通过” | A §4 | 例如一次都不应代做学习者正在做的那一步 |
| 惩罚不能让“什么都不做”成为最优 | A §4 | 只惩罚“代做”，系统可能干脆不讲；要和“讲授质量不低于教材”一起打分 |

## 4 学习场景的“结果”在哪里（设计侧推论，未验证）

B 说，对话型 agent 的评估通常要用第二个模型扮演用户（τ-bench、τ²-bench 都这样），而且最好有可核对的最终状态，不只看对话怎么说。

`03` §4 的构造正好提供了这个最终状态：模拟学习者的知识状态由单独的状态更新调用维护，对话结束时，状态变化就是“结果”——哪条误解被纠正了、哪一步从复现升到了结构。这样可以按结果打分，而不只是按对话记录。

**限制**：状态更新本身是一次模型判断，它也需要校准（`03` §6）；否则就是拿一个没校准的判断去评另一个判断。

## 5 通过率的两种算法（B）

| 指标 | 意思 | 在我们这里 |
| --- | --- | --- |
| pass@k | k 次里至少成功一次的概率 | 不适用 |
| pass^k | k 次全部成功的概率；每次成功率 75%，3 次全成功只有约 42% | **适用**：学习者每次都应该得到可靠的教学，偶尔一次好不够 |

## 6 开跑前必须过的检查（A）

| 检查 | 做法 | 在我们这里 |
| --- | --- | --- |
| 每个试次从干净环境开始 | 不留上一次的文件、记录 | 模拟不能共用 `records/owner/`（`01` §2.1 已提） |
| 随机要有种子 | 模拟器没有固定种子会带来与被测系统无关的波动 | `03` §3 的随机事件要带种子 |
| 分清是外壳的限制还是模型的限制 | 固定模型换外壳，或反过来 | 正对应技术方向重审的问题：教学表现是模型的还是框架的 |
| 用“标准答案”和“空答案”各跑一遍 | 标准答案应接近满分，空答案应接近零分 | 找一段产品负责人认为好的真人对话当标准答案，一段明显差的当反例 |
| 证明机制真的接上了 | 关掉它，分数应该下降 | 例如关掉教学工具 `skills/`，看相关分数有没有变 |
| 从原始记录重算总分 | 不信汇总字段 | — |
| 服务的模型就是要求的模型 | 从回复里读模型名并核对 | `llm.py` 已在做 |

## 7 保持评估可用（A §6、B）

| 做法 | 说明 |
| --- | --- |
| 读记录 | B：不读记录，就不知道打分器靠不靠得住；失败应该“看得出是公平的” |
| 评估是活的 | 新发现的失败方式变成新用例；做到满分的用例加难；评委偏移了就重新校准 |
| 每条用例的自动审查 | 用例多了以后，每条单独让模型检查：有没有歧义、标准答案是否可疑、打分是否过严或过宽、能不能取巧（A §1 给了现成的审查提示词） |
| 多种方法叠加 | 自动评估、真人试用、读记录、人工系统打分各有盲区，像瑞士奶酪一样叠起来用；我们的真人试用对应 B 里的“人工系统打分”，留给校准用 |
