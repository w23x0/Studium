# Opus 5.5 使用说明：要点与对项目的意义

> 状态：待定（2026-09-29 建）。参考材料，**不作产品结论**。
> 来源：Anthropic 博客《Getting the most out of Opus 5.5 in Claude and Claude Code》，2026-09-22，https://claude.dev/blog/getting-the-most-out-of-opus-5-5/
> 为什么放这里：它讲的是教学调用、守卫、评委所用模型的行为，评估要考虑；也和 `../agent框架学习/01-项目要从学习里拿什么.md` §3（模型的行为靠什么约束）有关，读那边时可以对照。

## 1 官方对 Opus 5.5 行为的描述

| 行为 | 原文要点 | 对项目 |
| --- | --- | --- |
| 自己干得更久 | 最大的进步在多步骤的长任务上，能在很少监督下连续跑几小时；建议一次交出整个任务、说清“做完”是什么样，然后放手 | 印证原则 7 的推断（“被优化成替用户完整做完任务”）：这不再只是设计侧的猜测，官方就是这样描述它的长处的。学习里要的恰好相反 |
| 会主动停下来汇报 | 长任务中有时停下来汇报、提议继续、列出选项；**它会遵守“什么时候停”的明确说明**；结对编程时也可以反过来要求它每步前说计划 | 与 me-9 的问题直接相关：`teach.md` 已写“一轮停在第一个取决于学习者回答的地方”。官方说它遵守**点名的停止点**，值得实测：写成具体的停止点，是否比写成原理更有效（**未验证**） |
| 每次回复前都会思考 | 删掉“仔细想”“一步一步想”这类话，不影响质量，回复更快；想改思考量就调 effort | 已查：`proto/studium/prompts/`、`skills/`、`learners/` 里没有这类话 |
| 长对话里会回头重审早先的回答 | 可以说明“已回答的就算定了”，但长分析里不要这样做，因为后面可能发现前面的错 | 教学是长对话；学习者纠正系统时恰好需要回头看，所以**不照用** |
| 说明自己做了什么更清楚 | 结尾会写做了什么、发现了什么、需要你什么 | 这是编程契约的一部分；对学习者来说是额外的阅读负担（原则 7：稀缺的是学习者注意力） |
| 能标出没确认的 | 让它“标出没能确认的、说明去哪找过”，效果好 | 可用于评委（`04` §3：给评委“无法判断”的退路）和状态更新调用（`03` §4） |

## 2 安全拦截与模型切换

| 要点 | 对项目 |
| --- | --- |
| Opus 5.5 带更严格的生物 / 网络安全拦截；被拦下的消息会**转给旧模型继续**，对话也留在旧模型上；日常教育问题应当不受影响，但可能误拦 | 评估里必须核对“服务的模型就是要求的模型”（`04` §6）。`proto/studium/llm.py` 目前只在不一致时打印提醒，做评估时要改成直接判为失败，否则分数会混进旧模型的表现 |
| **要求在回复里复述内部推理，属于会被拦截的一类**；建议改成“用三句话说明你为什么这样选” | 已查：现有提示词没有这类要求。以后写评委、状态更新提示词时，不要写“输出你的完整思考过程”，改成“写出判断理由” |

## 3 不适用的部分

设计相关的建议（点名不要的样式）、子代理拆分、任务清单放文件、快速模式、应用里的看图与文档检查：与教学和评估关系小，不展开。
