# 评估设计与爬坡：文章要点与对项目的意义

> 状态：待定（2026-09-29 建）。参考材料，**不作产品结论**；项目暂停期间只做储备。
> 来源：Anthropic 博客《Automating eval design and hillclimbing with Claude》，2026-09-28，https://claude.dev/blog/automating-eval-design-and-hillclimbing/ ；配套 `claude-api` skill 的 `/claude-api build-eval` 与 `/claude-api hillclimb` 两个子命令。
> 术语：**评估（eval）** = 一组固定任务加一个打分器，用来衡量系统表现；**爬坡（hillclimbing）** = 每轮只改一处，用评估分数决定留下还是撤回；**打分器（grader）** = 给输出打分的程序或模型。

## 1 文章说了什么

### 1.1 好评估的四个条件

| # | 条件 | 反例（出现就说明评估有问题） |
| --- | --- | --- |
| 1 | 任务取自真实使用场景 | 因为好出题、好打分才选的任务 |
| 2 | 模型越强、思考越多，分数越高 | 不升反降：任务有歧义，或打分器没校准好 |
| 3 | 最强模型也离满分有距离，而且差距不是题目本身造成的 | 某题每次都失败：多半题目不可能或有歧义。好题的标准是两位领域专家会给出同一判断，打分检查的每一项在题目里都写明了 |
| 4 | 同一配置多跑几次，分数差得小 | 题目含糊、打分器对同一输出给出不同结论；配置不一致；环境里留着上一次试跑的残留（文件、历史），等于把答案递给了系统 |

**选难题的方法**：不要因为“当前模型做错了”就把它收进来。模型的能力是参差不齐的，这样选只量到了这一个模型的坑。一道题要因为**人判断它难**才收，而且收之前能说出它难在哪。用户的真实流量也不能全信，因为用户往往只试他们觉得会成功的，按流量抽样会偏容易。

### 1.2 建评估的流程（build-eval）

| 步 | 做法 |
| --- | --- |
| 取样顺序 | 真实对话记录 → 问题报告 → 手写 5 到 10 个 → 从代码合成。合成的要以少量真实例子作锚 |
| 人工确认 | 生成一页，把全部输入列出来给人看，人确认有代表性再往下走 |
| 选打分器 | 输出范围受限就用程序检查；开放输出就用模型当评委：评分标准写成**可逐条核对的陈述**，不用 1 到 5 分。有基线时，把两份输出随机顺序给评委、不告诉哪个是基线，让它挑更好的。**评委模型不能是被测模型** |
| 验证打分器 | 先评几个，问人：“哪一个你会打不同的分？”信打分器之前，先读一部分打过分的记录 |
| 诊断 | 同一输出评两次，看结论变不变；查超时、报错、截断，别把基础设施的噪声当成模型的波动；基线已在 95% 左右就说明余地不够 |

### 1.3 爬坡与防过拟合（hillclimb）

| 项 | 做法 |
| --- | --- |
| 改哪里 | 选改起来便宜、分数变化能归到这一处的地方：提示词、skill、工具描述、模型与思考强度。开放式地改框架代码容易停滞 |
| 开始前 | 随机把评估集分成训练集和测试集；先确认评估本身的噪声（偶然能让分数动多少）小于你愿意采纳的最小改进，否则先加题或加重复次数 |
| 每一轮 | 读上一轮训练集的失败记录，只提**一处**改动，从根上改（重写造成问题的那一段），不是换个说法 |
| 留还是撤 | 训练集和测试集都涨，留；只有训练集涨，疑似过拟合，撤；有退步，撤 |
| 停滞时 | 连续两三轮不涨，就不再改东西，而是把剩下的失败按原因分类。这一步常能发现题目有歧义、打分器错了、框架有错；只有“真失败”才进下一轮 |
| 防过拟合 | 分开训练集和测试集；**永远不把失败内容贴进提示词**；答案在结构上放到模型够不着的地方（防止模型直接找答案） |
| 收尾 | 停在测试集最好的版本，报告和基线的差距及置信区间；差距在噪声以内就明说，不建议采用 |

文章里的一个例子：失败是因为模型按训练里记住的旧写法写代码，而不是 skill 缺内容。修法是在 skill 顶部放一张“你记得的写法 → 现在的写法”对照表。

## 2 对项目的意义（设计侧的初步看法，未验证）

### 2.1 现有做法对照

| 文章要点 | 项目现状 | 差距 |
| --- | --- | --- |
| 任务取自真实使用 | 真人试用 me-1 到 me-9 的对话记录都在 `proto/runs/`；每份实验发现里的问题就相当于问题报告 | 已有最好的来源，还没当成评估集用（待确认项 P-01） |
| 合成要以真实例子作锚 | 模拟学习者 `learners/owner-like.md` 是照产品负责人背景写的 | 没有检验过模拟得像不像；`m09check-sim` 已记录“配合度高，不代表真人” |
| 盲评、随机顺序 | `studium/compare.py` 已经把两份对话随机标成 A / B | 评分项还是旧闭环定义（验收范围、主张、“一次一步”），和现在的 `teach.md` 冲突；评委用 opus，和被测的教学调用是同一个模型，违反“评委不能是被测模型” |
| 评分标准写成可逐条核对的陈述 | `compare.py` 要求每格一句话加引用，没有可核对的陈述 | 需要重写 |
| 先验证打分器 | 没做过 | 应先让产品负责人给几份打分，再信打分器 |
| 噪声要小于想看的改进 | me-9 第 7 轮重放，每种设置只跑 2 次（834 / 1027 字对比 1090 / 1020 字） | 没估噪声。结论“加待办不变短”方向大概可信，但样本太小 |
| 不因当前模型做错就收题 | me-9 §6 #3（数学式误判）已定为模型能力问题、不加规则 | 一致；以后收题也要能说出“难在哪” |
| 不把失败贴进提示词 | 原则 5 的“补丁”与记忆“先打地基、不靠加规则” | 一致，而且文章给了可以操作的检验：看测试集涨没涨 |
| 环境残留会泄露答案 | 模拟运行共用 `records/owner/`（M09、停车场） | 模拟前要确认环境干净，或者每次用独立的学习者目录 |

### 2.2 学习场景和文章不一样的地方

| 不同 | 为什么要紧 | 不确定 |
| --- | --- | --- |
| 文章的输入是静态的一条；我们的输入是一整段多轮对话，由模拟学习者边聊边生成 | 模拟学习者本身就是评估环境的一部分，它也会带来波动和偏差。像验证打分器一样，它也得先验证 | 怎么验证：拿真人记录的开头喂给模拟学习者，比较后续回应？未想清楚 |
| 我们的“成功”是学习者脑中的变化，模拟学习者没有真的在学 | 模拟只能量**教学行为**（比如回复是否停在该停的地方、有没有代做学习者的一步），量不了学习效果 | 这个界线是否成立，要和产品负责人一起定 |
| 守卫本身就像一个打分器 | 容易混淆：守卫是产品的一部分（判断闭环是否闭合）；评估的打分器是用来衡量产品的，两者要分开，不能用守卫的结论当评估分数 | — |
| 爬坡最适合改提示词、skill | 正好对应 `prompts/teach.md`、`proto/skills/`；但交互契约要求“由结构保证”，结构改动属于文章说的容易停滞的开放式框架修改 | 契约问题可能要先靠原理定结构，再用爬坡调文字 |

### 2.3 以后可以做的（项目恢复后，按顺序）

| # | 事 | 依赖 |
| --- | --- | --- |
| 1 | 从 me-1 到 me-9 挑出评估用例：每个都写明为什么难、看的是哪种教学行为 | 交互契约先定下“要量什么” |
| 2 | 验证模拟学习者：和真人记录对照 | 1 |

| 4 | 估噪声：同一配置重复跑，看分数波动多大 | 2、3 |
