## 二、M1 技术决策

### 应用技术栈

确定使用：

- Node.js 24 LTS；不以本机偶然安装的 Node.js 25 作为项目基线。
- npm 11 和 `package-lock.json`。
- TypeScript、React、Next.js 单应用。
- 同源 `POST /api/chat` Route Handler 作为唯一浏览器后端入口。
- Zod 作为前后端共享的可执行契约。
- 原生 `fetch` 调用网关，M1 使用非流式 JSON 响应。

未采用：

- Vite 加 Fastify：当前会增加第二套应用入口和开发编排。
- React 加 FastAPI：M1 没有足以承担跨语言成本的 Python 业务逻辑。
- Vercel AI SDK：M1 只有一个非流式调用点，尚无新增抽象的必要。

### LLM 网关

评估了 LiteLLM、Portkey Gateway 和 Helicone：

- LiteLLM 支持自托管和 OpenAI-compatible 接口，最终选用。
- Portkey Gateway 当时的项目说明仍提示 2.0 为预发布，不作为 M1 首选。
- Helicone 同时带有较重的可观测性平台能力，超出 M1 所需范围。

最终边界：

- Studium 不复制 LiteLLM 源码，也不使用 Docker。
- uv 从正式 Python 包源安装并锁定 `litellm[proxy]`。
- uv 使用 Python 3.13；LiteLLM 1.92.0 的约束为 `>=3.10,<3.14`，不能使用本机默认 Python 3.14。
- LiteLLM 位于 `infra/litellm/`，是模型基础设施，不是第二套 Studium 业务后端。
- Studium 固定调用网关别名 `studium-m1`；浏览器不能选择供应商、模型或网关地址。
- M1 不启用 fallback、负载均衡、预算管理、管理后台或网关数据库。

### M1 接口契约

- 请求：`POST /api/chat`，包含 1 至 20 条 `user`/`assistant` 消息。
- 单条正文长度为 1 至 8000 个字符，总正文不超过 32000 个字符。
- 最后一条必须来自用户；浏览器不能提交 `system` 消息。
- 成功响应包含 assistant 消息和 `requestId`。
- 统一错误代码包括：
  - `INVALID_REQUEST`
  - `GATEWAY_NOT_CONFIGURED`
  - `GATEWAY_AUTH_FAILED`
  - `MODEL_RATE_LIMITED`
  - `MODEL_TIMEOUT`
  - `MODEL_UNAVAILABLE`
  - `MODEL_RESPONSE_INVALID`
  - `INTERNAL_ERROR`
- 上游原始错误正文和密钥不返回浏览器。

## 三、M1 应用基线实现

### 应用与页面

- 创建唯一 Next.js 应用和根目录 `package.json`。
- 创建响应式聊天页面，包含：
  - M1 空状态。
  - 用户与 Studium 消息气泡。
  - 输入与发送按钮。
  - 请求中状态。
  - 安全错误提示。
  - 请求失败时恢复未发送文本。
  - 当前页面内的多轮消息历史。
- M1 页面没有加入 Markdown 资料、学习诊断、持久化或闭环状态。

### 后端与模型边界

- 实现唯一 `POST /api/chat` Route Handler。
- 服务端生成 `requestId` 并通过响应头和 JSON 返回。
- 服务端追加固定 system message，浏览器不能覆盖。
- 通过环境变量读取网关地址、网关密钥、固定模型别名和超时。
- LiteLLM 非 2xx 状态被转换为 Studium 的稳定错误语义。
- 使用 AbortController 实现模型调用超时。
- 成功响应也经过结构校验，缺少有效回答时返回 `MODEL_RESPONSE_INVALID`。

### LiteLLM 与开发入口

- 创建 `infra/litellm/pyproject.toml`、`.python-version`、`config.yaml` 和 `uv.lock`。
- 锁定 LiteLLM 1.92.0，uv 使用 Python 3.13.9 创建本地隔离环境。
- 根目录 `.env.example` 只包含占位配置。
- 本地创建了被 Git 忽略的 `.env`，其中只有占位值，没有真实供应商密钥。
- `npm run dev` 使用 dotenv-cli 和 concurrently 同时启动：
  - Next.js，默认端口 3000。
  - LiteLLM Proxy，默认端口 4000。
- 没有拉取或复制 LiteLLM 源码，没有创建 Docker 配置。

## 四、实施过程中出现的问题与处理

### npm 首次安装超时

- 首次组合安装命令超过三分钟工具时限，命令被终止且没有及时输出。
- 检查发现 `package.json`、`package-lock.json` 和依赖实际上已经生成。
- 没有直接假定安装成功；随后使用 `npm ci` 重建并验证依赖树与审计结果。

### 最新 TypeScript 与 ESLint 不兼容

- 最初从包源解析到 TypeScript 7.0.2 和 ESLint 10.7.0。
- Next.js 的 TypeScript ESLint 工具链要求 TypeScript `<6.1`，部分插件只支持 ESLint 9。
- 改为 TypeScript 6.0.3 和 ESLint 9.39.5，没有使用 `--force` 或忽略 peer dependency。

### PostCSS override 范围过大

- 第一次全局 override PostCSS 8.5.10 时影响了 Vitest/Vite 自己的 PostCSS 8.5.19，导致依赖树 invalid。
- 将 override 收窄到 Next.js 的 PostCSS 后，Next.js 使用 8.5.10，Vite 保持 8.5.19，依赖检查恢复。

### npm 可选 WASM 包显示为 extraneous

- Windows 上 `npm ci` 后，`npm ls --depth=0` 将若干由可选 WASM binding 带入的 `@emnapi/*`、`@napi-rs/wasm-runtime` 和 `@tybys/wasm-util` 标为 extraneous。
- `npm prune` 后现象仍存在，但命令退出码为 0；这些目录位于被忽略的 `node_modules/`，没有进入提交，构建和测试未受影响。
- 如果未来升级 npm 或相关 binding，需重新观察该包管理器行为。

### uv 首次同步成本

- `uv sync --project infra/litellm --locked` 首次安装耗时约 131 秒，解析 106 个包并安装 103 个包。
- 主要体积来自 LiteLLM Proxy 的正式依赖；环境位于被忽略的 `infra/litellm/.venv/`，后续使用本地缓存。

### 自动化测试首轮失败

- 首轮结果为 16/18 通过。
- 一个失败来自 fetch mock 未在用例间清零；另一个来自测试选择器把 textarea 中恢复的文本误认为消息气泡。
- 修正测试隔离和选择器后，最终为 18/18 通过。

### ESLint 扫描第三方虚拟环境

- 首次 lint 进入 `infra/litellm/.venv/` 内的 LiteLLM 前端构建产物，产生大量第三方错误。
- 在 ESLint 全局忽略项中明确排除该虚拟环境；项目自身 lint 随后通过。

### `.next/` 未被忽略

- 第一次生产构建后发现原 `.gitignore` 没有 Next.js 的 `.next/`。
- 补充 `.next/` 忽略规则，确认构建产物、Node 依赖和 uv 虚拟环境均未进入 Git。

### 行尾规则补充

- 新增文件类型触发 Git 行尾转换提示。
- 在 `.gitattributes` 中补充 `.env.example`、`.node-version`、`.python-version`、`*.lock` 和 `*.mjs` 的 LF 规则，并重新规范 staged 内容。
