# ADR 0002：LiteLLM 网关边界与本地运行方式

- 状态：Accepted
- 日期：2026-07-14

## 背景

Studium 需要通过稳定边界调用真实模型，但 M1 不应绑定某家供应商 SDK，也不应建设多供应商网关管理后台。自托管 LiteLLM 能提供 OpenAI-compatible HTTP 接口，但把 LiteLLM 源码复制进仓库或要求 Docker 会增加不必要的维护和本地运行成本。

本机已有 uv；LiteLLM 当前 Python 版本约束为 `>=3.10,<3.14`，而本机默认 Python 为 3.14。

## 决策

- 使用 LiteLLM Proxy 作为 Studium 与真实模型之间的唯一网关。
- 不复制或修改 LiteLLM 源码；通过 uv 从正式 Python 包源安装并锁定 `litellm[proxy]`。
- 由 uv 为网关管理 Python 3.13，不依赖本机默认 Python 3.14。
- 网关配置和锁文件位于 `infra/litellm/`，它属于运行基础设施，不是第二套业务后端。
- 根目录 `npm run dev` 同时管理 Next.js 和 LiteLLM 两个进程；不要求 Docker。
- Studium 只调用一个模型别名 `studium-m1`，不知道也不接收浏览器指定的供应商模型名。
- M1 中该别名只映射一个上游模型，不启用 fallback、负载均衡、预算管理、管理后台或持久化数据库。
- 上游模型标识和密钥只通过未跟踪的本地环境变量提供；仓库只提交 `.env.example`。

## 理由

- OpenAI-compatible 边界允许以后在网关内更换供应商，而不改变浏览器契约。
- 包管理器安装和锁定比 vendoring 更易升级、审计和移除。
- uv 能隔离兼容的 Python 版本，避免 Docker 成为 M1 的前置条件。
- 单一模型别名保持调用可预测，避免用网关能力提前扩张产品范围。

## 后果

- 自托管网关必然增加一个本地进程和一个失败边界；统一开发命令负责进程编排。
- 没有有效的上游模型标识与密钥时，骨架、契约和失败状态仍可测试，但 M1 不能标记完成。
- 若未来需要网关数据库、管理界面、多模型路由或集中部署，必须另行评审数据根目录、鉴权和运维责任。

## 未采用方案

- Docker 部署 LiteLLM：隔离更强，但当前本地使用成本高于 uv 方案。
- Studium 直接调用供应商 SDK：进程更少，但会把应用绑定到供应商接口和错误语义。
- 将 LiteLLM 作为源码目录加入仓库：违反依赖管理和禁止整体复制第三方仓库的规则。
