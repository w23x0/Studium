# 技术方向确认：Studium Harness 定位与核心需求

> 状态：已确认路径 3（基于 DSH SDK Runtime 全权定制）。**DSH 只是承载基础能力的 runtime 底座，不是设计结论本身**——Studium 的 harness（上下文组合 + 图式运行）是自研的。  
> 更新：2026-09-09

## Studium ≠ 代码编程 Harness

| 维度 | 代码编程 Harness (DSH/CC/Pi) | Studium 学习任务 Harness |
|---|---|---|
| 任务类型 | 文件编辑、shell、搜索、git、测试运行 | 教学互动(M02)、练习活动(M03)、诊断判断(M04)、路线规划(M05) |
| 工具集 | 文件操作、命令执行、代码搜索 | 查询知识状态、写诊断、提交闭环、更新路线 |
| 上下文 | 代码库结构、文件内容、命令输出 | 当前闭环目标、学习者表现、通用知识(M08)、个人知识(M09)、资料(M07)、主线/分支/迂回路径关系 |
| 流程 | tool call → 执行 → 观察 → 下一步 | M02/M03/M04/M10 按图关系触发、回流、分支、暂停、等待输入 |
| **核心挑战** | 工具调用编排 | **上下文组合 + 图式运行** |

## 采用路径 3：基于 DSH SDK Runtime 全权定制

### 核心原则
1. 使用 DSH runtime 提供 agent loop、LLM 路由、会话持久化等基础能力
2. Studium 拥有自己的 Cordis 组合（不依赖 DSH Web profile）
3. Studium 前端通过 SDK / JSON-RPC 协议驱动 runtime
4. Studium 域层(M01-M15)、上下文工程、图式运行由 Studium 自行设计

### DSH 提供的基础能力

| DSH 能力 | Studium 使用 | 依赖程度 |
|---|---|---|
| Agent loop | 模型多轮循环的基础框架 | 核心依赖 |
| LLM service 与 provider adapter | 模型调用抽象 | 核心依赖 |
| Session log | append-only event log | 核心依赖 |
| Session persistence | JSONL / SQLite 后端 | 核心依赖 |
| Session checkpoint policy | durability checkpoint | 核心依赖 |
| Storage seam 与 non-session storage | 用于域状态(M01-M15)持久化 | 核心依赖 |
| SDK / JSON-RPC server | Studium UI 驱动 runtime 入口 | 核心依赖 |
| Tool registry 与执行流水线 | 学习工具注册（工具集完全不同） | 部分使用 |
| Subagent 服务 | 待评估是否用于图节点隔离 | 待定 |

### 明确不使用
- ❌ DSH Web Chat UI
- ❌ `ConversationNodeDefinition`
- ❌ DSH 默认工具集（文件编辑、shell、git）
- ❌ 固定循环的 agent 流程

## Studium 核心定制需求

### 1. 上下文组合工程（★核心需求）

**核心机制**：通过**不同的上下文组合方式**区分模块职责，而不是靠提示词角色设定。给什么上下文，自然产生什么输出。

**关键设计原则**：
- **模型选择**：M02（教学）可用低级模型（表达能力强），M04（诊断）用高级模型（分析能力强）
- **理由**：模型的理性分析能力和表达能力是相反的，旧模型表达能力强于先进模型的分析能力
- **不依赖提示词角色**：不用"你现在是诊断者"这种提示词设定
- **成本暂不考虑**：M02 用低级模型成本低

**M04 与 M02 的串行关系**（场景 A）：
```
学习者输入 → M04 分析 → M02 基于分析生成回复 → 回复给学习者
```
- M02 生成回复时**必须调用 M04 的分析**（上下文资产很重要）
- 不采用并行调用（并行会导致 M02 拿不到 M04 的分析）
- 延迟暂不考虑（成本优先级低）

#### 1.1 上下文分类与来源标记

**要求**：不能把全部信息合并成无类型聊天文本。

| 上下文类型 | 来源模块 | 信息内容 | 证据意义 |
|---|---|---|---|
| 当前目标与验收范围 | M01 | 闭环目标、验收范围、任务状态、主线/分支关系 | 判断边界 |
| 路径位置 | M01, M05 | 当前位置、主线/分叉决定、分叉范围、返回条件 | 上下文污染防护 |
| 学习者表现 | M02, M03 | 原始表达、答案、步骤、理由、行为表现 | 原始证据 |
| 教学条件 | M02, M10 | 讲解、提示、答案暴露、脚手架、策略、提示强度、挑战程度 | 证据权重调整 |
| 练习条件 | M03, M10 | 任务、完成条件、独立程度、挑战程度 | 证据权重调整 |
| 通用知识 | M08 | 概念、方法、前置、组成、混淆及来源 | 判断依据 |
| 个人知识 | M09 | 已结束闭环的个人知识、丰富理解、时间版本 | 背景参考 |
| 中间诊断 | M04 | 进行中的判断和替代解释 | 可被推翻 |
| 系统限制 | 跨模块 | 信息缺失、工具失败、模型降级 | 影响判断质量 |

**关键**：同一个正确答案在"独立完成"、"轻微提示"、"多次提示"、"答案已暴露"等条件下具有不同证据意义。

#### 1.2 上下文精准编排（而非简单压缩）

**核心要求**：准确提取需要的内容，不是只看近 N 轮。

M02 的输入需要精细编排：
- **核心层**：M04 最新分析 + 当前任务 + 闭环目标
- **知识层**：M07 资料 + M08 概念 + M09 个人知识（按需精准提取）
- **历史层**：相关对话片段（不是只看近 N 轮，是按相关性提取）
- **分支控制**：M04 判断出分支岔路时，通过 M04 分析结果进行上下文分类

**不是**：
- ❌ 只看近 N 轮对话摘要
- ❌ 把完整的 50 轮对话都塞进去
- ❌ 只给"补讲极限"四个字

**设计重点**：这是整个项目设计的核心之处——如何精准提取需要的上下文。

#### 1.3 同源不同契约的隔离执行

**场景**：M04 与 M15 读取同一份 M01 过程记录，但输出契约不同
- M04 每轮必跑 → 输出诊断与证据判断
- M15 低频触发 → 输出学习者状态与条件

**澄清**：
- 实际上它们读的**上下文不一样**（M04 读当前闭环对话，M15 读跨会话启动间隔）
- 不是"读同一份数据但用不同 prompt 约束输出"
- 是**拿的字段不同**，本质上是不同的上下文
- **不能纯靠 prompt**，要靠**组合模式的区别**实现

#### 1.4 闭环工作缓存

**场景**：M04 在一个学习闭环内要跨多轮持续修正诊断
- 第 1 轮：学习者答对了 A 题 → M04 判断"可能会 A 知识点"
- 第 2 轮：学习者答错了 B 题 → M04 判断"A 知识点可能有缺口"
- 第 3 轮：学习者在提示后答对了 C 题 → M04 判断"A 知识点在提示下能用"

**要求**：
- M04 **不把自己的分析结果塞回输入**（避免回环结构过拟合，不能产生自己的判断）
- 输出流式分析报告：只输出当前状态；**只出不回**
- 输出仍需留存（供 M02 取最新、M09 闭环一次提交、M13 审计），但**存储 ≠ 回流输入**
- **对话级分析**和**闭环级总结**的输出契约是一样的（只是上下文不同：部分历史 vs 完整历史）
- 串起来就是总体过程，闭环是否完成 M04 自然就知道了

**存储边界**：暂不确定（待后续设计）

### 2. 上下文资产的形态：便于推理的文字推理链

**核心诉求（上下文资产与人类可读无关）**：
- 上下文资产是**模块与模块之间传递的中间产物**，是给下一个模型/模块接着推理用的，**不是给人读、也不是给 UI 展示的**。
- ❌ 不是 JSON（LLM 不擅长，机器可读但无法接续推理）
- ❌ 不是无结构自由文本（难组合）
- ❌ 不是「为人类可读」的成段陈述 —— 那会把「给用户讲解」和「给下一个模块推理」混成一层
- ✅ 是**便于推理的原始逻辑事实 + 推理链（思维链）文字形态**

**设计要点**：
- 一个模块的输出是**一条带来源、证据关系、因果的推理链**：逐条、可组合、来源可核实。
- 推理链可被下一个模块继续推理，原子读数可以互相参照、可被下一环节替换、修改或推翻，被消费后不影响其它独立模块读取。
- **不给它分成"适合人看"和"适合机器"两层**，统一是文字推理链，专一一种形态。
- 人类可读不是目标，但推理链天然可被审阅、可被后续迭代核查。

**示例（错的，别学）**：
```json
{"diagnosis": {"hypothesis": ["limit_gap", "symbol_confusion"], "evidence": [...]}}
```

**作为本节的定型表述**，上下文资产与推理链的方向已确认：
- 第一版只做**简单完整的输入输出文字形式推理链**。能接续推理、来源可追溯即可。
- 不深入"思维链(CoT)优化"——那是后续可选方向，当前不展开、不在第一版承诺。

### 3. 图式运行（★核心需求）

#### 3.1 图节点关系而非固定循环

**错误理解**：
```text
❌ M02 → M03 → M04 → M10（固定循环）
```

**正确理解**：
```text
✅ M02 教学互动 ──┐
                 ├──→ M04 诊断 ──→ M10 策略 ──┐
   M03 练习活动 ──┘                          │
                 ↑                          │
                 └──────────────────────────┘
                         回流
                 
   需要改变跨闭环路线时：
   M04 ──→ M05 路线规划 ──→ M01 新会话
```

**澄清**：
- 模块不是循环节点，是**围绕中心上下文资产进行加工**
- "固定流程"是比喻，指**固定的上下文选取、组合、输出规则**
- **不是固定 N 轮**这种设计
- M04 可以判断出分支岔路，影响上下文编排

#### 3.2 类型化交接

不同模块之间的信息传递需要明确契约：
- M04 改线依据 → M05 分叉决定
- M05 路线决定 → M01 新会话/路径结构
- M04 诊断 + M15 状态 → M10 策略条件
- M10 策略与四项强度条件 → M02/M03 执行

**核心**：交接流程不是固定的，也不是通过工具调用，是**所有中间生成产物的组合**——即上下文组合。

### 4. 会话与域数据分离（Studium 特有架构）

**核心规则**：
1. 域状态默认不写入 DSH `SessionEventMap`
2. 域状态使用 DSH non-session storage seam + `storage-domain`
3. Studium 自己拥有域数据 schema、迁移、审计、一致性规则
4. 只有确实需要进入模型可见历史或 UI 回放的信息，才显式设计为 session surface event

**理由**：域状态是学习产品数据，不是模型对话面。放进 session log 会把产品生命周期、版本迁移、清理策略和模型上下文混在一起。

**域状态包括**：M01（项目/会话/闭环/路线）、M04（诊断上下文）、M05（路线决定）、M07（资料库）、M08（通用知识）、M09（个人知识）、M10（策略）、M15（学习者状态）、M14（产出物）

**一个闭环 = 一个对话**：
- 闭环内的所有交互都在同一个对话上下文里
- M04 是对话级的，每次用户回答都产出一份分析
- 输出存在"这次会话文件夹内"（具体格式待定，结合 harness 设计）

### 5. M09 存证据链（汇总提交）

**核心**：M09 存**证据链**而不是完整对话，也不是简单标签。

**内容**：总结对话历史的学习过程原始信息
- 结论 + 证据链 + 关键理解 + 关系
- 可追溯（能回到原始对话核实）
- 可压缩（不爆炸）

**示例**：
```
闭环：掌握导数定义
结论：已掌握（2026-09-09）
证据链：
  - [独立完成] 题目 A：求 f(x)=x^2 在 x=1 的导数（正确）
  - [轻微提示] 题目 B：求 f(x)=sin(x) 在 x=0 的导数（正确，需提示极限定义）
  - [独立完成] 题目 C：导数的几何意义（正确）
关键理解：
  - 导数定义：掌握
  - 极限定义：理解但不熟练
  - 几何意义：清楚
前置关系：
  - 依赖：极限定义（来自 M08）
  - 支撑：微分（后续学习）
```

**提交方式**：**汇总提交**，不是一次性提交。因为上下文资产在那里，为什么只选取最后结论？要保留过程信息。

## 运行架构

```text
Studium UI / 客户端
        │  SDK / JSON-RPC protocol
        ▼
Studium 定制的 DSH SDK runtime
  ├── sdk-jsonrpc-server
  ├── agent loop
  ├── LLM adapter
  ├── session log / persistence / checkpoint
  ├── storage backend / storage-domain
  │
  ├── ★ studium-context-composition
  │     ├── 上下文分类与来源标记
  │     ├── 上下文精准编排（而非简单压缩）
  │     ├── 同源不同契约隔离执行
  │     ├── 闭环工作缓存
  │     └── 输出模板（符合 LLM 训练分布）
  │
  ├── ★ studium-graph-runtime
  │     ├── 图节点路由（M02/M03/M04/M10）
  │     ├── 触发、回流、分支、暂停、等待
  │     └── 类型化交接
  │
  ├── studium-domain（域层 M01-M15）
  └── studium-tools（学习工具集）
```

## 实施阶段

| 阶段 | 内容 | 产出 |
|---|---|---|
| 0 | 跑通 DSH Python SDK minimal 组合 | 确认 SDK runtime、JSONL 持久化可用 |
| 1 | 固定 DSH 版本，建立兼容 baseline | 明确 Studium 0.1 支持的 DSH 版本 |
| 2 | 建立第一个 Studium Cordis 组合 | 验证插件加载 / 组合闭包 |
| 3 | 引入 storage backend 与 `storage-domain` | 非 session 域状态可持久化 |
| 4 | 实现 `studium-domain` 首个垂直切片 | 项目 / 活动 / 观察等最小域状态可用 |
| 5 | **设计并实现 `studium-context-composition` 最小原型** | **上下文分类、精准编排、输出模板可用** |
| 6 | **设计并实现 `studium-graph-runtime` 最小原型** | **图节点路由、回流可用** |
| 7 | 实现 `studium-tools` 首个工具 | Agent 可通过工具读写最小域状态 |
| 8 | 定义 Studium UI SDK 协议面 | UI 可通过 JSON-RPC 驱动 runtime |
| 9 | 建立 DSH 升级合同测试 | runtime、session、storage、SDK protocol 有回归保护 |

关键里程碑：阶段 5 和 6 是 Studium 与代码编程 harness 的核心差异所在。

## 版本策略

- Studium 0.1 支持 DSH 0.1.0-rc.5
- Studium 0.2 支持 DSH 通过兼容测试后的目标版本
- 不在用户版本矩阵中直接暴露 `DSH latest`

每次 DSH 升级检查：SDK 协议、Cordis schema、Agent loop、Session format、Storage、域数据迁移、UI 协议
