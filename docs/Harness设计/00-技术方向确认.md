# 技术方向确认：Studium Harness 定位与核心需求

> 状态：**已确认（2026-09-23 改定）**：Studium 按**智能辅导系统（ITS）结构**构建——一个确定性的循环程序，在固定的判断点上以**隔离调用**使用大模型；不基于 DSH 或任何现成 agent runtime，不做多身份 agent。依据见 [`_research/前沿架构对照-发现.md`](./_research/前沿架构对照-发现.md)。
> 更新：2026-09-23

## Studium ≠ 代码编程 Harness

| 维度 | 代码编程 Harness (DSH/CC/Pi) | Studium 学习任务 Harness |
|---|---|---|
| 任务类型 | 文件编辑、shell、搜索、git、测试运行 | 教学互动(M02)、练习活动(M03)、诊断判断(M04)、路线规划(M05) |
| 工具集 | 文件操作、命令执行、代码搜索 | 查询知识状态、写诊断、提交闭环、更新路线 |
| 上下文 | 代码库结构、文件内容、命令输出 | 当前闭环目标、学习者表现、通用知识(M08)、个人知识(M09)、资料(M07)、主线/分支/迂回路径关系 |
| 流程 | tool call → 执行 → 观察 → 下一步 | M02/M03/M04/M10 按图关系触发、回流、分支、暂停、等待输入 |
| **核心挑战** | 工具调用编排 | **上下文组合 + 图式运行** |

## 定位：ITS 结构 + 大模型作隔离判断（2026-09-23）

### 核心原则
1. **结构沿用经典 ITS**：外层循环（每个闭环一次，选下一闭环）= M05；内层循环（每轮一次，诊断 / 策略 / 反馈）= M04 / M10 / M02 / M03；领域模型 = M07 / M08；学习者模型 = M09 / M15。
2. **大模型是判断函数，不是 agent**：判断点只在**必须隔离**处分开——教学调用（M04 诊断 + M10 策略 + M02 / M03 表达，一次）、M04 闭环守卫、M15、M05；每个都是一次**隔离调用**，输入由运行时按读清单装配，输出写回资产；没有身份设定，调用之间不互相对话。
3. **流程由确定性程序控制**：谁在什么时候被调用、缺料怎么办、何时等学习者输入、何时存盘，由程序（状态机）决定，不交给模型自决。
4. **第一版只做 CLI**，先用纯 Python 自写状态机；等出现分叉 + 返回、多闭环并行，再评估是否引入图框架——届时联网调研、借鉴、组合再押注，评估标准含**社区活跃度**（发版频率、问题响应、有无更新的替代品；产品负责人判断图框架有过气风险）。原型里的 `claude -p` 只是接线，不属于架构。
5. **架构 / 补丁分界**（取向见产品总览「设计取向：做模型进步替代不了的部分」）：判断法 = **假设模型完美，这一条还需要吗**——需要的（数据归属、流程控制、隔离、产品规则）进架构；不需要的是补丁，只放提示词并注明来由（哪次运行引出），模型变强时删。**隔离粒度**按“信息是否不同 / 是否自我确认”定，不按模块逐个隔离：同信息的职责合在一次调用（实验 1），守卫独立核对、诊断记录不回灌、M02 / M03 / M10 / M15 不读历史仍保留。
6. **测试用模型**：判断点（M05 设计、教学调用、守卫、M05 改线）用当下最强模型，免得把模型不足误读成设计问题、诱发过度设计；模拟学习者不属于架构，可用便宜模型（原型默认 `oc:deepseek-v4.1-flash`）。实验只做需要确认的。

### 不做
- ❌ 基于 DSH 或其他 agent runtime 定制（DSH 在 agent 方案调研中评价最差）
- ❌ 多身份 / 角色扮演 agent、agent 之间对话协作
- ❌ 固定循环的 agent 流程

## Studium 核心定制需求

### 1. 上下文组合工程（★核心需求）

**核心机制**：通过**不同的上下文组合方式**区分模块职责，而不是靠提示词角色设定。给什么上下文，自然产生什么输出。

**关键设计原则**：
- **不依赖提示词角色**：不用"你现在是诊断者"这种提示词设定
- **成本暂不考虑**

**教学主链的运行方式**（2026-09-23 改定，依据 `_research/原型实验-1-发现.md`）：
```
学习者输入 → 一次教学调用（先写诊断记录：诊断 / 策略与强度 / 验证意图 → 再写给学习者的话）→ 回复
```
- M04 / M10 / M02 / M03 的职责在同一次调用内完成，诊断记录单独保存、不放进回复、学习者可查阅、不回灌下一轮
- 不拆成 M04 → M10 → M02 串行调用：拆开后没有任何一环负责“这个疑点值不值得查”，实测过度追问（口径以 M02 审查单「运行方式」为准）

#### 1.1 上下文分类与来源标记

**要求**：不能把全部信息合并成无类型聊天文本。

| 上下文类型 | 来源模块 | 信息内容 | 证据意义 |
|---|---|---|---|
| 当前目标与验收范围 | M01 | 闭环目标、验收范围、任务状态、主线/分支关系 | 判断边界 |
| 路径位置 | M01, M05 | 当前位置、主线/分叉决定、分叉范围、返回条件 | 上下文污染防护 |
| 学习者表现 | M02, M03 | 原始表达、答案、步骤、理由、行为表现 | 原始证据 |
| 教学条件 | M02, M10 | 讲解、提示、答案暴露、脚手架、策略、提示强度、挑战程度 | 证据权重调整 |
| 练习条件 | M03, M10 | 任务、完成条件、独立程度、挑战程度 | 证据权重调整 |
| 通用知识 | M08 | 概念、方法、前置、组成、混淆及来源 | 判断依据 |
| 个人知识 | M09 | 已结束闭环的个人知识、丰富理解、时间版本 | 背景参考 |
| 中间诊断 | M04 | 进行中的判断和替代解释 | 可被推翻 |
| 系统限制 | 跨模块 | 信息缺失、工具失败、模型降级 | 影响判断质量 |

**关键**：同一个正确答案在"独立完成"、"轻微提示"、"多次提示"、"答案已暴露"等条件下具有不同证据意义。

#### 1.2 上下文精准编排（而非简单压缩）

**核心要求**：准确提取需要的内容，不是只看近 N 轮。

M02 的输入需要精细编排：
- **核心层**：M04 最新分析 + 当前任务 + 闭环目标
- **知识层**：M07 资料 + M08 概念 + M09 个人知识（按需精准提取）
- **历史层**：相关对话片段（不是只看近 N 轮，是按相关性提取）
- **分支控制**：诊断判断出分支岔路时，据此对上下文分类

**不是**：
- ❌ 只看近 N 轮对话摘要
- ❌ 把完整的 50 轮对话都塞进去
- ❌ 只给"补讲极限"四个字

**设计重点**：这是整个项目设计的核心之处——如何精准提取需要的上下文。

#### 1.3 同源不同契约的隔离执行

**场景**：M04 与 M15 读取同一份 M01 过程记录，但输出契约不同
- M04 每轮必跑 → 输出诊断与证据判断
- M15 低频触发 → 输出学习者状态与条件

**澄清**：
- 实际上它们读的**上下文不一样**（M04 读当前闭环对话，M15 读跨会话启动间隔）
- 不是"读同一份数据但用不同 prompt 约束输出"
- 是**拿的字段不同**，本质上是不同的上下文
- **不能纯靠 prompt**，要靠**组合模式的区别**实现

#### 1.4 闭环工作缓存

**场景**：M04 在一个学习闭环内要跨多轮持续修正诊断
- 第 1 轮：学习者答对了 A 题 → M04 判断"可能会 A 知识点"
- 第 2 轮：学习者答错了 B 题 → M04 判断"A 知识点可能有缺口"
- 第 3 轮：学习者在提示后答对了 C 题 → M04 判断"A 知识点在提示下能用"

**要求**：
- M04 **不把自己的分析结果塞回输入**（避免回环结构过拟合，不能产生自己的判断）
- 输出流式分析报告：只输出当前状态；**只出不回**
- 输出仍需留存（供 M02 取最新、M09 闭环一次提交、M13 审计），但**存储 ≠ 回流输入**
- **对话级分析**和**闭环级总结**的输出契约是一样的（只是上下文不同：部分历史 vs 完整历史）
- 串起来就是总体过程，闭环是否完成 M04 自然就知道了

**存储边界**：暂不确定（待后续设计）

### 2. 上下文资产的形态：便于推理的文字推理链

**核心诉求（上下文资产与人类可读无关）**：
- 上下文资产是**模块与模块之间传递的中间产物**，是给下一个模型/模块接着推理用的，**不是给人读、也不是给 UI 展示的**。
- ❌ 不是 JSON（LLM 不擅长，机器可读但无法接续推理）
- ❌ 不是无结构自由文本（难组合）
- ❌ 不是「为人类可读」的成段陈述 —— 那会把「给用户讲解」和「给下一个模块推理」混成一层
- ✅ 是**便于推理的原始逻辑事实 + 推理链（思维链）文字形态**

**设计要点**：
- 一个模块的输出是**一条带来源、证据关系、因果的推理链**：逐条、可组合、来源可核实。
- 推理链可被下一个模块继续推理，原子读数可以互相参照、可被下一环节替换、修改或推翻，被消费后不影响其它独立模块读取。
- **不给它分成"适合人看"和"适合机器"两层**，统一是文字推理链，专一一种形态。
- 人类可读不是目标，但推理链天然可被审阅、可被后续迭代核查。

**示例（错的，别学）**：
```json
{"diagnosis": {"hypothesis": ["limit_gap", "symbol_confusion"], "evidence": [...]}}
```

**作为本节的定型表述**，上下文资产与推理链的方向已确认：
- 第一版只做**简单完整的输入输出文字形式推理链**。能接续推理、来源可追溯即可。
- 不深入"思维链(CoT)优化"——那是后续可选方向，当前不展开、不在第一版承诺。

### 3. 图式运行（★核心需求）

#### 3.1 图节点关系而非固定循环

**错误理解**：
```text
❌ M02 → M03 → M04 → M10（固定循环）
```

**正确理解**：
```text
✅ M02 教学互动 ──┐
                 ├──→ M04 诊断 ──→ M10 策略 ──┐
   M03 练习活动 ──┘                          │
                 ↑                          │
                 └──────────────────────────┘
                         回流
                 
   需要改变跨闭环路线时：
   M04 ──→ M05 路线规划 ──→ M01 新会话
```

**澄清**：
- 模块不是循环节点，是**围绕中心上下文资产进行加工**
- "固定流程"是比喻，指**固定的上下文选取、组合、输出规则**
- **不是固定 N 轮**这种设计
- M04 可以判断出分支岔路，影响上下文编排

#### 3.2 类型化交接

不同模块之间的信息传递需要明确契约：
- M04 改线依据 → M05 分叉决定
- M05 路线决定 → M01 新会话/路径结构
- M04 诊断 + M15 状态 → M10 策略条件
- M10 策略与四项强度条件 → M02/M03 执行

**核心**：交接流程不是固定的，也不是通过工具调用，是**所有中间生成产物的组合**——即上下文组合。

### 4. 会话与域数据分离（Studium 特有架构）

**核心规则**：
1. 域状态（学习产品数据）与模型调用的对话 / 上下文分开存放，不混在同一份日志里
2. Studium 自己拥有域数据 schema、迁移、审计、一致性规则
3. 只有确实需要进入模型可见上下文的信息，才由运行时按读清单装配进去

**理由**：域状态是学习产品数据，不是模型对话面。混在一起会把产品生命周期、版本迁移、清理策略和模型上下文搅在一起。

**域状态包括**：M01（项目/会话/闭环/路线）、M04（诊断上下文）、M05（路线决定）、M07（资料库）、M08（通用知识）、M09（个人知识）、M10（策略）、M15（学习者状态）、M14（产出物）

**一个闭环 = 一个对话**：
- 闭环内的所有交互都在同一个对话上下文里
- M04 是对话级的，每次用户回答都产出一份分析
- 输出存在"这次会话文件夹内"（具体格式待定，结合 harness 设计）

### 5. M09 存证据链（闭环结束一次提交，含过程证据）

**核心**：M09 存**证据链**而不是完整对话，也不是简单标签。

**内容**：总结对话历史的学习过程原始信息
- 结论 + 证据链 + 关键理解 + 关系
- 可追溯（能回到原始对话核实）
- 可压缩（不爆炸）

**示例**：
```
闭环：掌握导数定义
结论：已掌握（2026-09-09）
证据链：
  - [独立完成] 题目 A：求 f(x)=x^2 在 x=1 的导数（正确）
  - [轻微提示] 题目 B：求 f(x)=sin(x) 在 x=0 的导数（正确，需提示极限定义）
  - [独立完成] 题目 C：导数的几何意义（正确）
关键理解：
  - 导数定义：掌握
  - 极限定义：理解但不熟练
  - 几何意义：清楚
前置关系：
  - 依赖：极限定义（来自 M08）
  - 支撑：微分（后续学习）
```

**提交方式**：闭环守卫通过后**一次提交**，但提交的是**含过程证据的丰富记录**，不是只交最后结论（口径以 M04 / M09 审查单为准）。

## 运行架构（第一版，CLI）

```text
CLI（学习者输入 / 系统回复）
        │
        ▼
闭环运行程序（确定性状态机，纯 Python）
  ├── 内层循环（每轮）：装配上下文 → 教学调用（诊断记录 + 给学习者的话）→ 等待输入
  ├── 闭环守卫：M04 提议结束时触发，独立上下文逐条核对验收范围
  ├── 外层循环：闭环边界或 M04 改线依据触发 M05
  ├── 上下文装配：按各模块读清单（`02` §6）取上游资产，缺料按 A-03 规则降级 / 不发
  ├── 资产存储：纯文本文件（会话 / 轮次 / 模块产出，`文件:行号` 可引用）
  └── 模型调用：每个判断点一次隔离调用，模型按判断点分别选型
```

|---|---|---|---|---|

| 2 | ⏳ 加 M05：会话中改线 ✅（`_research/原型实验-2-发现.md`）；闭环设计 ✅（`_research/原型实验-3-发现.md`）；**钻研氛围检验**待做 | 验收范围能否被守卫逐条核对；改线不来回踢；教学是否让学习者带路（产品总览「教学目标」） | 改线：每轮至多一次 M05、无反向改动、闭环能结束。设计：场景由 M05 写出；守卫每条都给有 / 无 + 行号，不出现“太笼统无法判断”；冷启动首个闭环一次会话结束。氛围：好奇型模拟学习者的提问 / 猜想被接住而非拉回题目 | M05 写出场景后**先交产品负责人看场景**，再跑模拟；每个检查点一次模拟，涉及学习者体验的再加一次真人试用 |
| 3 | 加 M09 提交与下一闭环读取 | 闭环记录能否支撑下一次 M05 / M04 | 第二闭环由 M05 读首个闭环记录 + 路线偏差记录设计：不重复已有证据的主张、承接“下一闭环候选”；诊断能引用上次证据，不把已会内容重考 | 本步收尾、写发现文件时 |
