# 概念与边界

## 当前结论

“Graph Engineering”在 AI Agent 领域是一个正在形成、尚未标准化的名称。它所概括的工程思想并不新，主要来自：

- 工作流编排与数据流图；
- 有限状态机和状态转换；
- Agent 路由与多 Agent 协作；
- 持久化执行、检查点和故障恢复；
- 事件记录、追踪和可观察性；
- 人工审批、验证门和权限控制。

因此，后续使用这个词时，应把它理解为一个研究标签，而不是已经存在统一定义、统一方法和统一技术栈的成熟学科名称。

## 两种常见使用范围

### 广义：图式 Agent 工作流

只要执行过程由节点、边和状态构成，就可作为图式工作流讨论。节点既可以是普通函数、数据查询和工具调用，也可以是一次模型调用或一个 Agent。

这是 LangGraph、Microsoft Agent Framework 等图式工作流框架更接近的范围。

### 狭义：图结构多 Agent 系统

一些新近社区定义要求图中至少存在多个边界独立的 Agent，并强调角色、权限、类型化交接、共享状态、证据门和可观察的运行图。

这个定义更接近多 Agent 组织工程。它不应被默认套到 Studium 上，因为 Studium 是否需要多个 Agent 尚未得到产品事实和验收证据支持。

## 核心构件

### 节点

节点是一个可独立说明和执行的工作单元。合理的节点通常具有明确输入、明确输出、单一主要职责、可识别的失败方式和独立测试边界。

节点不必是 Agent。数据库查询、规则判断、模型调用、人工确认和外部动作都可以成为节点。

### 边

边描述控制或信息如何从一个节点转移到另一个节点。工程上的边不只是箭头，还应能够说明传递的数据、触发条件、触发权限、接受标准、失败去向和控制权变化。

### 状态

状态保存一次执行中需要跨节点使用的事实和进度。状态应有明确所有权和结构，不应成为无边界的聊天全文、提示词和临时数据集合。

### 路由与门

路由根据当前输入和状态选择后续路径。确定性条件应优先由代码判断；需要语义理解的条件可以使用模型；高风险判断需要确定性验证或人工确认。

门判断当前结果是否满足继续前进的条件，例如证据是否充分、输出是否符合契约、操作是否获得授权、预算是否耗尽。

### 检查点与子图

检查点保存节点边界上的执行状态，用于暂停、恢复、失败重试、人工介入和历史审查。子图则把一组内部节点封装成可独立理解、测试和复用的流程。

复杂系统通常更适合由多个小子图组成，而不是维护一张覆盖全部产品行为的巨型图。

## 图的主要形态

| 形态 | 特征 | 适用问题 |
| --- | --- | --- |
| 线性链 | 每步固定串行 | 短小、稳定且每步都必需的任务 |
| DAG | 可分支、并行和汇合，但没有回环 | 独立资料处理、并行分析和结果汇总 |
| 循环图 | 允许根据结果回到先前节点 | 练习反馈、检索补充、生成与评估迭代 |
| 动态图 | 运行中生成或修改任务结构 | 研究、复杂写作和无法预先确定步骤的开放任务 |

图不会减少完成目标真正需要的工作。它主要减少不必要的固定串行步骤，使条件分支、并行、暂停、恢复和失败处理变得显式。

## 必须保持的概念区别

- 产品模块图回答“系统拥有哪些职责和数据”。
- 执行工作流图回答“一次具体任务实际经过哪些步骤”。
- 知识关系图回答“概念、资料或方法之间有什么关系”。
- 学习者状态变化回答“个人学习状态如何随证据变化”。

这些图可能相互引用，但不能因为都使用节点和边就合并成同一张图。

## 与上下文工程的关系

图工程主要回答“下一步运行谁、如何分叉、回流、暂停、恢复和通过守卫”。上下文工程主要回答“当前节点需要看什么、信息从哪里来、如何分类/缓存/校验/压缩，以及结果按什么契约回写”。

两者不能割裂：没有上下文契约，图只有控制箭头；没有图的路由和生命周期，上下文无法知道何时装配、失效、冻结或晋升。Studium 的第二阶段设计应把二者结合，但仍以产品模块的数据归属和判断职责为前提。
