# 上下文工程与图工程联合设计入口

> 状态：第二阶段入口草案。当前产品模块仍在审查中，本文件只记录已经确认的联合设计范围，不设计具体节点、边、Agent 数量或技术框架。

## 为什么必须联合设计

Studium 的学习过程不是固定流水线。M02、M03、M04、M10 需要根据学习者表现、诊断、策略和路线约束反复触发、分叉和回流；M01/M05 还会建立新的分叉会话并在完成后恢复主线。这要求图工程表达控制关系。

同时，每一次判断质量取决于节点拿到的信息种类、来源、完整度、时间范围和教学条件。进行中的同步信息保存在当前闭环上下文，闭环结束后才按契约进入 M09；M09 的个人记录又只能经候选/审计反向增益 M08。这要求上下文工程表达信息关系。

因此第二阶段的对象不是一张孤立的执行图，而是：

```text
产品模块契约
  ├─ 数据所有权、判断职责、输入输出
  ↓
上下文工程
  ├─ 信息类型、来源、完整度、缓存、选择、压缩、写回
  ↕
图工程
  └─ 节点、边、触发、分叉、回流、守卫、检查点、恢复
```

## 已确认的联合设计问题

1. 为每个运行节点定义有界输入、输出、来源和失败语义。
2. 区分原始观测、业务事实、中间推断、替代解释、策略决定和正式写入。
3. 区分当前闭环同步上下文、跨模块过程记录和已结束闭环异步数据。
4. 为主线、分叉会话、返回位置和嵌套/关联闭环定义检查点与上下文作用域。
5. 让 M04 的诊断与改线依据、M10 对 M02/M03 的策略和活动条件、M05 的闭环外路线规划和 M01 的路线结构通过类型化交接协作。
6. 让 M04 在一个闭环内持续更新诊断缓存，但不逐轮写入 M09。
7. 为 M04 -> M09 定义闭环证据守卫和个人形成记录契约。
8. 为 M09 -> M08 定义去个人化候选、自动/人工审查、晋升、退回、撤回和版本机制（此处的“撤回”指已晋升候选的撤回，与 M15 已否掉的**状态记录撤回权**是两回事，不要混用同一机制）。
9. 把摘要和标签限定为可重建索引，保留回到权威数据和原始证据的路径。
10. 明确工具权限、自动写入权限、用户确认点、失败降级和审查可见性。用户确认点只用于流程推进（等待回答、完成练习），**不用于裁定某条状态记录是否成立**——M15 的自述与异议按一类来源记录，不覆盖可观察事实。审查可见性对应横切原则第 5 条：所有模块的产出、来源和依据都要能在前端展示。
11. 为同源不同契约的读取定义隔离执行：M04 与 M15 读取同一份 M01 过程记录但输出契约不同、频率不同（M04 每轮，M15 事件触发），必须是两次独立执行，单次执行输出两段不构成隔离。M15 → M04 严格单向，M04 只能回发重新确认请求；若该请求边仍可能污染上下文，可用分支会话承载该次读取。
12. 为竞争性结论定义裁决位置：M15 的解释候选与 M04 的知识诊断竞争同一现象，M04 的输出须带“已评估的状态候选”一段；而 M15 的承载读数与知识诊断正交，直连 M05/M10 不经裁决。图上表现为同一来源分出两条不同性质的边。
13. 为**状态使用闸门**定义位置：M05/M10 在什么证据强度与时效下才让 M15 的读数改变行动。这一项在模块审查阶段被明确留给本阶段，因为闸门位置取决于上下文如何在模块间传递。
14. 为两个对称的跨会话/跨闭环子模块定义读取范围：M15 的状态阶段判断读 M15 主体已产出的状态日志，M04 的阈值概念判断读 M04 已产出的闭环日志，**互不读取，也不新开跨模块通道**。两者输出各上三条锁（只出类型与时间跨度、只给读数不给动作、不合成单一「学习压力」量），M05/M10 各读两个读数。图上不得出现把两侧结论汇入同一节点再合成的路径——合成会要求某一方同时持有知识侧与状态侧结论，正是严格单向禁止的。
15. 为 M09 与 M15 的**无引用关系**定义链接方式：两者双向都没有引用边，“闭环完成时处于什么状态”经 M01 的链接获得。M01 只存事实（如各次会话的启动间隔），不存解释（如“启动困难”），解释每次由子模块重新导出。已知代价：输入可复现，导出的解释不可复现；本阶段若要改善，须先回答“是否建立长期状态结论存储”，而该存储是人格标签的入口，当前不建。
16. 为**遗忘标签的次序约束**定义写入门：M04 会话内发现的“以前会的现在答不出”只是候选（可给 M10 补讲或 M05 另开复习会话），只有闭环提交那一次才写成 M09 的记录，且提交前须已排除疲劳退化等状态侧解释。两者之间不设快速写入通道，闭环结束那一次提交是唯一过渡点。

## 第二阶段开始前需要的材料

- M01-M10、M14、M15 最终确认的职责、输入、输出和数据归属（M12 本轮已取消，模型与服务作为实现期横切事项一并在本阶段处理）。单模块审查已于 2026-08-03 收口，**本阶段就是产品设计里说的“模块之间的组合与系统性设计”**：信息传递、交流、独立与配合；
- M08 与 M09 的存储结构与选型结论——这是本阶段的前置未决项。M09 的规模问题（不覆盖旧结论导致体积单调增长）有三个方向都卡在选型上：重新规划 M09 自身结构、历史版本移交别的模块（如 M01）、M09 分历史区与现有边缘区；
- M11、M13 中仍有价值的上下文、权限、日志和审查要求；
- `M04-01` 的动态诊断上下文分类和缓存问题；
- `M04-02` 的闭环写入、候选和审查问题；
- 每个产品模块的正常路径、分叉路径、失败路径和人工确认要求。

## 当前不做的决定

- 不决定使用 LangGraph、Microsoft Agent Framework、Temporal 或其他运行时；
- 不决定单 Agent、多 Agent、普通函数节点或混合形态；
- 不把一个产品模块直接等同于一个节点或 Agent；
- 不预设一张覆盖全部行为的巨型图；
- 不用上下文窗口大小反推产品应该丢弃哪些权威信息；
- 不让模型自行决定正式数据所有权、晋升权限或闭环目标。
