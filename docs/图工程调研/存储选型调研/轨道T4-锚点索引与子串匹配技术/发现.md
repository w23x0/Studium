## 1. 必须回答的问题逐条回答（T4-1…T4-4）

### T4-1 大规模逐字锚点（几百 K 到几 M 条）的索引技术对比

> 注：契约问题写的是「几百 K 到几 M 条」的一般性问题；本项目实测与 01 文档的外推是**万级节点、数万锚点**。下表对两者都给出判断（详细论据见 §2）。

| 技术 | 语义是否匹配「逐字子串判等」 | 构建/查询成本（关键数据） | 对本项目的适配判断 |
| --- | --- | --- | --- |
| `grep -F` / Python `in` | ✅ 完全匹配（固定字符串逐字） | 无索引，线性扫描；921 条实测 0.7 ms（约 1 µs/条） | 当前与全学科规模首选，无需索引 |
| Aho-Corasick（pyahocorasick / ahocorasick_rs） | ⚠️ 定位出现位置；判等须逐条 membership 查询 | 构建 1.5–3.0 ms、扫描 423 KB 语料 1.9–4.0 ms（本项目实测） | 适合全表审计（共享引文/位置审计）；不能直接替代 `in` 判等 |
| pg_trgm（PostgreSQL） | ⚠️ 相似度/模糊匹配，非精确判等 | GIN/GiST 索引，为相似度查询设计 | 不用于锚点判等；近似查重可用 SimHash 在脚本层替代 |
| suffix array / suffix tree（SA-IS、MUMmer 系） | ✅ 任意子串匹配 | O(n) 构造（SA-IS 2011）；基因组级先例 | 423 KB–数十 MB 语料属过度工程；未来全学科全文子串检索再考虑 |
| Lucene / Tantivy | ⚠️ 需 NGramTokenizer 类 n-gram 分词才能子串匹配 | 索引构建 + 运维复杂度 | 对当前规模不成比例 |
| Meilisearch | ❌ 只做前缀匹配 + typo 容错，不做任意子串；单查询 ≤10 词 | 索引构建 + LMDB | 语义不符，不适用于锚点子串校验 |
| Hyperscan | ⚠️ 数万模式高吞吐流匹配（实测 1.1–3.2 Gbps） | 编译期预处理 | 极端性能标杆；423 KB 语料属过度工程 |

**结论**：索引技术解决的是「速度」，而本项目锚点判等在实测规模下已经快到可以忽略（§2.3）；真正需要设计的是「全表分组」类算法（共享引文，T4-2），它属于聚类而不是全文搜索。

### T4-2 共享引文检测的规模化实现

**现状**（06 §5.2/§6 + 代码核验）：`check_shared_quotes.py` 只做 `(file, quote)` 精确分组、输出「待人工审查清单」、默认退出码 0（不结案）；238/522 = 46% 节点因每条锚点都独有而永久不可见；全图 148 组共享引文尚未逐组审查。A3 手工审过 11 组：9 合法、2 漂移——共享≠借引，清单只能定向。

**规模化实现 = 三层流水线（全部是分组/聚类，不是全文搜索）**：

1. **精确重复层（已有，先跑）**：规范化 `(file, quote)` 后哈希分组。本项目实测已能分出：921 条锚点 → 708 个唯一 `(file,quote)` 对、**213 条是另一条锚点的精确重复**、158 个重复组、371 条卷入、≥4 次引用的组 9 个。这部分 100% 机器可查，先把 148 组未审清单补全。
2. **近似重复层（新增）**：SimHash（Charikar 指纹 + f-bit 指纹近邻），检出「引文微改/截断/换标点/OCR 差异」的近似重复。先例：Manku et al. WWW 2007，多十亿页面仓库（§2.9）。
3. **大图 LSH 层（备选）**：MinHash LSH / b-bit MinHash / LSH Forest（datasketch 2.0.0，affine32 修复大图相似度高估偏差），万级锚点毫秒级。

**关键点**：46% 不可见不是技术缺陷，是「per-node 视角没有全表视角」的结构性盲区——必须把「全表分组」做成独立审计环节（与 06 §5.2「审计必须有一个全表视角的环节」一致）。三层流水线输出一律为「待审清单」，不结案（红线 5）。

### T4-3 复合锚点三项校验的实现方案与库选型

06 §2.1 纸面设计的三条件：①`formula` 必须是某个 `$$` 块内一整条内容行，逐字整行照抄；②常规规则确实无法满足（该块每一条内容行都 <30 字符）；③必须与紧邻的、≥30 字符的非空散文行配对，quote 与 formula **分别独立校验、永不拼接**。一条复合锚点计 1 条，`formula_line` 必填。

**实现方案（纯 Python，无库选型需求）**：

| 校验项 | 实现方式 | 要点 |
| --- | --- | --- |
| ① quote/formula 双字段分别校验 | `quote in sources[file]`、`formula in sources[file]` 各一次 | Python `in` 底层是 BMH/Two-Way（§2.1-4），实测约 1 µs/条；与 `grep -F` 同为固定字符串语义 |
| ② formula 必须为 `$$` 块内整行 | 源文件按行读入，扫描 `$$` 围栏定位块边界；校验 `lines[formula_line]` 整行 `== formula`（去行尾空白后逐字比对） | 不拼接、不截取，保持「grep -F 语义不失效」 |
| ③ 同块其余内容行 <30 字符 | 对 formula_line 所在块，遍历除 formula_line 外所有内容行（排除 `$$` 标记行），`len(stripped) < 30` 全过 | 08.6% 背景数据：真实正文行 <30 字符占 8.6%（215/2496，06 §2） |
| ④ 相邻性判定 | 块外向上/向下找最近非空散文行，判定存在 ≥30 字符者且在「紧邻」行距内 | 「紧邻」阈值 06 §2.1 未给机器可判定义，需在 921 条真实数据上标定（见 §5-2、§6-实验1） |

**库选型结论**：不需要 PostgreSQL / Lucene / Meilisearch / 向量检索——三项校验全是精确文本与行号操作，外部依赖只增加运维与审计面。若未来需要「全表定位所有公式行」，可用 Aho-Corasick 批量定位（§2.4），但判等仍以逐条 `in`/`grep -F` 为准。工具形态遵循红线 15：真 argparse、`--dry-run`、`--only`、禁裸 `'w'`。

### T4-4 grep -F 在当前与全学科规模下的性能上限（可引用数据）

- **当前规模（本项目实测）**：921 条锚点、34 文件、423,050 字节语料，Python `quote in text` 逐条全量校验 **0.7 ms**（约 1 µs/条），921/921 通过（§2.3）。
- **算法层面（官方一手）**：GNU grep 单固定模式用 Boyer–Moore、多固定模式用 Aho–Corasick；gnulib kwset.c 明示 "Use Boyer-Moore if just one pattern, Aho-Corasick otherwise"；GNU grep 作者说明其快在「不必看每个字节」（§2.1）。
- **公开基准（一手）**：ripgrep 在 Linux 内核源码树（约 1.6 GB）`rg -w '[A-Z]+_SUSPEND'` = **0.082 s**；13 GB 单文件 `rg -w 'Sherlock [A-Z]\w+'` = **1.042 s**（§2.2）。
- **未来全学科（C 级推断）**：按 ~1 µs/条线性外推，5 万条锚点 ≈ 40–50 ms；语料 423 KB → 30–100 MB，Python `in` 逐条扫描仍为数十毫秒级；`grep -F` 单模式在 GB 级有秒级公开基准。**结论：无论 921 条还是数万条，逐字判等的计算成本都可忽略；瓶颈从来不在字符串匹配，而在人工审计（06 §6.1）。**
## 2. 关键发现（每条：论断 + 来源 + 原文摘录/要点）

### 2.1 固定字符串搜索已被深度优化，判等无需索引
**论断**：逐字 `grep -F` 语义＝固定字符串搜索；现代实现（GNU grep、ripgrep、CPython 的 `in`）用 Boyer–Moore、Two-Way、Aho–Corasick 等算法优化到「不必看每个字节」。在千条～万条锚点、MB～GB 语料下，判等不需要任何索引。
- 来源：GNU Grep 3.12 手册 Performance 章，Free Software Foundation，2024，https://www.gnu.org/software/grep/manual/html_node/Performance.html 【A】。原文："When feasible, the Boyer–Moore fast string searching algorithm is used to match a single fixed pattern, and the Aho–Corasick algorithm is used to match multiple fixed patterns."
- 来源：gnulib lib/kwset.c，Free Software Foundation（Mike Haertel 1989 年 8 月初稿），https://raw.githubusercontent.com/coreutils/gnulib/master/lib/kwset.c（上游 https://git.savannah.gnu.org/cgit/gnulib.git/plain/lib/kwset.c）【A】。原文："/* Written August 1989 by Mike Haertel. */"、"/* Use Boyer-Moore if just one pattern, Aho-Corasick otherwise. */"、"/* Aho-Corasick failure function. */"。
- 来源：Mike Haertel《why GNU grep is fast》，FreeBSD 邮件列表 freebsd-current，2010-08-21，https://lists.freebsd.org/pipermail/freebsd-current/2010-August/019310.html 【A】。原文："#1 trick: GNU grep is fast because it AVOIDS LOOKING AT EVERY INPUT BYTE. #2 trick: GNU grep is fast because it EXECUTES VERY FEW INSTRUCTIONS FOR EACH BYTE that it *does* look at."
- 来源：CPython Objects/stringlib/fastsearch.h，Python Software Foundation（main 分支），https://raw.githubusercontent.com/python/cpython/main/Objects/stringlib/fastsearch.h 【A】。原文："fast search/count implementation, based on a mix between boyer-moore and ..."、"If the strings are long enough, use Crochemore and Perrin's Two-Way"。

### 2.2 grep -F / ripgrep 在 GB 级语料的公开基准
**论断**：固定字符串搜索在 GB 级数据有秒级公开基准；本项目语料（423 KB）比该量级低 3–4 个数量级。
- 来源：ripgrep README 基准表，Andrew Gallant (BurntSushi)，https://raw.githubusercontent.com/BurntSushi/ripgrep/master/README.md 【A】。摘录：Linux 内核源码树 `rg -n -w '[A-Z]+_SUSPEND'` → 0.082s (1.00x)；约 13GB 单文件（OpenSubtitles）`rg -w 'Sherlock [A-Z]\w+'` → 1.042s。

### 2.3 本项目实测：921 条锚点全量判等 0.7 ms
**论断**：在当前真实数据（34 文件 / 423,050 字节 / 921 锚点）上，Python `quote in text` 逐条校验 0.7 ms、921/921 通过。判等性能不构成任何选型约束。
- 来源：本地微基准（本项目数据，脚本 t4_bench.py，2026-08-12）【A＝本项目实测】。输出：`A. python 'in' per anchor : 0.7 ms (1 us/anchor) ok=921`。

### 2.4 Aho-Corasick：全表定位工具，不是判等替代品
**论断**：Aho-Corasick 一次扫描可在数毫秒内给出 921 条锚点在 423 KB 语料中的所有出现位置；但「扫描命中计数」不能当「锚点校验通过数」——921 条锚点间存在大量重复与包含关系（213 条精确重复、91 条真子串），leftmost-* 匹配语义会遮蔽重叠的短模式。判等必须用逐条 membership 查询（实测 921/921 通过，0.3 ms）或 `grep -F`/`in`。
- 来源：pyahocorasick，PyPI 元数据与说明，作者 Wojciech Muła 等，https://pypi.org/pypi/pyahocorasick/json 【A】。原文："pyahocorasick is a fast and memory efficient library for exact or approximate multi-pattern string search... You can use it as a plain dict-like Trie or convert a Trie to an automaton for efficient Aho-Corasick search. And pickle to disk for easy reuse of large automatons."；用户证言："a library of 100k+ CRISPR guides that we have to count in a stream of millions of DNA sequences"。
- 来源：ahocorasick_rs，PyPI 元数据与说明，G-Research，https://pypi.org/pypi/ahocorasick_rs/json 【A】。原文："implemented as a wrapper of the Rust aho-corasick library, and provides a faster alternative to the pyahocorasick library"。
- 来源：Rust aho-corasick crate 文档，Andrew Gallant，https://docs.rs/aho-corasick/latest/aho_corasick/ 【A】。原文："unlike most other Aho-Corasick implementations, this one supports enabling leftmost-first or leftmost-longest match semantics"、"supports controlling the space versus time trade off"。
- 本地实测（本项目，t4_bench.py / t4_dbg*.py / t4_stats.py，2026-08-12）【A＝本项目实测】：pyahocorasick build 1.5 ms、scan 4.0 ms、命中 708/921；ahocorasick_rs build 3.0 ms、scan 1.9 ms、命中 624（Standard）/ 618（LeftmostFirst）/ 615（LeftmostLongest）；逐条 membership（`quote in automaton`）921/921 通过、0.3 ms。成因：921 条锚点 → 708 个唯一 `(file,quote)` 对（213 条精确重复、158 个重复组、371 条卷入）；91 条是另一条同文件锚点的真子串。

### 2.5 pg_trgm：近似字符串索引，语义不匹配「逐字判等」
**论断**：pg_trgm 是按共享 trigram 计算相似度的模糊匹配索引（GIN/GiST、支持 LIKE/ILIKE/=、忽略非字母数字字符、默认相似度阈值 0.3），为「近似查询」设计；用它做「锚点是否逐字出现」的判等语义绕远，且引入 PostgreSQL 依赖，与红线 9（存储＝JSONL+脚本，暂不选数据库）冲突。
- 来源：PostgreSQL 官方文档 pg_trgm，PostgreSQL Global Development Group，current（2026 访问），https://www.postgresql.org/docs/current/pgtrgm.html 【A】。原文："The pg_trgm module provides functions and operators for determining the similarity of alphanumeric text based on trigram matching, as well as index operator classes that support fast searching for similar strings."

### 2.6 后缀数组/后缀树：基因组级锚定先例，当前规模过度工程
**论断**：后缀树/后缀数组是「大规模序列中找精确锚点/最长公共子串」的权威先例（MUMmer 用后缀树做全基因组比对锚定；SA-IS 提供 O(n) 线性时间后缀数组构造），适用对象是 GB 级序列；423 KB 教材语料用后缀索引属过度工程。未来若全学科语料（数十 MB）需要「任意子串即时查询」，SA-IS 是合理候选，但当前无此需求。
- 来源：Kurtz S, Phillippy A, Delcher AL, Smoot M, Shumway M, Antonescu C, Salzberg SL《Versatile and open software for comparing large genomes》(MUMmer3)，Genome Biology 5:R12，2004-01-30，https://genomebiology.biomedcentral.com/articles/10.1186/gb-2004-5-2-r12 【B：标题/作者/日期经 Europe PMC 元数据核实，正文未全文核实】。
- 来源：Nong G, Zhang S, Chan WH《Two Efficient Algorithms for Linear Time Suffix Array Construction》，IEEE Trans. Computers 60(10)，2011，DOI 10.1109/TC.2010.188，https://dblp.org/rec/journals/tc/NongZC11 【B：DBLP 书目记录核实，论文全文未取】。

### 2.7 全文检索引擎：Meilisearch 语义不符，Lucene/Tantivy 需 n-gram 才能子串匹配
**论断**：Meilisearch 是前缀匹配 + typo 容错（不做任意子串匹配，且硬限制不可改），与「锚点逐字子串校验」语义不符；Lucene/Tantivy 需 NGramTokenizer 类 n-gram 分词器才能覆盖子串类匹配，引入索引构建与运维复杂度，对当前规模不成比例。
- 来源：Meilisearch 官方文档《Known limitations》与《Prefix search》，Meilisearch，2025，https://meilisearch.com/docs/resources/help/known_limitations.md、https://meilisearch.com/docs/resources/internals/prefix.md 【A】。原文（Known limitations）："These are hard limits you cannot change and should take into account when designing your application."；原文（Prefix search）："Prefix search is when document sorting starts by comparing the search query against the beginning of each word in your dataset."
- 来源：Apache Lucene 9.12.0 NGramTokenizer javadoc，Apache Software Foundation，https://javadoc.io/static/org.apache.lucene/lucene-analysis-common/9.12.0/org/apache/lucene/analysis/ngram/NGramTokenizer.html 【A】。要点：该类将输入切分为指定大小的 n-gram（"Tokenizes the input into n-grams of the given size(s)"）——是 Lucene 支持子串类匹配的路径。

### 2.8 Hyperscan：数万模式极端吞吐标杆，当前规模属过度工程
**论断**：Hyperscan（Intel 开源，NSDI'19）在 1k–26k 字符串模式下吞吐 1.1–3.2 Gbps（真实流量），是「数万条模式同时匹配」的极端性能标杆；对 423 KB 语料、921 条锚点无必要，且其定位是网络入侵检测类「高吞吐流匹配」，不是「存在性判等」。
- 来源：Wang X, Hong Y, Chang H, Park KS, Langdale G, Hu J, Zhu H《Hyperscan: A Fast Multi-pattern Regex Matcher for Modern CPUs》，USENIX NSDI '19，2019-02，论文 PDF 原文：https://www.usenix.org/system/files/nsdi19-wang-xiang.pdf（会议页 https://www.usenix.org/conference/nsdi19/presentation/wang-xiang）【A】。论文 Figure 11（ET-Open 规则集、真实 Web 流量、FDR 算法）：1k/5k/10k/26k 个字符串模式吞吐 3.2/1.3/1.2/1.1 Gbps；随机报文 2.5/2.1/1.7/1.5 Gbps。

### 2.9 共享引文规模化的算法先例：精确分组 + 近似指纹
**论断**：共享引文检测本质是「分组/聚类」；精确重复用哈希分组（已有实现），近似重复用 SimHash（f-bit 指纹 + 海明距离近邻）或 MinHash LSH；两者在万级锚点规模均为毫秒级。输出只能作为「待人工审查清单」（红线 5）。
- 来源：Manku GS, Jain A, Das Sarma A《Detecting Near-Duplicates for Web Crawling》，WWW 2007，论文 PDF 原文：https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/33026.pdf 【A】。原文（摘要）："In the course of developing a near-duplicate detection system for a multi-billion page repository, we make two research contributions. First, we demonstrate that Charikar's fingerprinting technique is appropriate for this goal. Second, we present an algorithmic technique for identifying existing f-bit fingerprints that differ from a given fingerprint in at most k bit-positions."
- 来源：datasketch 官方文档，Zhu E 等，https://ekzhu.github.io/datasketch/ 【A】。原文："datasketch gives you probabilistic data structures that can process and search very large amount of data super fast, with little loss of accuracy."；"Version 2.0.0 changes the default MinHash permutation scheme to 'affine32', which fixes a similarity over-estimation bias on large sets."

### 2.10 复合锚点校验的技术可行性
**论断**：06 §2.1 的三项校验全部可用纯文本操作实现（行号解析 + 整行比对 + 行长度判定 + 相邻性判定），Python 标准库足够；无数据库/检索引擎选型需求。
- 来源：`06-M08技术选型.md` §2.1，项目文档，2026 【A＝项目一手文档】。原文："`formula` 必须是某个 `$$` 块内的一条内容行，逐字整行照抄，不得从散文行截取。"、"块内有 ≥30 的行就必须引那一行。这一条必须机器可判"、"必须与紧邻的、≥30 字符的非空散文行配对。两者分别独立校验、永不拼接"。
- 现状核验：`verify_anchors.py` 只实现 `quote in text` 判等，无 formula/相邻性/块长逻辑（项目代码，2026）【A＝项目一手代码】——与 06 §2.1「只是纸面设计、未在 921 条锚点上跑过」一致。
## 3. 对决策点的输入

### D7 锚点索引与检索
1. **继续 `grep -F` / Python `in` 逐条判等，不引入索引**：921 条实测 0.7 ms；线性外推数万条 ≈ 40–50 ms（C 级推断）；公开基准证明 GB 级固定串搜索秒级。红线 4 保持不动。
2. **新增「全表审计」工具（可选、低成本）**：用 Aho-Corasick（pyahocorasick 或 ahocorasick_rs）一次扫描给所有锚点定位，输出 `(锚点 id, file, 出现位置列表)`，作为共享引文与锚点漂移审计的输入；判等仍以逐条 `in`/`grep -F` 为权威（§2.4 的语义张力见 §4-1）。
3. **共享引文检测升级为三层流水线**：①精确 `(file,quote)` 哈希分组（已有能力；921 条已能分出 158 组/371 条卷入、≥4 次组 9 个）→ ②SimHash 近似分组（检出微改/截断/换标点）→ ③人工逐组审查（148 组 + 近似新增组）。输出一律为「待审清单」，不结案。
4. **机械信号维持「只定向、不结案」**：无锚点数值筛查召回 1/4、共享引文覆盖上限 54%（≥2 次），索引技术解决的是速度而非召回/精确率，本调研未发现能突破该结论的技术（§2.5–§2.9 全部确认这一点）。
5. **明确「暂不引入」清单**：pg_trgm（语义不符 + 引入 PG）、Meilisearch（语义不符）、Lucene/Tantivy（复杂度不成比例）、suffix array（当前规模过度工程）、Hyperscan（当前规模过度工程）。以上与红线 9 一致。

### D8 复合锚点校验
1. **实现方案：纯 Python 脚本，无库选型**。在 `verify_anchors.py` 基础上扩展或新增 `check_composite_anchors.py`：
   - 步骤 A：`quote in sources[file]` 与 `formula in sources[file]` 分别判存在（各自独立、永不拼接）；
   - 步骤 B：源文件按行读入，定位 `$$` 围栏块，校验 `formula_line` 处整行 `== formula`（去行尾空白后逐字比对）；
   - 步骤 C：同块其余内容行（非 `$$` 标记行）`len(stripped) < 30` 全过；
   - 步骤 D：块外紧邻非空散文行存在 ≥30 字符者（「紧邻」阈值先按块前后 1 行实现，用 921 条真实数据标定）；
   - 工具安全：真 argparse / `--dry-run` / `--only` / 禁裸 `'w'`（红线 15）。
2. **不引入**：PostgreSQL、全文检索引擎、向量检索——三项校验全是精确文本/行号操作，外部依赖只增加运维与审计面。
3. **先做「复合锚点能否通过校验」的验证实验**（06 §2.1 明示未验证）：实现后对现有数据中已标注复合锚点的节点跑通，统计通过/失败及失败原因分类，把失败分布作为 D8 是否继续的判据（§6-实验1）。

## 4. 与产品约束的冲突/张力

1. **红线 4（锚点硬校验＝逐字 `grep -F`）vs Aho-Corasick 匹配语义【张力，必须标注】**：AC 扫描的「命中」语义与「逐字存在性判等」不是一回事。实测 921 条锚点中 213 条是另一条锚点的精确重复、91 条是真子串；AC 扫描命中计数（pyahocorasick 708；ahocorasick_rs 624/618/615）全部小于 921，leftmost-longest 会遮蔽重叠的短模式。**若把「AC 命中数」当「校验通过数」，会系统性误报失败。**缓解：判等一律用逐条 membership 查询（实测 921/921 通过）或 `grep -F`/`in`；AC 只用于「定位」。
2. **红线 5（机械信号只定向、不结案）【一致，无冲突】**：本调研给出的共享引文方案（精确分组、SimHash、MinHash LSH）都只产出「待审清单」，与 06 §5.2「148 组待审」直接衔接；任何「检出即判死/晋升」的设计仍违反红线 5。
3. **红线 9（存储＝append-only JSONL + 独立校验脚本，暂不选数据库）【一致，无冲突】**：D7 结论支持「不因锚点检索引入 PostgreSQL/图数据库」；pg_trgm 的唯一合理用途（近似查重）可用 SimHash/MinHash 在脚本层完成，不触碰存储层。
4. **红线 2（节点身份＝锚点集合）【注意，无冲突】**：共享引文分组会把「多个节点引用同一条原文」聚在一起，可能被误读为「这些节点是同一对象」；但判等以锚点集合（全集）为准，单条共享不足以判等，分组清单只是审计提示。合成阶段需明确这一点，防止把共享引文清单误当身份合并依据。
5. **红线 4 的延伸（不跨行拼接）【一致】**：复合锚点「分别校验、永不拼接」正是为保持 `grep -F` 语义成立（拼接会造出书里不存在的字符串）；本报告的整行比对方案与之一致。

## 5. 未决与风险

1. **复合锚点方案本身未验证**（06 §2.1 明示「只是纸面设计」）：实现后可能发现设计中的复合锚点不满足三条件（公式行其实可作锚点、相邻散文行 <30 字符、`$$` 围栏嵌套/缺失等边界情形），需人工修订或调整「紧邻」定义。**这是 D8 的最大不确定性，必须先跑最小实验。**
2. **「紧邻」阈值未定义**：06 §2.1 写「紧邻的散文行」但未给机器可判的精确行距阈值；需在 921 条真实锚点/短公式数据上标定，否则相邻性判定不可复现。
3. **共享引文 148 组未逐组审查**：瓶颈是人工而非技术；SimHash/MinHash 阈值（海明距离 ≤k、Jaccard ≥τ）若标定不当会以假阳性淹没清单，需坚持「精确分组优先、近似分组降级」的顺序。
4. **规模外推为推断**：921 → 数万锚点的线性外推（≈40–50 ms）未经实测；§6-实验4 的合成基准可消除该不确定性。
5. **AC 扫描语义的工程陷阱**：若未来用 AC 做位置审计，必须明确定义「重叠/遮蔽」处理方式，并保留逐条 `in`/`grep -F` 作为权威判等，避免两套语义混用造成校验口径漂移。
6. **数据侧风险不在匹配技术**：OCR 噪声、全角/半角、Unicode 归一化会影响逐字判等；`grep -F`/`in` 本身不受正则元字符影响（公式中的 LaTeX 控制符无碍）。

## 6. 建议的下一步实测（可执行的最小实验）

1. **实验 1｜复合锚点校验器（D8 核心）**：实现 `check_composite_anchors.py`（纯 Python，argparse / `--dry-run` / `--only`），输入第 15 章 nodes-*.jsonl + source/ 与「复合锚点标注」；对每条复合锚点执行三项校验（双字段存在、整行 formula、块内其余行 <30、相邻散文行 ≥30）。判据：设计内复合锚点全部通过；失败按原因分类（公式非整行/相邻散文行 <30/块内混有 ≥30 行/`$$` 边界异常）。通过标准：失败均为数据修订问题且可逐条解释；失败标准：三条件本身不可判定（如「紧邻」无法定义）。
2. **实验 2｜AC 语义核对（红线 4 张力验证）**：在 921 条锚点上，用逐条 membership（`quote in automaton`）与三种 MatchKind 扫描各跑一遍，核对差异 ＝ 213 条重复 + 91 条真子串的遮蔽；验证「AC 定位 + `in` 判等」组合流水线结果与 `in` 全量一致（921/921）。
3. **实验 3｜共享引文三层流水线（D7 核心）**：在 522 节点/921 锚点上实现：①精确 `(file,quote)` 分组（对照 check_shared_quotes.py 清单与 148 组）→ ②SimHash（64-bit，k=1..5 扫描）近似分组 → ③人工抽查 20 组判「合法共享/借引」。判据：近似层相对精确层新增组数、抽查精确率。通过标准：新增组 <20% 且人工可读；失败标准：假阳性淹没清单（>50%）。
4. **实验 4｜规模外推基准**：合成 5 万锚点 × 30–100 MB 语料（可由现有 34 文件重复拼接生成），测 Python `in` 全量 / `grep -F` 逐条 / AC 扫描三者耗时与内存，验证 §1-T4-4 的毫秒～秒级结论。
