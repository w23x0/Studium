# 存储选型调研：问题清单与产品约束（共享上下文）

> 本文供所有调研轨道代理开工前通读。它是契约的正文（与 `00-调研workflow设计.md` 配套）。
> 所有轨道必须回答自己轨道定义的问题，不得越界回答，也不得漏答。

## 产品背景（一句话）

Studium 是一个单学习者自学系统（数学/物理方向）。第三次重构已把产品模块切成 M01–M15：
M06 资料入库 → M07 静态资料库 → M08 通用知识结构（不属任何个人）；M04 关闭学习闭环 → M09 个人知识形成记录（属某个学习者）；
M08 与 M09 通过「候选/审计/晋升」管道交替递增；M14 高阶产出也走同一候选通道。

## 存储选型要服务的真实数据形态（来自实验实测）

| 数据 | 规模（实测） | 特征 |
| --- | --- | --- |
| M08 基础图（Apostol 第15章 + Strang 第3–4章） | 522 节点 / 1433 边 / 921 锚点 | 4 类节点（concept/method/theorem/notation），9 关系词封闭表 |
| 锚点 | 每节点 1–3 条 / 30–200 字符 | 逐字原文，`grep -F` 机器校验 100% 通过 |
| 跨教材对齐 | 42 匹配 / 180 对象 | strict-same 21%、special-case 67%、type-flip 12%、单侧独有 99 |
| 高层结构（L2–L7） | L2 候选 24 → 存活 4 | 候选池 + 双审计（A 正确性 / B 抽象增益） |
| M09 个人记录 | 无实测（设计阶段） | 已结束闭环 + 证据边 + 时间版本 + 开放字段 + 未映射对象 |

关键外推（推断）：三四章产出 522 节点；一门学科 30+ 章、多本教材。审计 A/B 全人工且处置单点 ⇒ 一次穷尽全学科不可行，只能「用到哪块建哪块」。

## 各轨道必须回答的问题（逐条）

### T1 图数据库与查询触发条件（→ D1）
1. 主流图数据库引擎（Neo4j、Kuzu、Memgraph、ArangoDB、TigerGraph、Amazon Neptune 等）在「锚点+证据+版本+候选池」这类混合负载下的能力与代价？
2. 「三跳以上遍历」「实时交互查询」作为上图触发条件是否合理、可判定？业界判定框架是什么？
3. JSONL+脚本（当前形态）在大规模下的已知边界（多少节点/边后查询不可忍）？有没有可引用的基准？
4. GQL 标准与 Cypher 的现状；图数据库与 JSON/关系数据库的混合架构（如 DuckDB+图、Postgres+Apache AGE）是否适配本数据形态？

### T2 时间版本与证据链存储（→ D3、D5）
1. bitemporal 建模（valid time / transaction time）如何映射「M09 不覆盖旧结论 + 复检/遗忘/重新掌握」？
2. event sourcing / append-only 与图数据的结合先例？CQRS/物化视图是否必要？
3. 版本化知识库/内容寻址（nanopub trusty URI、Git 式对象模型、DVC）各自的粒度与查询代价？
4. 更正/撤回/回退三种操作的存储语义与先例？（注意：M09 侧「撤回」指已写入记录的撤回，与 M15 状态记录撤回权是两回事）
5. 时间版本的最小保留粒度怎么定？（M09 审查问题 4）

### T3 开放字段与半结构化个人记录（→ D2）
1. 「开放但可查询可审查」的字段模型：PostgreSQL JSONB、文档数据库、EAV、属性图、混合？各自的查询/校验/迁移代价？
2. M09 的「丰富个人形成记录」（理解、应用、结构解释、心智模型、可提取性、干扰、迁移、直觉、缺口、适用条件）怎么建模才能既开放又稳定审查？
3. 开放字段 + 证据边 + 版本链三者的组合存储形态？
4. 最小记录单位怎么定（M04-02 未决问题）？

### T4 锚点索引与子串匹配技术（→ D7、D8）
1. 大规模逐字锚点（几百 K 到几 M 条）的索引技术：pg_trgm、suffix array/automaton、Aho-Corasick、Lucene/Tantivy/Meilisearch？各自的构建与查询成本？
2. 共享引文检测（多节点共引一条引文）的规模化实现？（实验现状：`check_shared_quotes.py` 对 46% 节点永久不可见）
3. 复合锚点校验三项逻辑（quote/formula 双字段分别校验、相邻性判定、同块其余行 <30 字符）的实现方案与库选型？
4. grep -F 在当前 921 锚点规模与未来全学科规模下的性能上限有没有可引用数据？

### T5 候选池/审计/工作流状态存储（→ D6）
1. 候选队列 + 审计轨迹 + 审批晋升 + 墓碑（graveyard）的工程先例（代码审查系统、数据治理、内容审核流水线）？
2. 「检测并行、处置单点」对应什么存储模式（如 append-only 事件 + 单写者裁决）？
3. 审计记录（谁判的、依据什么、结果）的不可变存储与回溯查询？
4. 候选与正式内容隔离的存储形态（命名空间/分区/独立库）？

### T6 领域先例对照（→ D1、D2、D5）
1. 形式化数学库（mathlib、MML、Metamath）的依赖图/库存储形态与规模？
2. MMT/OMDoc 模块化理论图的存储与查询？
3. 教学系统（ALEKS 知识空间 KST、课程图、知识追踪 KT）如何存储学习者状态与知识结构？
4. 间隔重复系统（Anki、FSRS、SuperMemo）如何存储卡片状态、历史复习记录与调度参数？
5. 数学知识图谱（Wikidata 公式实体、OntoMath、MaRDI、QUDT）与 GraphRAG 系统的存储选型与经验？
6. 哪些先例的结构可直接映射到 M08/M09？哪些证明「该形态在更大规模才成立」？

### T7 M09 规模三方向技术评估（→ D4）
1. 个人学习历史/记录单调增长的存储先例：学习记录系统、电子健康档案（版本化）、审计日志、时间序列？
2. 三方向各自的存储成本、查询代价、迁移风险：
   方向1 重新规划 M09 自身结构（历史版本内部独立位置）
   方向2 历史版本移交别的模块（如 M01，作为对会话的一种存储）
   方向3 M09 分两区：历史区与边缘区（动态体现在边缘网，历史沉底）
3. 每个方向与「当前视图可从底层记录派生」的兼容性；与 M08 锚定/候选管道的关系。

### T8 向量/混合检索在候选发现中的实证边界（→ D9）
1. 向量检索（hnsw/ivf/标量量化）在实体发现/候选生成上的假阳性率实证数据？
2. 图+向量混合检索（GraphRAG 系）何时真加分、何时不加分的负面结果研究？
3. rerank 是否可能把「机械信号只定向不结案」升级为可靠信号？业界证据？
4. 在「锚点 grep -F 是唯一硬校验」的前提下，向量检索参与候选发现的最小实验设计。
