## 0. 一句话结论

当前 522 节点 / 1433 边 / 921 锚点规模下，JSONL+脚本**远未触及任何已知不可忍边界**；「三跳以上遍历 / 实时交互查询」作为上图触发条件**方向正确且可判定**——业界基准 LDBC SNB 正是用「≤3 跳邻域复杂读 + 短读 + 连续更新」定义交互式图负载；**当前判定：未触发**。若未来触发，建议走轻量混合路线（Postgres+Apache AGE 或 DuckDB+SQL/PGQ，关系表 `WITH RECURSIVE` 作中间态），不首选重运维的 Neo4j / TigerGraph / Neptune；**Kuzu 已于 2025-10-10 被归档（read-only），不可作为推荐项**。

## 1. 必须回答的问题逐条回答（T1-Q1 ~ Q4）

### Q1 主流图数据库引擎（Neo4j、Kuzu、Memgraph、ArangoDB、TigerGraph、Amazon Neptune 等）在「锚点+证据+版本+候选池」这类混合负载下的能力与代价？

**先拆负载再比引擎。** 本数据形态是四种负载的叠加，图引擎只覆盖其中一块：

| 负载 | 本质 | 归属 |
| --- | --- | --- |
| 知识关系图（遍历/查询） | 属性图 | **图引擎覆盖** |
| 锚点逐字校验（`grep -F` 语义） | 子串匹配/全文索引 | 属 T4，不是图引擎负载 |
| 证据边（902/902 校验通过） | 图边上的属性 | 图引擎可存 |
| 时间版本 / 候选池 / 审计 | 版本链 + 工作流状态 | 属 T2/T5，图引擎不专门解决 |

各引擎能力与代价（按部署形态分组）：

**嵌入式（进程内，运维面最小）**
- **Kuzu**：嵌入式、无服务器、Cypher、列式磁盘存储、可串行化 ACID；曾是「本地单机 + Cypher」最贴合形态。**但 GitHub 仓库 2025-10-10 被所有者归档为 read-only，README 宣布项目转型、0.11.3 后扩展需本地扩展服务器——新项目不可依赖（详见 F1）。**
- **DuckDB（非图库，但可作图查询）**：进程内列式分析库，`WITH RECURSIVE` 原生支持图遍历、JSON 文件直接查；写路径弱，无成熟审计/版本机制，适合分析侧。

**服务器（自托管，运维面中到大）**
- **Neo4j**：属性图 + Cypher（Cypher 25 现行）+ ACID + 生态最全；Community 版 GPL v3；官方硬件指南「2GB 最小、16GB+ 建议」（F9）——引入 JVM 堆/备份/版本运维，对单学习者本地工具偏重。
- **Memgraph**：Cypher 变体；三种存储模式（`IN_MEMORY_TRANSACTIONAL` 默认 / `IN_MEMORY_ANALYTICAL` 无 ACID / `ON_DISK_TRANSACTIONAL`）；内存占用有官方量化（F10）；许可为 APL/BSL/MEL 组合（以官方条款为准）；需服务器进程。
- **ArangoDB**：多模型（图/文档/键值）+ AQL + RocksDB（F13）；图模型是文档式边集合，与属性图/Cypher 心智不同；本次官方 docs 被 Cloudflare 拦截，一手文档未取到。
- **TigerGraph**：分布式原生图 + GSQL；官网宣称「<100ms 确定性多跳推理、十亿关系级」（F12，**厂商营销，未经第三方审计**）；分布式运维最重。

**托管（云）**
- **Amazon Neptune**：托管、openCypher/Gremlin/SPARQL 三语言、集群卷上限 128 TiB（F11）；免运维但强绑定 AWS、无本地形态。

**混合/扩展**
- **Postgres+Apache AGE** / **DuckDB+DuckPGQ**：见 Q4 与 F16/F17。

**代价结论**：图引擎只买「多跳遍历 + 交互延迟」两件事；当前已知需求（1–2 跳、按 id、全表校验）用脚本就够（06 §7 原文）。「锚点+证据+版本+候选池」四项里只有证据边是图负载，其余三项图引擎帮不上忙——所以即使触发，也应是**「图引擎补遍历」而非「整体迁移」**。

### Q2 「三跳以上遍历」「实时交互查询」作为上图触发条件是否合理、可判定？业界判定框架是什么？

- **合理**。业界对「交互式图负载」的权威定义（LDBC SNB Interactive）正是「复杂读查询访问给定节点邻域 + 连续插入更新」；其最典型复杂读查询 IC1 就是「与起点 ≤3 跳相连」（F3）。「三跳以上遍历」是图数据库区别于普通表连接的标志性负载深度，红线 9 的措辞与业界框架一致。
- **可判定**。给出操作化判定清单（四条，见 §3 输入 1）。「实时交互查询」的延迟阈值，业界用吞吐量（ops/s）与单查询执行时间描述（SNB 审计，F4）；本产品建议初始阈值 **P95 < 1s 且位于用户直接等待路径**（待产品侧确认，见 §5-5）。
- **业界判定框架**：LDBC SNB 双工作负载划分——Interactive（事务型交互：复杂读 + 短读 + 更新）vs BI（聚合/join 重的分析型）（F2/F3）；SNB 规范论文 arXiv:2001.02299（24 位作者，2020 v1 / 2024 v11）；已审计结果表证明该框架被产业界实际采用并审计（F4）。判定时把「真实产品需求」翻译成「是否等价于 SNB 复杂读模式的查询」，即可判定。

### Q3 JSONL+脚本（当前形态）在大规模下的已知边界（多少节点/边后查询不可忍）？有没有可引用的基准？

- **直接答案：没有针对「JSONL+脚本做图查询」的权威基准**——这是本轨道最重要的未决之一，边界数字必须自家实测（§6 实验 A/B 给出最小实验）。
- **可引用的邻近基准**：
  - DuckDB 官方博客实测：4.4M JSON 记录 `count(*)` gzip 7.3s / 未压缩 5.4s（2020 M1 MacBook Pro 16GB）——单机解析百万级 JSON 行是秒级（F14）；
  - ripgrep 作者 25 项工具对比基准 + 几 GB 语料方法学；memchr 吞吐「several gigabytes a second」——与 `grep -F` 同构的逐字子串匹配在 GB/s 级（F18，更细的锚点规模上限属 T4）；
  - PostgreSQL `WITH RECURSIVE` 官方文档原生支持图遍历（含环检测、深度/广度排序）——「JSONL → 关系表」是成熟升级中间态（F15）。
- **量级参照**：LDBC SNB 最小数据集 SF1 = 1 GiB CSV（图引擎基准起算规模），比本项目大 4 个数量级；522/1433/921 在图引擎基准面前是「零头」（F3）。
- **边界推断（标注为推断，待实测）**：JSONL+脚本三类查询代价不同——全表校验 O(N)（线性，机器校验成本≈0，06 §6.1）；按 id 取 O(N) 线性扫描无索引（万级节点后可感知，十万级变慢）；多跳遍历需全图加载建邻接表 O(V+E)。「不可忍」拐点取决于查询类型与实现，**预估在十万节点量级前后出现（非断言）**。

### Q4 GQL 标准与 Cypher 的现状；图数据库与 JSON/关系数据库的混合架构（如 DuckDB+图、Postgres+Apache AGE）是否适配本数据形态？

- **GQL**：ISO/IEC 39075:2024，2024-04-12 发布，受 SQL / Cypher / GSQL 影响；首个研究实现来自 TU Eindhoven（Olof Morra）；Google Spanner 已提供 GQL 语法查询（F6）；Neo4j 官方 GQL 一致性页列出支持/不支持的 mandatory 特性（F7）。SQL 侧对应物 SQL/PGQ（ISO/IEC 9075-16，经维基词条转引 ISO 页）。**生态处于早期**：标准 2024 年才落地，实现少、工具链未成熟（§5-3）。
- **Cypher**：Neo4j 现行版本 **Cypher 25**（2025.06 起新功能只进 Cypher 25、Cypher 5 冻结；2026.02 起新库默认 Cypher 25）（F8）；openCypher 是开放规范，Memgraph / AGE / Kuzu 各自实现变体——「学 Cypher 不锁定 Neo4j」基本成立，但变体差异需实测。
- **混合架构**：
  - **Postgres+Apache AGE**：2022-05-17 从 Apache 孵化器毕业；v1.8.0、支持 PostgreSQL 18；openCypher 查询（F16）；图与关系/JSONB **同库同事务**，可同时承载 M08 图 + 审计/版本/候选池表 + 开放字段 JSONB——**与本数据形态的耦合度最高**；
  - **DuckDB+DuckPGQ**：DuckDB 社区扩展，支持 SQL/PGQ；官方自述「research project and a work in progress」（F17）——可实验、不可依赖；
  - **DuckDB 原生 `WITH RECURSIVE` + JSON**：适合分析型查询与导入试验。
- **适配性结论：适配**。本数据形态 = 属性图 + 开放字段 + 审计/版本 + 候选池，**单一 Postgres 系统即可全覆盖**；DuckDB 适合查询与分析侧；独立图引擎仅在 Q2 触发条件满足后作为补强层考虑。

## 2. 关键发现（每条：论断 + 来源 + 原文摘录 + 证据等级）

### F1 Kuzu 已归档——本次调研最重要的意外发现【证据：原文到手】
- **论断**：曾被视作最贴合「嵌入式 + Cypher + 本地单机」的图引擎 Kuzu，GitHub 仓库已被所有者归档为 read-only，不再适合新项目依赖。
- **来源**：https://github.com/kuzudb/kuzu （Kuzu README，2026-08-12 抓取）；https://github.com/kuzudb/kuzu/releases （GitHub 归档横幅）
- **原文摘录**（README）：「We are archiving the KuzuDB project here… prior Kuzu releases will continue to be usable… we have a new release 0.11.3 that bundles many (but not all) of the extensions, or you can follow the instructions here to run a local extension server.」
- **原文摘录**（releases 页横幅）：「This repository was archived by the owner on Oct 10, 2025. It is now read-only.」+「Public archive」徽标。
- **影响**：Kuzu 从候选降级为「不可推荐」（§5-1）。

### F2 LDBC SNB 定义「交互式图负载」【证据：原文到手】
- **论断**：业界判定「实时交互图查询」的权威框架是 LDBC SNB Interactive 工作负载：复杂读（访问给定节点邻域）+ 短读 + 连续插入更新，以吞吐量（ops/s）为指标。
- **来源**：https://ldbcouncil.org/benchmarks/snb/interactive/ （Graph Data Council / LDBC，2026-08-12 抓取）
- **原文摘录**：「LDBC SNB Interactive workload captures a transactional graph processing scenario with complex read queries that access the neighbourhood of a given node in the graph and update operations that continuously insert new data in the graph. The workload produces the throughput metric to characterize the performance at the given scale.」

### F3 SNB 的「三跳」是交互复杂读的典型深度【证据：原文到手】
- **论断**：「三跳以上遍历」不是拍脑袋——SNB 交互复杂读 IC1 就是「与起点 ≤3 跳相连」的查询；SNB 也是「交互 vs 分析」负载划分的业界标准。
- **来源**：https://arxiv.org/abs/2001.02299 （Renzo Angles 等 24 位作者，《The LDBC Social Network Benchmark》，2020-01-07 v1 / 2024-09-07 v11）；全文 https://ar5iv.labs.arxiv.org/html/2001.02299
- **原文摘录**（IC1）：「find Persons with a given first name that the start Person is connected to (excluding start Person) by **at most 3 steps** via the knows relationships.」
- **补充**：SNB Interactive v2 操作混合 ≈ 8% 复杂读 / 72% 短读 / 20% 插入 / 0.2% 删除；SF = 生成 CSV 的 GiB 数（SF1=1 GiB、SF100=100 GiB、SF10000=10000 GiB）。

### F4 SNB 已审计结果给出量级参照【证据：原文到手】
- **论断**：交互式图负载在 SF30–1000（30–1000 GiB 数据）下，产业级系统审计吞吐约 3.3 万–14 万 ops/s——比本项目规模大 4–6 个数量级；说明「多跳 + 交互」正是图引擎的主业负载。
- **来源**：https://ldbcouncil.org/benchmarks/snb/interactive/ （LDBC「SNB Interactive audited results」表，2026-08-12 抓取）
- **示例行**：Huawei Cloud Graph Engine Service（2025-12-01）：SF100=129,090 ops/s、SF300=139,411、SF1000=125,873；GraphScope Flex（Alibaba Cloud，2025-04-21）：SF30=37,650、SF100=79,244、SF300=80,511。
- **注意**：这些是大型分布式系统审计结果，不是单机嵌入式参考；仅用作负载性质佐证，不可外推到本项目硬件。

### F5 GQL 标准【证据：原文到手（维基词条；标准号以 ISO 官网为准）】
- **论断**：GQL 是 ISO/IEC 39075:2024 属性图查询语言标准，2024-04-12 发布，受 SQL / Cypher / GSQL 影响；首个研究实现来自 TU Eindhoven。
- **来源**：https://en.wikipedia.org/wiki/Graph_Query_Language （Wikipedia，2026-08-12 抓取；词条内引 ISO 官网 https://www.iso.org/standard/76120.html）
- **原文摘录**：「GQL (Graph Query Language) is a standardized query language for property graphs first described in ISO/IEC 39075, released in April 2024 by ISO/IEC.」「Influenced by SQL, Cypher, GSQL」；参考区「First GQL research implementation from Olof Morra at TU Eindhoven!」
- **SQL 侧对应物**：SQL/PGQ = ISO/IEC 9075-16（维基词条引 ISO 页——**二手转引**标准号）。

### F10 Memgraph 存储模式与内存量化【证据：原文到手】
- **论断**：Memgraph 三种存储模式：`IN_MEMORY_TRANSACTIONAL`（默认，ACID+WAL+快照）、`IN_MEMORY_ANALYTICAL`（导入/分析快，无 ACID）、`ON_DISK_TRANSACTIONAL`（ACID+落盘，性能换成本）；官方文档量化各类型内存占用。
- **来源**：https://memgraph.com/docs/fundamentals/storage-memory-usage （Memgraph 文档，2026-08-12 抓取）
- **原文摘录**：「Memgraph supports three different storage modes: IN_MEMORY_TRANSACTIONAL - the default database storage mode that favors strongly-consistent ACID transactions using WAL files and snapshots… IN_MEMORY_ANALYTICAL - speeds up import and data analysis but offers no ACID guarantees besides manually created snapshots. ON_DISK_TRANSACTIONAL - supports ACID properties… with the additional ability to store data on disk (HDD or SSD), thus trading performance for lower costs.」
- **许可**：仓库徽标显示 APL/BSL/MEL 三种许可文件（README 徽标，具体条款以官方许可页为准）。

### F11 Neptune 托管形态与上限【证据：原文到手】

- **来源**：https://docs.aws.amazon.com/neptune/latest/userguide/intro.html 与 https://docs.aws.amazon.com/neptune/latest/userguide/limits.html （AWS 文档，2026-08-12 抓取）

### F14 DuckDB JSON 实测【证据：原文到手】

## 3. 对决策点 D1 的输入

**D1 = M08 基础图存储形态：继续 JSONL+脚本，还是换关系表/图数据库/混合？触发条件是否合理、何时兑现？**

**输入 1（触发条件判定——给合成阶段的四条可判定清单）：**
1. 出现真实产品需求，其查询**等价于「从给定节点出发、可变长度路径深度 ≥3 的模式匹配 / 邻域聚合」**（对照 SNB IC1 的 ≤3 跳，F3）；
2. 该查询位于**用户直接等待路径**（页面/交互），且单查询 P95 超过本产品交互阈值（**建议初始值 <1s**，待产品侧确认）；
3. 该需求是**常规反复执行的功能**，不是一次性后台脚本；
4. 现有 JSONL+脚本在 1–2 跳 / 按 id / 全表校验之外的查询上**已实测不可忍**（数据来自 §6 实验 A/B）。

四条全部成立 → 触发。**目前 1、2、3、4 均不成立**（06 §7 已知需求 = 1–2 跳、按 id、全表校验），**当前判定：不触发，维持 append-only JSONL + 独立校验脚本**。触发条件的措辞本身与业界框架一致，**无需修改红线，只需操作化**。

**输入 2（若触发后的路线，按运维成本递增排序）：**
- 档 1：**Postgres + `WITH RECURSIVE` / Apache AGE**——关系表中间态，单系统覆盖图 + 审计/版本 + JSONB 开放字段（F15/F16）；
- 档 2：**DuckDB + DuckPGQ / `WITH RECURSIVE`**——分析型、只读场景（F14/F17）；
- 档 3：独立图服务器（Neo4j / Memgraph / TigerGraph / Neptune）——仅在遍历深度大且延迟极敏感、前两档实测不达标时考虑（F9–F12）。
- **不建议**：Kuzu（已归档，F1）、ArangoDB（一手资料受限 + 文档式图模型差异，F13）、TigerGraph / Neptune（运维/云绑定，F11/F12）作为本项目首选。

**输入 3（混合负载边界）**：即使触发，图引擎只接管「知识关系图遍历」；锚点校验（T4）、时间版本（T2）、候选池（T5）仍按各自轨道方案，**不并入图库**（红线 11 的图不合并原则同样适用于存储层）。

## 4. 与产品约束的冲突/张力

- **红线 9（append-only JSONL、图数据库暂不选、触发条件已写明）：无冲突**。本调研不改红线，只把「三跳以上遍历 / 实时交互查询」从主观描述翻译成四条可判定清单（§3 输入 1），并给出业界参照（LDBC SNB）。
- **红线 11（四种图不能合并，M08 只谈知识关系图）：无冲突**。本轨道全程只评估知识关系图存储；未把产品模块图/执行工作流图/学习者状态变化纳入任何引擎评估。
- **红线 16（运行时、向量检索、跨学科命名空间三项刻意不决定）：无越界**。本轨道未对运行时/向量检索下结论；「实时交互」的延迟阈值只给图引擎侧业界参照，不替运行时选型。
- **张力 1（提示非冲突）**：Neo4j Community 为 GPL v3（F9），若未来选 Neo4j 需评估对本地工具的分发/嵌入影响；本调研因此把 Neo4j 排在轻量混合路线之后。
- **张力 2（标注）**：TigerGraph「<100ms」为厂商营销（F12），本调研只引用为业界卖点佐证，不作为性能证据；任何后续方案引用它必须标注。

## 5. 未决与风险

1. **Kuzu 归档（本轨道最重要风险，等级：高）**：若此前方案或合成阶段曾倾向 Kuzu，需整体重估；0.11.3 为最后常规版本，扩展生态转入本地扩展服务器模式（F1）。后续任何「嵌入式图库」候选都需重做健康度核查（归档/停止维护/许可变更）。
2. **JSONL+脚本的「不可忍边界」无直接基准**：业界没有「JSONL+脚本做图查询」的基准；§1-Q3 的边界数字是**推断**（十万节点量级前后），必须靠自家实测（§6 实验 A/B）才能作为 D1 判据。
3. **GQL 生态尚未成熟**：ISO/IEC 39075:2024 发布仅两年，实现稀少（研究实现 + Spanner + Neo4j 部分一致性，F5–F7）；若以 GQL 为标准选型，存在「标准很新、工具链未跟上」的迁移风险；SQL/PGQ（ISO/IEC 9075-16）同样年轻。
4. **ArangoDB 一手文档获取受限**：官方 docs 被 Cloudflare 拦截，本次仅取到维基（二手）与首页（F13）；若 ArangoDB 进入候选，需重新抓一手文档再评估。
5. **「三跳 / 实时交互」的量化阈值待产品侧确认**：本调研给出建议初始值（P95 <1s、用户直接等待路径），但最终阈值是产品决策，不是调研结论。
6. **规模外推不可靠**：522 节点来自「两本教材各三四章」（06 §6.1 原文），全学科规模是推断；任何「何时触发」的预测都要以 §6 实测为准。

## 6. 建议的下一步实测（可执行的最小实验）

**实验 A——当前规模 3 跳查询计时**（判断「3 跳是否已不可忍」的最直接证据）
- 输入：现有 M08 图 JSONL（522 节点/1433 边/921 锚点）+ 一组代表查询（从 SNB IC1 模式翻译：给定节点、≤3 跳、带筛选/属性返回）。
- 做法：Python 加载 JSONL 建邻接表（并对照每查询全扫描实现），对 10–50 个随机起点计时，记录 P50/P95/最大、内存、加载时间。
- 判据：若 P95 < 100ms（且 <1s），记录「当前规模 JSONL+脚本可忍」；结果回填 §3 判定清单第 4 条。

**实验 B——合成图找拐点**（回答「多少节点/边后不可忍」）
- 输入：合成知识图 1 万 / 10 万 / 100 万节点（保持 4 类节点、9+1 关系词、每节点 1–3 条 30–200 字符锚点的形态），JSONL。
- 做法：重复实验 A 的三类查询（按 id 取 / 全表校验 / 3 跳遍历），记录延迟随规模曲线。
- 判据：找出各查询类型延迟越过 1s（或产品阈值）的规模点；该点即为 D1「何时兑现」的实测依据。

**实验 C——关系表中间态对照**（回答「混合路线是否可行」）
- 输入：与实验 B 相同的合成数据导入 PostgreSQL。
- 做法：建 nodes / edges / anchors 三表（可选启用 Apache AGE 扩展），用 `WITH RECURSIVE`（或 AGE openCypher）重跑实验 B 的 3 跳查询。
- 判据：对比 JSONL+脚本与 Postgres 在 10 万–100 万节点下的延迟；若 Postgres 在更大规模保持 <1s，则「先关系表、后图扩展」路线成立。

**实验 D——读频率清单**（产品侧输入，非本轨道结论）
- 输入：产品负责人列出 M08/M09 未来真实会做的查询清单（哪些页面/功能、频率、是否用户直接等待）。
- 判据：对照 §3 判定清单 1–4 逐条打钩；此清单决定触发条件的「真实产品需求」半句。
