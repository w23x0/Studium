## 0. 一句话结论

先例总体支持「当前 append-only JSONL + 脚本 + 派生索引」的形态：六个领域（形式化数学库、MMT/OMDoc、教学系统、间隔重复、数学知识图谱、GraphRAG）**没有一个把图数据库当作源存储**——图（依赖图/理论图/知识图）在每一处都是派生的查询/分析层，源存储是纯文本+Git、XML、SQLite 关系表或 parquet 表格；mathlib 30.8 万声明/840 万边、MML 5 万定理、set.mm 51MB 单文件均以文本+Git 为源，ALEKS 万亿知识态以闭包系统的紧凑表示而非枚举存储，GraphRAG 默认 parquet 落盘——「三跳+实时交互才上图」的触发条件与这些先例相容，M08/M09 预期规模下无需提前上图；M09 的「当前视图可从不可变历史派生 + 版本不覆盖旧结论」直接对应 Anki `cards/revlog` 分离与 FSRS 从 revlog 重建记忆状态的成熟先例。

## 1. 必须回答的问题逐条回答（引用轨道定义的问题编号）

### T6-1 形式化数学库（mathlib、MML、Metamath）的依赖图/库存储形态与规模？

**形态：源=纯文本源码 + Git；依赖图=派生物，不是源存储。**

- **mathlib**：仓库就是数千个 `.lean` 源文件 + Git 版本控制（GitHub API 实测仓库 size 473,333 KB ≈ 462 MiB，2026-08-12）；文档由工具从 `.lean` 源文件自动生成（mathlib4 README 原文）。依赖结构由 Lean 编译器/工具链合成：`2604.24797` 把 mathlib 抽成 **308,129 个声明 / 840 万条边 / 7,563 个模块**的多层图，并区分显式边与编译器合成边；还测得开发者中位只用导入范围的 **1.6%**、命名空间间耦合 50.9%——即使在大库里，实际查询也高度局部化。
- **MML**：`1107.4721` 原文：>1100 篇文章、约 **250 万行文本、>5 万定理、1 万定义、7 千符号**；细粒度依赖由 mizar-items 系统**计算**出来并建站供查询（mizar.org 实测：MML Version 5.94.1493，2025-05-30）。
- **set.mm**：**单文件**纯文本库（GitHub API 实测 51,125,969 字节 ≈ 48.8 MiB；jsdelivr 拒绝托管该包并报「Package size exceeded the configured limit of 50 MB」，交叉印证 >50MB）；us.metamath.org 主页原文「Over 40,000 proofs」。查询/校验靠 Metamath 自带工具（metamath.exe/mmj2）直接解析该单文件。
- **premise selection（1108.3446）**：用最小依赖分析构建「证明依赖知识库」供 ATP 复核与训练——再次说明依赖图是**从库中派生的索引/知识库**，被当作训练语料消费。

### T6-2 MMT/OMDoc 模块化理论图的存储与查询？

- **MMT = 模块化理论图框架**，是下一版 OMDoc 的底座（`1005.5232` 摘要原文：「the MMT framework for modular theory-graphs…which forms the base of the next OMDoc version」）。
- **存储 = XML + 版本化仓库**：OMDoc 是「标准 XML 格式」；六库（Coq/HOL Light/IMPS/Isabelle/Mizar/PVS）统一翻译为 OMDoc/MMT（`2005.03089`，ar5iv 全文到手：「We use OMDoc omdoc as the standard XML format for holding the library exports」）。版本化由 **TNTBase** 承担（`1005.5232` 摘要原文：「TNTBase, a versioned storage system for XML-based document formats. TNTBase becomes an MMT database by instantiating it with special MKM operations for MMT」）。
- **查询 = 库内查询引擎，不是外部图数据库**：QMT 查询语言内建于 MMT API（`1204.4685` 摘要原文：「QMT can span different mathematical libraries. We have implemented QMT as a part of the MMT API. This combination provides a scalable indexing and query engine」）。
- 理论图被主张为「组织大规模数学知识的合适结构」（`1806.00810` Farmer；`1306.3198` biform theory graphs），但其落盘形态始终是 XML + 版本化仓库 + 库内索引，未出现「把理论图存进图数据库」的做法。

### T6-3 教学系统（ALEKS 知识空间 KST、课程图、知识追踪 KT）如何存储学习者状态与知识结构？

- **KST 理论**（`1511.06757` 摘要原文）：知识态 = 闭包系统；学习空间是**巨大的组合结构**，「may be difficult to manage」，需要「efficient and comprehensive summaries of such large structures」；学生评估用马尔可夫过程；ALEKS 已用于数百万学生。
- **ALEKS 产品**（aleks.com 官网「About ALEKS」页，2026-08-12 原文到手）：50M+ 学生；「places the student within a **space of trillions of feasible knowledge states**」；「billions of data points from student interactions accumulated over 26 years」；机器学习 + KST。要点：**万亿知识态不是逐态枚举存储**，而是 KST 闭包系统的紧凑组合表示；学生状态 = 评估算法在空间中的定位（每个 topic 是否掌握、准备学什么），训练数据 = 海量交互日志。
- **课程图**（`2511.15536` CAPIRE 摘要原文）：课程在机构数据库里是「linear lists of courses」，实践上却是前驱关系 DAG；论文把课程**形式化建模为有向无环图**、算中心性特征（1,343 名学生）——课程图是建模/分析层，不是源存储。`1811.12640`（PREREQ）、`1805.04617`（TutorialBank）表明概念前驱关系是**推断/人工标注**出来的数据。
- **KT/BKT**：
  - BKT（`2105.00385` pyBKT 摘要 + README 原文）：**按 skill 拟合模型参数**（先验掌握/学习率/猜/滑），状态 = 模型参数 + 作答序列；README 原文：「estimating student cognitive mastery from problem solving sequences」；支持 per-item guess/slip、per-item learn rate 等变体。
  - DKT（`1506.05908` 摘要原文）：知识状态 = RNN 隐状态，直接从作答序列学习，**不显式存储知识结构**。
  - Mamba4KT（`2405.16542` 摘要原文）：明确把「数据增长带来的时间/空间消耗」列为 KT 的可扩展性挑战，解决方向是模型效率而非换存储。

### T6-4 间隔重复系统（Anki、FSRS、SuperMemo）如何存储卡片状态、历史复习记录与调度参数？

- **Anki**（官方 `rslib/src/storage/schema11.sql` 原文到手，2026-08-12 核验 URL 有效）：SQLite，5 张表 `col / notes / cards / revlog / graves` + 索引（`ix_cards_sched`、`ix_revlog_cid` 等）。
  - `cards` = 每张卡**当前调度状态**（ivl/factor/reps/lapses/queue/due/left/odue…）；
  - `revlog` = **不可变完整复习历史**（id=毫秒时间戳/cid/ease/ivl/lastIvl/factor/time/type）——Anki 文档原文：「it has a row for every review you've ever done」；
  - `graves` = 删除墓碑（usn/oid/type）；
  - `col` = 集合级配置，conf/decks/dconf 均为 **text 字段存 JSON**。
  - 结构语义：**当前状态（cards）与完整历史（revlog）分离存储，历史可无限回溯**。
- **FSRS**（KDD 2022 论文 + awesome-fsrs wiki 原文到手）：
  - 记忆状态 = 每卡 (Stability, Difficulty, Retrievability)（ABC 原文：「Each card has its own DSR values」）；调度参数随版本演进：FSRS-4.5=17 参数、FSRS-5=19、FSRS-6=21（The-Algorithm 原文参数表与公式）。
  - 参数训练 = 从 revlog 时间序列重建状态：按卡分组排序成 rating/interval 序列 → **MLE + BPTT** 端到端训练（optimization 原文）；默认参数由**几亿条复习记录、~10k 用户**训练得到（ABC 原文）；SSP-MMC 仓库公开数据集 = 220M 条学习日志、1.6GB TSV（GitHub README 原文）。
  - 存储语义：**当前状态是可从不可变历史派生的**（FSRS 优化器直接消费 revlog）；卡片级只需 S、D 两个数字随复习更新，调度参数是全局配置。
- **SuperMemo**（supermemo.guru 原文到手）：collection = 组织成**知识树**的数据库；元素分 topic/item/concept/task；repetition history 最小记录对 = 「(1) 复习日期，(2) 回忆评分」。内部 `.col` 二进制格式未取到官方原文（help.supermemo.org 被 Cloudflare 拦截）→ 列入未决。

### T6-5 数学知识图谱（Wikidata 公式实体、OntoMath、MaRDI、QUDT）与 GraphRAG 系统的存储选型与经验？

- **Wikidata**（Special:Statistics 页面 + SPARQL 实测，2026-08-12）：内容页 **122,864,308**；属性总数 **13,808**（SPARQL `COUNT(?p) WHERE { ?p wikibase:propertyType ?t }`）；自建立以来编辑 2,529,713,977 次（注意：这是**编辑量**，不是语句数）。公式实体：属性 **P2534「defining formula」**，datatype=math，描述「mathematical formula representing a theorem or law」，实测被 **113,084 条语句**使用——**公式是属性的 math 类型值，不是独立节点**。底层是 MediaWiki/Wikibase（关系+文档混合），非图数据库。
- **OntoMathPRO**（`2303.13542` 摘要原文）：三层本体（foundational / domain / linguistic）；语义出版平台把 LaTeX 论文集合转成 Linked Open Data；生态含公式语义检索与论文推荐。
- **MaRDI**（`2309.11484`，ar5iv 全文到手）：基于 **Wikibase** 的数学知识图谱；Bravo 首发（portal.mardi4nfdi.de）；实体来自 Wikidata 导入 + 8 个外部源（DLMF、swMATH、zbMATH Open、arXiv 等）；**以 >1 亿三元组播种**；公式用 texvc→MathML/SVG 渲染流水线。
- **QUDT**（qudt.org 原文到手）：源自 NASA NExIOM 项目；主本体用 **SHACL** + datatype，外加 unit / quantitykind / dimensionvector / constant / sou / soqk 六个 vocabulary 各给 base URI；面向 RDF/JSON 互操作 + SPARQL endpoint——单位/量纲知识的结构化先例。
- **Microsoft GraphRAG**（`2404.16130` 摘要 + 官方文档原文到手）：
  - 用 LLM 建图索引两阶段：从文档派生实体知识图 → 预生成社区摘要；在 1M token 规模上对「全局感知识别」类问题优于 vanilla RAG。
  - 知识模型 = 7 类表：Document / TextUnit / Entity / Relationship / Covariate / Community / CommunityReport；默认 chunk **1200 tokens**；**实体/关系/声明都带 `text_unit_ids` 溯源列**（Entity 表还有 frequency/degree，Relationship 表即边表 source/target/weight/combined_degree/text_unit_ids）。
  - 默认输出**全部 parquet 表落盘**；向量默认 **lancedb**（可选 azure_ai_search / cosmosdb）；存储插件 file / blob / CosmosDB；snapshots 可导出 embeddings / graphml / raw_graph。
  - 负面结果（`2506.05690`、`2502.11371` 摘要原文）：GraphRAG 在不少真实任务上**不如** vanilla RAG；图只有在特定层次/多跳推理场景才加分——「图何时有用」是实证问题。

### T6-6 哪些先例的结构可直接映射到 M08/M09？哪些证明「该形态在更大规模才成立」？

**可直接映射到 M08：**
1. 源存储 = 文本/JSONL + 派生索引 ← mathlib/MML/set.mm 的「源文本 + 依赖派生索引」；mizar-items、premise selection 依赖知识库。
2. 锚点/证据溯源 ← GraphRAG 的 TextUnit + `text_unit_ids`（实体/关系表带来源列）；OMDoc 的内容/叙事分离。
3. 命名空间 id 不合并实体 ← QUDT 的 base URI 体系；MaRDI/Wikidata 的 QID 保留（实体先导入、再 enrichment，不吞并）。
4. 不物理删除 ← Anki `graves` 墓碑表。

**可直接映射到 M09：**
5. 当前视图从不可变历史派生 + 版本不覆盖旧结论 ← Anki `cards/revlog` 分离；FSRS 从 revlog 用 MLE+BPTT 重建状态（M09 只需「派生当前视图」，不需要训练）。
6. 开放字段 + 稳定可查字段 ← GraphRAG entity 表（开放文本 description + 结构化 frequency/degree）；Anki `col` 表 text JSON 配置。
7. 证据边 ← GraphRAG 实体/关系/声明的 `text_unit_ids` 溯源；Anki revlog 的 (id 时间戳, cid) 外键。
8. 已结束闭环才写长期记录 ← ALEKS/KST「评估输出知识态，而非逐轮日志」，与 M09「只收已结束闭环」同构（同步/中间诊断另存）。

**可直接映射到 M08–M09 连接层（D5）：**
9. 通用知识结构与个人状态分离 ← ALEKS/KST 的「知识空间（领域结构，共享）vs 知识态（学生位置，个体）」。
10. 去个人化候选管道 ← premise selection「个体证明 → 库级依赖知识库」；mathlib 的 PR 审查/合并制度（2508.21593）是「人工审计晋升」的大规模先例。
11. 未映射对象暂存再锚定 ← MaRDI「实体先带 QID 导入、再本地 enrichment」；Wikidata 实体先存在、属性后补。

**证明「更大规模才成立/才需要更强存储」的证据（即：小规模 JSONL 够用）：**
- mathlib：30.8 万声明 / 840 万边 / 7,563 模块仍以文本+Git 为源，依赖图为派生物；中位开发者只用导入范围 1.6%（`2604.24797`）——全域遍历需求稀疏。
- set.mm：51MB 单文件 + 工具链支撑 4 万+证明（us.metamath.org + 实测文件大小）。
- MML：250 万行 / 5 万定理仍为文本文章 + 依赖提取建站（`1107.4721`）。
- ALEKS：万亿知识态用闭包系统紧凑表示，不枚举存储（`1511.06757` + aleks.com）。
- GraphRAG：默认 parquet 落盘、lancedb 向量、图是 LLM 派生物（官方文档）；且图不总是加分（`2506.05690`、`2502.11371`）。
- **共同模式**：当规模大到「需要图」时，先例的动作是「**从源派生图索引**」（mizar-items、premise selection、mathlib 网络分析、GraphRAG 索引）或「**紧凑组合表示**」（KST 闭包），而不是把源存储换成图数据库。

### 2.1 形式化数学库

**F1｜mathlib 源存储 = 纯文本 `.lean` + Git；依赖图是派生物**【原文到手】
- 论断：mathlib 不以数据库存依赖图；依赖图由编译器/工具链合成，文档从源码自动生成。
- 来源：https://github.com/leanprover-community/mathlib4（README，mathlib 社区，2026-08-12 抓取）
- 原文摘录：「documentation [generated automatically] from the source `.lean` files」；仓库 size 实测 473,333 KB（GitHub API，2026-08-12）。

**F2｜mathlib 依赖网络规模：30.8 万声明 / 840 万边 / 7,563 模块**【原文到手】
- 论断：这是「大规模真实依赖结构」的量化基线；同时揭示查询高度局部化（中位 1.6%）。
- 来源：https://arxiv.org/abs/2604.24797 ，《The Network Structure of Mathlib》，Xinze Li, Nanyun Peng, Simone Severini, Patrick Shafto，2026-04-26（arXiv:2604.24797）
- 原文摘录：「extracting its dependency structure into a multilayer graph of 308,129 declarations, 8.4 million edges, and 7,563 modules…developers utilize a median of 1.6% of the imported scope…50.9% coupling across namespaces」。

**F3｜MML：250 万行 / 5 万定理 / 1 万定义 / 7 千符号，依赖由 mizar-items 计算派生**【原文到手】
- 论断：MML 是文本文章库；细粒度依赖是 mizar-items 系统的**派生产物**（含查询网站）。
- 来源：https://arxiv.org/abs/1107.4721 ，《mizar-items: Exploring fine-grained dependencies in the Mizar Mathematical Library》，Jesse Alama，2011-07-24（arXiv:1107.4721）
- 原文摘录：「more than 1100 "articles" summing to nearly 2.5 million lines of text, expressing more than 50000 theorems and 10000 definitions using more than 7000 symbols…computing dependency relations among these items…a website for exploring these dependencies」。
- 补充（原文到手）：mizar.org 主页实测「MML Version: 5.94.1493 (May 30, 2025)」，2026-08-12。

**F4｜set.mm = 51MB 单文件纯文本库，40,000+ 证明**【原文到手】
- 论断：最大单文件形式化库之一以单文本文件为源，查询/校验靠工具链直接解析。
- 来源：https://us.metamath.org/ （Metamath 主页，2026-08-12 抓取）
- 原文摘录：「ZFC set theory axioms. Over 40,000 proofs.」；文件大小实测 51,125,969 字节（GitHub API）；jsdelivr 报「Package size exceeded the configured limit of 50 MB」交叉印证。

**F5｜premise selection 把「证明依赖知识库」当作派生语料**【原文到手】
- 论断：依赖分析产物被建成知识库供 ATP 与机器学习消费——依赖图是索引/训练语料，不是源。
- 来源：https://arxiv.org/abs/1108.3446 ，《Premise Selection for Mathematics by Corpus Analysis and Kernel Methods》，Jesse Alama, Tom Heskes, Daniel Kühlwein, Evgeni Tsivtsivadze, Josef Urban，2011-08-17（arXiv:1108.3446）
- 原文摘录：「a newly available minimal dependency analysis of existing high-level formal mathematical proofs is used to build a large knowledge base of proof dependencies」。

**F6｜mathlib 维护 = 源码治理（弃用/linter/技术债），不是数据库工程**【原文到手】
- 论断：大规模库的增长管理重点是源码治理与工具，无图数据库介入。
- 来源：https://arxiv.org/abs/2508.21593 ，《Growing Mathlib: maintenance of a large scale mathematical library》，Anne Baanen 等，2025-08-29（arXiv:2508.21593）
- 原文摘录：「dealing with breaking changes via a deprecation system, using code quality analysis tools (linters)…dealing with technical debt as well as writing custom tooling to help with the review and triage of new contributions」。

### 2.2 MMT/OMDoc

**F7｜MMT = 模块化理论图框架，TNTBase = 版本化 XML 存储**【原文到手】

## 3. 对决策点的输入（明确写到 Dx）

### D1（M08 基础图存储形态：继续 JSONL+脚本 vs 关系表/图数据库/混合；触发条件是否合理）

- **输入 1（先例支持维持现状）**：六领域先例无一以图数据库为源存储。mathlib（30.8 万声明/840 万边）、MML（5 万定理）、set.mm（4 万+证明、51MB 单文件）都是「文本源 + 派生依赖索引」；GraphRAG 的图也是从文档派生的索引且默认 parquet 落盘。→ **M08 继续 append-only JSONL + 脚本 + 派生索引，与领域先例一致。**
- **输入 2（触发条件的可判定化建议）**：先例显示「需要图查询」时的标准动作不是迁移源存储，而是**从源派生图索引/查询层**：mizar-items 建站、QMT 库内索引、GraphRAG 的 parquet 图表、set.mm 的工具链。→ 建议把触发条件（三跳+实时交互）的**兑现路径**预先写成「先派生索引，仍不满足再上图数据库」，给合成阶段 D1 一个低成本中间步骤。
- **输入 3（规模参考）**：中位开发者只用导入范围 1.6%（F2）说明大库真实查询高度局部化；M08 的 522 节点/1433 边/921 锚点远低于先例中「文本+脚本仍可行」的最低规模两个数量级以上。→ 无先例支持在 M08 当前与全学科预期规模下提前上图。

### D2（M09 个人记录存储形态：开放字段 + 证据边 + 未映射对象）

- **输入 1（当前视图=派生视图）**：Anki `cards/revlog` 分离（F16）+ FSRS 从 revlog 用 MLE/BPTT 重建状态（F18）是「当前状态从不可变历史派生、版本不覆盖」的直接先例。→ M09 可同样采用「不可变闭环记录（append-only）+ 派生当前视图」两态分离；重放成本是合成阶段待实测项（见 §6）。
- **输入 2（开放字段与稳定字段共存）**：GraphRAG entity 表 = 开放文本 description + 结构化列 frequency/degree + 溯源列 text_unit_ids（F25）；Anki `col` 表以 text JSON 存配置（F16）。→ M09 的「开放但可稳定查询审查」（红线 14）在表格/JSON 形态下被先例反复验证，无需文档数据库。
- **输入 3（证据边）**：GraphRAG 的 `text_unit_ids` 溯源即「结论→来源」的边/列；Anki revlog 以 (时间戳, cid) 外键关联历史与卡（F16）。→ M09 证据边 = 记录级外键/溯源列即可，不需要图数据库承载。
- **输入 4（未映射对象）**：MaRDI 先导入 Wikidata 实体（保留 QID）再 enrichment（F23）；Anki `graves` 墓碑表（F16）。→ 未映射个人对象以「带来源、仅个人有效」暂存、晋升后重锚定（产品已定方向）与先例相容；graveyard 语义有 Anki graves 直接对应。

### D5（M08–M09 连接层：锚定、未映射对象暂存、晋升后重新锚定、去个人化候选管道）

- **输入 1（两图分离的先例）**：ALEKS/KST 明确区分「知识空间（领域结构，共享、不属个人）vs 知识态（学生位置，个体）」（F11、F12）——与产品红线 11「知识关系图/学习者状态变化不合并」+ M09 锚定 M08 的分离完全同构，是领域侧最强先例。
- **输入 2（去个人化候选管道）**：premise selection 把「个体证明过程」聚合成「库级依赖知识库」供训练与复核（F5）；mathlib 的 PR 审查/合并/弃用制度是「人工审计晋升」的大规模先例（F6）。→ M09→M08 的候选/审计/晋升管道形态与先例一致：候选=派生数据，晋升=人工/规则裁决，不自动写正式库。
- **输入 3（锚定=命名空间+身份判定）**：QUDT 以 base URI 命名空间组织且不合并实体（F24）；MaRDI 保留 Wikidata QID 再本地 enrichment（F23）。→ 「id 只作命名空间、判等看锚点」与先例中「标识符与身份分离」实践一致；别名/跨库对齐可参考 Wikidata 的 same-as/别名机制（本轨道未深挖，列入未决）。

## 4. 与产品约束的冲突/张力

1. **GraphRAG 的自动抽取与红线 7「高层结构=候选池+审计晋升，不自动生成」直接冲突**（标注张力）：GraphRAG 用 LLM 自动抽实体/关系并自动生成社区报告（F25）。若把该流程照搬进 M08 会违反红线 7/8（检测可并行、处置必须单点；模型不能决定正式写入）。**可取**的是其「表格式存储 + 溯源列 + 派生态文件」的存储形态，**不可取**的是自动生成正式结构。本轨道只陈述张力，不改变红线。
2. **图+向量的并存与红线 16「向量检索不参与候选发现（刻意不决定）」**：GraphRAG 默认把 embedding 索引与图并存（F25），说明两者正交可叠加；但「向量是否参与 M08 候选发现」的解锁条件是假阳性率实证（红线 16），属于 T8 轨道，本轨道不裁决（F26 提供负面结果线索：图/向量并不总是加分）。
3. **ALEKS 的自动诊断与学生「三跳/实时交互」不同域**：ALEKS 的自动性在评估/教学（F12），与 M08 的「正式写入权限」不是一回事；不构成对红线 8 的挑战。
4. **mathlib 的「编译器合成边」与 M08 的「边关系词表封闭 9+other」**：mathlib 明确区分显式边与编译器合成边（F2）——M08 的语义边更接近「显式边」；若未来需要自动派生依赖（如共享引文），可借鉴 mathlib「派生边单独统计、不与显式边混同」的做法，这与红线 5（机械信号只定向不结案）相容。
5. **无其他直接冲突**：其余先例（文本源、派生索引、cards/revlog 分离、graves 墓碑、URI 命名空间）与红线 2/3/4/9/10/12/13/14 方向一致，未见违反。

## 5. 未决与风险

1. **SuperMemo 内部 `.col` 二进制格式**未取到官方原文（help.supermemo.org 被 Cloudflare 拦截）；现有结论基于 supermemo.guru 词条（原文到手）与 FSRS 社区的转述（二手转引）。若 D2 需要 SuperMemo 级细节（元素级属性、调度矩阵存储），需换途径（下载 SM-18 试用版解包或 Wayback Machine）。
2. **BKT/ALEKS 的生产级学习者状态持久化细节未公开**：pyBKT 证实「按 skill 存参数 + 作答序列」（原文到手），但 ALEKS 内部存储是专有的，无一手来源；「万亿知识态」是产品口径（原文到手）而非工程文档。D3/D5 若需精确状态存储先例，属 T7/T2 范围。
3. **Neo4j+向量（官方 GraphRAG 类文档）一手来源未取到**：neo4j.com 连接被中断；本轨道以 Microsoft GraphRAG 默认（parquet+lancedb）与 GraphRAG-Bench 负面结果为准。T1 轨道有 Neo4j 引擎对比，可交叉引用。
4. **MaRDI 当前条目规模**：论文给的是 2023 年 Bravo 首发的「>1 亿三元组」（原文到手）；portal 实时统计未在论文中，未单独核验。
5. **mathlib4 仓库 size 为 GitHub API 当日实测**（473,333 KB），会随版本变化；仅作量级参考。
6. **FSRS 默认参数训练规模**（几亿条/~10k 用户）来自 awesome-fsrs wiki（社区文档，原文到手但非论文），属高质量二手；论文本体未公开训练数据规模。
7. **风险提示**：Wikidata 统计页易误读（编辑量≠语句数、活跃用户数≠属性数），本轨道已用 API/SPARQL 实测校正（F21）；合成阶段引用时请以此为准。

## 6. 建议的下一步实测（可执行的最小实验）

1. **M08 规模外推 + grep -F 成本**：用合成数据把 921 锚点/522 节点 ×10、×100、×1000，测 `grep -F` 全量校验与 JSONL 追加/重放的耗时与内存；以 set.mm 51MB 单文件 + Metamath 工具链为参照物（证明「文本源+脚本校验」在更大规模仍可行）。判据：×100 后单次全量校验是否仍在秒级。
2. **M09 派生视图原型**：按 Anki `cards/revlog` 两态分离，在 JSONL 上实现「不可变闭环记录 → 派生当前视图」的最小重放脚本（含版本链与证据边外键）；测 1k/10k/100k 条闭环记录的重放耗时。判据：10k 条重放是否 <1s；以此给 D2/D3 提供量化输入。
3. **共享引文派生索引原型**：仿 mizar-items（F3），写脚本从 M08 JSONL 派生「锚点/共引索引」（对应红线 D7 的共享引文检测 46% 永久不可见问题），验证脚本派生是否覆盖查询需求；若三跳查询出现，先试派生索引而非图数据库（D1 输入 2 的兑现路径）。
4. **三跳触发条件的量化基线**：在真实 M08 图（522 节点/1433 边）上实现三跳遍历脚本并计时，产出「现在到底痛不痛」的量化基线，作为 D1 触发条件的可判定输入。
5. **FSRS 状态重建对照**（可选）：用公开 220M 条数据集的一个子集（或本地 Anki revlog），按 F18 流程做「从 revlog 重建卡片状态」的最小复现，验证「当前视图可从历史派生」在个人规模下的工程成本。
