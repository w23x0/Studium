## D1 M08 基础图存储形态

- **候选方案**：
  1. 维持 append-only JSONL + 独立校验脚本（现状）；
  2. Postgres + `WITH RECURSIVE`/Apache AGE（关系中间态）；
  3. DuckDB + DuckPGQ / `WITH RECURSIVE`（分析只读）；
  4. 独立图数据库（Neo4j/Memgraph/TigerGraph/Neptune）；Kuzu 已归档出局。
- **支撑/反对证据（引用轨道）**：
  - 支撑现状：T1 实测「1–2 跳/按 id/全表校验」已知需求全部覆盖，触发条件四条可判定清单当前均不成立；T4 锚点校验 0.7 ms；T6 六领域（mathlib 30.8 万声明/840 万边、MML 5 万定理、set.mm 51MB 单文件、ALEKS 万亿知识态、Wikidata/MaRDI、GraphRAG parquet）全部「源存储非图库、图为派生层」。
  - 反对图库先行：T1 运维成本对比（Neo4j Community GPLv3、Memgraph 内存模式、TigerGraph 分布式最重）+ TigerGraph「<100ms」为厂商营销不可作证据；T6 负面结果（GraphRAG 频繁不如 vanilla RAG）。
  - 若触发后的路线：T1 按运维成本给出 档1 Postgres / 档2 DuckDB / 档3 独立图服务器。
- **与产品约束兼容性**：与红线 9 完全一致（不违反，只操作化触发条件）；红线 11 四图不合并获 T1 显式确认。
- **推荐**：**维持 append-only JSONL + 独立校验脚本**；同时把红线 9 的触发条件操作化为 T1 四条清单（深度≥3 的可变长度模式查询 + 用户等待路径 P95 建议 <1s + 常规反复功能 + JSONL 已实测不可忍，四条全成立才触发）【实测+推断】。
- **待实测项**：触发条件第 4 条的「JSONL 不可忍」实验（模拟 3 跳以上遍历在全学科规模的耗时曲线）；若触发，先做 Postgres 中间态原型而非直接上图库。

## D2 M09 个人记录存储形态

- **候选方案**：
  1. 关系骨架 + JSONB 开放字段 + JSON Schema 校验（pg_jsonschema + CHECK）；
  2. 纯文档数据库（MongoDB 类）；
  3. 属性图（Neo4j 类）；
  4. EAV（否决）。
- **支撑/反对证据**：
  - 支撑方案 1：T3 25 条论断——PG 官方文档（jsonb 分解式存储、GIN/jsonpath 查询）、pg_jsonschema 官方用法（CHECK + jsonb_matches_schema）、`WITH RECURSIVE` 图遍历；FHIR profile 原则（资源可安全处理、知识显式在实例）映射「维度可空可扩展」；xAPI 不可变/void 语义映射撤回。
  - 反对 EAV：T3 引用 Wikipedia 综述 + 工程实践（pivot 易错吃 CPU、JSONB 相对 EAV 千倍性能）【二手转引已标注】。
  - 反对纯文档/属性图：T3——schema validation 是补充控制非默认、开放优先可审查靠使用者；属性图开放字段深层校验需外部工具。
  - 交叉支撑：T6 的 GraphRAG entity 表（开放 description + 结构化列）、Anki col 表（text JSON）、FHIR/xAPI 先例。
- **与产品约束兼容性**：与红线 14（开放字段可稳定查询审查）直接兼容；与红线 9 的当前 JSONL 不冲突（T3 明确 JSONL 等价形态备选，JSONB 是「若迁移数据库」的首选）。
- **推荐**：当前 JSONL 阶段用「固定字段 + 开放 JSON 对象」的等价形态承载 M09 记录（与 T3 的 JSONB 模型同构）；**若 D1 未来迁移 Postgres，M09 采用关系骨架+JSONB+JSON Schema**。最小记录单位 = 断言/闭环级记录（T3：xAPI 式 statement 粒度 + FHIR 断言最小单位）【实测+推断】。
- **待实测项**：开放字段 JSON Schema 在 921 锚点/模拟闭环数据上的校验回归测试；「维度可空可扩展」的 schema 版本演进实验。

## D3 M09 时间版本机制

- **候选方案**：
  1. bitemporal 简化形态：valid time（掌握区间）+ transaction time（写入时间）+ `superseded_by`/`retracted_at` 指针，append-only；
  2. 完整 bitemporal 引擎（TPGM/BiTeGra 类）；
  3. 状态字段原地覆盖（否决——违反红线 13）。
- **支撑/反对证据**：
  - 支撑方案 1：T2——PostgreSQL 19 temporal table（`WITHOUT OVERLAPS`）、Fowler Event Sourcing（快照可选、CQRS 多数系统不必要）、Helland 不可变（CIDR 2015）、Kreps The Log（compaction 与红线冲突须排除）；TPGM/BiTeGra 原型（TT 代价 9.74%）证明双轴可负担但复杂度不必需。
  - 反对方案 2：T2——完整 bitemporal 引擎与图数据库结合对单学习者规模不成比例，Anselma 2025 演示稿仅为原型。
- **与产品约束兼容性**：与红线 13（不覆盖旧结论）直接一致；与红线 10（graveyard）一致；撤回语义 = M04-02 已写入记录的撤回（T2/T5 均确认与 M15 状态撤回权两回事）。
- **推荐**：**方案 1（bitemporal 简化形态）**：闭环级记录带 `valid_from/valid_to + asserted_at + superseded_by + retracted_at`；复检/遗忘/重新掌握/更正/撤回全部以追加新记录表达；当前视图由派生索引提供；最小保留粒度 = 闭环级记录【T2 实测+推断】。
- **待实测项**：版本链长度对「取最新版」性能的影响（10/100/1000 版）；回退/更正的追加语义在现有校验脚本上的回归。

## D4 M09 规模三方向

- **候选方案**：
  1. 方向1：M09 内部给历史版本独立位置；
  2. 方向2：历史版本移交 M01 保管（否决）；
  3. 方向3：M09 分历史区/边缘区两区。
- **支撑/反对证据**：
  - 支撑方向1：T7——FHIR 全历史随资源（versionId/history 交互含已删除资源）、xAPI 语句不可变+voiding 墓碑；单学习者年增量 MB 级推断【推断】；无跨模块迁移风险。
  - 反对方向2：T7——M01 审查单「不保存另一份个人知识模型」「只存事实、不存解释」；当前视图需跨模块组装【项目一手文档】。
  - 支撑方向3：T7——TimescaleDB 保留策略+连续聚合+对象存储分层（删除部分与红线 10 冲突须排除）；M09 审查单原文「方向3 与当前视图派生一致，但区划写进结构」。
- **与产品约束兼容性**：方向1 与红线 9/10/13 全兼容；方向2 违反 M01 边界（红线 12 精神）；方向3 需「沉底规则」判定标准（新增结构决策）。
- **推荐**：**方向1（默认）+ 方向3（规模实测触发后的演进路径）**；方向2 除非产品负责人先改 M01 边界，否则不进入技术方案。规模阈值未定义前不提前分区【推断】。
- **待实测项**：年增量模拟实验（100–500 闭环/年 × 2–3 版本）在 JSONL 上测当前视图派生耗时；沉底规则候选模拟。

## D5 M08–M09 连接层

- **候选方案**：未映射对象暂存于 M09 + 锚定边 + 晋升后重新锚定（既有方向）+ 存储层「锚定记录」形态（T2：superseded_by 复用；T6：GraphRAG `text_unit_ids` 溯源列、MaRDI 先导入 QID 再 enrichment）。
- **支撑/反对证据**：
  - 支撑：T6 直接映射清单（GraphRAG 实体/关系表带 `text_unit_ids`、MaRDI「实体先带 QID 导入再本地 enrichment」、premise selection「个体证明→库级依赖知识库」去个人化）；T5 候选区/正式区隔离为晋升管道提供存储分区。
  - T2：证据事件走证据边、模型身份必须实际执行模型（与 M09 审查单证据边要求一致）。
- **与产品约束兼容性**：与红线 12（M09 锚定 M08、只收已结束闭环）、红线 7/8（候选+审计晋升）一致。
- **推荐**：**存储层用「候选区→正式区 + 锚定记录带来源（text_unit_ids 式溯源）」**；未映射对象暂存 M09、晋升后重新锚定，不合并节点（红线 3）【T6 实测+推断】。
- **待实测项**：未映射对象暂存→晋升→重新锚定的端到端数据流实验（含 42 匹配/180 对象实测数据回放）。

## D6 候选池与审计晋升管道数据模型

- **候选方案**：四区 JSONL（候选区/正式区/墓碑区/审计事件区）+ 状态机单写者裁决（T5 公共交集：Gerrit NoteDb 不可变元数据、DataHub Change Proposals 权限分离、Wikipedia pending changes、OpenReview 审计）。
- **支撑/反对证据**：T5 36 条论断——Gerrit change 状态机（NEW→MERGED/ABANDONED，可 restore）、NoteDb 元数据 Git commit 链、submit 单动作；DataHub「Propose vs Manage」权限分离；FlaggedRevs 反面教训（复杂状态字段方案不推荐生产）。
- **与产品约束兼容性**：与红线 8（检测并行处置单点）、10（graveyard）、15（工具安全：真 argparse/--dry-run/--only/禁裸 'w'）直接兼容；红线 8 的「单点」在 JSONL 上需显式互斥协议（T5 张力 1 已标注）。
- **推荐**：**四区 JSONL + 裁决脚本单点 + 审计事件 schema**（`{event_id, ts, actor, action, target_id, axis, result, evidence, prev_state, next_state}`），状态只由追加审计事件推进，禁止原地改状态【T5】。
- **待实测项**：审计事件日志原型（24 个 L2 候选回放）；并发追加协议（O_APPEND 单行 vs 多行块、kill -9 恢复）实验。

## D7 锚点索引与检索

- **候选方案**：grep -F/Python `in`（现状，首选）；Aho-Corasick（全表定位审计工具，非判等）；pg_trgm/suffix array/检索引擎（当前规模过度工程）。
- **支撑/反对证据**：T4 实测——921 条锚点全量校验 0.7 ms；AC 命中计数 624–708 ≠ 921（213 条重复+91 条真子串），语义不能替代逐条判等；Meilisearch 只做前缀匹配语义不符（官方文档硬限制）；Hyperscan 1.1–3.2 Gbps 对 423KB 语料属过度工程；共享引文规模化 = 精确 `(file,quote)` 哈希分组（708 唯一对、158 重复组）+ SimHash/MinHash LSH（Manku WWW 2007）。
- **与产品约束兼容性**：与红线 4（grep -F 唯一硬校验）一致；共享引文清单只定向不结案（红线 5）。
- **推荐**：**维持 grep -F/Python `in` 为判等手段；新增「共享引文全表分组审计」流水线（精确层先跑、近似层后加）；复合锚点三项校验用纯 Python（行号解析+整行比对+行长度判定+相邻性判定）实现**，无数据库/检索引擎选型需求【T4 实测】。
- **待实测项**：148 组未审共享引文清单补全；SimHash 近似重复层在 921 锚点上的假阳性调参；复合锚点三项校验脚本开发与回归。

## D8 复合锚点校验

- **候选方案**：纯 Python 脚本实现三项逻辑（quote/formula 双字段分别校验、相邻性判定、同块其余行 <30 字符）；无第三方库选型（可选用 `in`/正则/行号解析）。
- **支撑/反对证据**：T4——项目 `verify_anchors.py` 现状只实现 `quote in text`，与 06 §2.1 纸面设计一致；三项校验全部可用纯文本操作实现（06 §2.1 原文逐条核验）；无数据库/检索引擎需求。
- **与产品约束兼容性**：与红线 4 一致（复合锚点为纸面设计待实现，本方案即实现路径）。
- **推荐**：**纯 Python 校验脚本**，纳入现有校验工具链（真 argparse/--dry-run/--only），在 921 条锚点上跑全量回归【T4 实测】。
- **待实测项**：三项校验的准确率/误报率在 921 锚点上的全量测试；与 `verify_anchors.py` 合并的接口设计。

## D9 向量检索参与候选发现

- **候选方案**：维持「只定向不结案」+ 四臂对照实验（BM25 vs 稠密 vs RRF 混合 vs 混合+rerank）；GraphRAG 系全量图索引不推荐。
- **支撑/反对证据**：T8——ann-benchmarks（近似检索=召回↔吞吐权衡，已停止维护转 VIBE）、BEIR（BM25 最稳、稠密域外跑输）、SPLADE v2（稀疏+精确词匹配 BEIR SOTA）、GraphRAG 2404.16130（仅全局感知识别加分）、2506.05690（GraphRAG 频繁不如 vanilla RAG）、2502.11371（各有优势）、LazyGraphRAG（索引成本 0.1%、查询成本低 700 倍，官方博客非同行评审）、cross-encoder 1901.04085（MRR@10 +27%）、RRF SIGIR 2009。
- **与产品约束兼容性**：红线 5（机械信号只定向不结案）被证据强化而非推翻；红线 16（刻意不决定）本轨道只提供证据与实验设计。
- **推荐**：**继续维持「只定向不结案」；解锁条件操作化为「候选通道在真实查询集上 precision@10 ≥ 50% 且相对 grep -F 有净召回收益」（建议初值，最终产品定）；即使解锁也只作候选生成器，走候选池+审计晋升，不改变 grep -F 唯一硬校验**【T8 实测+推断】。
- **待实测项**：四臂对照实验（M08 实测数据 + 真实未锚定引文/公式查询）；领域 embedding 快速探测（bge-m3 类对 921 锚点的假阳性率）；解锁条件判定会。
