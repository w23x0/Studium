## 0. 一句话结论

「候选区 / 正式区双区隔离 + append-only 审计事件日志 + 状态机单写者裁决 + 墓碑（graveyard）」是代码审查（Gerrit、Phabricator、GitHub）、数据治理（DataHub Change Proposals、Medallion）、内容审核（Wikipedia pending changes、Stack Exchange suggested edits）、论文评审（OpenReview）四类先例的**公共交集**：检测/建议可以并行进入候选区，但正式写入只由单一裁决者以追加方式完成，判死不物理删除而是进墓碑，且每一步审计（谁判的、依据什么、结果）都以不可变记录保留——这套模式与当前 append-only JSONL + 独立校验脚本的路线兼容，D6 无需引入图数据库即可落地。

## 1. 必须回答的问题逐条回答

### T5-问题1：候选队列 + 审计轨迹 + 审批晋升 + 墓碑（graveyard）的工程先例（代码审查系统、数据治理、内容审核流水线）？

**先例充分且一致，四类系统都具备同一四段结构：候选入队 → 并行审计/评审 → 单点审批晋升 → 判死入墓碑且可复活。**

- **代码审查（最贴近的类比）**
  - Gerrit 把每次推送转成一条 change 记录（`refs/for/<branch>` 并不真的创建分支，而是转换为 change record），change 有生命周期状态机：NEW → MERGED（晋升）/ ABANDONED（判死）；abandoned 的 change 可以 restore（判死不物理删除）[来源 2、3、4]。
  - 评审轨迹本身不可变：Gerrit NoteDb 把 change 的元数据（投票、评论）存为 **Git notes 分支上的一串 commit**，「modifications to changes are stored as a sequence of Git commits, automatically preserving history of the metadata」[来源 1]。
  - 提交（submit，即正式写入）是单一动作：默认 submit-requirement 要求「至少一个 MAX 票、且无 MIN 票」才允许提交 [来源 5]。多人投票并行，但只有 submit 环节把 change 合入正式分支。
  - Phabricator Differential：author 提交 revision → reviewers 异步评审（approve 或 request changes）→「Once everything is satisfied, some reviewer accepts the change and the author pushes it to the upstream」——评审与合入分离 [来源 6]。
  - GitHub protected branches：required reviews 使合并必须经过指定数量审批；CODEOWNERS 把特定文件的审批权绑定给特定 owner [来源 7、8]。
  - Kubernetes OWNERS：reviewer / approver **两阶段角色分离**，`/lgtm`（审阅）与 `/approve`（批准）是不同权限 [来源 9]。
  - GitLab approvals：required approvals 不满足则无法 merge [来源 10]。
- **数据治理**
  - DataHub Change Proposals：数据用户可以「建议」给数据资产加 Tag/术语/Owner/描述，data owners / stewards 负责 review 并 approve / deny；**创建提案的权限与审批管理的权限分开授予**——这是「模型/用户可提候选、不能决定正式写入」在数据治理里的直接对应物 [来源 11]。
  - Databricks Medallion：bronze（raw）→ silver（validated）→ gold（enriched）逐层验证的数据分层，各层存不同 schema；「Enables reprocessing and auditing by retaining all historical data」[来源 12]。
- **内容审核流水线**
  - Wikipedia pending changes：未注册/新用户的编辑被保存为 pending change，**公众默认只看到最近一次 accepted（stable）revision**，只有 reviewer/管理员接受后才成为对所有读者可见的版本 [来源 13]。
  - MediaWiki FlaggedRevs：扩展「prevents recent changes to wiki articles from being displayed to all readers until they have been ratified by editors with special permissions」；数据库形态是 `flaggedpages` / `flaggedpage_pending` / `flaggedrevs` 等表，即**在同一页面集合上用状态字段区分候选与正式** [来源 14、15]。注意该扩展 2014 年后不再部署、官方警告复杂不推荐生产（见 §5 风险）。
  - Stack Exchange suggested edits：编辑入队（peer review queue），批准前只有提交者自己可见，「only visible to you until it's been approved by trusted community members」；两个 accept/reject 票即出队并应用或丢弃 [来源 16、17]。
- **论文评审系统**
  - OpenReview：投稿=Note，评审=挂在投稿下的 Reply Note，Decision Stage 由 Program Chairs 创建 decision invitation，决策是枚举（Accept (Oral)/Accept (Poster)/Reject）；所有创建/修改/删除都经带 `signatures`（谁操作的）的 Edit 对象，invitation 定义「谁能做什么」[来源 18、19、20]。
  - arXiv 2010.05137（OpenReview 数据研究）说明这套流水线在真实规模（ICLR 等）上运行多年 [来源 22]。
- **墓碑（graveyard）**
  - 本项目已有 graveyard 实践（判死写 graveyard、不物理删除），工程事故史还催生了「graveyard 必须 append-only 且拒绝重复 id」[项目内：06-M08技术选型.md §6、§7、§7.1]。
  - 工程先例：Gerrit abandon/restore（判死可复活）[来源 2]；Cassandra 删除不物理移除而是写 tombstone、由 compaction 延迟清理 [来源 28]。后者还提示墓碑的代价（读放大与延迟清理），JSONL graveyard 没有该代价但有单调增长问题。

### T5-问题2：「检测并行、处置单点」对应什么存储模式（append-only 事件 + 单写者裁决？裁决状态机？）

**对应的是「append-only 事件日志（并行检测产物）＋ 裁决状态机（单写者推进）＋ 正式区单写者追加」三件套；三个组件缺一不可。**

1. **append-only 事件日志承载「检测并行」**：所有检测/审计发现（谁提出、谁在哪个轴判了什么、依据什么）作为事件只追加。先例：事件溯源「Capture all changes to an application state as a sequence of events」[来源 24]；Gerrit NoteDb 把每一条投票/评论作为 commit 追加到 meta 分支 [来源 1]；Sigstore Rekor「the log remains append-only and entries are never mutated or removed」[来源 32]；RFC 6962 Certificate Transparency 用公开 append-only 日志 + Merkle tree 让人人可审计 [来源 33]。
2. **裁决状态机承载「处置单点」**：每个候选一个状态记录，合法状态转移由**单一裁决者**推进（不投票、不多写多份）。先例：Gerrit change 生命周期（NEW/MERGED/ABANDONED，abandon/restore/submit 都是单点动作）[来源 2、4、5]；分布式共识里 Raft 的「Election Safety: at most one leader can be elected in a given term」「Clients of Raft send all of their requests to the leader」——写入收敛到单 leader [来源 25]；DDD Aggregate「Transactions should not cross aggregate boundaries」——把状态推进收敛到单个聚合根/单事务边界 [来源 24b]。
3. **正式写入只允许裁决者追加**：Dynamo 把「检测冲突」与「解决冲突」显式分开——「conflicting changes which must be detected and resolved… two problems: when to resolve them and who resolves them」，并选择由应用方（单点裁决者）做冲突解决 [来源 26]。对应到本存储形态：检测者可以并行向候选区/审计事件区追加，**正式区（nodes JSONL）只有裁决脚本能追加**。

**存储层面的含义**：append-only 本身允许多写者，但「单点」必须由**写入所有权/互斥协议**表达——本项目当前形态是「写型工具受约束（argparse/--dry-run/--only/禁裸 'w'）+ 正式区单写者脚本 + graveyard 拒绝重复 id」；若未来换数据库，则用角色权限（谁可写候选表、谁可写正式表）表达同一约束 [来源 34、11]。

### T5-问题3：审计记录（谁判的、依据什么、结果是什么）的不可变存储与回溯查询？

**审计记录的最小字段是「actor（谁判的）+ evidence（依据什么）+ result（结果）+ 时间」；不可变用 append-only 事件或版本化历史表达；回溯查询靠按实体过滤事件 + 重放（或物化投影）。**

- **谁判的/依据什么/结果**的语义模型有标准：W3C PROV-DM 的 provenance 三元组（entity/activity/agent）正好对应「结果（判定结论）— 活动（审计动作）— 判定者」；`wasAttributedTo`（结论归因于谁）、`wasAssociatedWith`（活动由谁执行）[来源 27]。DataHub 的 `auditStamp {actor, time}` 是工程实现里最小可用形态 [来源 31]。
- **不可变**：Gerrit NoteDb 用 Git commit 序列保存审查历史（「automatically preserving history of the metadata」）[来源 1]；SQL Server Ledger 提供防篡改账本（历史保留在 history table，SHA-256 + Merkle tree 校验）[来源 29]；SQL Server 系统版本化时态表由系统自动把每次更新/删除前的旧行写入 history table，支持 point-in-time 回溯 [来源 30]；pgaudit 提供会话/对象级审计日志 [来源 31b]；Rekor 提供「never mutated or removed」的透明日志 [来源 32]。
- **回溯查询**：时态表/账本的「历史表 + 当前表」是「事件流 + 物化投影」的关系库等价物 [来源 30]；事件溯源则是「从事件流重放得到任意时刻状态」[来源 24]。对 append-only JSONL，回溯 = 按 `target_id` 过滤事件 + 独立校验脚本重放/统计，当前校验脚本模式（`verify_anchors.py` / `check_graph.py` 可脱离产出流程重跑）已经具备这个形状 [项目内：06-M08技术选型.md §7]。
- **本项目建议**：每条审计事件记录 `{event_id, ts, actor, action, target_id, axis(A/B/升降级/判死), result(KILL/FIX/KEEP/APPROVED/REJECTED/…), evidence(引用的死因清单项/审查单编号/锚点), prev_state, next_state}`；状态由事件推进而非原地修改，天然满足「不覆盖旧结论」。

### T5-问题4：候选与正式内容隔离的存储形态（命名空间/分区/独立库）？

**三种形态都有先例，可按规模演进；当前 JSONL 规模下推荐「物理分区（独立文件/目录）+ id 命名空间 + 状态字段 + append-only 事件」的组合。**

- **独立库/独立存储层（物理隔离）**：Medallion 的 bronze/silver/gold 各层存不同 schema（示例 `ops.bronze` / `ops.silver` / `ops.gold`），逐层验证后才进下一层 [来源 12]。Gerrit 的候选与正式也是物理分离：`refs/for/branch` 推送并不创建正式分支，而是转成 change record，只有 submit 后才合入正式分支 [来源 3]。
- **命名空间/权限分区**：PostgreSQL schema 是标准命名空间隔离 + 权限控制手段 [来源 34]。本项目已有对应物：id 前缀（`apostol:` / `strang:` / `d:` / `x:` / `L2:`…）本身就是带证据责任的命名空间 [项目内：06-M08技术选型.md §1、§10-Q4]。
- **状态字段 + 不可变历史（同一集合内区分）**：Wikipedia pending changes 与 FlaggedRevs 是在同一页面集合上靠「pending / stable（accepted）」状态区分候选与正式，配 flaggedpage_pending 等状态表 [来源 13、14、15]。DataHub 是「同实体、不同权限、审批后应用」的形态（aspect 版本化，Change Proposals 审批通过后才应用）[来源 11、31]。
- **结论**：三形态不互斥。候选区内容与正式通用结构**必须可见可区分**（审查单原文要求「候选区的内容与正式通用结构分离」），最小实现是：候选 JSONL 与正式 nodes JSONL 物理分文件/目录，候选行带 `status` 字段，任何状态变化只通过追加审计事件产生；未来若换数据库，用 schema + 角色权限复刻同一隔离。

## 3. 对决策点的输入（明确写到 D6）

**D6（候选池与审计晋升管道的数据模型）建议采用如下形态**（与红线 8/9/10/15 兼容）：

1. **存储分区（物理隔离，当前 JSONL 即可实现）**
   - 候选区：`candidates/*.jsonl`，检测者（含模型输出）**并行、只追加**写入；每条含 `candidate_id`、`source`、`proposed_by`（可为人/模型/闭环）、`evidence`、`status`。
   - 正式区：`nodes/*.jsonl`（现有），**只有裁决脚本可追加**。
   - 墓碑区：`graveyard/*.jsonl`（现有，append-only、拒绝重复 id）。
   - 审计事件区：`audit-events.jsonl`（新增），append-only，作为唯一权威轨迹。
2. **状态机（处置单点的载体）**：每候选一条状态，枚举建议 `CANDIDATE → IN_REVIEW → {APPROVED, FIX_REQUIRED, REJECTED, KILLED}`，KILLED 只进 graveyard；状态**只能由裁决脚本通过追加审计事件推进**，禁止原地改状态字段（与「不覆盖旧结论」红线一致）。
3. **审计事件最小 schema**：`{event_id, ts, actor, action, target_id, axis, result, evidence, prev_state, next_state}`；axis 区分审计 A（正确性）/审计 B（抽象增益）[项目内 §5 两轴]；evidence 引用死因清单（六死因）与审查单条目。
4. **权限的存储层表达**：当前形态 = 文件所有权 + 写型工具约束（argparse/--dry-run/--only/禁裸 'w'）；未来上数据库 = schema + 角色权限复刻 DataHub「Propose 权限 vs Manage 权限」分离 [来源 11] 与 Kubernetes「reviewer vs approver」[来源 9]。
5. **候选与正式可区分性的最小保证**：id 命名空间前缀（`L2:` 等）已带证据责任 [项目内 §1]，候选区/正式区分文件即满足「候选区内容与正式通用结构分离」（M08 审查单原文要求）。

## 4. 与产品约束的冲突/张力（如无则明说无）

1. **红线 8「检测并行、处置必须单点」在 JSONL 上的实现张力（必须标注）**：append-only 允许多写者，但「单点」需要显式互斥协议。候选区并发追加要考虑行级原子性（单行 `O_APPEND` 追加 vs 多行块写入的中间态）；正式区必须由单一裁决脚本独占写入。项目 §7.1 事故史（--help 无条件 `open(...,'w')` 清零 graveyard）恰好证明：裁决者本身必须是受约束的写型工具，否则「单点」只是名义上的。
2. **红线 10「不物理删除、写 graveyard」与墓碑先例的代价（张力提示）**：Cassandra tombstone 有读放大与延迟清理代价 [来源 28]；Gerrit abandon 可 restore [来源 2]；JSONL graveyard 无读放大，但 graveyard 与审计事件都单调增长（与红线 9 的 append-only 同源，增长问题留待 T7 方向处理，见 §5）。
3. **红线 9「append-only JSONL + 独立校验脚本」与审计事件规模**：审计事件与数据同速增长；「事件流 + 物化投影」需要快照/压缩策略，否则重放成本随时间线性上升。这是 D6 与 D4/T7 的交界，本轨道只指出方案（快照 + 保留事件），不替代 T7 结论。
4. **红线 8「模型可提候选、不能决定正式写入」的存储层含义**：先例（DataHub Change Proposals 权限分离 [来源 11]、LLM 审核升级到人审 [来源 23]）支持该红线；张力在于：若未来上数据库且权限粒度过粗（如「内容写入」一个权限包打天下），单库容易被绕过，必须把「propose」与「approve/manage」拆成不同权限角色。
5. **FlaggedRevs 先例的反面教训（张力提示）**：状态字段方案虽有 Wikipedia 先例 [来源 13、14]，但 FlaggedRevs 官方自认复杂、不推荐生产、2014 年后不再部署 [来源 14]——说明「同一集合内状态字段 + 复杂权限」形态运维代价高，本项目应选更简单的「物理分区 + 单写者脚本」形态，而不是把状态机做进数据库引擎。
6. **红线 15 工具安全**：与存储模式正交，但直接约束「单点裁决」的实现——裁决脚本必须是真 argparse / --dry-run / --only / 禁裸 'w'，且 `--help` 不得视为只读。

## 5. 未决与风险

1. **审计事件的权威源 vs 物化状态**：状态由事件重放派生还是物化存储？若物化，必须保证「状态推进只能通过新增事件」这一不变式被校验脚本强制（否则退回可覆盖状态字段 = 违反红线 10 的不覆盖旧结论）。
2. **并发追加协议**：多检测者并行写候选区时，行级原子性、部分写、崩溃恢复的具体协议未实测（JSONL 单写者场景已有事故恢复经验，多写者场景没有）。§6 给出最小实验。
3. **审计事件规模**：append-only 事件与 graveyard 的单调增长，快照/压缩/归档策略未定（与 T7「M09 规模三方向」耦合，本轨道不越界定案）。
4. **裁决「依据」字段的结构化程度**：evidence 若只存自由文本，回溯查询会退化为全文搜索；六死因清单 [项目内 §5] 与审查单条目编号应成为可枚举引用。需要定最小 schema 并校验。
5. **OpenReview 先例的边界**：OpenReview 的决策可被 Edit 修改（审计靠 Edit 历史）[来源 18]；本项目红线是「不覆盖旧结论」——等价于禁止对已产生结论的事件做修改，只允许追加新事件表达更正/撤回（M04-02 中的「更正/撤回」语义）。这一边界要在 D6 数据模型中显式写死。
6. **自动晋升条件**：M04-02 提到「明确无问题且满足授权条件的 M08 候选可自动晋升」——自动晋升仍由裁决者脚本执行（脚本即裁决者），不改变「单点」；但自动晋升的触发规则与人工门的分界属于产品问题，本轨道只保证存储形态两侧都可承载。

## 6. 建议的下一步实测（可执行的最小实验）

按「可判定性优先」排序，全部以现有 append-only JSONL + 独立校验脚本模式为基底：

1. **审计事件日志原型（判定 D6 核心形态）**
   - 输入：新增 `audit-events.jsonl`（schema 见 §3.3）；用现有 24 个 L2 候选（存活 4）[项目内 §4.1] 回放「候选 → A 审计 → B 审计 → 裁决 → 晋升/判死」全过程；裁决脚本 `adjudicate.py` 满足真 argparse / --dry-run / --only / 禁裸 'w'。
   - 判据：从事件流可重建每个候选的最终状态且与人工裁决一致；`--dry-run` 不落盘；非法状态转移被拒绝。
2. **并发检测落盘协议（判定「检测并行」的 JSONL 边界）**
   - 输入：两个检测进程并发向候选区追加（A：单行 `O_APPEND`；B：多行块写入），中途 kill -9 一个进程。
   - 判据：校验脚本（行完整、无交错损坏）通过；恢复后磁盘上仍是合法 JSONL；记录并发追加的原子性上限。
3. **状态机 schema 校验脚本**
   - 输入：状态枚举 `CANDIDATE/IN_REVIEW/APPROVED/FIX_REQUIRED/REJECTED/KILLED` 与合法转移表；用现有 graveyard 68 条判死记录回放转移合法性。
   - 判据：非法转移（如 KILLED→APPROVED 无 restore 事件）被拒绝；KILLED 只进 graveyard。
4. **graveyard 拒绝重复 id 落实**
   - 输入：把 §7.1 已要求的「graveyard 拒绝重复 id」实现为独立校验脚本（现为纸面要求）。
   - 判据：重复 id 写入在 --dry-run 即报错；现有 68/88 条记录迁移后无重复。
