## 0. 一句话结论

三方向中**方向1（M09 内部给历史版本独立位置）与方向3（两区分离：历史区+边缘区）都与业界先例相容，且都可在当前 append-only JSONL+脚本路线内落地**；**方向2（历史版本移交 M01 保管）与 M01 已确认的产品边界直接冲突**——M01 审查单明文「M01 保存闭环及其相关记录的项目/会话归属，不保存另一份个人知识模型」「只存事实、不存解释」，把 M09 历史版本移交 M01 等于让 M01 承担个人知识模型的版本语义，除非先改产品边界否则不成立。个人学习历史的单调增长在可预期规模（单学习者、年百级闭环、千级版本记录）下**远未到需要分区/冷热分层的量级**；先例（FHIR 全历史随资源、xAPI 语句不可变+voiding 墓碑、TimescaleDB 保留策略+连续聚合+对象存储分层）支持「当前视图派生、历史全留」，方向1 是成本与风险最低的默认，方向3 是规模实测触发后的演进路径。

## 1. 必须回答的问题逐条回答（T7-1…T7-4）

### T7-1 个人学习历史/记录单调增长的存储先例

**结论：三个直接先例分别支持三方向的某种侧面，且全部是「历史全留 + 当前视图派生」而非「覆盖/删除」。**

- **电子健康档案（FHIR R5）——「全历史随资源」先例（方向1 同构）**：FHIR 每个资源带 `meta.versionId` 与 `meta.lastUpdated`；`update` 产生新版本；`history` 交互返回「包含已删除资源在内、最旧在最后」的完整版本历史；规范鼓励 `versioned-update`（版本感知更新，If-Match 防并发覆盖）。即医疗这类「必须保留旧版本以免责任问题」的领域，做法是把全部版本保留在资源本身内部，而不是把历史搬到别处。
- **学习记录（xAPI / LRS）——「append-only + voiding 墓碑」先例（与红线 10 graveyard 同构）**：xAPI 规范 2.3「Statement Lifecycle」原文「Statements are expected to be permanent. The only way to undo a Statement within this specification is to void it」；voiding 不是删除，而是发一条引用旧 Statement id 的新 voided 语句，LRS 判定「某语句被 void 当且仅当库中存在指向它的 voiding 语句」。学习记录领域（xAPI 即学习体验数据的行业标准）的既定做法就是：**永不物理删除、永远追加、以墓碑表达撤回**。
- **时序数据（TimescaleDB）——「保留策略 + 连续聚合 + 对象存储分层」先例（方向3 同构，但注意删除冲突）**：TimescaleDB 官方文档「数据保留」原文「Data retention policies delete raw old data for you on a schedule… By combining retention policies with continuous aggregates, you can downsample your data and keep useful summaries of it instead. This lets you analyze historical data - while also saving on storage」；「连续聚合」章节原文「real-time aggregation enables you to combine pre-aggregated data from the materialized view with the most recent raw data」（注：v2.13 起默认关闭 real-time）；且连续聚合/表可「tiered to object storage」。即**历史沉底 + 聚合派生当前视图 + 分层存储**是时序领域的标准做法；但它的「删除旧原始数据」与本项目红线 10（不物理删除）冲突，只能借用「聚合 + 分层」部分。
- **审计日志/append-only**：T2 已覆盖（Helland《Immutability Changes Everything》「会计不用橡皮擦」、Kreps《The Log》、Fowler Event Sourcing），本轨道不重复取证，仅引用其结论：审计类存储的普遍形态就是全量保留 + 按需派生。

### T7-2 三方向各自的存储成本、查询代价、迁移风险

> 规模外推前提（推断，标注 C）：M08 实测 2 章 ≈ 522 节点/1433 边/921 锚点（`01` 文档）；M09 只收已结束闭环（红线 12），单学习者一年闭环数在数十到数百量级（推断 C），每条 M09 记录 = 1 条形成记录 + 证据边若干 + 时间版本链（复检/遗忘/重新掌握平均 2–3 版/对象，推断 C）。据此年增量 ≈ 数百到数千条记录、单条 1–10 KB 文本，年存储量 MB 级、十年百 MB 级（推断 C）。该量级下三方向的**存储成本差异都可忽略**，差异主要在查询组织与迁移风险。

**方向1：重新规划 M09 自身结构，历史版本内部独立位置**
- 存储成本：全量历史随 M09 记录保留，年 MB 级（推断 C）；无跨模块重复存储。
- 查询代价：当前视图 = 从底层记录过滤（`superseded_by`/`retracted_at` 为空的最新版本），可由派生视图/索引承担；历史查询 = 同一存储内按版本查询。T2 已论证「当前视图可由底层记录派生」。
- 迁移风险：最低——不涉及任何跨模块搬迁；未来改结构只动 M09 内部。
- 先例支撑：FHIR 全历史随资源（A）。

**方向2：历史版本移交别的模块（如 M01，作为对会话的一种存储）**
- 存储成本：M09 需保留「移交后的指针/引用」+ M01 保存版本内容，跨模块重复或拆分的双份维护；若只移交不复制，则 M09 当前视图也要跨模块读。
- 查询代价：当前视图与历史查询都要跨 M09–M01 组装，模块间引用链变长；「M01 是 M09 与 M15 的唯一链接位置」的现状会被扩展为「M01 持有 M09 历史」，职责混杂。
- 迁移风险：最高——需要改写 M01 边界与既有存储、迁移历史数据、并保证移交过程原子性。
- **产品边界冲突（判死级，项目一手文档 A）**：M01 审查单边界原文「M01 保存闭环及其相关记录的项目/会话归属，不保存另一份个人知识模型」「M01 只存事实，不存解释」。M09 历史版本是个人知识模型的版本语义，不是会话事实。
- 先例：无直接先例——归档/冷存储先例（TimescaleDB tiering、S3 生命周期）是「移出主系统到更廉价存储」，不是「移交给另一个语义模块」。

**方向3：M09 分两区（历史区与边缘区）**
- 存储成本：单格式内分区（如同库两目录/两前缀或两表），历史区 append-only、边缘区当前活跃；年规模下双区总量 ≈ 方向1 总量（推断 C）。
- 查询代价：当前视图只读边缘区（最活跃路径最快），历史按需读历史区；两区在 JSONL+脚本路线下就是「读哪个文件集」，不需要图数据库。
- 迁移风险：中——「沉底」规则（何时从边缘区移入历史区）是新增的结构决策，需要可判定标准；区划写进数据结构（M09 审查单原文已指出这一点）。
- 先例支撑：TimescaleDB 连续聚合 + 对象存储分层（A）；「实时聚合 = 聚合区 + 最近原始数据」与「边缘区 + 历史区」同构（A）。
- 产品边界：不违反任何红线，但「沉底规则」属待设计项。

### T7-3 与「当前视图可从底层记录派生」的兼容性；与 M08 锚定/候选管道的关系

- 兼容性：三方向都允许「当前视图从底层记录派生」。方向1 最直接（单存储内过滤）；方向3 次之（边缘区即派生后的活跃视图，历史区保留底层记录，二者同格式可重派生）；方向2 最弱（当前视图跨两个模块组装，且 M01 侧缺乏语义所有权，派生逻辑落在模块边界上）。
- 与 M08 锚定/候选管道：三方向都不改变「M09 锚定 M08、候选去个人化后经审计晋升 M08」的管道。注意区分：**历史版本是个人知识（留在 M09），候选来自当前形成（去个人化后晋升 M08）**；方向2 若把历史移交 M01，会在「M01 会话事实」与「M09 个人知识」之间制造职责漂移，污染候选管道的输入边界——M09 侧丢失版本语义的所有权后，「哪些是当前形成、哪些是历史」的判定也要跨模块。
- M09 审查单原文（方向3 与当前视图派生的关系）：「方向 3 与『当前视图可从底层记录派生』那条内部功能一致，但它把区划写进了数据结构，因此同样受选型约束」（项目一手文档 A）。

## 2. 关键发现（每条：论断 + 来源 + 原文摘录/要点）

### 2.1 FHIR R5：每个资源带版本元数据，update 产生新版本，history 返回含已删除资源的全版本历史
- 论断：电子健康档案类「旧版本必须保留」领域，标准做法是把全部版本保留在资源内部，并提供 `vread`（按版本读）与 `history`（全版本列表）交互；版本感知更新（If-Match）防覆盖。
- 来源：https://hl7.org/fhir/R5/http.html 《FHIR R5 Specification - HTTP》，HL7 International，2026-08-12 访问（原文抓取到手）。
- 原文摘录：「Each resource has an associated set of resource metadata elements… Version Id (.meta.versionId) … represented in the ETag header」；「The Version Id is considered a 'weak' ETag」；「Supporting versions like this allows for related systems to track the correct version of information, and to keep integrity in clinical records」；history 交互「sorted with oldest versions last, and including deleted resources」。
- 证据等级：A（原文到手）。

### 2.2 xAPI：语句预期永久，唯一撤销方式 = voiding（墓碑追加，非删除）
- 论断：学习记录（LRS）行业标准明确「语句不可变、永久、只允许 void」；voiding 是引用被 void 语句 id 的新语句；voided 语句不可再被 void。
- 来源：https://github.com/adlnet/xAPI-Spec/blob/master/xAPI-Data.md 《Experience API Data Specification》（IEEE 9274.1.1 前身，ADL），2026-08-12 访问（原文到手）。
- 原文摘录：「Statements are expected to be permanent. The only way to undo a Statement within this specification is to void it. Voiding does not destroy a Statement, rather indicates the evidence in the Statement is to be disregarded.」「An LRS MUST consider a Statement it contains voided if and only if the Statement is not itself a voiding Statement and the LRS also contains a voiding Statement referring to the first Statement.」
- 证据等级：A（原文到手）。

### 2.3 TimescaleDB：保留策略删旧原始数据，但「连续聚合 + 对象存储分层」提供历史沉底与当前视图派生
- 论断：时序数据库的标准做法是保留策略（删旧）+ 连续聚合（预计算摘要）+ 分层（热/温/冷）；其中「聚合 + 分层」与本项目方向3 同构，「删除」部分与红线 10 冲突。
- 来源：https://docs.timescale.com/use-timescale/latest/data-retention/ 与 https://docs.timescale.com/use-timescale/latest/continuous-aggregates/ 《Understand data retention / Understand continuous aggregates》，Timescale，2026-08-12 访问（原文到手）。
- 原文摘录（retention）：「Data retention policies delete raw old data for you on a schedule that you define. By combining retention policies with continuous aggregates, you can downsample your data and keep useful summaries of it instead. This lets you analyze historical data - while also saving on storage.」（contagg）：「Real-time aggregation enables you to combine pre-aggregated data from the materialized view with the most recent raw data.」（注意「In TimescaleDB v2.13 and later, real-time aggregates are DISABLED by default」）；「you can query them in exactly the same way as your other tables. This includes continuous aggregates… or tiered to object storage.」
- 证据等级：A（原文到手）。

### 2.4 M09 审查单：三方向的原文表述 + 「方向 3 与当前视图派生一致但把区划写进结构」
- 论断：三方向是产品层未决项，方向 3 明确标注「与『当前视图可从底层记录派生』一致，但把区划写进数据结构，同样受选型约束」。
- 来源：`docs/模块需求设计/模块审查单/M09-动态学习者模型.md` 文末「由第 4 问引出的规模问题（本轮记录，未决）」（项目一手文档）。
- 原文摘录：「不覆盖旧结论意味着 M09 体积单调增长。三个方向，都需要在 M08/M09 存储选型时一并决定：1. 重新规划 M09 自身的结构，让历史版本在内部有独立位置 2. 历史版本移交别的模块保管（例如 M01，作为对会话的一种存储） 3. M09 分两区：历史区与现有边缘区」；「方向 3 与『当前视图可从底层记录派生』那条内部功能一致，但它把区划写进了数据结构，因此同样受选型约束。」
- 证据等级：A（项目一手文档）。

### 2.5 M01 审查单：M01 不保存另一份个人知识模型、只存事实不存解释
- 论断：方向2（历史移交 M01）与 M01 已确认边界冲突。
- 来源：`docs/模块需求设计/模块审查单/M01-学习项目与会话.md`（项目一手文档）。
- 原文摘录：「M01 保存闭环及其相关记录的项目/会话归属，不保存另一份个人知识模型」「M01 只存事实，不存解释」「M01 是 M09 与 M15 之间唯一的链接位置」。
- 证据等级：A（项目一手文档）。

## 3. 对决策点的输入（D4）

- **D4 推荐（按优先级）**：
  1. **方向1（默认）**：M09 内部给历史版本独立位置（`superseded_by` / `retracted_at` 字段 + append-only JSONL + graveyard 墓碑，语义已由 T2 论证），与红线 9/10/13 完全兼容，迁移风险最低，先例最直接（FHIR/xAPI）。
  2. **方向3（规模触发后的演进）**：当实测年增量 + 查询延迟越过阈值时，在同一格式内分历史区/边缘区（读哪个文件集），借用 TimescaleDB「聚合+分层」思路但**排除删除旧数据**（红线 10）。
  3. **方向2（不推荐）**：除非产品负责人先改 M01 边界，否则技术方案不成立。
- **给合成的判据建议**：以「单学习者年闭环数 × 版本倍数」实测外推；阈值未定义前不提前分区（推断 C：分区是结构决策，M09 原文已确认「同样受选型约束」）。

## 4. 与产品约束的冲突/张力

1. **方向2 与红线 12/M01 边界冲突（显式张力）**：红线 12 规定 M09 锚定 M08、只收已结束闭环；M01 审查单规定 M01 不保存个人知识模型。方向2 若实现，等于让 M01 承载 M09 历史版本，违反两条已确认边界——除非产品负责人变更边界，本轨道按红线 16「不做」精神不把它作为技术方案推荐。
2. **TimescaleDB retention（删除旧数据）与红线 10 冲突**：借用的只是「连续聚合 + 分层」模式，删除部分明确排除。
3. **方向3 的「沉底规则」是新增结构决策**：M09 原文已声明其受选型约束；本轨道不越界替产品定规则，只要求规则可判定（何时移入历史区、依据什么条件）。

## 5. 未决与风险

1. 单学习者 M09 的年增量数据无实测（M09 尚无实现），三方向规模评估基于推断（已标注 C）。
2. 「沉底规则」判定标准未定义（方向3 的可落地前提）。
3. 多项目/多学习者并发使用 M09 时规模假设失效（当前产品是单学习者自学系统，若未来扩展需重新评估）。
4. 方向2 若产品侧坚持，需要 M01 边界变更评审 + 跨模块一致性设计（本轨道未展开）。
5. FHIR 的 `history` 交互在 JSONL+脚本下的等价实现（按版本读取的索引/文件组织）未实测。

## 6. 建议的下一步实测（可执行的最小实验）

1. **规模外推实验（最高优先）**：用 M08 实测数据（522 节点/1433 边/921 锚点）为底，模拟 1/5/10 年量级的 M09 闭环记录（推断年 100–500 闭环、每闭环 1 条记录 + 2–3 版本），在 append-only JSONL 上测「当前视图派生」（过滤最新版本）与「历史查询」的耗时曲线，得到三方向共同需要的规模基线。
2. **沉底规则模拟（方向3 前置）**：定义候选沉底规则（如「某对象 12 个月无新版本且无引用则沉底」），用模拟数据测边缘区/历史区读延迟差异，判断分区收益是否超过实现成本。
3. **版本链长度压力测试**：对单一对象的版本链长度（10/100/1000 版）测「取最新版」与「全历史遍历」的性能，验证方向1 是否需要派生索引。
4. **方向2 边界审查（产品决策，非技术实测）**：若产品负责人考虑方向2，先做 M01 边界变更评审，再谈存储方案。
