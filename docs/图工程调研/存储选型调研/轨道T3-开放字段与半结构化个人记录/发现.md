## 0. 一句话结论

M09 应采用「**关系骨架 + JSONB 开放字段 + JSON Schema 校验（pg_jsonschema + CHECK）+ 断言为最小记录单位 + xAPI 式不可变/void 语义**」的混合模型：固定列（锚点/证据引用/条件/时间/版本/模型身份）保证开放字段可稳定查询与审查，JSONB 开放对象承载"维度可空、可扩展"的丰富个人形成记录，证据边与版本链作为独立结构，不覆盖旧结论（红线 13）；EAV 因查询与 pivot 代价应否决，纯文档库与属性图可用但校验/审查能力弱于"关系骨架+JSONB"组合。

## 1. 必须回答的问题逐条回答（引用轨道定义的问题编号）

### T3-1「开放但可查询可审查」的字段模型：JSONB / 文档库 / EAV / 属性图 / 混合，各自的查询、校验、迁移代价？

**结论：混合模型（关系骨架 + JSONB 开放字段）最匹配"开放但可查询可审查"，其次纯文档库，EAV 否决。**

- **PostgreSQL JSONB**：jsonb 为分解式二进制存储，可索引、可被 GIN 索引支持存在/包含/jsonpath 查询（PG 官方文档）；开放字段放在 jsonb 列中，新增维度不需要 ALTER TABLE（无结构迁移）；校验通过 CHECK 约束 + `jsonb_matches_schema`（pg_jsonschema 扩展）实现，属"写入即拒绝"的强制校验；查询代价 = 标准 SQL + jsonpath/GIN，审查可用普通 SQL 完成。
- **文档数据库（MongoDB 等）**：默认灵活 schema，同集合文档不必同字段/同类型（官方文档）；schema validation 是"补充控制"而非默认，规则不必覆盖每个字段，可配置拒绝或仅告警、可控制对存量文档的生效级别——即"开放"优先、"可审查"靠使用者自行加约束；查询用聚合管道/Query API，审查需额外建立抽取管道；迁移代价低（无 DDL），但 schema 语义分散在应用层与可选的 validation 规则里。
- **EAV**：为稀疏/动态属性设计，但大体积下 pivot（行转列）转换"既易错又吃 CPU"，是公认的 Achilles heel；Wikipedia 转引工程实践称 PostgreSQL JSONB 相对传统 EAV 表设计性能改善可达千倍以上。对 M09 这种"维度数量有界（10 个既定维度 + 少量扩展）"的形态，EAV 完全没有必要，且查询、校验、审计都更贵。
- **属性图（Neo4j 等）**：节点/关系/属性/label 模型；"开放"不是属性图自带的（其术语表明确 schema = "为节点与关系规定的属性存在性与数据类型"，即属性图同样可以设约束）；开放字段在属性图里就是节点上的任意属性，JSON Schema 式深层校验需要外部工具；对 M09 的"个人形成图 + 证据边"，图的边有价值，但开放字段的校验/审查能力不优于 JSONB；图引擎选型属 T1/T6，不在本轨道展开。
- **混合**：固定骨架（锚点、证据、条件、时间、版本、模型身份为强制列）+ JSONB 开放对象 + JSON Schema/CHECK 双重校验；SQL 的 `WITH RECURSIVE` 已支持深度/广度优先树遍历与环检测，可覆盖个人形成图的遍历需求；Apache AGE 作为"PostgreSQL 上的图数据库扩展"是可保留的解锁选项（触发条件见红线 9，属 T1/D1）。

### T3-2 M09「丰富个人形成记录」（理解、应用、结构解释、心智模型、可提取性、干扰、迁移、直觉、缺口、适用条件）怎么建模才能既开放又稳定审查？

**结论：固定骨架列 + `formation` JSONB 开放对象，借鉴 FHIR profile 原则与 VC evidence 结构；"核心词汇封闭、扩展受控"。**

- 十个维度作为 JSONB 对象内的**受控键**（可空、可扩展），不做强制满填的固定模板——与 M09 审查单"维度可空、可扩展，不强制压成四级或一个总结"一致。
- 审查稳定性的关键是 FHIR 的原则："**必须能在不知道 profile 的情况下安全处理一个资源**"、"知识必须显式写在实例里，而不是隐含在 profile 里"。映射到 M09：任何一条记录即使带未知扩展键，也必须能被标准读取器安全读取并判断"哪些是受控字段、哪些是扩展"；扩展的语义要由记录自身（如扩展键的命名空间/类型）携带，而不是依赖外部全局 schema。
- 每个形成结论的证据对象采用 VC 2.0 的 evidence 模式：**type 必填、id 可选**——M09 的"证据边必须记录由哪个模型、哪个版本得出，且必须是实际执行模型"（M09 审查单主干）可直接落成 evidence 对象的强制属性。
- JSON Schema 2020-12 提供工具：`additionalProperties` / `unevaluatedProperties` 控制"未声明字段是否允许、如何校验"，vocabulary/dialect 机制支持"核心词汇封闭 + 扩展词汇受控"；断言（assertion）与注解（annotation）分离，适合"结构校验 + 检索索引"两条路分开走。
- 代码侧对应形态：Pydantic `extra='allow'` + `__pydantic_extra__`（未声明字段被保留并可被注解校验）、TypeScript index signature（已知字段 + 未知字段的值类型约束）——说明"typed open record"在主流语言里都有成熟表达，M09 校验脚本可用这些机制实现"核心字段强类型 + 开放字段受控"。

### T3-3 开放字段 + 证据边 + 版本链三者的组合存储形态？

**结论：三条独立结构——开放字段（JSONB）、证据边（边表/引用）、版本链（新版本不覆盖旧结论 + void/更正边），xAPI 是最近的一手先例。**

- 开放字段：`formation` jsonb（见 T3-2）。
- 证据边：独立表/关系（断言 → 已结束闭环、具体表现、教学/提示条件、时间、原始过程位置），每条证据边带 type + id + 来源引用（VC evidence 模式）；"判断主体（模型+版本）"是证据边的一部分而非别名。
- 版本链：**新结论 = 新断言，旧结论原样保留**（红线 13）；更正/撤回 = 写入一条 void 型断言指向旧断言（xAPI 先例：Statement 不可变，唯一撤销方式是 void，void 不销毁原 Statement 而只是标记其证据应被忽略；void 语句本身不可再被 void）；历史数据保留原形、不迁移（MongoDB Data Versioning 模式：保留历史版本可避免高成本的 schema 迁移与停机，且"把文档更新到新 schema 不是必需条件"）。
- 事件溯源（Fowler）作为 append-only 的理论底子："所有对应用状态的变更都以事件序列存储"，可用事件日志重建任意过去状态；但 M09 是否要做"事件日志 + 物化视图"双份，属 T2（D3）的粒度与成本权衡，本轨道只确认其存储形态可行。

### T3-4 最小记录单位怎么定（M04-02 未决问题）？

**结论（技术侧约束）：以「断言（assertion）」为原子最小记录单位；「闭环记录」为聚合容器。产品侧"一个闭环涉及多个对象/关系/个人结构时如何切分"仍需产品负责人确认，但技术侧可给出硬约束。**

- xAPI 一手先例：Statement 是证据的最小载体，**"A Statement MUST use 'actor', 'verb', and 'object'"**，且 Statement 不可变、可 void——即"一个不可变的最小断言 + 指向证据的引用"是学习记录行业已验证的原子单位。
- Open Badges 3.0（基于 VC 2.0）同样分层：**Assertion 断言单个成就（核心原子单位），CLR（Comprehensive Learner Record）是断言的集合包**——"断言原子、记录聚合"的分层被 IMS 规范确认。
- 映射到 M09：一条断言 = 一个目标（M08 锚点对象或未映射个人对象）× 一组形成维度字段（开放）× 一组证据引用 × 条件 × 时间/版本 × 模型身份；一个已结束闭环 = 一条闭环记录（容器），内部含 ≥1 条断言。M09 审查单"M09 写入一次闭环级个人形成记录"与"一个闭环多个对象"不矛盾：容器级元数据（目标、路线、总体诊断、未满足项）写在记录上，逐对象/逐维度的形成事实写在断言上。
- 技术侧硬约束（无论产品如何切分）：原子单元必须 (a) 可按锚点/对象、维度、时间稳定查询；(b) 可独立审查（证据引用完整、模型身份明确、摘要不替代底层）；(c) 可独立撤回/更正（void 语义，不改写原断言）。

（说明：T3-4 只回答"最小单位怎么定"的技术形态；"一个闭环拆几条断言"的产品规则属 M04-02 待确认项，见第 5 节。）

### 2.1 jsonb 的特性与索引能力（开放字段的"查询"底座）

**论断 1**：PostgreSQL 的 `jsonb` 是分解式二进制存储，处理无需重复解析，且支持索引；`json` 文本型不保序/不除重处理虽少但查询能力弱。绝大多数应用应优先 jsonb。

- 来源：https://www.postgresql.org/docs/current/datatype-json.html，[8.14. JSON Types，PostgreSQL 官方文档（当前版 18）]，访问日期 2026-08-12。
- 原文摘录："The `json` data type stores an exact copy of the input text, which processing functions must reparse on each execution; while `jsonb` data is stored in a decomposed binary format that makes it slightly slower to input due to added conversion overhead, but significantly faster to process, since no reparsing is needed. `jsonb` also supports indexing, which can be a significant advantage."；"In general, most applications should prefer to store JSON data as `jsonb`, unless there are quite specialized needs, such as legacy assumptions about ordering of object keys."
- 证据等级：🟢原文到手。

**论断 2**：jsonb 的 GIN 索引可高效检索"大量 jsonb 文档中的键或键值对"，支持存在算符（`?`、`?|`、`?&`）、包含算符（`@>`）与 jsonpath 匹配（`@?`、`@@`）；`jsonb_path_ops` 算子类体积更小、特异性更好。

- 来源：https://www.postgresql.org/docs/current/datatype-json.html#JSON-INDEXING，[8.14.4. jsonb Indexing，PostgreSQL 官方文档（当前版 18）]，访问日期 2026-08-12。
- 原文摘录："GIN indexes can be used to efficiently search for keys or key/value pairs occurring within a large number of jsonb documents (datums). Two GIN "operator classes" are provided… The default GIN operator class for jsonb supports queries with the key-exists operators `?`, `?|` and `?&`, the containment operator `@>`, and the jsonpath match operators `@?` and `@@`."；"A `jsonb_path_ops` index is usually much smaller than a `jsonb_ops` index over the same data, and the specificity of searches is better… search operations typically perform better than with the default operator class."
- 证据等级：🟢原文到手。
- 对 M09 的意义：开放字段若需按维度键（如 `formation.迁移`）或按条件值稳定查询，GIN + jsonpath 可直接支撑，不需要把每个开放键反规范化成独立列。

### 2.2 CHECK 约束 + JSON Schema 扩展 = "开放但强制校验"的现成组合

**论断 3**：CHECK 是 PostgreSQL 最通用的约束类型，把列值限定为布尔表达式；但它不能引用被检查行之外的表数据——即跨行约束必须靠应用层/触发器。

- 来源：https://www.postgresql.org/docs/current/ddl-constraints.html，[5.5.1. Check Constraints，PostgreSQL 官方文档（当前版 18）]，访问日期 2026-08-12。
- 原文摘录："A check constraint is the most generic constraint type. It allows you to specify that the value in a certain column must satisfy a Boolean (truth-value) expression."；"PostgreSQL does not support CHECK constraints that reference table data other than the new or updated row being checked."
- 证据等级：🟢原文到手。

**论断 4**：pg_jsonschema 是 PostgreSQL 扩展，把 JSON Schema 校验暴露为 `jsonb_matches_schema(schema, instance)`，官方用法就是配 CHECK 约束——"开放字段 + 写入即拒绝"在 PG 上是现成组合（违法写入返回 CHECK violation 报错）。

- 来源：https://supabase.com/docs/guides/database/extensions/pg_jsonschema，[pg_jsonschema: JSON Schema Validation，Supabase 文档]，访问日期 2026-08-12。
- 原文摘录："pg_jsonschema is generally used in tandem with a check constraint as a way to constrain the contents of a json/b column to match a JSON Schema."；示例中非法 payload 报错："ERROR: new row for relation "customer" violates check constraint "customer_metadata_check""。
- 证据等级：🟢原文到手（Supabase 为官方维护方之一；pg_jsonschema 本身是开源扩展，非 PG 内核，成熟度见第 5 节风险）。

### 2.3 SQL 内图遍历（开放字段 + 证据边的"边"部分不需要图数据库才能查）

**论断 5**：PostgreSQL `WITH RECURSIVE` 可做 SQL 内的树/图遍历，且内建 `SEARCH DEPTH FIRST` / `SEARCH BREADTH FIRST` 排序语法与环检测（`CYCLE`）——个人形成图在关系表上的遍历有标准 SQL 路径。

- 来源：https://www.postgresql.org/docs/current/queries-with.html，[7.8. WITH Queries (Common Table Expressions)，PostgreSQL 官方文档（当前版 18）]，访问日期 2026-08-12。
- 原文摘录："The optional RECURSIVE modifier changes WITH from a mere syntactic convenience into a feature that accomplishes things not otherwise possible in standard SQL."；"There is built-in syntax to compute a depth- or breadth-first sort column… `SEARCH DEPTH FIRST BY id SET ordercol` … `SEARCH BREADTH FIRST BY id SET ordercol`"；环检测示例："We add two columns is_cycle and path to the loop-prone query"。
- 证据等级：🟢原文到手。

### 2.4 文档数据库：灵活 schema 是默认、校验是补充控制

**论断 6**：MongoDB 默认"同集合文档不必同字段/同类型"（灵活 schema）；schema validation 用于防止意外的 schema 变更与类型错误，规则不必覆盖每个字段，可配置"拒绝"或"仅告警"，并可通过 validationLevel 控制对存量文档的生效——即"开放优先、可审查靠使用者自行加规则"。

- 来源：https://www.mongodb.com/docs/manual/core/schema-validation/，[Schema Validation，MongoDB 官方文档（Database Manual 8.3 Current）]，访问日期 2026-08-12。
- 原文摘录："MongoDB uses a flexible schema model. By default, documents in a collection don't need the same fields or data types. After you establish an application schema, use schema validation to prevent unintended schema changes and data type errors."；"Schema validation rules are also flexible, so they don't need to cover every field in a document, unless your application requires that they do."；"By default, MongoDB rejects any insert or update operation that would produce an invalid document. Alternatively, you can configure MongoDB to allow invalid documents and log a warning when a schema violation occurs."
- 证据等级：🟢原文到手。

**论断 7**：MongoDB 官方数据建模介绍明确"灵活 schema 支持迭代演进、只对需要严格控制的 section 加校验"——文档库的开放性是产品特性而非缺陷，但其"可审查性"需要显式补建 validation 与审计管道。

- 来源：https://www.mongodb.com/docs/manual/core/data-modeling-introduction/，[Data Modeling Introduction，MongoDB 官方文档]，访问日期 2026-08-12。
- 原文摘录："MongoDB has a flexible data model that allows you to store polymorphic data… Documents within a single collection are not required to have the same set of fields."；"MongoDB's flexible schema lets you iteratively improve your data model as you develop your application… Add schema validation only to the sections and aspects of the documents that need stricter control."
- 证据等级：🟢原文到手。

**论断 8（版本化模式）**：MongoDB Data Versioning 模式的关键是"保留历史文档的原形"：schema 变化时保留历史版本可避免高成本迁移与停机，"把旧文档更新到新 schema 不是必需条件"；历史数据放独立集合不影响当前数据查询——与 M09"不覆盖旧结论"（红线 13）直接对应。

- 来源：https://www.mongodb.com/docs/manual/data-modeling/design-patterns/data-versioning/，[Versioning Pattern，MongoDB 官方文档]，访问日期 2026-08-12。
- 原文摘录："By retaining historical versions of documents and schemas, you avoid performance-intensive schema migrations and downtime."；Use Cases 包括 "Updating documents to the new schema is not a requirement."；"Historical data is stored in a separate collection, and does not impact queries on current data."
- 证据等级：🟢原文到手。
- 注意：该模式的具体形态（历史集合、schemaVersion 字段）是"怎么存"，粒度与回退语义（D3）由 T2 回答。

**论断 9（多态模式）**：MongoDB Polymorphic Pattern 确认"同集合文档结构可以异构"是官方一等设计模式——但它说明的是文档库的容纳能力，不解决"异构字段如何稳定校验/审查"（那是 T3-2 里 JSON Schema/FHIR 原则要回答的）。

- 来源：https://www.mongodb.com/docs/manual/data-modeling/design-patterns/polymorphic-data/，[Polymorphic Pattern，MongoDB 官方文档]，访问日期 2026-08-12。
- 原文摘录："MongoDB uses a flexible data model, which means documents in a single collection do not need to have the same structure. Polymorphic data is data in a single collection that varies in document fields or data types."
- 证据等级：🟢原文到手。

### 2.5 EAV：为稀疏/动态属性设计，但查询与 pivot 代价是硬伤

**论断 10**：EAV 的公认软肋是大体积数据下的"行↔列（pivot）转换"——手动做易错、CPU 密集；对 M09 这种维度有界、需要频繁按维度审查的场景，EAV 的查询/校验/审计成本都不划算。

- 来源：https://en.wikipedia.org/wiki/Entity%E2%80%93attribute%E2%80%93value_model，[Entity–attribute–value model，Wikipedia]，访问日期 2026-08-12（页面 2026-03 起被标注"需要更多引用"，本身即二手综述）。
- 原文摘录："The Achilles heel of EAV is the difficulty of working with large volumes of EAV data. It is often necessary to transiently or permanently inter-convert between columnar and row-or EAV-modeled representations of the same data; this can be both error-prone if done manually as well as CPU-intensive."
- 证据等级：🟡二手转引（Wikipedia 综述；关键论断部分，Wikipedia 正文即承认需要更多引用）。

**论断 11**：Wikipedia 转引工程实践称 PostgreSQL JSONB 相对传统 EAV 表设计性能改善"可达千倍以上"（factors of a thousand or more）；"基于 JSONB 的 schema 表更少、SQL 更简洁"。

- 来源：同上，[EAV — Considerations for server software §8.1 PostgreSQL: JSONB columns，Wikipedia]，访问日期 2026-08-12。
- 原文摘录："PostgreSQL version 9.4 includes support for JSON binary columns (JSONB), which can be queried, indexed and joined. This allows performance improvements by factors of a thousand or more over traditional EAV table designs. A DB schema based on JSONB always has fewer tables… That makes the DB schema easy to comprehend and SQL queries concise."
- 证据等级：🟡二手转引（Wikipedia 转引其脚注 [27] 的工程数据，未核到原始基准；仅作为"EAV 不划算"的方向性旁证，不作为 M09 性能定量依据）。

**论断 12（历史对照）**：Martin Fowler 的 Serialized LOB 模式（2003）早已把"对象图序列化进单个字段"当作关系库上处理复杂图的务实手段；JSONB 是它的"可查询、可索引"进化版——本轨道推荐的"开放对象整存单列"在模式史上是有根据的，而非临时设计。

- 来源：https://martinfowler.com/eaaCatalog/serializedLOB.html，[Serialized LOB，Martin Fowler，收录于《Patterns of Enterprise Application Architecture》（Addison-Wesley，2003）]，目录页访问日期 2026-08-12。
- 原文摘录："Saves a graph of objects by serializing them into a single large object (LOB), which it stores in a database field."
- 证据等级：🟢原文到手（模式原文）；该书出版年份 2003 为出版信息（凭记忆，不影响论断）。

### 2.6 属性图：开放不是自带属性，校验/审查仍需外部工具

**论断 13**：Neo4j 术语表把 schema 定义为"为节点与关系规定的属性存在性与数据类型"——属性图同样可以有 schema 约束；"开放字段"不是属性图的天然卖点，任意属性的 JSON Schema 级深层校验需要外部工具。

- 来源：https://neo4j.com/docs/getting-started/data-modeling/，[Data Modeling — Glossary，Neo4j 官方文档]，访问日期 2026-08-12。
- 原文摘录："schema: The prescribed property existence and datatypes for nodes and relationships."
- 证据等级：🟢原文到手。

**论断 14（PG 上图能力）**：Apache AGE 是"PostgreSQL 的图数据库扩展"，让 PG 用户在同一关系库里获得 openCypher 图查询——若红线 9 的触发条件（三跳以上遍历/实时交互查询）兑现，可在 PG 上解锁图查询而不必换库（引擎级对比属 T1）。

- 来源：https://age.apache.org/，[Apache AGE — Graph Database for PostgreSQL，Apache Software Foundation]，访问日期 2026-08-12。
- 原文摘录："Apache AGE™ is a PostgreSQL Graph database compatible with PostgreSQL's distributed assets and leverages graph data structures to analyze and use relationships and patterns in data."；"The goal of Apache AGE™ is to provide graph data processing and analytics capability to all relational databases."
- 证据等级：🟢原文到手（厂商官网，功能声明类证据；性能/成熟度不由此断言）。

### 2.7 开放但稳定审查的一手先例：FHIR、VC、Open Badges、xAPI

**论断 15**：FHIR 以 Resource 为基本单元 + 内建扩展机制覆盖核心集之外的内容——"核心封闭、扩展开放"是医疗互操作标准的选择。

- 来源：https://www.hl7.org/fhir/overview.html，[FHIR Overview，HL7 FHIR（v5.0.0: R5，当前发布版），FHIR Infrastructure Work Group]，访问日期 2026-08-12。
- 原文摘录："The basic building block in FHIR is a Resource. All exchangeable content is defined as a resource."；"There is a built-in extension mechanism to cover the remaining content as needed."
- 证据等级：🟢原文到手。

**论断 16（本轨道最关键的审查原则）**：FHIR profiling 明确要求"**必须能在不知道 profile 的情况下安全处理一个资源**"，并进一步说"知识必须显式写在实例里，而不是隐含在 profile 里"——这正是"开放但稳定审查"的判定标准：读者/审查者只凭实例本身就能安全读取与校验，扩展语义由实例携带。

- 来源：https://www.hl7.org/fhir/profiling.html，[Profiling FHIR §5.1.0.7 Limitations of Use，HL7 FHIR（v5.0.0: R5）]，访问日期 2026-08-12。
- 原文摘录："It must be safe to process a resource without knowing the profile"；"Another way of saying this is that knowledge must be explicit in the instance, not implicit in the profile."
- 证据等级：🟢原文到手。
- 对 M09 的直接推论：formation 开放对象必须自带"受控键 vs 扩展键"的可判别信息（如扩展键带命名空间/类型），任何读取器/审查脚本都不得依赖外部 schema 才能理解记录。

**论断 17**：W3C Verifiable Credentials 2.0 的证据对象结构——`evidence` 值可以是单个或一组对象，每个证据对象 **type 必填、id 可选**——是"证据引用必须可分类、可定位"的最小规范先例，可直接映射到 M09 证据边。

- 来源：https://www.w3.org/TR/vc-data-model-2.0/，[Verifiable Credentials Data Model v2.0，W3C Recommendation，2025-05-15，W3C Verifiable Credentials Working Group]。
- 原文摘录："If present, the value of the evidence property MUST be either a single object or a set of one or more objects. The following properties are defined for every evidence object: id — The id property is OPTIONAL… type — The type property is REQUIRED."
- 证据等级：🟢原文到手。

**论断 18（最小记录单位的一手先例）**：xAPI Statement 是学习记录行业验证过的原子断言：**必须含 actor、verb、object 三者**；Statement 不可变、预期永久保存，唯一撤销方式是 void（不销毁原 Statement，只标记其证据应被忽略；void 语句本身不可再被 void）；LRS 对核心属性严格拒绝 null/类型错误/格式不符，但对 extensions 的值不得拒绝（"LRS MUST NOT reject a Statement based on the values of the extensions map"），扩展语义由 IRI 控制者定义——"核心严格、扩展开放"的规范级范例。

- 来源：https://raw.githubusercontent.com/adlnet/xAPI-Spec/master/xAPI-Data.md，[Experience API (xAPI) Specification, Part Two: Data — xAPI-Data（1.0.3，master），ADL Initiative / Experience API Working Group，U.S. Department of Defense]，访问日期 2026-08-12。
- 原文摘录（多处）：
  - "A Statement MUST use "actor", "verb", and "object"."
  - "Statements are immutable (they cannot be changed)."
  - "Statements are expected to be permanent. The only way to undo a Statement within this specification is to void it. Voiding does not destroy a Statement, rather indicates the evidence in the Statement is to be disregarded."
  - "Any Statement that voids another cannot itself be voided."
  - "The LRS MUST reject Statements with any null values (except inside extensions)… where the wrong data type is used…"
  - "The keys of an extensions map MUST be IRIs. An LRS MUST NOT reject a Statement based on the values of the extensions map."；"The meaning and structure of extension values under an IRI key are defined by the person who controls the IRI."
- 证据等级：🟢原文到手。

**论断 19（断言/记录分层）**：Open Badges 3.0（基于 VC 2.0）确认分层模型——Assertion 是"关于成就的断言"核心单元（含 issuer、日期、results、evidence），CLR 是断言的集合包——即"原子断言 + 聚合记录"的规范级分层。

- 来源：https://www.imsglobal.org/spec/ob/v3p0/，[Open Badges Specification v3.0（Final Release，Document Version 1.4.5，Date Issued 2026-06-29），IMS Global（1EdTech）]，访问日期 2026-08-12。
- 原文摘录："Assertion: The core of both Open Badges and CLR is the assertion about achievement(s). Assertion properties are specific to one learner's achievement and specify metadata such as issuer, date of achievement, expiration data, as well as results and evidence that support the assertion."；"Comprehensive Learner Record (CLR): Set of assertions that can be packaged as a verifiable credential…"；摘要："This specification… aligns with the conventions of the Verifiable Credentials Data Model v2.0".
- 证据等级：🟢原文到手。

### 2.8 开放字段校验与 schema 演进的工具层

**论断 20**：JSON Schema 2020-12 把"断言（assertion）"与"注解（annotation）"分离，提供 `additionalProperties`、`unevaluatedProperties` 与 vocabulary/dialect 机制——可以表达"核心词汇封闭、扩展受控"的 schema，而校验与检索索引可各取所需。

- 来源：https://json-schema.org/draft/2020-12/json-schema-core.html，[JSON Schema: A Media Type for Describing JSON Documents（draft-bhutton-json-schema-01，2022-06-16），A. Wright / H. Andrews / B. Hutton / G. Dennis，IETF Internet-Draft]。
- 原文摘录："This specification defines JSON Schema core terminology and mechanisms… Other specifications define the vocabularies that perform assertions about validation, linking, annotation, navigation, and interaction."；正文含 "11. A Vocabulary for Unevaluated Locations / 11.3. unevaluatedProperties"、"10.3.2.3. additionalProperties"（注解影响 additionalProperties 与 unevaluatedProperties 行为）。
- 证据等级：🟢原文到手（注意：2020-12 目前仍是 IETF draft 状态，非最终 RFC——见第 5 节风险）。

**论断 21（代码侧 typed open record）**：Pydantic 的 `extra='allow'` 会把未声明字段保留在 `__pydantic_extra__` 中，且该字典可被显式注解以对额外字段做校验——"已知字段强类型 + 未知字段受控类型"在 Python 侧有成熟表达，可直接用于 M09 写入校验脚本。

- 来源：https://docs.pydantic.dev/latest/concepts/models/，[Models — Extra data，Pydantic 官方文档（v2，latest）]，访问日期 2026-08-12。
- 原文摘录："'allow': Providing extra data is allowed and stored in the __pydantic_extra__ dictionary attribute. The __pydantic_extra__ can explicitly be annotated to provide validation for extra fields."
- 证据等级：🟢原文到手。

**论断 22（类型级开放对象）**：TypeScript index signature 表达"不知道全部属性名、但知道值的形状"——开放对象在静态类型系统里同样有规范表达，可作为 M09 开放字段 schema 的类比与实现参照。

- 来源：https://www.typescriptlang.org/docs/handbook/2/objects.html，[TypeScript Handbook — Index Signatures，Microsoft TypeScript 官方文档]，访问日期 2026-08-12。
- 原文摘录："Sometimes you don't know all the names of a type's properties ahead of time, but you do know the shape of the values. In those cases you can use an index signature to describe the types of possible values."
- 证据等级：🟢原文到手。

**论断 23（schema 演进规则）**：Avro schema resolution 给出明确的读写 schema 演进规则：reader 缺 writer 有的字段 → 忽略该字段；reader 有而 writer 没有的字段 → 有 default 用 default，无 default 报错；字段按名匹配、递归解析——这是"开放字段随版本演进时，旧数据可读、缺值有默认、未知字段不炸"的机器可执行规则，可借鉴到 M09 版本化 schema 设计。

- 来源：https://avro.apache.org/docs/1.11.1/specification/，[Apache Avro 1.11.1 Specification — Schema Resolution，Apache Software Foundation]，访问日期 2026-08-12。
- 原文摘录："if the writer's record contains a field with a name not present in the reader's record, the writer's value for that field is ignored. if the reader's record schema has a field that contains a default value, and writer's schema does not have a field with the same name, then the reader should use the default value from its field. if the reader's record schema has a field with no default value, and writer's schema does not have a field with the same name, an error is signalled."
- 证据等级：🟢原文到手。

### 2.9 追加支撑：事件溯源与厂商立场

**论断 24（事件溯源）**：Fowler 事件溯源定义"所有应用状态变更都以事件序列存储"，事件日志可用于重建过去任意状态与时间点查询——append-only 个人记录（红线 9 当前形态）与 M09"不覆盖旧结论"在理论上同源；但 M09 是否需要"事件日志 + 物化当前视图"双份存储，属 T2/D3 的成本权衡。

- 来源：https://martinfowler.com/eaaDev/EventSourcing.html，[Event Sourcing，Martin Fowler，2005-12-12]。
- 原文摘录："Event Sourcing ensures that all changes to application state are stored as a sequence of events. Not just can we query these events, we can also use the event log to reconstruct past states…"
- 证据等级：🟢原文到手（Fowler 本人标注为 draft 性质文章，作为模式参考而非规范）。

**论断 25（厂商立场，低证据）**：MongoDB 官方对比页声称文档模型"无需事先声明结构、加字段零停机、不需要中央系统目录/ORM 更新"，并暗示 PostgreSQL 结构性变更需要跨团队协调——这是 MongoDB 的营销立场，只说明文档库在"灵活演进"维度的自我定位，不作为"文档库优于 PG"的结论依据。

- 来源：https://www.mongodb.com/resources/compare/mongodb-postgresql，[MongoDB vs PostgreSQL: A Comparison，MongoDB, Inc.]，访问日期 2026-08-12。
- 原文摘录："Developers do not need to declare the document structure beforehand, and new fields can be added with a simple write command. This eliminates the need for maintaining a central system catalog or updating an object-relational mapper (ORM), and is done without any downtime or system impact."
- 证据等级：🟡二手转引（厂商立场，营销对比页，非独立评测；仅用于说明文档库声称的收益，不采信其对比结论）。

## 3. 对决策点的输入（明确写到 Dx）

### D2（M09 个人记录存储形态：开放字段 + 证据边 + 未映射对象的可行方案）——本轨道主决策点

**推荐方案（首选）**：**关系骨架 + JSONB 开放字段 + JSON Schema 校验（pg_jsonschema + CHECK）+ 断言原子单位 + void/版本语义**。

- 表/结构划分建议（形态级，非最终 DDL）：
  - `formation_record`（闭环记录容器）：闭环 id、目标、路线/来源、总体诊断、未满足项、时间、版本；
  - `assertion`（原子断言）：断言 id、目标对象引用（M08 锚点或未映射个人对象）、`formation` jsonb（受控键：理解/应用/结构解释/心智模型/可提取性/干扰/迁移/直觉/缺口/适用条件 + 命名空间化扩展键）、条件、时间、版本、模型身份（实际执行模型 + 版本，非别名）；
  - `evidence_edge`（证据边）：from_assertion → 已结束闭环/具体表现/教学提示条件/原始过程位置，type + id + 引用（VC evidence 模式）；
  - `unmapped_object`（未映射个人对象）：暂存区，供后续锚定或去个人化候选（T3-2/T3-3 已覆盖其存储形态；晋升规则属产品/审查设计）。
  - 版本/更正：新断言 + void 边（xAPI 语义）；历史断言原样保留（红线 13；MongoDB Data Versioning 类比）。
- 支撑证据：论断 1–5（PG jsonb/GIN/CHECK/pg_jsonschema/RECURSIVE）、论断 15–19（FHIR/VC/OB3/xAPI 先例）、论断 20–22（JSON Schema/Pydantic/TS 工具层）、论断 10–12（EAV 否决 + Serialized LOB 历史）。
- 否决项：**EAV**（论断 10–11：pivot 代价 + JSONB 千倍级改善旁证）；不把**纯文档库**作为首选（论断 6–7：校验是补充控制而非默认，审查管道需自建；但其"历史原形保留"模式被吸收进本方案，见论断 8）。
- 备选方案（按接受度排序）：
  1. 若 D1 最终维持 JSONL+脚本（红线 9 现状）：采用等价形态——JSONL 记录固定顶层键 + 开放对象 + 写入脚本用 JSON Schema 校验（Pydantic `extra='allow'`，论断 21），"证据边/版本"以引用字段表达；本推荐的所有结构原则（核心封闭、扩展受控、断言原子、void 语义）不变，只是载体从 PG 表换成 JSONL+脚本。
  2. 若团队明确倾向文档库：MongoDB，使用"固定元字段 + 开放文档 + schema validation（可选严格段）+ Data Versioning 模式"；需自建审计/审查抽取管道（论断 6–9），并接受 validation 默认是"灵活"的立场。
  3. 属性图（Neo4j 等）不作为 D2 的开放字段载体：开放字段的 JSON Schema 级校验需外部工具（论断 13）；个人形成图的边查询若触发红线 9 条件，优先考虑 PG+`WITH RECURSIVE`（论断 5）或 Apache AGE（论断 14），图引擎整体对比交给 T1/T6。

### 对 D1 的交叉输入（一句话，不展开）
若 D1 选择 PostgreSQL，则 D2 的"开放字段 + 审查查询"可直接由 JSONB + GIN + CHECK 承载，无需额外引入文档库或图库；若 D1 维持 JSONL+脚本，D2 的推荐以"JSONL 等价形态"落地（见上）。

### 对 D3/T2、D4/T7 的交叉引用（一句话，不展开）
版本粒度与"事件日志 vs 物化视图"的成本权衡归 T2（D3），本文仅确认"历史原形保留 + void"的存储形态可行（论断 8、18、24）；规模单调增长的存储成本/迁移风险归 T7（D4），本文的"历史断言不迁移、原形保留"是 D4 方向 1/3 的技术前提之一，但不替 T7 下结论。

## 4. 与产品约束的冲突/张力

- **红线 9（当前存储 = append-only JSONL + 独立校验脚本；图数据库暂不选）**：本轨道**不推翻**红线 9。张力点：D2 首选方案以 PostgreSQL 为假设载体，若 D1 仍选 JSONL+脚本，则 pg_jsonschema/CHECK 不适用，需退化为"写入脚本 + JSON Schema 校验"的等价形态（见第 3 节备选 1）。已显式标注，不构成越界。
- **红线 4（锚点硬校验 = 逐字 grep -F，唯一硬校验）**：张力必须说明——JSONB/JSON Schema 只能做**结构校验**（字段类型、必填、枚举），不能替代锚点逐字 grep -F 校验；两者是正交的两条校验线，M09 写入链路必须同时保留 grep -F 硬校验。
- **红线 14（M04-02：开放字段必须可稳定查询与审查；摘要/标签只作索引，不得替代底层记录）**：本方案直接支撑（固定列 + JSONB 开放对象 + 断言原子单位 + 证据边），无冲突；"当前视图/索引摘要可重建、不得替代底层"与 xAPI"void 不销毁、extensions 开放"同构（论断 18）。
- **红线 13（M09 时间版本不覆盖旧结论）**：本方案以"新断言 + void 边 + 历史原形保留"支撑之（论断 8、18、24），无冲突；由此引出的规模单调增长（D4）交给 T7。
- **红线 16（跨学科命名空间治理刻意不决定）**：张力——xAPI 的扩展开放依赖"扩展键 IRI 由控制者定义"（论断 18），FHIR 的扩展机制同理；M09 的开放字段若完全无命名空间治理，会出现"同名扩展键语义漂移"风险。建议：技术侧先用"受控核心键 + 命名空间前缀化扩展键"守住可判别性（满足 FHIR"知识显式在实例"原则，论断 16），跨学科命名空间的正式治理仍按红线 16 留作解锁条件，不在本轨道决定。
- **红线 2/6/7/8/11/12/15**：与本轨道无直接冲突（红线 12 的"M09 锚定 M08"被本方案的 assertion→M08 锚点引用支持）。

## 5. 未决与风险

1. **多对象闭环的切分规则（产品未决，M04-02）**：本轨道给出"断言原子 + 闭环记录聚合"的技术形态（T3-4），但"一个闭环内多个对象/关系/个人结构如何切分断言、是否允许一条闭环记录跨多条断言"需产品负责人确认（M04-02"当前尚未解决的问题"、M09 审查问题 1/2/3）。技术侧能承诺的是：无论怎么切，原子单元满足可查询/可审查/可撤回三约束。
2. **pg_jsonschema 的定位**：非 PG 内核扩展（Supabase 维护/推广），JSON Schema 版本支持与长期维护风险需实测确认；PG 内核只保证 CHECK 语义（论断 3），不保证扩展可用。
3. **CHECK 内 JSON Schema 校验的性能**：每条写入执行一次 `jsonb_matches_schema`，M09 目前无实测规模（设计阶段），写入吞吐是否可接受需最小实验验证；对单学习者低频写入大概率可忽略，但不能凭推断下结论。
4. **JSON Schema 2020-12 规范状态**：仍是 IETF Internet-Draft（draft-bhutton-json-schema-01，2022-06-16，论断 20），未转 RFC；选型时应锁死实现（如 pg_jsonschema 支持的 draft 版本）并记录在案。
5. **扩展键语义治理缺失**：xAPI/FHIR 的开放都依赖"扩展键 IRI 控制者"机制（论断 16、18），M09 无治理机制（红线 16 刻意不决定）；先用前缀化命名空间兜底，长期治理待解锁。
6. **厂商立场来源**：论断 9（MongoDB vs PG）与论断 14（Apache AGE 官网）为厂商功能声明，只作方向参考，不作对比结论依据。
7. **xAPI 规范的"严格核心"代价**：xAPI 通过 LRS 拒绝 null/类型错误保证核心可互操作，但代价是 Learning Record Provider 侧的实现负担（规范原文明示部分校验"extremely difficult"）；M09 校验脚本需自己实现同等严格度，不能指望数据库代劳全部。

## 6. 建议的下一步实测（可执行的最小实验，按可判定性优先）

1. **PG 写入即拒绝验证（判定 CHECK+JSON Schema 组合是否可用）**
   - 输入：PG 临时库 + pg_jsonschema；`formation_record` 表带 `CHECK (jsonb_matches_schema('<schema-v1>', formation))`；schema-v1 定义 10 个受控键（可空）+ `additionalProperties: false`。
   - 判据：合法 payload 插入成功；非法类型/未知键插入被拒并返回明确报错（对照 Supabase 文档示例）。
   - 通过/失败：通过 = 两条路径行为符合预期；失败 = 报错信息不可定位到字段，需换校验策略。
2. **真实闭环样本编译断言（判定最小记录单位是否可用）**
   - 输入：取 1 个已结束闭环（M08 锚点 + 总体诊断 + 证据引用），按"闭环记录 + 2–3 条断言（不同对象/维度）"编译成 JSON；分别查询：按锚点、按维度（formation.迁移 存在性）、按时间范围。
   - 判据：三类查询全部可由 SQL/jsonpath 完成且结果可逐条回溯到证据边；审查脚本能列出"某断言用了哪条证据、哪个模型版本"。
   - 通过/失败：通过 = 查询与审查双向闭环；失败 = 暴露结构缺陷（如断言粒度不当导致证据引用歧义）。
3. **更正/撤回（void）语义实验（判定"不覆盖旧结论"的落地代价）**
   - 输入：对 1 条断言写入更正（新断言 + void 边指向旧断言）；查询"当前有效断言"与"全部历史断言"两条视图。
   - 判据：旧断言物理存在且可查；当前视图不含被 void 断言；void 语句本身不可被 void（按 xAPI 语义）。
   - 通过/失败：通过 = 语义正确且查询代价可接受；失败 = 需评估物化视图/索引补偿（此步的粒度权衡交 T2）。
4. **JSON Schema 核心封闭 + 扩展开放草案（判定 schema 演进路径）**
   - 输入：schema-v2 增加一个受控键、允许一个前缀命名空间扩展键（如 `x-` 前缀），验证旧数据（schema-v1 写入）在 v2 读取规则下的校验/迁移成本（对照 Avro resolution 规则，论断 23）。
   - 判据：v1 数据在 v2 规则下可读、可校验；未知扩展键不被静默丢弃。
   - 通过/失败：通过 = 演进规则可执行；失败 = 需引入 schemaVersion 字段（MongoDB Schema Versioning 做法，论断 8）。
5. **WITH RECURSIVE 遍历粗测（判定关系表能否承载个人形成图）**
   - 输入：用实验数据（如 M08 522 节点/1433 边规模的个人形成子图）做 2–3 跳递归查询 + `SEARCH BREADTH FIRST`。
   - 判据：查询在单学习者规模下延迟可接受（秒级内）；环检测（CYCLE）生效。
   - 通过/失败：通过 = 关系表可承载；失败 = 该负载移交 T1 评估图库解锁条件（红线 9）。
