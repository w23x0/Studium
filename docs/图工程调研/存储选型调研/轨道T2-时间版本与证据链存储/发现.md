## 0. 一句话结论

M09 时间版本机制应采用「**append-only 不可变闭环记录 + 双时间戳（valid time=掌握区间 / transaction time=写入时间）+ 墓碑/重定向指针（retracted_at / superseded_by）**」的 bitemporal 简化形态：复检/遗忘/重新掌握各写新版本且旧版本永不覆盖，更正/撤回/回退全部以「追加新记录」表达，当前视图由底层记录按需派生（可另建派生索引）——**不需要**为此引入图数据库、完整 bitemporal 引擎或 CQRS，现有 append-only JSONL + graveyard 骨架可直接承载，最小版本单位为闭环级记录，证据事件走证据边。

## 1. 必须回答的问题逐条回答

### 1.1 T2-1：bitemporal 建模如何映射「M09 不覆盖旧结论 + 复检/遗忘/重新掌握」

**定义锚点**（证据 A，见 §2.1–§2.3）：
- **valid time（有效时间）**：事实在建模现实中为真的时间，通常由用户/业务提供。在 M09 中对应「这个掌握结论在现实中的成立区间」——何时形成、何时被复检覆盖、何时遗忘导致区间关闭。
- **transaction time（事务时间）**：事实存入数据库并「当前可检索」的时间；系统生成、按事务序列化顺序、不可更改。在 M09 中对应「这条记录何时被写入（asserted_at）、何时被撤回/更正」——审计轴。
- 两轴正交：DB 的「观点时间」（何时知道）与「现实时间」（何时为真）相互独立；单轴系统（只有 TT 的 AeonG、只有 VT 的 T-GQL）无法同时表达「更正」和「被更正事实的原有效时间」（Anselma 2025，证据 A）。PostgreSQL 19 官方文档同样定义：application time=外部世界的历史、system time=数据库自身的历史，两者都做叫 bitemporal（证据 A）。

**到 M09 的映射**（本轨道推断，基于上述定义 + M09 红线，红线见 §4）：

| 学习者事件 | bitemporal 语义 | 存储动作（append-only） |
| --- | --- | --- |
| 闭环结束、形成结论 | valid 区间起点 + asserted_at | 写入 v1：`valid_from=闭环完成时间, asserted_at=写入时间` |
| 复检（重新确认） | 新区间/新版本 | 写入 v2：v1 加 `superseded_by=v2`，v2 带新 valid_from |
| 遗忘/提取失败 | 旧结论 valid 区间关闭 | v1 补 `valid_to`（最后可提取时间），或写入 v3 记录「掌握状态降低」新版本；旧版本不删 |
| 重新掌握 | 新 valid 区间 | 写入 v4 新版本，新区间 |
| 更正（学习者更正/证据推翻） | 旧事实关闭 + 新事实 | v1 标 `superseded_by=v5`，v5 为新记录；v1 留档 |
| 撤回（已写入记录的撤回） | 墓碑 | v1 标 `retracted_at` 并写 graveyard；默认视图排除，历史可查（见 1.4） |

**要点**：bitemporal 的标准建模就是「同一实体多条 valid 区间并存」——PostgreSQL 19 temporal table 允许同一实体多行，只要区间不重叠，用 `PRIMARY KEY (..., valid_at WITHOUT OVERLAPS)` 强制（证据 A）。因此技术侧完全容纳 M09「不覆盖旧结论」红线：旧区间与新区间并存、零覆盖写；M09 红线使该建模从「可选」变为「强制」。transaction time 轴则保证任何 as-of 审计查询（某时刻系统里有什么结论、何时被撤回）都可回答。

### 1.2 T2-2：event sourcing / append-only 与图数据的结合先例？CQRS/物化视图是否必要？

**事件溯源定义**：把「对应用状态的每次变更」捕获为事件序列，当前状态可由此重放派生；官方记录可以是事件日志或当前状态（或两者并存）；版本控制系统被 Fowler 明指为事件溯源案例（证据 A，§2.8）。Fowler 还指出纠正过去事件=逆转错误事件+重放后续事件（这正是「回退」的事件溯源语义）。

**图数据 + 时间/append-only 的工程先例**：
- Datomic：不可变 datoms + 事务时间，`as-of`/`since`/`history` 查询，「当前视图不读历史、历史再多零代价」（证据 A，§2.4）。
- TPGM+/BiTeGra（Rost 等 2021）：bitemporal property graph 模型 + 基于 RDBMS 的原型——顶点/边/属性各自带 VAL_TIME 与 TX_TIME 区间并配完整性约束；属性变化若建模不当会产生大量重复（证据 A，§2.6）。
- Anselma 等 2025：「Delta+anchor」=周期完整版本(anchor)+相邻变更(delta)，在 Memgraph+RocksDB 上实现，TT 支持仅 9.74% 性能退化（证据 A，§2.7）。
- GraphAware TimeTree：把时间建模为图内一棵按需构建的树（year→month→…→millisecond），可挂事件节点（证据 A，§2.11）。
- 一般理论：Kreps 的 log=append-only、按时间全序的记录序列（证据 A，§2.10）；Helland 的「会计不用橡皮擦」=append-only + LSM + tombstone，写侧留事实、读模型按需派生（证据 A，§2.9）。

**CQRS / 物化视图是否必要**：
- **CQRS 非必要**。Fowler（CQRS，2011）原文："for most systems CQRS adds risky complexity"；CQRS 只适合复杂领域或读写负载悬殊场景，多数系统用同一模型读写更简单（证据 A，§2.8b）。
- 「当前视图从底层记录派生」在本项目有两种实现：① 查询时由脚本派生（当前 JSONL+grep 模式的自然延伸）；② 按需维护派生索引/物化视图（sqlite-history 的「主表 + 历史表」双表形态即是，证据 A，§2.14）。两者都是可选的读侧优化，不改变权威存储=append-only 记录。Datomic「当前视图零历史代价」证明当前视图可独立于历史实现高效（证据 A，§2.4）。
- 结论：事件溯源/append-only 是 M09 的正确骨架；CQRS 不必引入；物化视图作为待实测的可选优化（§6 实验 2）。

### 1.3 T2-3：版本化知识库/内容寻址的粒度与查询代价对比

**先纠正名称**：问题清单 T2-3 所写「datasette-version-history」经核实**不存在**（PyPI 404、GitHub 搜索 0 结果，2026-08-12 核验）；实际对应项目为 Simon Willison 的 **simonw/sqlite-history**（及 sqlite-history-json）。下表按实际项目对比。

| 方案 | 版本粒度 | 历史/版本查询代价 | 去重/验证 | 与本项目的契合点 |
| --- | --- | --- | --- | --- |
| Git 对象模型（内容寻址） | 文件内容(blob) + 整树快照(tree) + 提交(commit)，commit 引用 parent 成链 | 任意历史点=直接取快照；checkout 需物化；未变内容不重复存 | 内容哈希去重 | 「内容寻址 + 父引用版本链」的语义模板；粒度（文件/树）大于 M09 记录粒度，适合整体快照场景 |
| nanopub + trusty URI | 最小可发布断言（单图块，自包含 assertion+provenance+pubinfo） | 验证=沿 trusty URI 递归重算哈希；检索依赖索引/网络 | 哈希内嵌 URI；可验证范围=整棵引用树 | 证据链可核性的最强先例；M09 每条记录可仿「自包含 + 可验证引用」 |
| DVC | 文件/目录数据集版本 | 元数据(.dvc 占位文件，含 md5)进 git、内容存 cache/remote；checkout 按需拉取 | 内容寻址到 cache，git 版本化元数据 | 「元数据与内容分离」分层先例；本项目单条记录很小，通常不需要 |
| sqlite-history（simonw） | 行级版本（触发器自动记录 INSERT/UPDATE/DELETE 到 `_表_history`） | SQL 直接查历史表；`_version` 单调递增、`_updated` 毫秒时间戳、`_mask` 位掩码（-1=删除）；sqlite-history-json 用 json_patch 存列级 diff 并 restore 到任意版本/时间戳 | 每表一份历史表，触发器写放大 | 与 M09「记录级版本 + 墓碑」最接近的行级工程实现 |
| TerminusDB | 图文档库级版本（schema versioning、JSON-LD 文档、分支/合并） | 时间旅行/分支查询内建 | 文档级版本化 | 图数据库形态的版本化先例，但引入全套引擎，与红线 9（图数据库暂不选）冲突 |
| IPFS 内容寻址（CID） | 块/文件级 | CID=哈希定位；验证完整性/去重/免信任 | 哈希即地址 | 只提供内容寻址底层，无版本语义 |

**粒度结论**：版本粒度由「需要回查的最小语义单位」决定，不由存储技术决定。快照式（Git）=任意历史点 O(快照大小) 直取、空间大；事件/delta 式（事件溯源、sqlite-history-json、delta+anchor）=存储省、审计强、回查需重放。M09 的版本单位取「闭环级记录」（见 1.5）。

**查询代价要点**：Datomic「当前查询零历史代价」（证据 A）；PostgreSQL 19 temporal PK `WITHOUT OVERLAPS` + GiST 给出「valid 区间唯一 + 区间检索」的现成索引语义（证据 A）；内容寻址（Git/trusty URI/IPFS）的代价在「验证/物化」而非「存储」——验证需重算哈希或递归引用树（trusty URI「可验证范围=整棵引用树」，证据 A，§2.12）。

### 1.4 T2-4：更正/撤回/回退三种操作的存储语义与工程先例

统一原则：**三者都以「追加新记录」表达，被操作对象永不物理删除**（Helland「会计不用橡皮擦」；nanopub「you can never edit nor delete it」；Git revert=新提交反转旧提交；ICMJE「归档所有先前版本」——均证据 A，§2.9/§2.13/§2.15/§2.16）。

| 操作 | 语义 | 工程先例 | M09 落地 |
| --- | --- | --- | --- |
| **更正**（correction/amendment） | 保留原记录 + 新记录；原记录标记被替代（superseded_by），引用/搜索指向最新版本 | ICMJE：发布 correction notice 详细说明变更并引用原文、**归档所有先前版本**、旧电子版显著标注存在更新版本、引用指向最新版本（证据 A，§2.16）；nanopub：不可编辑不可删，只能发新声明（新版本即更正载体）（证据 A，§2.13） | v1 标 `superseded_by=v2`，v2 写新内容；**不采用** git commit --amend（改写最近提交、旧对象仅 reflog 可能保留）语义（证据 A，§2.15） |
| **撤回**（retraction） | 保留原记录 + 写撤回声明/墓碑；默认视图排除，历史可查 | nanopub：「A nanopublication is persistent, you can never edit nor delete it. You can however retract…by publishing a new nanopublication that states that you retract the original publication.」；「有效撤回默认不再出现在搜索结果」（证据 A，§2.13）；Datomic 官方示例：把「已知坏事务号」集合用于 filter，视图层排除错误 datom、存储层保留全部历史（证据 A，§2.5） | v1 标 `retracted_at` + 撤回原因 + 撤回声明引用；写 graveyard（红线 10）；默认视图=排除 retracted、历史视图=可见。**注意**：这是「已写入记录的撤回」（M04-02 待确认 5），与 M15 状态记录撤回权无关 |
| **回退**（rollback/revert） | 把状态恢复到某历史版本 = 写一条新的「回退事件」指向目标版本；中间版本保留 | Git revert：给定已有提交，创建新提交反转其变更并保留历史（证据 A，§2.15）；Fowler 事件溯源：纠正过去事件=逆转+重放（证据 A，§2.8）；sqlite-history restore=从历史表重建目标版本，重建是派生动作不删历史（证据 A，§2.14） | 写回退事件 `revert_to=v_k` + 新 asserted_at；当前视图指向 v_k；历史链 A→B→C+回退事件完整保留 |

**语义风险提示**：本项目语境中「撤回」最容易被误用为「删除」、「回退」最容易被误用为「物理回滚」；两者都必须以追加表达（§5）。

### 1.5 T2-5：时间版本最小保留粒度怎么定（M09 审查问题 4）

**判定框架**（本轨道推断，基于证据）：最小保留粒度 = **使「当前视图可从底层记录派生」成立的最小稳定写入单位 + 其时间事实**。粒度太细（每次诊断、每次交互）会把「运行过程」混入「长期个人知识」，违反 M09「只收已结束闭环结果」与「摘要/标签只作索引，不能替代底层记录」两条红线；粒度太粗（合并成一句话总结）则丢失证据链。

**结论建议**：
1. **版本主体粒度 = 闭环级记录**（一个已结束闭环对一个/一组 M08 对象形成的记录 = 一个版本）。依据：M09 审查单原文「已结束闭环是长期个人知识的稳定写入单位，可避免逐轮波动污染长期记录」（产品文档，证据 A）；M04-02「M04 判断闭环完成后作一次闭环级总体诊断」「M09 写入一次闭环级个人形成记录」（产品文档，证据 A）。
2. **更低粒度（每次复检证据、单次提取/表现）** 不参与版本主体，作为**证据边/附加事件流**保存在记录引用之下——M09 审查单「证据不是 M09 的一个层级，而是连接个人结论与已结束闭环、具体表现和原始过程的支撑边」。
3. **时间粒度**：用 valid 区间（range）而非逐时刻点。PostgreSQL 19 原文：「a table with application-time ranges/multiranges is equivalent to a table that stores application-time 'instants'… But such a table would contain far too many rows, so ranges/multiranges offer an optimization to represent the same information in a compact form」（证据 A，§2.3）——直接支持「版本用区间不用逐时刻」。Anselma delta+anchor 证明「完整快照 + 相邻 delta」可在恢复与存储间平衡（证据 A，§2.7）。chronon 定义表明时间粒度下限由业务语义决定而非存储（证据 A，§2.1）。
4. **复检/遗忘/重新掌握是否都形成新版本**：技术形态上完全可以且建议都形成新版本（append-only + 版本链天然支持）；但「每次复检是否都值得形成新版本」是产品语义问题（M09 审查问题 4 需产品负责人确认）。本轨道给出可同时承载两种答案的形态（版本主体 + 证据边两级），并把「复检频率高导致版本膨胀」标注为 D4（T7）的输入。

## 2. 关键发现

> 每条：论断 + 来源[URL, 标题, 作者/机构, 日期] + 原文摘录/要点 + 证据等级。

### 2.1 bitemporal 权威定义（valid/transaction time、chronon、bitemporal 区间）
- 论断：valid time=事实在现实为真的时间、通常由用户提供；transaction time=事实在库中当前可检索的时间、系统生成、按事务序列化顺序、不可更改；chronon=最小不可分解时间单位；bitemporal 区间=valid×transaction 二维区域。
- 来源：[https://www2.cs.arizona.edu/~rts/pubs/SIGMODRecordMarch94p52.pdf](https://www2.cs.arizona.edu/~rts/pubs/SIGMODRecordMarch94p52.pdf)（PDF）《A Consensus Glossary of Temporal Database Concepts》，Jensen/Clifford/Gadia/Segev/Snodgrass 等，SIGMOD Record 23(1)，ACM，1994-03。
- 原文摘录（按 PDF 文本转写）：「The valid time of a fact is the time when the fact is true in the modeled reality… Valid times are usually supplied by the user.」「The transaction time of a database fact is the time when the fact is current in the database and may be retrieved… transaction times cannot be changed.」「A bitemporal interval is a region in two-space of valid time and transaction time.」
- 证据等级：A。

### 2.2 Temporal database 综述（时间轴分类）
- 论断：时间轴分 valid/transaction/decision 三类；bitemporal=同时使用 valid 与 transaction 两轴。
- 来源：[https://en.wikipedia.org/wiki/Temporal_database](https://en.wikipedia.org/wiki/Temporal_database)《Temporal database》，Wikipedia，2026-08-12 访问。
- 要点：「Using one axis: valid time or transaction time」「Using two axes: valid time and transaction time」「Using three axes: valid time, decision time, and transaction time」。
- 证据等级：A（页面原文到手，属二手综述，仅作背景）。

### 2.3 PostgreSQL 19 temporal tables：application time + temporal PK + 区间压缩
- 论断：PostgreSQL 19（开发版，调研日已发 Beta 2）提供 application time 表（range/multirange 单列存储、temporal primary key `WITHOUT OVERLAPS`、GiST 索引、temporal foreign key）；system time 尚不支持、可用触发器/扩展模拟；区间表示是对逐时刻表的压缩优化。
- 来源：[https://www.postgresql.org/docs/19/ddl-temporal-tables.html](https://www.postgresql.org/docs/19/ddl-temporal-tables.html) PostgreSQL 官方文档 §5.7 Temporal Tables，PostgreSQL Global Development Group，2026-08-12 访问（页面标注「This documentation is for an unsupported version of PostgreSQL」，19 Beta 2，2026-07-16 发布）。
- 原文摘录：「Application time tracks the history of a thing out in the world, and system time tracks the history of the database itself. (A database that does both is also called bitemporal.)」「In principle, a table with application-time ranges/multiranges is equivalent to a table that stores application-time 'instants'… But such a table would contain far too many rows, so ranges/multiranges offer an optimization…」「PostgreSQL does not currently support system time, but it could be emulated using triggers, and there are external extensions that provide such functionality.」
- 证据等级：A（beta 文档，已标注）。

### 2.4 Datomic：不可变事务 + 事务时间 + 当前视图零代价
- 论断：Datomic 以不可变 datoms 存储，交易可 reify 为实体并带 `:db/txInstant`（可显式指定以导入已知历史时间）；提供 as-of/since/history 视图；「当前视图不读历史、历史再多零代价」。

## 3. 对决策点的输入

### 3.1 输入 D3（M09 时间版本机制：粒度、版本链、回退、遗忘/复检/重新掌握）

1. **存储形态**：延续 append-only JSONL + graveyard（红线 9/10），每条闭环记录增加时间版本字段。最小字段契约（推断，待实验 1 验证）：
   ```text
   record_id        # 单调递增或 UUID，版本唯一标识
   subject          # 锚点集合 / M08 对象引用（含对象版本引用）
   closed_loop_ref  # M04 编译来源引用（不可变闭环记录）
   valid_from       # 掌握区间起点（现实时间，闭环完成时间）
   valid_to         # 掌握区间终点，空=当前有效（遗忘/复检关闭时填写）
   asserted_at      # 写入时间（系统生成，不可改）
   superseded_by    # 可选：被哪个新版本替代
   retracted_at     # 可选：撤回时间（写 graveyard 时填写）
   prev_version     # 可选：版本链父指针
   ```
2. **版本链**：单调递增版本号 + prev/superseded_by 指针（Git commit 链语义，§2.15）；不物理覆盖（红线 13）。
3. **复检/遗忘/重新掌握**：全部形成新版本（红线强制），旧版本保留；「遗忘/提取失败」用 valid_to 关闭旧区间或写新版本表达（产品语义二选一，见 1.5.4）。
4. **回退**：写回退事件（revert 语义），不删中间版本（§1.4）。
5. **当前视图**：从底层记录派生（取最新非撤回版本）；可选派生索引（待实测）。
6. **不做**：不引入图数据库/完整 bitemporal 引擎（红线 9，无触发条件）；不引入 CQRS（§1.2）。

### 3.2 输入 D5（M08–M09 连接层：锚定、未映射暂存、晋升重新锚定、去个人化候选）

1. **锚定边版本化**：M09 记录对 M08 对象的引用带对象版本号/内容摘要 + asserted_at；锚点 `grep -F` 仍是唯一硬校验（红线 4），版本引用校验是新增校验面（§5.3）。
2. **未映射对象暂存**：同样 append-only，标记 `mapping_status=unmapped` + 来源闭环引用；不因暂无法锚定而丢失（M09 审查单问题 2 方向已定）。
3. **晋升后重新锚定**：不修改原暂存记录，写新版本/锚定记录并在原记录加 `anchored_by`/`superseded_by` 指针（与「不覆盖」一致）。
4. **去个人化候选管道**：候选=从 M09 记录派生的只读视图 + 来源引用（M04-02「M09 记录及其证据引用可作为候选依据」）；候选评审/晋升/退回事件本身追加记录，与 M09 历史链同构；去个人化是视图变换，不触碰底层记录。
5. **证据边**：每条 M09 记录的证据边指向已结束闭环记录（M04 编译产物，不可变引用），构成证据链；可选 trusty-URI 式内容哈希验证（§2.12，待实验 5）。

## 4. 与产品约束的冲突/张力

- **无实质冲突**：本轨道结论与红线 9（append-only JSONL、图数据库暂不选）、10（graveyard、不物理删除）、12（M09 只收已结束闭环）、13（时间版本不覆盖旧结论）完全兼容，并为它们提供理论支撑（bitemporal、事件溯源、撤回先例）。
- 张力 1（规模单调增长）：不覆盖 → 体积单调增长（红线 13 的直接推论，D4 归 T7）。本轨道只保证「版本机制与存储形态」与三方向兼容：三方向（内部历史区/移交 M01/两区分离）都可在「append-only 记录 + 派生视图」骨架上实现——区划只影响派生与归档策略，不改变记录不可变性。此为给 T7 的接口说明，不在本轨道作答。
- 张力 2（compaction 不可用）：Kafka 式 log compaction「保留最新、丢弃旧状态」（§2.10）与红线 13 冲突，明确排除。
- 张力 3（amend 不可用）：git commit --amend 式「改写历史」（§2.15）与红线 13 冲突；M09 的更正一律用新版本 + superseded_by（§1.4）。
- 张力 4（命名纠正）：问题清单 T2-3 点名「datasette-version-history」，该包/项目不存在；实际对应 simonw/sqlite-history（§2.14）。不影响调研结论，但合成阶段引用时请用正确名称。

## 5. 未决与风险

1. **完整 bitemporal vs 简化双时间戳**：TPGM+ 的完整性约束（边区间须含于顶点区间、属性区间须含于所在元素区间等，§2.6）对 JSONL 形态过重；是否需要在 M09 引入区间约束/校验，取决于未来「按有效时间回溯查询」是否成为真实需求。当前建议简化形态（valid_from/valid_to + asserted_at），标注为推断。
2. **复检是否总是形成新版本**：产品语义问题（M09 审查问题 4），技术形态可同时承载「每次复检=新版本」与「复检证据走证据边」两种答案；若每次复检都升版本，版本膨胀速度加快——这是 D4（T7）的输入。
3. **跨模块证据链一致性**：M04 日志→M09 编译→M08 候选的引用链 + 版本引用的组合校验尚未设计；锚点 grep -F 是唯一硬校验（红线 4），版本引用校验是新增面。
4. **语义风险**：「撤回=删除」「回退=物理回滚」是本项目最容易被误用的两个词；M04-02 已明确 M09 侧「撤回」=已写入记录的撤回（≠M15 状态记录撤回权），实现层必须用墓碑+撤回声明而非删除。
5. **派生视图与权威记录的一致性**：若采用派生索引/物化视图（如 SQLite 索引），需要重建机制（sqlite-history 的 restore 模式可作为参考，§2.14）；一致性用独立校验脚本保证（红线 9 模式）。
6. **证据等级说明**：Anselma 2025 为会议演示稿（非正式论文）；PostgreSQL 19 文档为 beta 版本页（§2.3）；Kreps 原文经 web.archive 存档获取（§2.10）；Wikipedia 为二手综述（§2.2）。均已标注，引用时勿升格。

## 6. 建议的下一步实测（可执行的最小实验）

1. **实验 1（版本字段契约）**：在 M08 现有 JSONL 工具链上为 M09 记录实现最小字段契约（record_id/valid_from/valid_to/asserted_at/superseded_by/retracted_at），写校验脚本 + 真 argparse/--dry-run/--only（红线 15）。判据：复检/遗忘/重新掌握三种写路径生成新版本；校验脚本可验证「同一对象同一时刻至多一个有效版本」；全程无覆盖写。
2. **实验 2（当前视图派生与索引对比）**：用 M08 实测规模（522 节点/1433 边/921 锚点）+ 模拟 M09 版本增长（×10/×100），对比「JSONL+grep/脚本派生」与「SQLite 派生索引（仿 sqlite-history 双表）」的查询延迟、磁盘占用、重建成本。判据：万级记录下两种方案给出数量级数字，据此决定是否引入派生索引。
3. **实验 3（撤回语义演练）**：写记录 → 写撤回墓碑 → 验证默认视图排除、历史视图可见、校验通过（红线 10）。
4. **实验 4（回退演练）**：A→B→C 三版本后回退到 B；验证 C 不删除、当前视图=B、历史链 A→B→C+回退事件完整。
5. **实验 5（证据链可核性，可选）**：对锚定边/证据引用加内容哈希（sha256）并实现递归验证脚本；验证与 grep -F 硬校验（红线 4）组合后的成本与误报（与 T4 协作，避免重复）。
