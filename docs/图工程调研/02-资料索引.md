# 资料索引

## 建议阅读顺序

### 1. Agent 工作流的基本模式

- [Anthropic：Building Effective AI Agents](https://www.anthropic.com/research/building-effective-agents)
  - 区分预定义工作流与自主 Agent。
  - 介绍提示链、路由、并行、编排者与工作者、生成与评估循环。
  - 核心提醒是从最简单的可用方案开始，只在结果证明有价值时增加复杂度。

### 2. 怎样把过程拆成节点、边和状态

- [LangGraph：Thinking in LangGraph](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph)
  - 从离散步骤、状态、节点和路由构造工作流。
  - 讨论不同错误的重试、回环、人工暂停和恢复方式。
  - 说明节点粒度与可观察性、恢复成本和测试边界的关系。

### 3. 什么时候需要图 API

- [Microsoft Agent Framework：Workflows overview](https://learn.microsoft.com/en-us/agent-framework/workflows/overview)
  - 对比普通函数式工作流与显式图工作流。
  - 顺序流程、简单循环和临时并行可以继续使用原生控制流。
  - 固定拓扑、扇出汇合、类型化消息路由和检查点更适合图执行模型。

### 4. 长期任务的持久化执行

- [Temporal：Workflow Execution](https://docs.temporal.io/workflow-execution)
  - 介绍事件历史、状态转换、重放、失败恢复和长期运行。
  - 它不是 LLM 专用框架，但为跨进程、跨时间的可靠工作流提供基础理论和实现参照。

## 正式研究

- [Language Agents as Optimizable Graphs](https://arxiv.org/abs/2402.16823)
  - ICML 2024 工作。
  - 将 LLM Agent 统一描述为计算图：节点处理数据或调用模型，边表示操作之间的信息流。
  - 同时研究节点提示优化和边连接优化，说明系统结构本身可以成为评估和优化对象。

- [Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)
  - 基于多个框架的大量执行轨迹，归纳系统设计、Agent 间失配和任务验证三类失败。
  - 它提醒我们：节点和边增加后，协调错误、验证缺失和误差传播也会增加。

## 新近社区资料

- [Awesome Graph Engineering](https://github.com/ChaoYue0307/awesome-graph-engineering)
  - 将图工程描述为对图结构 Agent 系统的角色、拓扑、交接、状态、证据门、可靠性和演化进行整体工程化。
  - 项目本身明确称“Graph Engineering”是新兴、非标准术语。
  - 可作为资料地图使用，不作为 Studium 的架构依据或效果证明。

## 阅读时的证据等级

| 类型 | 主要用途 | 不能单独证明什么 |
| --- | --- | --- |
| 官方框架文档 | 理解框架能力和作者建议的使用方式 | 不能证明该框架适合 Studium |
| 正式论文 | 理解方法、实验和已发现的问题 | 不能直接替代产品验收 |
| 工程案例 | 观察真实实现和运维问题 | 不能保证场景可迁移 |
| 社区文章或资源表 | 发现术语、案例和进一步线索 | 不能建立行业共识或技术决策 |

后续做技术选型时，应回到原始文档、正式论文、可运行实验和 Studium 自己的验收结果，不依据转载摘要或“路线图”直接决定。
