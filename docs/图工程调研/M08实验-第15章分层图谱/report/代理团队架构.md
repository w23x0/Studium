# 代理团队架构

本文件记录**团队怎么分层、每层为什么存在、并发与串行的边界在哪**。
产出内容本身在 `data/`，评判在 `report/audit-*`，本文件只谈组织方式。

## 一、为什么不能用一层代理

最省事的做法是：一个代理读完第15章，直接吐一张图。这条路会同时坏在三个地方。

1. **粒度会停在标题层**。一个代理为了覆盖 16 节，只能给每节留一两个节点，于是"定理15.13"变成一个不可分的黑箱——而学习者真正卡住的地方恰恰在黑箱内部（Gram-Schmidt 的哪一步用到了归纳假设）。
2. **它会给自己打分**。生产者和评判者同一个上下文，就没有独立判断，只有自我辩护。
3. **它会静默截断**。上下文压力下最容易被牺牲的是最后几节，而没有人会知道被牺牲了什么。

所以团队按**职责**分层，而不是按**章节**分片。分片只解决体量，分层解决的是"谁能反驳谁"。

## 二、五层结构

```
第 0 层  契约        SPEC.md（不是代理）
                     ├─ 关系词表 9+1 封闭、节点类型 4 封闭
                     ├─ 锚点规则（30–200 字符逐字连续子串）
                     └─ 各层 schema 与判死条件
                            │  每个代理开工第一件事是完整读它
                            ▼
第 1 层  抽取        A1(Apostol 63) ┊ S1(Strang 62)        ← 并行，互不可见
                     A2-s1/s2/s3（分节补抽）┊ A2-x2（习题反例 34）
                            │  L1 一旦机器校验通过即冻结，下游禁止重抽
                            ▼
第 2 层  纵向        向下：D1(81) → D2(80) → D3(69) → D4(54)   ← 严格串行
                     向上：L2-a ┊ L2-b ┊ L2-c（三视角）→ L3 …  ← 层内并行，层间串行
                            │
第 3 层  横向        H-in（章内兄弟辨析）┊ H-back（跨章回指）┊ H-cross（跨教材，产出 X 22）
                            │  三条线彼此独立，可完全并发
                            ▼
第 4 层  审计        A（正确性与归属）┊ B（抽象增益）        ← 成对、互不可见
                     覆盖每一层的产出；判决落 JSONL，由我执行
```

第 0 层不是代理，这一点是刻意的。契约必须是**静态文件**而不是提示词里的转述，否则十几个代理各自记住一个略有出入的版本，图就会长出方言。提示词与 SPEC 冲突时以 SPEC 为准，这句话写进了每一个提示词。

## 三、纵向为什么必须串行，横向为什么可以并发

**向下（D 层）串行**：D3 的输入是 D2 的节点。它要问的是"D2 这个节点还能不能再拆"，没有 D2 就无从提问。跳层并发只会得到一堆悬空的碎片。

**向上（L 层）层内并行、层间串行**：L2 的三个视角（同一验证套路 / 计数 / 正交性与最优性）刻意互不可见，因为**抽象是有视角的**——同一批下层节点从不同角度看会归成不同的类，而哪个视角更有解释力事先不知道。让它们互相看会收敛到第一个提出来的那个分类，多样性就没了。层间必须串行，理由同 D 层。

**横向三条线全并发**：H-in 只看章内、H-back 只看跨章引用、H-cross 只看跨教材，三者的输入集合不相交，没有依赖。

**审计与生产严格隔离**：审计代理被明令禁止读另一位审计的报告，也不得读旧实验目录（`M08实验-Apostol微积分卷1/`，第10章）。前者防止判决趋同，后者防止把上一章的结论当成本章的既有事实。

## 四、两把正交的尺子

每一层的产出都由**两个互不可见的审计**独立判，这是本架构最关键的设计。

| | 审计 A | 审计 B |
|---|---|---|
| 问什么 | 数学对不对？归属真不真？**锚点支撑不支撑它挂的那句断言**？ | 把这个节点删掉，学习者只凭 parent 能不能自己推出来？ |
| 死因 | 1 量词过度断言 / 2 编造归属 / 3 错误教材归属 / 4 数学错误 | 5 伪抽象或层级塌缩 |

两者**正交**，不是冗余：一个节点可以数学上无懈可击（A 判 KEEP）而仍然只是把 parent 换个说法（B 判 KILL）。本实验里出现过 28 个这样的节点，它们**不是判决冲突**，而恰恰是设计生效的证据。反过来也成立：一个节点可以很有增量而数学是错的。

单靠一把尺子的后果很具体：只有 A，图会长成一棵正确但全是复述的树；只有 B，图会长成一棵有洞见但引文挂错的树。

## 五、机器能查什么、不能查什么

这是本实验最重要的一条方法论发现，直接决定了审计 A 为什么不能被脚本替代。

`tools/verify_anchors.py` 用 `grep -F` 逐字比对，能证明的**只有**：引文是原文的未改动连续子串。它**证明不了**引文支撑得住它所挂的断言。审计 A1、A2、A3 三轮各自独立抓到实例，全部藏在 100% 通过机器校验的锚点集合里：

- 两个 D 层节点的锚点互相挂错；
- 一条指向 `apostol:theorem-15-7` 的 `origin: source` 边，evidence 引的是定理 **15.5** 的结论句；
- A3 在 D4 层 101/101 全通过的锚点里又挖出 5 处，并给出了失配的三种形态。

A3 的三型分类，决定了这件事有多少可以自动化：

| 形态 | 表现 | 可机械化？ |
| --- | --- | --- |
| A 变量位置错 | 引文讲的是相邻但不同的对象（把"第二变元可加"当成"第一变元线性"） | 不能 |
| B 借来的引文 | 引文其实属于另一个节点；线索是同一 `(file, quote)` 被多个节点同时引用 | **半可以** |
| C 终点冒充中间步 | 引文是作者写下的最终显示式，断言描述的却是作者从未写出的中间步骤 | 不能 |

只有 B 型做成了工具：`tools/check_shared_quotes.py`。它把每一个被 ≥2 处引用的 `(file, quote)` 连同各引用方的 statement 并排列出，写成 `report/共享引文清单.md`。**默认 exit 0**，因为共享引文多数合法——一句定义天然同时支撑概念节点、它的记号节点和它的直接推论；A3 手工看了 11 组，9 组合法、2 组漂移。所以它输出的是**人工审查清单，不是缺陷清单**。全图当前 840 个不同引文对，473 个被复用，其中 148 组涉及 ≥2 个不同节点，构成 form B 审查集。

**因此 "N/N evidence verified" 这个指标不得作为正确性保证呈现。** 它只覆盖"未被篡改"，不覆盖"锚点—断言吻合"。后者中 A 型与 C 型无法机械化，只能靠人（或独立审计代理）逐条并排读引文与 statement，永远需要一道人工判读。

机器该负责的是**它确实擅长的那些**：id 悬空、对称关系写两遍、关系词越界、层级环、成员引用越界、引文长度越界或跨行。这些由 `tools/check_graph.py` 与 `tools/check_layer.py` 全量拦。

## 六、抗中断设计

网关（`api.skiapi.dev`）在本实验期间持续不稳定：503 / 502 / ECONNRESET / 证书校验失败 / 600 秒挂死。三个代理曾在**首次写盘之前**被掐断，产出全部无法挽回。据此形成两条硬规则，现已写进每一个提示词：

1. **每完成 5–8 条就增量追加写盘**，不许攒到最后一次性写。被掐断时磁盘上必须是合法 JSONL（每行一个完整对象，不留半行）。
2. **宁可把一个大代理拆成两个窄范围代理**。范围越窄，单次存活概率越高，被掐断时损失越小。

被掐断后的处置是**等网关恢复再重发**，不加压重试。

## 七、我（编排者）保留的职责

不下放给代理的有三件：

1. **执行判决**。审计只写 JSONL 判决，改盘由我做。原因是判决本身也会错——本实验中审计 A 有一条指控挂在了错误的节点上（那句"从未调用公理1"的话在兄弟节点里，而 A 自己给了那个兄弟 KEEP），还有一条建议的锚点长 207 字符、超出 SPEC 的 200 上限。**每条判决都必须回原文独立复核后才执行**，偏离判决的地方要留记录。
2. **口径裁定**。例如 X 层的成员资格：只有**陈述该不变量本身**的节点才算成员，证明里用到的引理不算，必须改用 `requires` 边表达。这类裁定一旦下放，各代理会各写一套。
3. **台账**。所有被杀、被弃、未覆盖的东西都记进 `report/丢弃与未覆盖清单.md`，被杀节点原件留在 `data/graveyard/` 以便回溯。**静默截断是本实验明令禁止的行为**——报告可以说"这块没做"，不可以让它看起来像做过。

## 八、已知的架构缺陷

如实列出，不粉饰：

- **审计覆盖不均**。D2/D3/D4 通过了 A、B 双判，D4 的 A 判由 A3 补齐。D1、X、A2-x2、以及继承来的 A1/S1 底座的覆盖情况见 `report/丢弃与未覆盖清单.md` 第六节。
- **关系词表缺一个位置**。"本节点在第二个使用点上复用了那个节点的引理"这件事，9+1 个关系词里没有合适的：`requires` 在语义上是错的（它表示依赖关系的建立，而非同一结论的二次调用）。A3 报出的空缺，属待补契约。
- **L1 底座冻结的代价**。冻结换来了下游一致性，代价是底座自身的缺陷会被继承——而它是最早、在规则最不成熟时抽的。
- **`parent` 语义未定死**。有 7 个标了 `atomic: true` 的节点却挂着子节点。这暴露 SPEC 没说清 `parent` 边到底只表示"分解"，还是也兼表"从属"。属待补契约。
- **三视角 L2 之间的重叠没有前置约束**。靠审计事后发现重复，而不是靠设计避免。视角数一多，事后去重的成本会超过并行省下的时间。
