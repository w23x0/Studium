## 四 锚点集合与 sections 集合的不一致（若有）

**两个集合完全一致，无不一致。** 这是机器核过的：

```
集合 A = awk 取 anchors.tsv 中 file 含 15.05 的 node_id，去重 → 11 个
集合 B = awk 取 nodes.tsv 中 sections 含 15.05 的 id，去重 → 11 个
comm -23 A B → 空
comm -13 A B → 空
```

11 个 id 全部是 `apostol:cx-*`，全部来自 `data/nodes-CX2.jsonl:1–11`，
`nodes.tsv` 的 `node_type` 全为 `concept`、`parent` 与 `layer` 列全空、`n_anchors` 全为 2。
`anchors.tsv` 里 15.05 的锚点共 22 条 = 11 × 2，`has_nl` 全为 0，charlen 区间 35–167，全部在界内。
与反例层报告 §1 自报的「15.05：11 节点 / 28 边 / 22 锚点」的节点数与锚点数吻合。

**但有三处值得主控注意的次级不一致（不是 A/B 集合不一致）：**

1. **node_type 全为 `concept`，而这 11 个节点讲的都是具体的反例结构。**
   封闭词表里有 `example` 类型，`d:example-1-the-real-numbers-form-a-linear-space` 等
   15.03 的同类节点也用了 example。这 11 个是否应改为 `example` 是分类一致性问题，
   我**未核**其它 `cx-` 节点（15.09/15.12/15.16）的 node_type 是否也全是 concept，
   所以不给建议动作，只报出。
2. **11 个节点的 `parent` 与 `layer` 列全空**，`partof.tsv` 里也不出现。
   相应地 `exposure.tsv` 对它们的 `n_partof_desc`、T2、T3 全为 0（唯一例外是
   `cx-addition-reading-one-coordinate-from-each-summand` 的 T2=1，来自那条自反例边）。
   即这 11 个节点在 part-of 树上是**孤立点**。
3. **反例层报告 §1 说 15.05 有 28 条边，但 `edges.tsv` 里 ev_file 落在 15.05 的只有 1 条。**
   这不矛盾（其余 27 条是 `origin: model`、无 evidence，或 evidence 指向别的源文件），
   但意味着 15.05 的 28 条边中 **27 条没有本节的逐字依据**。报告 §6.5 已自认标注保守。
