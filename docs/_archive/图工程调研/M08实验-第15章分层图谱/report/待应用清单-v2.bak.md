# 待应用清单 v2

## 〇 本清单的产生方式与它的已知局限

本清单由只读裁决代理产出，**未改 `data/` 下任何文件**，也未运行 `tools/` 下任何脚本。
输入是 `report/待应用-提案/` 下 73 份提案。

**读法（决定了本清单的可信度上限）**：按简报要求，每份提案只读其「〇 结论速览」与明确标为
可执行 / 清单 / 修改 / 条文的小节，逐条推理**未读**。需要判某条张力时才单点回查。
因此：凡本清单标「已核」的，是我本轮在 `tmp_index/` 上重测过的；凡标「采信」的，
是照抄提案自报值、**我没有独立复现**。两者在正文里逐条区分，不要混读。

本轮我独立实测的项（全部在 `tmp_index/` 上，可复算）：
- 三个 L1 分组节点各自的第二条 `part-of` 指向（裁决 9 的承重事实）；
- 公理 2 锚点 = **175** 字符及其 **5 个持有者**；
- `origin` 字段分布：24 `model` + 9 `source` = 33（裁决 8）；
- `d:ten-axioms-listed-in-three-groups` 两条锚点的持有者数，与它作 dst 的 5 条边；
- A4 剥锚目标（`nodes-A2-x2.jsonl:2–6`）与 G1b 唯一载体（`:12`、`:18`）的 id 不相交（裁决 6）；
- `edges-D1.jsonl:106` 的 114 字符 evidence 有 8 个持有者。

### 已知局限（四条，都会影响结论强度）

1. **19 条 KILL 的死因判定本身，本清单未复核。** 与 G1d 一致：本清单做的是装配、排序、
   冲突消解，不重审 B2 的 KILL 判决。若某条 KILL 的死因是错的，本清单会把错误照序执行。
2. **G4 十六份完备性报告的 21 条补建缺口，本清单未逐条裁决**（见 §四）。它们要新建节点，
   与本轮「先改接再删」的执行序列正交，且 G4z 自报严重度 4 占 15 条。
3. **锚点是否**支撑**断言，本清单一条都没有独立验证。** 所有「引文支撑」类判断均采信提案。
   按盲区五型，这正是 grep 查不出的那一层，D 型（覆盖不足）尤其查不出。
4. **执行后 `check_graph` 是否通过，是推断而非实测。** 每步不变量由「悬空 id 只减不增」
   这条结构论证给出，我没有跑过任何脚本。§六 给的是必须重跑的命令，不是已跑过的结果。

### 裁决 1 —— A9 的两处反转：一条不成立、一条成立

**裁决：A9 的自我更正全部维持。** 即：`apostol:zero-element` 的「死因 6 → 0」**不成立**，
死因 6 维持；某分片的 **100 字符**锚点计数**是对的**，89 是另一条子串。

- 依据（zero-element）：G2e §1.2/§1.3 与 A9 更正三**结论一致**。G2e 逐条列了该节点的
  池 7 行（`pool.tsv`）与 TD 14 行（`pool-TD-excluded.tsv`），并指出上一轮用来归零的那条边上
  `apostol:zero-element` 是 **dst**，按四层定义属 TD、不入池。G2e 另加一层实测：句 2 的源行
  `15.03.md:19` 的 `n_sentence_end=4`，属多句行，**不得按行号做覆盖比对**（过报通道 b）——
  即便按行号看起来「覆盖了」，池内 15.03 的条数仍是 0。
- 依据（100 vs 89）：G2f §1.2/§1.3 **未沿用 A9**，用 Python `len()` + `in` 独立重测，
  得 A = 100（含 `EXAMPLE 3. `）、B = 89（`edges-D2.jsonl:85` 的边引文）、C = 79（节点锚点），
  100 − 89 = 11 = `EXAMPLE 3. ` 的长度。100 有两个互不依赖的测量来源，89 没有任何来源指向 A。
- 简报的「以有逐字实测的那一方为准」在此**不触发**：G2e、G2f 与 A9 三方一致，无分歧可裁。
- 死因编号：zero-element **6**（针对 statement 句 2）；100/89 一项 **0**（记账错）。
- 建议动作：zero-element **FIX**，且必须按 G2e A 案**同批**落两项——补 `15.03.md:19` 内一条锚点
  **并**补 `sections` 15.03。G2e 的关键耦合已核过并采信：**单补 `sections` 不能消死因 6**
  （sections 是元数据不是证据），单补会制造「sections 声称覆盖 15.03、池里查不到」的新不一致。
- 置信度：高。不确定点：G2e 新构造的那条 15.03.md:19 锚点字符数我**未实测**（采信 G2e）。

### 裁决 2 —— SPEC.md:53 与 :55 的矛盾，P05 是否消解

**裁决：P05 消解了矛盾，但留下两个缺口，本清单在 §三 一并补掉。**

- 矛盾确认（A3 §1 提出）：`:53`「至少 1 条」无条件成立时，`:55` 第二分支「找不到可逐字引用的
  依据 ⇒ … 或标 `origin: model` 并如实说明」的前提永远无法执行，是死条文。
- P05 的消解方式：把「无锚」从「找不到锚点」收紧为「**原理上不可锚**」，新增封闭词表字段
  `unanchorable`（`external-proof` / `negative-claim` / `derived-criterion`），
  并明文写「`origin: model` **不构成**无锚的凭据」。这一句把 A5 的授权与锚点下限**解耦**，
  矛盾消解成立。
- **缺口 A（P05 × P06 正面冲突，必须裁）**：P06 的 `NO_ANCHOR_NO_EXEMPTION` 豁免 2 写的是
  「`origin ∈ {model,mixed}` + 非空 `origin_note`」，**明确拒绝新增字段**；P05 与 A3 都要
  `unanchorable`。**裁决：采 P05/A3 的专用字段，否决 P06 的豁免 2。**
  依据是我本轮实测：`origin=model` 的 24 个节点里 **20 个有锚点、4 个无锚点**
  （`nodes.tsv` 第 7 列 + 第 6 列交叉）。既然 20/24 带锚，`origin` 与「可否无锚」正交，
  用 `origin` 当豁免会一次性授权 24 个节点无锚，而实际只有 4 个需要豁免。
  P06 被否决的理由不是它算错了（它的 4 个节点已带 `origin_note` 这一实测是对的），
  而是它选的判据**射程比它要豁免的对象大 6 倍**。P06 的其余部分（六类 FAIL、stdout 契约、
  「机器不判只能人工判」那一段）全部采纳。
- **缺口 B（P05 未处理）**：A3 §5.3 指出 `:72`/`:73` 的 `sections` 写 `["15.08"]` 而内容不在
  15.08 里。P05 的条文**已覆盖**这一条（「拿委托语所在的节号冒充内容所在的节号判死因 3」），
  但 P05 没有给这两个节点的落盘裁决。**本清单不裁**（见 §五 第 3 条），标为未完成。
- 死因编号：0（SPEC 条文缺陷，非图谱缺陷）。建议动作：**进 SPEC**，见 §三 R2、R5。
- 置信度：高（24/20/4 三个数我实测）。不确定点：`unanchorable` 落盘后 `verify_anchors.py`
  的补丁本清单只给条文、不给代码。
