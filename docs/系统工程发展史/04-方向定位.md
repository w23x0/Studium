---

## § 1 四层归属

同一个东西，四个圈层各有一个名字。

| 层级 | 方向名 | 代表工作 |
| --- | --- | --- |
| 最宏观 | **神经符号（Neuro-symbolic）** | LLM 管不确定的语义判断，代码管确定性的计算 |
| 学术 | **Code-as-Action / CodeAct** | CodeAct (2024)、Code as Policies (2022) |
| 学术 | **Agent-Computer Interface (ACI)** | SWE-agent (2024) |
| 工程 | **Context engineering** | Anthropic，2025-09-29 |
| 工程 | **Agent harness / scaffolding** | 各家 agent SDK、pi 本身 |
| 产品 | **Tool infrastructure** | MCP、PTC、Tool Search Tool |

### 1.1 ACI（Agent-Computer Interface）

SWE-agent 2024 年提出。核心洞察：

> 人和机器之间要设计界面（HCI），**模型和计算机之间也要设计界面（ACI）**。

**同样的模型，换个界面，成绩差一大截。**目录结构、报错信息格式、工具返回什么——都算界面设计。

**PTC 就是一次 ACI 的重新设计**：从「一次一个 JSON 调用」换成「工具是代码里的函数」。改的是界面，**模型没变**。

### 1.2 Context engineering

2025-09-29 Anthropic 给的正式命名。它比 prompt engineering 大一圈：

| | 管什么 |
| --- | --- |
| prompt engineering | 话怎么说 |
| **context engineering** | **上下文里到底装什么**——工具定义、工具结果、记忆、检索内容、历史压缩 |

PTC 是 context engineering 的一个手段。

## § 2 谱系

| 时间 | 工作 | 贡献 |
| --- | --- | --- |
| 2020 | RAG | 把外部知识**塞进**上下文 |
| 2022 | **Code as Policies**（Google） | LLM 写代码控制机器人——最早原型 |
| 2022 | ReAct | 推理-行动交替的循环 |
| 2023 | **Voyager**（Minecraft） | 写代码 + **把跑通的代码存成技能库** ← Skills 的祖先 |
| 2024 | **CodeAct** | 正式提出「代码当动作空间」优于 JSON 动作 |
| 2024 | **SWE-agent** | 提出 ACI 概念 |
| 2024-11 | MCP | 工具接入协议统一 |
| 2025-09 | Context engineering 命名 / Code Mode | 命名 + 工程化 |
| 2025-11 | **PTC / Tool Search / Skills** | 产品化 |
| 2026 | 正式文档 / 沙箱周期管理 | 基础设施沉淀 |

**注意 2022 → 2025 的三年空档**：想法早就有了，产品化晚了三年。

**原因是模型水位**：2022 年的模型写不出可靠的编排代码。三年后同一个想法才成立——这条规律可复用于判断其他「过早失败」的原型（见 `01-史线总表.md` §5 的 R3）。

## § 3 容易混淆的邻居

### 3.1 与 RAG：方向相反

```
RAG  ：怎么把更多资料塞进上下文        （inflow）
PTC  ：怎么让更少的东西进上下文        （outflow）
```

同属 context engineering，但一个往窗口里加，一个往窗口外赶。

### 3.2 与 prompt engineering：不是一回事

| | 改什么 |
| --- | --- |
| prompt engineering | 措辞（加一句「请小心」） |
| PTC | **信息通路的结构**（把工具搬到沙箱里） |

### 3.3 与 multi-agent / orchestration：手段与目的

多 agent 编排是「要干的事」，PTC 是「**用代码来干这件事**」的实现方式。

交叉点：

```python
results = await asyncio.gather(*[ask_subagent(q) for q in questions])
```

一旦这条成立，「把模型变成代码里可 `await` 的函数」与 Plan 9 把进程变成文件是同一思路的延续。

### 3.4 它不属于

| ❌ 不属于 | 理由 |
| --- | --- |
| 模型能力本身 | 不是训练问题，是 harness 层 |
| fine-tuning | 同上 |
| 产品/业务逻辑 | 是通用机制 |

✅ 属于**模型之外、但仍属于系统**的工程层。

## § 4 这个方向的中心问题

> **模型的上下文是有限的、昂贵的、还会变笨；但任务需要的数据是无限的。怎么调和？**

历史上三个答案，一个比一个激进：

| 答案 | 做法 | 局限 |
| --- | --- | --- |
| **不进上下文** | RAG / 检索 | 检索结果还是得塞进去 |
| **少进上下文** | 压缩、摘要、context editing | 信息**有损** |
| **根本不需要进** | **PTC**——代码在沙箱里处理完再交结论 | 需要沙箱；需要模型会写代码 |

**PTC 是第三个答案**，也是唯一**信息无损**的：原始数据一直在沙箱里躺着，模型随时可以再去读。

## § 5 门槛在哪

这条线的门槛不在模型，在**运行时能力**：

| 需要模型会的 | 现状 |
| --- | --- |
| 写可靠的编排代码 | 2025 年才够稳（2022 年不行） |
| 按需探索文件树 / 类型 | 天然会（训练语料里有） |
| 判断哪些数据不该进上下文 | 需要 prompt/训练引导 |

| 需要 harness 有的 | 现状 |
| --- | --- |
| 沙箱 | 技术成熟（45 年） |
| 工具→函数的转换层 | 已产品化 |
| 生命周期管理 | 已有（见 `02-三个底座.md` §2.4） |
| **权限边界** | ⚠️ **空白**（见 `05-推演与信号.md` §4） |
