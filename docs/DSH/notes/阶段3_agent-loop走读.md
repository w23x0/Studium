# 阶段3 · agent-loop 走读：一次 agent 运行的全过程

> 2026-08-15 · 源码精读第一站（正常话版）
> 目标：追踪「一次 agent 运行到底发生了什么」——从驱动到单步到工具调度，看懂 agent 设计架构的核心。
> 依据：`packages/core/agent-loop/src/agent.ts`（主循环）、`tool-calls.ts`（工具调度）、`docs/subsystems/core.md`。

## 0. 一个顶层模型：三层循环

agent-loop 是三个套在一起的循环，每层管一个时间尺度：

```
kick()   ← 最外层：只要还有活就再开一个回合
  └─ turn()   ← 中层：开/关一个回合，回合里跑若干单步
       └─ step()  ← 最内层：一次模型请求 + 它引发的工具执行
```

最外层核心就一句 `while (await this.turn()) {}`。退出条件：消息队列空 + 模型没有欠账（见第 4 节）。

## 1. 最小单位：step（单步）

一个 step = 一次模型请求 + 这次请求引发的 0 到多个工具执行。程序实际动作是固定的四步：

1. 把当前对话历史整理好，发给模型；
2. 模型返回一段文字，里面**可能夹带"调用某个工具"的指令**（比如 `read_file("foo.md")`）；
3. 有这种指令就去执行工具，拿到结果；
4. 记录下来，step 结束。

注意"0 个"：模型这次回复如果没带任何工具指令，这个 step 就只包含一次请求。

## 2. 中层：turn（回合）

turn 是一串连续的 step，从程序收到一条新的用户消息开始，到该停为止。停的条件（逐个检查）：

- **模型的某次回复里没有工具调用**——它把话说完了，不需要再查东西；
- 某个工具结果里带了"到此为止"的标记（代码里叫 `concludesTurn`）；
- 或者消息被拦截、请求出错、被取消。

所以一个 turn = 你问一件事，程序从第一次去问模型，到最后给出最终回答的整个过程。中间常常要经历好几轮"查资料 → 再问"。

## 3. 最外层：kick（驱动）

kick 就是代码里的外层 `while` 循环。一个 turn 跑完不代表整个任务结束（比如还有别的消息在排队）。这个循环负责：**回合结束后检查还有没有待处理工作，有就再开一回合，没有就退出**，agent 回到空闲状态。

## 4. 循环靠什么决定：就看最后一条回复

判断"这件事干完没"，只看模型最后一次回复里**有没有工具调用指令**：

- 有 → 没干完。执行工具，拿回结果，带着结果再去问一轮（这就是下一个单步）；
- 没有 → 没欠账，回合结束。

没有别的魔法。工具结果里的 `concludesTurn` 标记是另一个出口：让工具自己说"到此为止"。

## 5. session log：唯一正本（最重要的设计）

程序身边有一份日志。规则：**凡是可能影响以后对话的事，先落日志，再做**。

- 用户说了什么 → 记一笔（`user/message`）
- 模型回的每个字 → 逐字记一笔（`assistant/chunk`）
- 模型调了哪个工具、传了什么参数 → 记一笔（`tool/call`）
- 工具返回了什么 → 记一笔（`tool/result`）
- 回合开/关、单步开/关 → 都记一笔

关键：再次问模型时，**不是另存一份"对话记录"**，而是**翻开日志，把相关几页读出来，拼成对话**（代码里 `deriveMessages()`）。日志是唯一正本。

好处：**日志永远跟真相一致**。程序崩溃重启，翻开日志一切可还原；界面显示聊天记录、续接对话、统计用量，全部读日志。不存在"日志一套、实际另一套"的分裂。架构文档里那条 `model-visible ⟺ logged`（模型能看到的必定在日志里）就是这条运行时结构的表达。

## 6. 工具并行：同时跑，但按序记账

如果模型一次要求调多个工具：

- **执行可以同时进行**（省时间）；
- 但**记回日志时，严格按模型给出的顺序记**——哪怕后一个工具先完成，日志里也是前一个的结果写在前头。

为什么？因为日志要永远"读起来像正常对话"，对话是有顺序的。这样任何时刻读日志重放，都是连贯的。取消时也一样留痕：没来得及启动的工具调用，会补一条"未执行（已取消）"的结果，保证日志完整。

## 7. 瀑布（waterfall）：一串排队的监听函数

某些关键动作前，程序不是直接做，而是**把数据交给一串函数，让它们一个个过目**：

- 每个函数按注册顺序执行，拿到当前数据，能做三件事之一：
  - **不动，传给下一个**（数据原样交给链里下一个函数）；
  - **改了再传**；
  - **不传，直接给结果**（拦截，链终止，用它的结果作为最终结果）。
- 程序拿到最终结果，才继续往下做。

例子：真正发请求前触发 `agent/request` 瀑布。插件可以返回不同的模型/参数（那成了实际请求），也可以决定"别发了"。名字来源：数据像水从第一个流到最后一个，传下去 = 水往下流，不传 = 堵住。

## 8. 状态与取消

- **状态**：agent 只有两个可观察状态——`idle`（没干活）和 `running`（在跑）。翻转时广播 `agent/status`。中间有 `maintenance`（后台维护任务），对外算空闲。
- **取消**：每个回合带一个"停止信号"。程序**只在它自己选定的检查点检查**："有人要求停止吗？"有就干净停在这，并记下原因（代码里 `signal.throwIfAborted()` 出现的位置就是这些检查点）。这叫协作式取消——哪里能安全停，由代码自己决定。

## 9. max-tokens 粘性

如果任何一个单步顶到 token 上限（模型没写完被截断），回合最终结果记为"触到上限"。之后就算有单步正常完成，**也不能把结果改回"正常完成"**。一旦触顶就是定论，让你能看出"这回合其实没正常收尾"。

## 10. 四个扩展点（全部"改行为"位置）

插件不改循环本身，只在四个关口挂监听：

| 关口 | 类型 | 插件能做什么 |
| --- | --- | --- |
| `agent/pre-step` | 瀑布 | 改写或拒绝将要进入单步的消息 |
| `agent/request` | 瀑布 | 替换请求配置（换模型/参数） |
| `agent/request-error` | 瀑布 | 决定请求失败后要不要重试 |
| `agent/turn-stopping` | 串行 | 回合关门前叫停，塞新指令续命 |

这就是仓库约定 "Plugins, not loop changes"（新行为挂瀑布，不动循环本身）的落地。

## 11. 怎么读这种代码（通用技能）

1. **先找最外层循环，画调用树**——`kick → turn → step`，别从构造函数开始读。
2. **看 append 调用**——在"日志即权威"的架构里，"程序往日志写了什么"比"改了什么变量"更重要。
3. **看 waterfall / serial 调用**——这些是留给插件的口子，也是架构的分层线。
4. **看 `throwIfAborted()` 位置**——它出现的地方就是"这里可以安全停下来"。
