# 阶段1 · 设计点总览：DSH 真正值得学的三件事

> 2026-08-15 · 主线笔记（论文 §1 + §3 摘要层面的提炼）
> 这是整个 DSH 研究的中心；其余笔记（插件树、loop、工具流水线）都是这三个设计点的零件。
> 依据：论文《A Programming Paradigm for Spatiotemporal Composability》摘要与引言、Cordis Primer、DSH 架构文档。

## 设计点一：总目标——自进化的 harness

论文 §1.2.2 的动机场景：**未来的 agent harness 会一边持续服务请求，一边生成并部署对自己组件的修改**（换工具、换插件、改循环行为）。

- 对比：多数 agent 框架解决"怎么跑好任务"；DSH 解决"**怎么让系统自己安全地改自己**"。
- 为什么难：修改持续发生、缺少人工监督。每次自我修改要是必须重启进程丢状态，累积不可用不可接受；更糟的是，一个错误的自我修改可能弄坏"用来恢复它的那个进程"本身。
- 这就是 harness 时代和 framework 时代的本质区别。

## 设计点二：核心理论——动态组合的两个维度

要支持"运行中改自己"，必须有**动态组合**（运行时加载/卸载/重配组件）。两个正交难题，论文形式化：

### 时间维：可回滚副作用（revertible effects）

- 问题：组件被移除时，它做的**所有改动必须彻底回滚**——注册的事件、占的资源、改的状态，全部还原。
- 手段：每次上下文变换携带**逆变换**，由运行时追踪；组件移除时按逆变换回收。
- 代码对应：**每个注册返回 disposer（撤注册函数）**；`ctx.effect()` / `ctx.on()` 的返回值即逆。插件树的 HMR 靠它做到热卸载不残留。

### 空间维：反应式 coeffect（reactive coeffects）

- 问题：组件之间的依赖要能**声明、发现、响应**——依赖出现、消失、换身份时自动协调。
- 手段：组件按自己的 coeffect 规格声明"我需要什么上下文"；上下文变化时按规格通知组件。
- 代码对应：**`inject` 声明服务依赖**；加载顺序由服务可用性驱动，不是手动排 boot 顺序；`settings`/`credentials` 配置**热更新**无需重启。

## 设计点三：架构推论——没有特权核心，一切皆插件

- 因为连"核心"都要能被热替换，所以模型适配器、工具注册表、会话日志、**agent 循环本身**都是插件行。
- 扩展点 = 事件/瀑布（`agent/pre-step`、`agent/request`…），不是改循环。仓库约定 "Plugins, not loop changes" 由此而来。
- 系统由什么组成 = **一份数据（YAML 配置树）**，不是代码。改系统 = 改配置/换 bundle。

## 怎么验证这个设计是真的（而不是包装）

读代码时的检验标准：
1. 任意一个"核心"插件（如 agent-loop）能不能从配置替换？能 → 无特权核心是真的。
2. 任意注册是否都有逆（disposer），卸载是否干净？是 → 时间维是真的。
3. 依赖是否靠声明而非手动排序？是 → 空间维是真的。
4. 配置改动能否热生效？能 → 动态组合是真的（不是重启式假动态）。
