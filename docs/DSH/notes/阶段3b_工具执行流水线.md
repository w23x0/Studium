# 阶段3b · 工具执行流水线：一个工具调用要过五道检查

> 2026-08-15 · 源码精读第二站（正常话版）
> 目标：看清「模型说调工具」到「工具结果记回日志」之间发生了什么——权限、策略、超时、结果修正怎么夹进来。
> 依据：`packages/core/tools/src/index.ts`、`docs/subsystems/tools.md`。

## 0. 一句话模型

模型说"调用 `read_file`"之后，这个调用**不是直接执行**，而是过一道固定流水线。五道关卡，每道都有名字和职责：

```
pre-execute  →  守卫  →  execute  →  post-execute  →  result
 (预检查)      (兜底)    (执行包装)    (结果处理)       (最终广播)
```

## 1. 第一道：pre-execute（预检查，瀑布）

工具执行前，先问："这个调用可以放行吗？"插件们排队过目，最终三个决定之一：

- **允许**（allow）——放行；
- **拒绝**（deny）——带着原因拦截；
- **问用户**（ask）——跳出来请求批准。用户批了才继续；没有批准通道、或用户不批，都按拒绝处理。

这是"权限批准"落进来的地方。

## 2. 第二道：守卫（guards，只减不增）

一道额外的策略层，设计得很讲究：**守卫只能拒绝，不能批准**。

- 守卫返回一个"拒绝原因" → 这个调用被拦；
- 守卫什么都不返回 → 维持原样（等于没意见）；
- 但守卫**永远不能**把一个已经被拒的调用重新放行。

为什么这样设计？因为这样**监听器之间的顺序就无关紧要了**——不管谁先谁后，谁都不能把"拒绝"翻回"允许"，策略只会越收越紧，不会越放越松。

## 3. 第三道：execute（执行包装，瀑布）

真正调用工具函数前后"围着转"的事在这一关：**超时、重试、计量**。比如超时策略包在外面——工具跑超了就砍掉。

工具函数本体在这一关执行。

## 4. 第四道：post-execute（结果处理，瀑布）

工具返回结果后，问："这个结果行吗？"三个决定：

- **接受**（accept）——收下结果；
- **替换**（replace）——换成别的内容或值（二选一，不能同时换）；
- **拦截**（block）——把结果变成错误，附上纠正反馈（比如"这样不对，改成那样"）。被拦的结果以"错误"形态回到模型那边。

## 5. 第五道：result（最终广播）

结果到这里已经**冻结**（深度冻结，不可再改），广播给所有观察者。观察者只能看，不能改。任何监听器抛异常也不影响主流程（失败被隔离）。

## 6. 几条硬规则（设计精髓）

1. **参数一旦进流水线就不能改写**。因为参数已经写进日志了——历史、审计、界面、执行必须完全一致。改参数 = 改历史，不允许。
2. **工具失败不会杀死整个回合**。工具不存在、工具抛异常，都变成结构化错误结果（比如"未知工具 UNKNOWN_TOOL"），这个调用失败，但回合继续，模型可以换别的方法。这是 agent 健壮性的关键。
3. **执行结果带"到此为止"标记**（`concludesTurn`）时，回合在这批结果之后停止——前面 agent-loop 讲过。
4. **作用域**：工具可以注册成"全局可见"或"只属于某个 agent"。子 agent 通过 `deny`（移除）/`allow`（只留）过滤看到哪些工具。这是"不同 agent 不同权限"的机制。

## 7. 对 Studium 的意义

这条流水线就是"工具分层与权限"的完整样板：

- Studium 要给不同模块不同工具权限 → 用 `pre-execute` 的 allow/deny/ask + 作用域过滤；
- 要保证策略只收紧不放宽 → 用"只减不增"的守卫；
- 工具出错了不能拖垮整个任务 → 结构化错误结果，回合继续。
