# 阶段2 · 插件树解剖：一切皆插件是真的

> 2026-08-15 · 轻路（只读源码配置，未编译未运行）
> 目标：把"一切皆插件"从口号变成眼睛看得见的结构——一个 DSH 启动时到底挂什么、怎么组合。
> 依据：`packages/bundle/*/cordis.patch.yml`、`examples/headless-agent/cordis.yml`、`docs/architecture.md`。

## 1. 先看组合机制：profile → bundle → patch 行

一个跑起来的 DSH 不是一棵"写死的树"，而是**配置按层叠出来的**：

```
profile（你选的形态，如 web / headless）
  └─ bundle 列表（按顺序叠）
       └─ 每个 bundle 的 cordis.patch.yml（一行一个插件）
            └─ 用户自己的 cordis.patch.yml（最后叠，覆盖任意一行）
```

- 每个 npm 包在 `package.json` 里声明自己是 profile 还是 bundle：`dsh.profile` / `dsh.bundle.patch`。
- `dsh-base` 是**每个** profile 的第一层（共享核心）；`dsh-web-app` 加浏览器界面；`dsh-headless` 加无服务器的一次性 runner。
- **patch 是整行替换 config，不是 merge**——同一行 `id` 后写的赢。
- **加载顺序跟文件行序无关**，由服务可用性驱动（`inject` 声明的依赖到了才激活）。文件里分组只是为了读起来方便。

> 学到的第一课：在这个框架里，**"系统由什么组成"是一份数据（YAML），不是代码**。改系统 = 改配置或换 bundle，不动 agent 循环本身。

## 2. base 层的 78 行插件（按职责分组）

`packages/bundle/base/cordis.patch.yml` 是每个 profile 的地基，共 78 行。分组看，`ctx` 挂的东西一目了然：

| 职责组 | 插件 id（节选） | 一眼看出什么 |
| --- | --- | --- |
| **核心循环** | `agent` `agent-loop` `tools` `system-prompt` `agent-default-model` | agent 循环本身就是一个插件行——没有特权核心 |
| **LLM 适配** | `llm` `llm-deepseek` `llm-pi-ai` `llm-retry` | 模型适配器可换：DeepSeek ↔ pi-ai，配置里换 name |
| **会话/持久化** | `session` `session-title` `session-persistence-jsonl` `session-query-sqlite` `session-projection` `session-telemetry-otel` | 会话日志、标题、JSONL 落盘、SQLite 查询、投影、遥测 |
| **执行能力（工具 seam）** | `bash-sandbox` + `tool-bash`、`pwsh-sandbox` + `tool-pwsh`、`fs-sandbox` + `tool-fs`、`web` + `tool-web`、`tool-jobs` | **capability seam 成对出现**：provider（xx-sandbox）+ consumer（tool-xx） |
| **安全/策略** | `sandbox` `sandbox-policy` `approval` `permission` `timeout-policy` | 权限批准、沙箱、超时策略都是插件 |
| **技能/指令** | `skill` `skill-filesystem` `tool-skill` `agent-instructions` | 技能注册表、文件系统技能、agent 指令 |
| **目标/规划/压缩** | `goal` `goal-round-driver` `plan-mode` `token-meter` `compaction-basic` | 目标域、计划模式、token 计量、上下文压缩 |
| **子 agent/工作流** | `subagent` `subagent-spawn-in-process` `subagent-fork-in-process` `tool-subagent*` `workflow-worker-thread` `tool-workflow` | 子 agent 两种出生方式（spawn/fork）+ 工作流引擎 |
| **上下文管理** | `spill-local` `spill-policy` `session-checkpoint-policy` `tool-result-pruner` | 溢出、检查点、工具结果裁剪 |

| **类型/网关** | `typert` `typert-loader` `typert-gateway` | 类型图生成/加载（DSH 特色） |
| **基础/设置** | `timer` `hmr` `settings` `credentials` `attachment-local` `tool-todo` `tool-ralph` `tool-str-replace-editor` | 热重载、设置文件、凭据、todo/Ralph 工具 |

## 3. 一个最小完整示例：headless-agent 是怎么写的

`examples/headless-agent/cordis.yml` 是独立的可运行组合。看懂它 = 看懂整个框架的最小骨架：

```yaml
- id: llm-deepseek          # 模型适配器：换 name 就换模型服务商
  name: '@deepseek-ai/dsh-llm-deepseek'
  config:
    thinking: enabled
    reasoningEffort: max
    models: [...]            # 上下文窗口在此声明

- id: bash                   # 工具 provider
  name: '@deepseek-ai/dsh-bash-local'
  config: { timeoutMs: 60000 }

- id: tool-fs                # 工具 consumer（模型可调的）
  name: '@deepseek-ai/dsh-tool-fs'
  # fs-observation-policy 保证"写入前必须先观察到文件"

- id: agent-spine            # 预创建 agent
  name: '@deepseek-ai/dsh-agent-spine-demo'
  config:
    agents: [{ id: main, model: deepseek-v4-flash, ... }]
    persona: |               # 系统提示词就是配置
      You are headless-agent...
```

三个值得停下来的点：

1. **模型适配器是插件**：注释里明说换 `@deepseek-ai/dsh-llm-pi-ai` 就换服务商。Studium 将来接多个模型商，这就是样板。
2. **persona（系统提示词）也是配置**：不是写死在代码里，是 YAML 里的字符串。
3. **策略是插件，且可热更新**：settings/credentials 注释说文件"hot-reloaded"——改配置不用重启。这就是 Cordis 的 HMR + 可回滚副作用在真实产品里的落点。

## 4. 现在回看「一切皆插件」的准确含义

- 不是说"可以用插件扩展"（很多框架都行），而是**整个运行时就是一棵插件树**：模型、工具、会话、循环、策略全部同构，全部可从配置替换、可动态装卸。
- 连带的结果（也写在 AGENTS.md）：**改 agent 循环 = 改配置 + 更新架构文档**，而不是打补丁。这跟"特权核心"架构（如 Claude Code）形成鲜明对比。
