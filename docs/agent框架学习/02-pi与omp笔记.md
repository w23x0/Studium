"agent"的通行说法：模型在循环里调用工具、直到完成目标（Anthropic《Building effective agents》2024-12；Simon Willison 2025-09）。Anthropic 同文区分 **workflow**（程序按预设路径编排模型和工具）与 **agent**（模型自己决定流程）。产品负责人的看法：两者是同一条"灵活性"轴，没有新旧之分；业内偏向 agent 端是因为编程和通用智能需要。

## 3 对问题清单的回答

| # | 回答 | 出处 |
| --- | --- | --- |
| 1.1 | pi 默认由模型控制：有工具调用就执行、结果喂回模型，直到某次回复不再调用工具。没有最大步数限制。程序在每一步的边界上可以插手：`finishTurn`（结束或继续）、`beforeToolCall` / `afterToolCall`（拦截、终止）、`transformContext`（发给模型前改写消息）、steering / follow-up（中途插话，下一步前注入）。这些钩子设计文章里没写，是后来加的 | `agent-loop.ts:174-316`、`:389`、`:724`、`:829` |
| 1.2 | 独立核对有三种形态。**顾问**：omp advisor，另一个模型只读旁观，只看主对话的新增部分，自己的意见不回看；按严重程度（小问题 / 有风险 / 阻断）决定打不打断；有噪声过滤、条数上限，打断一次后 3 轮内不再打断；主模型可以不听。**评审**：omp reviewer 子 agent，交回结构化结论（对 / 不对 + 把握 + 问题清单）。**门**：我们的守卫，结论决定流程能不能往下走，位置相当于 pi 的 `finishTurn`。omp 的"做完没有"（goal 模式）由主模型自己调用 `goal complete` 宣布，靠提示词里的清单约束（"不确定就算没完成""核对范围要和声称的范围一样大""预算用完不等于完成"），不是独立调用。omp 的 `judgment` 是小而窄的分类调用（例如判断 agent 是不是意外停下），可以用小模型。pi 三种都没有 | omp `docs/advisor-watchdog.md`、`prompts/agents/reviewer.md`、`prompts/goals/*.md`、`src/judgment/index.ts` |
| 1.2 底层逻辑（产品负责人确认） | 每个判断交给手里有对的证据、或者有权决定的一方。① 有硬证据的（能算、能对照）→ 程序或便宜的模型；② 要推断的（只有软证据，例如懂没懂）→ 独立的模型调用（守卫）；③ 方向与价值（学什么、多深、走哪条路）→ 模型建议、人来选，模型要重新想人说得对不对，可以提异议，决定权仍在人。编程里①最多，所以能全自动；学习里①少、②是核心、③一直存在。学习者身兼两职：在②里是被判断的对象（不能自己判自己懂没懂，参照 DeepTutor 把"学习者自称"和"系统判定"分开记录），在③里是有权决定的人。所以框架上有两道门：②的门是守卫，③的门是人的选择 | 对话 2026-09-29 |
| 1.3 | 隔离就是切断上下文。**干活的不拆，核对的要拆**。依据（2026）：Cognition 改了 2025 年"不要做多 agent"的立场，变成"多个 agent 可以一起贡献判断，但写入保持单线程"；审阅 agent 平均每个 PR 多抓 2 个 bug，其中 58% 严重，并且"写代码和审阅的 agent 事先不共享上下文时效果最好"（理由：上下文越长判断越差，即上下文腐化；看不到需求说明，只能从实现往回推）；论文《When More Is Less》（2026-09）：多 agent 只在长任务、各部分依赖少时占优，前后紧密相连的工作单 agent 更好。对应到三类判断：① 交给程序（最彻底的隔离）；② 另开隔离调用；③ 交给人；干活本身不隔离。对我们真正要紧的代价不是 token，而是交接时给守卫什么：按 Cognition 的实测，不该给教学模型的推理。背景（2025）：Anthropic 多 agent 约耗普通对话 15 倍 token；Cognition 原文。数据来自编程，学习场景的软证据下未实验 | [Cognition 2026-04-22](https://cognition.com/blog/multi-agents-working) · [arXiv 2609.19759](https://arxiv.org/abs/2609.19759) · [Anthropic 2025-06](https://www.anthropic.com/engineering/multi-agent-research-system) · [Cognition 2025-06](https://cognition.com/blog/dont-build-multi-agents) |
| 2.1 | pi：会话只追加，可分叉成树；快满时把旧消息压缩成摘要，新消息原样保留；切分支时总结离开的那一支。平台规则（Anthropic，2026-08/09，Opus 5.5 与 Sonnet 5.5）：前面的系统提示、工具、历史消息一个字都没改，上一轮的思考才保得住，否则作废（2026-08-31 后注册的账号直接报错）；提示缓存也只在前面不变时命中；官方替代办法是把新指令追加为新消息，太长了用官方压缩。**判断（产品负责人认同，未实验）**：会话开头装配一次，会话内只追加，太长了再压缩。优点：教学连续、保住思考、缓存命中、外壳简单、少一层"替模型挑内容"的假设。缺点：会话长了判断会变差、之前的错误推断会留在上下文里、单独一轮不好复现。控制上下文要改用追加，不再改写。产品负责人补充：这加强了"最小闭环"的设计（闭环小，会话就短，少需要压缩；闭环边界就是重新装配的点） | pi `coding-agent/docs/compaction.md`、`sessions.md`；Claude API 技能内置的迁移文档（preserved thinking） |
| 2.2 | 由 2.1、1.3 推出：教学方带着自己上一轮的判断（这叫连续，不叫污染）；防污染落在守卫的输入上，守卫不看教学模型的推理。**原先"诊断记录不放回下一轮"的做法待重审**；对照实验暂不做 | 同上 |
| 2.3（只提出了大致样子，**未讨论**） | 三层：常驻（pi 不到 1000 token 的系统提示 + 逐级加载的 AGENTS.md）；按需读（skill 只挂名字和描述，需要时加载正文；用命令行工具加说明文档代替 MCP）；触发注入（omp 的 TTSR：程序盯着模型输出，按正则、代码结构或小模型判断匹配条件，命中就中断、注入规则、重试）。按需读的前提是模型知道自己需要什么，失效在"不知道自己不知道"。TTSR 留到 3.1 / 3.2 展开 | pi `docs/skills.md`；omp `docs/ttsr-injection-lifecycle.md`、`docs/rulebook-matching-pipeline.md` |
| 2.4 | 行号引用不是照搬 Claude Code，出于原理（可追溯：判断能指回学习者原话，便于复盘），保留；只追加的对话里行号天然稳定。参照：omp hashline（能复述随机标签说明知道在改哪）、Anthropic 引用功能（返回原文片段与位置）。**低优先想法**：守卫引用"行号 + 一小段原话"，程序核对原话在不在那一行，把"引用真不真"变成程序能查的硬事实；实验记录里还没出现过引用错误，所以现在不做 | omp `docs/`、Claude API 技能内置文档（Citations） |
| 3.1 重点（产品负责人定） | **操控模型的主要手段是输入的上下文及其编排组合**，不是提示词，也不是动作范围（项目原立场：`Harness设计/02-上下文资产格式.md` §3.3"职责靠上下文组合区分"）。底层逻辑：行为只由模型和它看到的上下文决定；指令只是上下文的一种，更有力的是事实（给它看"学习者在第 37 行把符号弄反了"，它自己推出该做什么）。编排五个维度：**选什么**（pi 作者"精确控制进入上下文的内容"；`transformContext` 钩子）、**什么时候给**（omp TTSR 的核心其实是时机：规则平时不在，违规当下注入）、**放在哪**（常驻索引 + 按需全文；追加为隐藏消息）、**给谁看**（守卫与教学看不同组合）、**用什么形式**（资产格式）。我们原来主要做了"选什么"和"给谁看"，"什么时候给"几乎没做（每轮重装时一次性全放）。接 2.1：会话内只追加后，编排从"每轮拼一整份"变成"会话开头装配一次 + 程序按事件在对的时机追加对的事实"（学习者答完一步 → 追加 M08 相关片；守卫判完 → 追加结论；状态变化 → 追加一条事实），问题变成"什么事件触发追加什么" | 对话 2026-09-29 |
| 3.1 提示词分层（产品负责人定） | 提示词按层次组合：底层写定义与边界，不依赖具体模型；上面按模型、按任务叠加。换模型、模型升级时只动上层（类比 pi 项目说明从全局到项目逐级加载）。不必担忧模型能力：连 pi 这种基础设施也会随模型能力变化 | 对话 2026-09-29 |
| 3.1 动作范围（次要） | 结构管"能做什么"（工具、权限、一轮何时结束），提示词管"怎么选"，内容质量由独立核对兜底。例：omp 计划模式提示词说"工作区只读"，`tools/plan-mode-guard.ts` 在代码里拒绝改文件——提示词解释为什么，代码保证做不到；pi 扩展的 `tool_call` 可拦截执行（`docs/extensions.md:104`）。TTSR 逻辑：规则 + 触发条件（正则、代码结构可当场打断重写；交给模型判的问句只事后警告、从不拦），核心是程序判定。讨论曾滑向修原型回复过长，已存档到 `05-讨论存档-回复过长与分析资产.md` | omp `docs/ttsr-injection-lifecycle.md`、`src/tools/plan-mode-guard.ts` |
| 3.2 | **一轮结束 = 模型某次回复不再调用工具**（官方同此：Opus 5.5 提示指南 "A message with no tool call in it ends your turn"）。程序能插手的三处：`finishTurn` 每步后判结束 / 再来一步；一批工具全带终止标记就停；出错或中止硬退出；无最大步数。omp 的 `ask` 工具不结束这一轮：阻塞等人选择，答案作为工具结果交回模型继续（提示词："只在用户必须决定的实质取舍时问"）。**原理**：没有下一步动作就把话交还；**针对编程**：没有下一步 = 活干完了，模型被训练成一口气做完。**对项目**：框架只管两次调用之间的边界，管不到一次回复内部写多少——"回复过长"不在循环层。官方另有两样可用：对话中途追加系统消息（可只管一轮，不破坏缓存与保留的思考），是 3.1"按事件追加事实"的落地手段；Claude Code 官方学习插件（SessionStart 钩子注入提示词）把"交还"定义为搭好上下文、留出 5–10 行给人写、然后等。输出风格的讨论超出框架范围，存档到 `06-讨论存档-一轮话的输出风格.md` | pi `packages/agent/src/agent-loop.ts:183`、`:245`、`:262-293`、`:690`，`types.ts:146-158`；omp `packages/coding-agent/src/tools/ask.ts`、`src/prompts/tools/ask.md`；[Opus 5.5 提示指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)；[对话中途系统消息](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)；anthropics/claude-code `plugins/learning-output-style` |
| 3.3（讲了一半，学习到此停止） | pi：系统提示对所有模型同一份（`coding-agent/src/core/system-prompt.ts` 无按模型分支），差异压在 `pi-ai` 接口层（消息格式、兼容开关、`thinkingLevelMap` 把统一档位译成各家参数）。omp 三层：① 接口翻译（剥 DeepSeek 漏出的模板标记、把写进正文的工具调用修复成调用、空回复重试）——工程；② 工具形式按模型换（编辑默认 hashline，Kimi / DeepSeek / MiniMax 等退回 replace）——拟合训练；③ 运行中按症状纠偏（Gemini 连续只写计划不调工具 → 中断 + 追加提醒；思考打转、空停、说继续却停 → 各有纠偏消息）——程序判硬事实、当下追加。规律：常驻提示词基本不按模型变。**线索（未定）**：提示词分层的上层可以是“按症状在当下追加”，不只“按模型叠常驻段落”；厂商按模型的提示指南本身就是一份现成的上层。产品负责人判断：pi / omp 属工程层面，对当前设计参考有限，3.3 余下、3.4、3.5、§4 不再讲，转去重审技术方向 | omp `docs/provider-quirks.md`、`src/utils/edit-mode.ts`、`src/session/stream-guards.ts:200-245`、`src/prompts/system/*-retry.md`、`thinking-loop-redirect.md`；pi `packages/ai/README.md:1319` |

## 4 omp 相对 pi 的改动

| 改了什么 | 哪层 | 动机 / 证据 | 三分法 | 换到学习场景 |
| --- | --- | --- | --- | --- |
| hashline 编辑：读文件时每行带 2–3 字符内容哈希，编辑时引用哈希，不复述原文 | 工具 | 复述原文时空格错一个就失败；实验见上 | 主要是原理（降低表达负担），与训练无关 | 同一思路：对话带行号、守卫按行号引用 |
| 31+ 内置工具（LSP、调试器、持久内核、多格式读取） | 工具 | 给模型可核对的反馈 | 针对编程 | 大多不需要 |
| 子 agent、按角色路由模型 | 循环 / 模型 | 并行、分工 | 原理 + 编程 | 待 1.3 |
| advisor 旁路审阅 | 循环 | 见 1.2 | 待定 | 待 1.2 |
| 40+ 模型提供商 | 模型接口 | 覆盖面 | 工程 | 我们只做两个模型，见 §6 |

代价：一份第三方测试（Composio，30 个任务，DeepSeek V4 Flash）里 pi 通过 20 个，omp 通过 17 个，omp 单次成功成本约为 pi 的 3.7 倍。单一二手来源，样本小。[来源](https://composio.dev/content/pi-vs-omp)

## 5 三分法小结：两人对"拟合"的态度

| | pi 作者 | omp 作者 |
| --- | --- | --- |
| 态度 | 承认靠拟合，主动利用：模型练过什么就给什么 | 认为拟合脆：换一个没练过该格式的模型就失败，外壳按"出错面"设计 |
| 厂商公布了什么 | 厂商会公布自家训练过的工具与格式（Anthropic 官方定义的编辑、命令行工具；OpenAI 提示词指南里的补丁格式）；其他格式的表现不公布，只能实验 | |
