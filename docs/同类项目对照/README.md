# 同类项目对照

> 状态：待定（2026-10-01 建）。**参考材料，不作产品结论**；对照中想到要改自己设计的，记成 `任务线路.md` §3 的新线，走审查单 / Harness 流程，不在这里直接定。
> 目的（产品负责人原话）：一个一个看别人的项目，学习对比技术、方向、边界，扩大视角，确立自己的方向和边界。

## 做法（DeepTutor 一轮后定型）

| 步 | 做什么 |
| --- | --- |
| 1 准备 | 读本页；`git clone --depth 1` 到 `~/参考项目/<名字>`；同时派两个子代理：**读码**（结构 / 流程谁控制 / 学习者状态 / “学会了”怎么判 / 上下文 / 记忆 / 评测），**读文档**（方向 / 边界 / 证据 / 定位变化 / 开发团队与贡献者结构）。主会话抽查关键行再讲 |
| 2 讲 | 按 1.1、1.2… 一次一条讲**这个项目本身**，等回应再讲下一条；不跑去查或展开我们自己的技术路线 |
| 3 讨论 | 产品负责人直接指出和我们不同的地方；agent **先对照我们的设计分析再记**：它为什么这样设计（根因取舍），双方各自的代价，不一概否认；拿不准就标出来 |
| 4 记 | 当场写进 `NN-<项目名>.md`：§1–4 事实（带出处），§5 产品负责人判断 + agent 分析，§6 启示 |
| 5 收尾 | 产品负责人说够了就停，不为“看全”而硬挖技术细节；更新本页清单与 `任务线路.md` §3 #20 |

## 讨论时守的规矩

| 规矩 | 来由（DeepTutor 轮） |
| --- | --- |
| 不凑优点：我们已有对应的算“同”，不算“借鉴”；真没有可借鉴的就说没有 | 1.5 列了四条“可借鉴”，三条其实是我们已有的、一条是补丁 |
| 讲设计先讲成因：同一做法放在它的约束下（模型、判分方式、团队）是否自洽 | 1.5b 0.5 / 0.8 封顶：在只拿到对错信号的前提下是唯一能做的 |
| 猜测要核实：产品负责人对背景的猜测，agent 去查事实再回应（团队、贡献者、发版节奏） | 1.1 “学生分工开发”→ 核实是一名本科生主导 |
| 重点是功能、方向、侧重 → 定位与边界；技术细节只在影响定位时才挖 | 收尾时放弃了切书模块 |

## 每个项目看什么

| 维度 | 要回答的问题 |
| --- | --- |
| 方向 | 它想解决什么学习问题、面向谁（自学 / 课堂 / 教师）、成功怎么算；定位怎么变过 |
| 团队 | 谁做的、几个人主导、发版节奏——用来解释定位与功能形态 |
| 技术 | 流程谁控制（程序 / 模型）、学习者状态存什么怎么存、“学会了”由谁怎么判、路线学前定还是学中长、记忆、上下文怎么装配；**首要判别：学习结构是否进到 harness 里，还是“通用 harness + 学习插件”** |
| 边界 | 它刻意不做什么、明说的局限、做不到的地方；有没有“决定不做”这一档 |
| 证据 | 效果数据从哪来、样本多大、自报还是第三方、评测用的什么模型 |
| 和我们对照 | 同 / 不同 / 各自代价；归类：同 · 方向不同 · 反例 · 边界 · 只作参考 · 暂缓 |
| 对方向与边界的启示 | 我们的方向或边界要不要动、往哪动（只提出，不定） |

我们这边的对照对象：`docs/模块需求设计/00-第三次重构-产品设计总览.md`「闭环定义」「设计取向」· `docs/Harness设计/00-技术方向确认.md`（核心原则，正在重审）。
