## 2. 技术

| 项 | 内容 | 出处 |
| --- | --- | --- |
| 流程谁控制 | 模型：自研 agent 循环，模型自己决定讲什么、出什么题、调什么工具；没有状态机，没有用 LangGraph（一个按流程图编排模型调用的框架）。掌握路径和 chat 用的是同一个循环，只是换了一套提示词 | `D/capabilities/mastery/capability.py:3-20`；`D/runtime/agentic/loop.py` |
| 知识点分类 | 四类：记忆 / 步骤 / 概念 / 设计。由 tutor 在建大纲时给每个点打标签，分类的作用只是决定用哪种判法；注释给的理由是概念、设计类“很少有唯一标准答案”，没法用程序对答案 | `D/learning/models.py:24-28`；`D/learning/policy.py:41-46`；`D/capabilities/mastery/prompts/en/mastery_loop.yaml:92` |
| 知识结构 | 线性大纲：模块 → 知识点列表。“下一步做什么”的顺序是：先批改还没批的题，再做到期的复习，再按大纲顺序找第一个没掌握的点。知识点上记了先修关系，但注释写明**还不参与放行**。另有一套四类错因标签：结构 / 理解偏差 / 应用 / 元认知 | `D/learning/policy.py:219-232`；`D/learning/objective_relations.py:1-5`；`D/learning/models.py:36-40` |
| 记忆、步骤类的判法 | tutor 自己出题、自己写标准答案，程序对答案（选择题要完全一致；简答题相似度 ≥ 0.85；开放题关键词命中 ≥ 60%）；掌握度 = 最近 5 次作答加权，≥ 0.9 放行；答 1 次最多算 0.5、答 2 次最多算 0.8；0.9 这个值注释说是照搬 Alpha School 的“90% 才前进” | `D/learning/grading.py:12-48`；`D/learning/mastery.py:17-37`；`D/learning/policy.py:33-39` |
| 概念、设计类的判法 | 学习者用自己的话讲一遍（费曼式），由**同一个 tutor** 判断，只记“通过 / 不通过”，没有独立的评判调用 | `D/learning/policy.py:41-46`；`D/capabilities/mastery/prompts/zh/mastery_loop.yaml:98` |
| 学习者自行声明 | 学习者可以直接声明“已掌握”，系统记下来源是学习者本人；也可以暂缓某个目标 | `D/learning/policy.py:93-111` |
| 学习者状态 | SQLite 里存一整份 JSON：掌握度、作答记录、错题、间隔复习参数、学习者画像；跨会话记忆是三层 Markdown 文件 | `D/learning/models.py`；`D/services/memory/paths.py` |
| 上下文 | 系统提示按块拼接（身份、模式、画像、记忆……）；检索到的资料放在用户消息里；历史占窗口的 35%，其中 40% 用来放滚动摘要 | `D/agents/loop/prompt_blocks.py:118-185`；`D/services/session/context_builder.py:29-38` |
| 跨会话记忆 | 三层文件：L1 每轮原始记录（按功能、按天，只追加）→ L2 每个功能一份 Markdown 摘要 → L3 跨功能四份（近况 / 画像 / 范围 / 偏好），由模型“整理器”逐层提炼，每条写明出自哪一层哪一块。L3 有禁用词表（“掌握”“完全理解”“专家”“总是”“从来不”等），而且必须写成“在 N 次 X 互动中，用户……”这种留有余地的说法。整理只找到工作台接口的手动入口，自动触发没找到（未核实）。L3 每轮拼进系统提示 | `D/services/memory/paths.py:1-12`；`consolidator/guards.py:14-40`；`consolidator/prompts/zh/update_l3.yaml`；`D/api/routers/memory.py:240-262` |
| 记忆和掌握数据的关系 | 两套各管各的：掌握度、错题在 SQLite；记忆是通用聊天助手那一套。L1 的功能列表（chat / notebook / quiz / kb / book / partner / cowriter）里没有掌握路径 | `D/services/memory/paths.py:49-58` |
| 资料 | 默认用 LlamaIndex 做向量 + 关键词混合检索，每块 512 token；LightRAG / GraphRAG 是可选项 | `D/services/rag/factory.py` |

## 5. 和我们对照：产品负责人的判断

| # | 点 | 产品负责人判断（2026-10-01） | 归类 |
| --- | --- | --- | --- |
| 1.1a | 多次重构、定位多变 | 背景是大学团队，成员多是学生；AI 工具（如 RAG）今年变化快。重构多是背景和环境造成的，不代表方向本身对或错 | 只作参考 |
| 1.1b | 学习者账号、家长、教师端、班级 | 我们**不做** | 边界 |
| 1.1c | 聊天软件陪伴（Partners） | 我们**不做** | 边界 |
| 1.1d | 功能多、彼此割裂 | 判断是团队分工开发、各人水平不一造成的。我们的定位是清楚的 | 反例 |
| 1.1e | 成功标准 | 它研究得不深，只有模拟打分；我们做过实验，已有一些结论 | 只作参考 |
| 1.2a | 知识点分成四类、按类决定判法 | 分得不够细，属于贴标签式分类，设计得不好 | 反例 |
| 1.3a | 遗忘曲线 / 复习 | 我们目前也没有遗忘曲线机制：模块设计和技术实验还没走到这一步 | 只作参考 |
| 1.4a | 评测用的模型 | 学生和 tutor 都用 Gemini-3-Flash，选得很有问题，但考虑到模型在发展也能理解；评测实验还有很大优化空间。我们自己做过模拟评测，参考了 Anthropic 的 evals 博客（见 `../学习者模拟与评估/04-评估体系补充要点.md`） | 只作参考 |
| 1.5a | 学习者报“题出错 / 答案错”→ 作答作废 | 方向对：我们也得靠学习者指出、靠模型少出错、靠守卫（守卫也不是万能的），反馈机制要加强。但我们还没遇到出错的情况，等上线后按用户反馈再考虑；这不是核心。这类修补很难做巧：要么加复杂度，要么只是记录特例、标记模型短板，解决不了模型本身的问题 | 暂缓（上线后） |
| 1.5b | 答 1 次最多算 0.5、2 次最多 0.8 | 设计很不好。我们的判断依靠模型准确读出每一次的细节和时间线上的变化；这种只看对错的分数信息密度极低，不值得借鉴 | 反例 |
| 1.5c | 改内容不能越出模块目标 | 就是我们的闭环设计（段链有边界） | 同 |
| 1.5d | 学习者声明与系统判定分开记来源 | 不是优点，不要为了凑优点而列；更像是弱模型幻觉逼出来的补丁 | 不采 |
| 1.5e | 为弱模型加防错机制 | 测试时用弱模型放大错误没问题，但不该因此在产品里加机制，会让项目多出冗余限制 | 边界 |
| 1.6a | 按学习者目标排大纲、不按书的章节 | 想法不错；但底层有问题：大纲是学习前一次列好的，而学习过程会反过来影响它。我们要的是使用过程中的动态反馈闭环。M08 的发展空间很大：多用户真正部署后可以吸收学习数据（容量等还要调整，属于远期） | 方向不同 |
| 1.6b | 路线怎么定 | 我们是按动态知识面确定路线 | 方向不同 |
| 1.7a | 记忆 | 记忆技术一直有争议；面向学习领域的做法很少有人证明过。我们项目里的“记忆”就是日志和知识面 | 只作参考 |
| 1.7b | 三层记忆 | 像之前记忆功能火的时候的跟风做法：一个简单的记忆层次，测试也很乱；几个持续开发的记忆项目效果都不太好，原因不清楚（是否只在特定场景有效？）。来得快、去得也快，不是底层的东西 | 反例 |

### agent 分析（对照产品负责人判断）

| # | 分析 |
| --- | --- |
| 1.1b | 它做学习者账号，是因为用户里有未成年人，需要第三方监督。我们的使用者只有学习者本人，产出只给学习者自己看（横切原则 5），所以没有第三方观察者。边界可以表述为：**使用者 = 学习者本人** |
| 1.1c | Partners 是为了“去用户已经在的地方”、增加接触面，单位是零散的消息。我们的单位是闭环，消息零散进来接不上闭环，所以不做是一致的 |
| 1.1d | 割裂除了团队原因，还有一个结构原因：工作台把各种能力摆成菜单，没有一个对象把它们串起来。我们的串联对象是“知识链上的闭环”。这是定位上的差别，不只是开发水平的差别。团队核实后发现是一名本科生主导开发，不是多人分工，更说明割裂主要来自“工作台”定位，加上发版快、不断往上叠功能 |
| 1.1e | 它的 10 项打分评的都是单次辅导的质量。我们的检验写明“单次不差于通用模型 + 教材，跨闭环明显更好”，重心在跨时间。这正是它没测的部分 |
| 1.2a | 它的四类不是知识模型，而是“判分路由”：能用程序对答案的走程序，不能的交给模型。我们不给知识点贴类型，用的是统一的收口判据（能自己走一遍链、换问法仍能用），差异体现在“连上了哪些点”上。反过来，它有一块是程序可核对的，我们的判定全靠模型（M04 守卫），这一点我们没有对应物 |
| 1.2b | 核实结果：确实只靠这四个标签，再加一条线性大纲；先修关系记了但不用。分类是为了“能判分”做的取舍，注释里写了理由。所以它的知识结构很薄，判定倒做得比较硬 |
| 1.5 | 收回“可借鉴”的说法。1.5b：它只能拿到“对 / 错”这种粗信号（因为判分走程序对答案），加权分加封顶是在粗信号上唯一能做的事；我们拿的是细节和时间线，代价是全靠模型读得准。两边各自自洽，根源是“判定交给程序还是交给模型”的取舍。1.5c、1.5d 我们已有对应（闭环边界；横切原则 5 学习者异议按自述来源记），是“同”，不是“借鉴”。1.5a、1.5d 的成因：它的题和答案都由 tutor 现场生成，无论用哪个模型都会有错答案，不只是 Gemini 的问题（论文评测用 Gemini-3-Flash，产品里模型由用户自选） |
| 1.6 | 它的大纲在学习前一次定好，之后只在学习者提出异议时局部修改、或推倒重建；过门失败、错题这些学习数据不会改大纲（`mastery_loop.yaml` study 段：“不要随意重建大纲”）。我们是每个闭环结束后由 M05 按结果选下一段，路线是在学的过程中长出来的。吸收多用户学习数据，在设计里对应 M09 → M08 的候选通道（总览闭环定义 ③） |
| 1.7 | 它的记忆是“记住这个用户”（偏好、近况、画像），我们是“记住这个人学到哪、怎么学会的”（闭环日志 + 知识面）。它的掌握数据和记忆分开、互不相通，所以记忆里不知道学会了什么，掌握数据里也不知道这个人怎么学的。禁用词 + 强制“在 N 次中”的写法，和我们“不贴标签”是同一个担心（模型爱下绝对结论），但它是用词表在输出端拦截，治标 |
| 1.8 | 它算有 harness：自研 agent 循环、提示词按块拼接、工具系统、历史预算与滚动摘要。但这是一套通用聊天 agent 的 harness，“学习”只是挂在上面的一组工具 + 一套提示词（掌握路径和 chat 用同一个循环）。学习的结构（闭环、证据、知识面）没有进到 harness 里，这正是我们阶段 5/6 要做的。所以它是“通用 harness + 学习插件”，不是“为学习设计的 harness” |

## 6. 对方向与边界的启示（只提出，不定）
