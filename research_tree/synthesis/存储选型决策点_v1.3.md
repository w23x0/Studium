### D3 版本化机制（M09 动态模型）——本版终裁

**最终建议 = L2 采用 FHIR _history 式**：

- **形态**：结论对象=一个资源，`meta.versionId` 随内容变更更换（不透明、同资源唯一）；create/update/delete 均产生 `_history` 条目、只追加不可改写、旧版本仅审计保留、delete=墓碑不删历史；单链不支持并发版本/多分支；`verificationStatus` 状态机（unconfirmed/provisional/differential/confirmed/refuted/entered-in-error）+ `clinicalStatus`；Provenance 可指向任意版本纠错（不覆盖）、AuditEvent 安全日志。
- **叠加 revlog 式「历史流/当前状态分离」降规模**：`_history` 天然即 revlog 式历史流（每次变更追加一条）；历史区（_history 追加条目）+ 当前区（各资源最新版本=当前视图，可从历史重放重建，M3 幂等底数 0.145s/522 节点）；体积增长后用 CB 增量补丁压缩历史（B1c K10 先例，代价=delta 重建成本上移）。
- **叠加 L3 本地哈希链审计**：每版本写入=一条审计事件进哈希链 + 周期签名 checkpoint（见 L3）。
- **落 RDF 语义层**：每资源每版本一个命名图 + 版本号元数据三元组放默认图（B1c IC 策略，A 级先例），无版本语义用 PROV-O/OWL-Time 词汇补足。

**选它的决定性理由（3 条）**：
1. **与 L1 RDF 整合成本最低**：L1 已定 RDF 1.2 + TriG 命名图（atemporal）；FHIR 资源级版本化在 RDF 上落地有现成先例（每资源每版本命名图，B1c IC A 级），**无需在 atemporal RDF 上自建双区间版本行**；时态图双区间在 RDF 层无标准表达、无统一交换格式（B2c C 级）。
2. **refuted vs entered-in-error 的区分正好覆盖 M09 两种语义**：「复检推翻旧结论」=refuted vs「写错撤回」=entered-in-error；「旧版本保留仅审计、delete=墓碑、单链」与红线不物理删除、revlog 事件追加幂等、M3 重建幂等直接同构。
3. **资源级粒度贴合 M09**：每结论对象独立演化 + 按对象回溯（`_history` 按资源查、vread O(该资源版本数)、不扫全图）；复检一个结论不影响其他结论。

**条件性在哪（2 个设计待定项，须产品先裁决）**：① 复检后旧结论可见性；② 单轴/双轴。若产品裁决结论为「旧结论按时间可回溯（审计视图全量可见）+ 事务时间轴即可满足（或双轴用 PROV-O/OWL-Time 标准词汇在版本元数据上补足）」→ FHIR 式胜出；**若裁决必须原生双区间 + 旧结论纠正后即不再当前（ZEP 式失效语义）→ 需重估时态图路线**（此时 L2 条件未满足，回退走 B2c 时态图或与 L1 分叉，工程成本更高）。

| 候选 | 终稿判定 |
|---|---|
| **FHIR _history（B6d）** | **采纳（条件性）**：资源级版本 id + _history 只追加 + verificationStatus + Provenance/AuditEvent；叠加 revlog 分离 + L3 哈希链 |
| 时态属性图 assert/retract/correct（B2c） | **未采纳（条件性备选）**：语义最贴 M09（correct/retract/assert），但 RDF 层无标准表达、无统一交换格式、TGMS 2026-07 预印本无第三方复现（B2c U5）、工程成本更高；仅当产品裁决 ZEP 式原生双区间时重估 |

## 3 设计待定清单（移交产品，5+ 项）

> **这些是产品/模块边界裁决，非调研可解决。** 调研已给出每种裁决下的技术承载与成本；裁决落地后选型定案即完全闭口。按裁决优先级排列——前 2 项决定 L2 条件是否满足（若不满足则触发 D3 的时态图重估），3-5 项为版本层形态细化，6+ 项为 v1.2 遗留的建模/工程裁决。

### 3.1 L2 版本层选型条件项（决定 FHIR 式是否胜出）

1. **复检后旧结论的可见性**（B2c 冲突 6；B4c 冲突 5）：TGMS 式（correct 后 as-of 过去时间仍返回旧值，位时不可变性）vs ZEP 式（失效即不再当前）→ 决定 correct/refuted 语义与双视图设计（默认视图排除墓碑、审计视图全量可见）。**FHIR 式两种可见性都能表达**（当前视图=最新版本、历史视图=_history 可查）；若裁决 ZEP 式（纠正后旧结论即不再当前）且必须原生双区间 → 需重估时态图路线。
2. **单轴 vs 双轴**（B2c 冲突 1/未决 1）：若只需「当前掌握状态 + 历史版本」可单轴（valid time）；若要审计「当时记录 vs 后来纠正」必须双轴。**FHIR `_history` 天然是事务时间**（何时写入/变更）；若需双轴，在版本元数据上用 PROV-O/OWL-Time 补 valid time 即可——此裁决决定「FHIR 式是否够用」。

### 3.2 L2 版本层形态细化项

3. **版本粒度**（M09 审查问题 4）：复检/遗忘/提取失败/重新掌握是否都形成新版本而不覆盖旧记录——决定版本条目生成规则。
4. **M09 体积单调增长的三个方向**（M09 审查单末尾）：内部版本化 / 历史移交 M01 / 分两区（历史区+当前边缘区）。方向 3 与 revlog 分离、FHIR 式（_history+最新版本）兼容；「区划写进数据结构」与否需产品裁决。
5. **候选池→审计→晋升状态机定义**（M09 审查问题 5）：自动生成条件、自动/人工审核、晋升/退回权限。两条路线都需自建（S1），本选型不区分，但必须先行定义。

### 3.3 v1.2 遗留（建模/迁移工程裁决，仍非调研可解决）

6. **anchor 身份方案**：`anchor/{file}#{quote}`（29→26 折叠、跨节点共享锚点折叠为一主体）vs 节点 id 纳入 anchor IRI vs 空白节点（M2 §5）。
7. **pyld bug 处理策略**：本地补丁 / 绕行（自行反序列化）/ 锚点不进 RDF 三选一（M1 §6）。
8. **6 个非法 YAML 转义文件的修复方案**：修引号（`\s`→`\\s` 或改单引号）vs 宽容解析器（M1 §6.2）。
9. **「9+other」中 other 是否受控（白名单/类型）**（S3 补入）：LEX/PG-Schema 的 OPEN/CLOSED 语义若进 GQL v2 可能裁决，但 2026 内不给裁决，应用层不假设标准会裁决。
10. **锚点引用存在性语义**：evidence ∈ 节点锚点 vs ∈ 源文本（P2 实测暴露的真实建模分歧，205 条违规待裁决）。
11. **迁移过渡期长度与运行窗口**（B8c）。
12. **实时交互图查询延迟阈值**（P95 <1s 为建议值，产品决策，S2 不代定）。
13. **图查询层触发判据的 P95 阈值与「3 跳计时」实验**（S2，T1 实验 A/B 列入待实测）。
