## 二、合并要点（去重后净新增，按分支）

### B3a 增量 Datalog（基线 B3 R1）
- DDlog：无存储引擎、内存差分数据流；CLI 文本命令（insert/delete/commit/dump）是接口层非存储层；字符串 C-like 转义（grep 前须规范化）。
- DBSP：任意程序的一般增量算法、覆盖非单调递归、Z 集合负多重度=删除、时间=事务计数；VLDB 2023 最佳论文、Feldera 落地。
- RDFox：EDB 可删/IDB 不可显式删（belief revision/view update 难题官方点名不做）；Delta Queries 增量计算答案变化+可追溯；官方审计日志 commit procedure 先例（"rules can only add facts"=单调事实层支撑）。
- LogicBlox：增量维护工作量∝trace edit distance；O(1) 版本分支、时旅行、版本图=任意 DAG——状态机式推进。
- Soufflé：弹性增量=Bootstrap（高影响全量重算）/Update（低影响增量）两策略。
- Q5 关键结论：事实文本可 grep 只在"系统边界追加式纯文本层"成立，引擎内存态不可 grep；逐字校验须先按格式转义规则规范化。

### B1a RDF 1.2 建模（基线 B1 R1）
- triple term 仅限宾语；reifying triple=rdf:reifies 谓词+triple term 宾语；reifier 可作主语扩展→triple annotation；rdf:Proposition 为 rdf:reifies 的 rdfs:range。
- 官方四元组模式（Primer §5.1.2.3）：Bob 兴趣边+reifier+类型+日期。
- 「未断言的 triple term=候选、晋升=另行断言同一 triple」映射与 RDF 语义对齐（推断 C）；但 W3C 无候选/审计/晋升状态机规范示例（未核 U1）。
- 命名图承载四图分离；TriG=多图+再述统一语法；对齐边=桥接三元组（owl:sameAs 等归 B5）。
- 锚点集合判等：IRI/字面量解析还原转义后比对最直接；bnode 需图同构（RDFC-1.0 REC 2024-05-21 可作审计指纹）。
- N-Triples/N-Quads 逐行文法→追加即合法；atemporal+命名图快照与 B4 版本化互洽。

### B4a nanopub/trusty URI（基线 B4 R1）
- 三段式+Head 图（四图模型）；9 条 well-formed MUST 判据；np:hasAssertion/hasProvenance/hasPublicationInfo 为 OWL FunctionalProperty。
- trusty URI：末 45 字符=SHA-256 哈希（RA=图集合层、FA=文件字节层）；"发布后 issuing authority 无权改变其含义"；RA 模块 blank node 规范化困难（论文 2014）。
- 不可变语义：发布后不可删、只可撤回/supersede（PeerJ CS 2016 原文）；但 server 无查询、无 triple store，粒度查询须自建上层 SPARQL/索引。
- 规模：10M+ nanopub、10-15kB/条，面向科学数据大规模去中心发布；个人规模=可用但小马拉大车（推断 C）。
- 标准状态：非 W3C 标准、社区 working draft。

## 三、冲突登记（不删旧，双轨保留）

新增（R2）：
9. **RDF-star 对称语法 vs RDF 1.2 仅宾语**（B1a 冲突1）：2021 CG Report 允许 quoted triple 作主语/宾语，RDF 1.2 收窄为仅宾语+reifier 主语。迁移期资料与 1.2 不一致，选型须以 1.2 为准。
10. **triple term 未断言=候选池 vs 无官方名称/无状态机规范**（B1a 冲突4/U1）：语义上完全对齐（未断言=不主张为真），但 W3C 无"候选池/audited/promoted"规范示例，状态词汇表须自建冻结。
11. **nanopub server 无查询 vs M09 需稳定查询审查**（B4a 冲突2/3）：官方 server 只返回整条 nanopub、无 triple store；"当前掌握状态"查询需上层物化/SPARQL 服务——不可变层与查询层语义分离（与 B4 一轮"单调事实层+非单调当前视图"一致）。
12. **"完全增量"理论承诺 vs 工程必要时重算**（B3a 冲突2）：DBSP 论文一般算法 vs Soufflé 明确"增量并不总比重算便宜"——两者都属实，选型须接受"高影响变更全量重算"的现实。
13. **派生事实删除语义**（B3a 冲突3）：RDFox 官方不做派生三元组显式删除（belief revision 难题）；状态转换必须经"事实层增删+规则重算"表达，不能直接改派生事实——审计晋升建模的硬约束。
14. **"程序即数据"措辞 vs DDlog 无事实文件**（B3a 冲突1）：DDlog 关系=内存状态非外部文件；RDFox 有 N-Triples 文本层但 Datalog 规则/事实格式专有（application/x.datalog）。
15. **nanopub 社区规范 vs 项目"可稳定查询审查"红线**（B4a 冲突1）：非 W3C 标准、working draft；若采用须自建冻结版本。

### B1b 合并要点（基线 B1 R1 + B1a）
- 转义规则（RDF 1.2 N-Triples/N-Quads/Turtle WD 2026-07）：引号/LF/CR/反斜杠必须转义；还原=去定界符+处理转义后与源逐字一致（规范 A 级）；中文/全角空格不在排除集（UTF-8 直接编码）。
- N-Quads 文法 `nquadsDoc ::= statement? (EOL statement)* EOL?`——逐行追加在语法层永远合法（与 JSONL 同构），但崩溃安全仍是应用层承诺。
- Canonical N-Triples/N-Quads：唯一句法表示、每 quad 单行、无 VERSION 指令；RDFC-1.0（REC 2024-05-21）默认 SHA-256、稳定 bnode 标识，但规范明言"graph signature 由应用层定义"。
- 工具链三件套：rdflib（纯 Python 全格式）、Jena RIOT（--validate/--check、行式输出、StreamRDF）、rdf-canonize（JS，RDFC-1.0 实现，复杂度控制防 poison graph）。
- Q5 红线结论：源 markdown 文本层 grep -F 不受影响；RDF 文件内锚点须先解析还原转义再判等——红线精神保留（仍是逐字比较），载体改变后判等路径须换。

### B4b 合并要点（基线 B4 R1）
- IPLD：CID=内容哈希（multihash 自描述），修改即新 CID、旧块永不覆盖（IPFS 官方原文 "Nothing is overwritten"）；版本历史=新块 CID 链接旧块构成链表/DAG（git 同构）；无签名、无第三方证明，与 RFC 6962 CT 的审计保证语义边界不同。
- dag-json 层规范化可读可 grep -F；CID 本身 base32/base58 不透明（官方明示 human-readable form "is not a wire format"）；锚点若落在 CID 内人审退化为不透明串比对（推断 C）。
- 工程先例：ipfs-log/OrbitDB 日志层成熟；个人笔记/知识图谱应用层（uprtcl、interplanetary mind map、Welding）全为原型或终止——522 节点个人规模无成熟全栈先例（推断 C）。

### B4c 合并要点（基线 B4 R1 + B4a U1 接力回填）
- bitemporal：valid time=现实为真、transaction time=库中记录；SQL:2011 提供双时态构造（维基 B 级）；SQL Server system-versioned 表自动保留全史（A 级）；"information cannot be discarded even if it is erroneous"（维基原文 B 级）。
- 撤回：nanopub 持久不可编辑/删除；撤回=发布新 nanopub + `npx:retracts` 谓词；有效撤回须与原 pub 同公钥签名；被有效撤回的默认不出现在搜索结果（A 级，**回填 B4a U1**）。PROV-DM Invalidation/wasInvalidatedBy（W3C REC A 级）；学术撤稿（维基 B 级）。
- 补偿/事件：Saga 补偿事务、Azure 补偿事务、Fowler Event Sourcing（状态=事件序列可重建）、Transactional Outbox（原子落盘）——均为 A 级；M09"复检"=追加新版本/新事件，绝不回写旧事件（推断 C）。
- 墓碑/软删除：Kafka log compaction tombstone markers（保留删除事实、有独立保留期配置）；Azure soft delete（保留期后永久删除）——工程界"保留期/压缩后物理清理"与红线"不物理删除"对照：红线更强，M09 历史须视为不可压缩键空间（推断 C）。
- Q5 推荐表达（推断 C）：候选→审计→晋升→废弃（墓碑）；废弃=墓碑标记+终止时间；默认视图排除墓碑、审计视图全量——与 M08 候选池+审计一致。

### 新增冲突登记（追加，不删旧）
19. **直接 grep RDF 文件不成立 vs 红线"锚点判等=逐字 grep -F"**（B1b 冲突1）：JSONL 下锚点在文本层逐字；N-Triples/N-Quads 下锚点以转义形式存在，直接 grep 会漏/误匹配——判等路径须改为"解析还原转义后逐字比较"，红线精神保留（仍是逐字判等），载体变则路径换。
20. **Canonical 唯一表示 vs 追加日志乱序**（B1b 冲突2）：Canonical 要求排序+严格格式，append-only 按时间无序——两者不能同时成立；审计指纹须在追加后全量重新规范化，或"日志+周期化 canonical 快照"双轨（推断 C）。
21. **RDFC-1.0 明示不定义 graph signature vs 审计需确定性指纹**（B1b 冲突3）：指纹=对 canonical 做 SHA-256 是应用层约定，须自建并冻结，不能指望规范直接给出。
22. **IPLD 不可变块层 vs 可变视图层**（B4b 冲突1）：IPFS 旧块永不覆盖、只有 IPNS/命名指针可变——与 B4 R1"单调事实层+非单调当前视图"一致；IPLD 不提供可变视图，最新版本指针须应用自建。
23. **物理清理 vs 红线"不物理删除"**（B4c 冲突3）：Kafka 压缩删旧值、Azure 保留期后永久删除——工程界常态；项目红线更严格；若采纳压缩类方案 M09 历史须不可压缩（推断 C）。
24. **系统自动版本 vs 应用语义版本**（B4c 冲突2）：system-versioned 表只记"何时改"，不记"为何改"（复检/遗忘/重新掌握语义）——M09 需在自动版本上叠加语义版本。

### B6d 合并要点（基线 B6 R1）
- FHIR 双模型：**资源可变、版本不可变**——PUT 产生新版本，历史版本一经产生不可改写/删除（"there is no support for updating past versions"，A 级原文）。
- 版本 id 放在资源自身 meta.versionId："Changes each time the content of the resource changes... The same versionId can never be used for more than one version of the same resource"（A 级）——直接回应「把版本放资源自身」诉求。
- 版本 id **无固定顺序**：客户端不得假设数值/字典序即新旧（A 级）——移植时当作不透明标识，勿依赖大小比较。
- _history 交互（实例/类型/系统三级 + vread）：返回 history Bundle，"sorted with oldest versions last, and including deleted resources"；删除=墓碑条目不删历史（A 级）——与 M09「时间版本不覆盖旧结论」高度同构。
- 旧版本保留原文："All past versions of a resource are considered to be superceded, and no longer active, but retained for audit/integrity purposes"（A 级，R4/R5 同文）。
- 纠错不覆盖：对过去版本标 entered-in-error 的官方做法是 "use a Provenance resource pointing to the past version of the resource"（A 级）——错误标记外置，不篡改历史。
- 结论状态机：Condition verificationStatus（unconfirmed/provisional/differential/confirmed/refuted/entered-in-error）+ clinicalStatus（active/recurrence/relapse/inactive/remission/resolved）（A 级）——与 M09「复检/遗忘/重新掌握」可类比迁移；须区分「结论被推翻 refuted」与「录入错误 entered-in-error」两种语义。
- 版本能力分级：no-version / versioned / versioned-update，规范用 SHOULD 而非 SHALL——M09 若承诺版本化应自设为硬性契约（冲突张力 2）。

### B6e 合并要点（基线 B6 R1 / B4 边界声明）
- **经典逐行哈希链公式**（Crosby & Wallach, USENIX Security 2009，A 级原文）：`Ci = H(Ci−1 ∥ Xi), C−1 = □`——append-only 逐行链的标准形式；**证明代价线性**（800MB/8000 万事件场景），Merkle 历史树对数（3KB 证明）——"工程上为何不只用逐行链"的关键依据（KF-02）。
- **防篡改双重目标**（A）：单日志内篡改可检测 + 多实例不一致声明可检测（KF-03）。
- **RFC 6962 CT**（A）：定义"公开可审计、append-only、不受信"日志 + Merkle 树 + STH + gossip 检测追加性违约；RFC 9162 为 CT v2（KF-04/05/06/07）；Trillian 为泛化工程实现且官方已进入维护模式（KF-08）。
- **开源逐行哈希链实现**（A）：BBVA/QED（签名快照）、tegmentum/secure-log（逐行哈希链+分段 Merkle+签名 checkpoint）——**个人最小可行方案 = 本地哈希链/内容寻址 + 周期签名 checkpoint + 可选外部时间戳锚定**（推断 C）。
- **"append-only"标签不可靠**（A）：Hypercore 自称 append-only log 但 v10 官方支持 truncate（KF-12）；Git 内容寻址天然链式但 rebase/amend/force-push 可改写历史——**链式≠不可篡改，必须靠签名锚定**（KF-17，冲突 2）。
- **时间戳锚定**（A）：OpenTimestamps（区块链时间戳标准格式）、RFC 3161 TSA——均外部依赖，纯离线个人场景只能退化"本地签名 checkpoint + 物理介质隔离"（推断 C）。
- **保留策略 vs 红线**（A）：NIST SP 800-92 允许保留期后删除；auditd rotate/keep/remove；**S3 Object Lock 只能保证保留期内不可删**；chattr +a 可物理防删——与红线"不物理删除"直接冲突面，需把归档目标设为不可变存储（冲突 3）。
- **轻量签名锚点**（A）：ssh-keygen -Y sign / allowed_signers / namespace——无 PKI 的签名方案（KF-18）；Rekor（sigstore）签名透明日志为现行实现（KF-22）。
- **负面证据**（未核/无原生实现）：syslog-ng 3.37 Admin Guide 与 rsyslog.conf(5) 未见哈希链/完整性模块（KF-20/21 标未核）。

### 新增冲突登记（追加，不删旧）
47. **"append-only"标签 vs 实际可删改能力**（B6e 冲突1）：Hypercore v10 支持 truncate、Git 可改写历史——引用"append-only"先例时必须核对该实现的严格程度；M09 若承诺 append-only 必须自建物理层契约（与 B6c 冲突 37 呼应：API 契约 vs 物理层）。
48. **哈希链提供可检测性，签名提供不可抵赖锚点**（B6e 冲突2）：链式结构本身可被整体重算（攻击者可连链带数据一起重哈希）；GPG 签名/周期 checkpoint 才是外部锚——M09 若用哈希链须配签名，二者缺一不可。
49. **常规运维删除 vs 不物理删除红线**（B6e 冲突3）：NIST 允许到期删除、auditd/logrotate 默认 rotate+remove——M09 红线"不物理删除"无权威通用背书，只能靠实现层强制（不可变存储/只读介质/chattr +a）。
50. **CT 多方可信模型 vs 单机个人场景**（B6e 冲突4）：RFC 6962 对抗"不受信日志撒谎"，需公开审计+gossip；个人单机写入者即所有者，全套 CT 属过度设计（推断 C）——个人最小方案为本地哈希链+周期签名。
51. **逐行链证明线性 vs Merkle 对数**（B6e 冲突5）：逐行链实现简单但证明 O(n)，Merkle 历史树 O(log n)——个人小规模（千条级）逐行链足够，规模增长再升级（推断 C）。

### B5a 合并要点（基线 B5 R1 + B5b）
