# 任务卡 B7 — 文档-图混合与人可读写载体
角色：深度调研树分支调研员（B7）。
分支名：人可读写优先的文档-图混合存储。

## 问题清单
1. Markdown + frontmatter + wiki 链接（Obsidian 式）与大纲块引用（Logseq 式）各自的数据模型：节点=文件还是=块？边=链接还是=属性？能否表达"节点身份=锚点集合"（锚点即文中逐字串）？
2. Logseq 从 Markdown 文件存储迁向数据库版本（DB version）的公开理由与官方说明：纯文本文件存储在什么规模/什么需求下被认为不够？
3. Semantic MediaWiki 的存储模型（页面+属性+RDF 导出）：wiki 作为图谱存储的先例，其版本历史机制（每页 revision）与 M09 版本语义的异同？
4. YAML-LD、文档内嵌图片段（一篇文档内含结构化学术断言，如 nanopub 的 Markdown 化尝试、RDFa、JSON-LD in HTML）：文档与图共存的标准化路径有哪些？
5. 对"锚点逐字 grep -F + 人审"工作流，文档-图混合载体的增益与代价：grep 直接作用于源文档是否反而强化了锚点硬校验？

## 候选空间与线索
Obsidian 数据模型（社区文档/插件 API 文档）、Logseq（含 DB 版迁移公告）、Org-roam、Semantic MediaWiki 官方文档、YAML-LD（W3C 社区草案）、RDFa、nanopub 的人可读序列化尝试。

## 搜索关键词
中文：Logseq 数据库版 迁移 原因、Obsidian 数据模型 文件即节点、语义 wiki 存储 RDF、Markdown 知识图谱 存储
英文：Logseq database version markdown limitations、Obsidian data model files links、Semantic MediaWiki storage model RDF export、YAML-LD specification、document graph hybrid format RDFa

## 工作量红线
可核来源>=15 且原文到手>=10；来源类型>=3 类（官方文档/公告、学术论文、工程先例）；候选逐一查证>=5（Logseq、Obsidian、Semantic MediaWiki、YAML-LD、RDFa 或同类）；关键词>=4 组。

## 产出格式（发现.md）
0 一句话结论 / 1 逐条回答 / 2 关键发现（论断+URL+标题+机构+日期+原文摘录+等级 A/B/C）/ 3 冲突与张力 / 4 未决问题 / 5 来源清单 / 6 判死自查

## 禁止项
不做笔记软件产品对比评测（只挖其数据模型与存储决策的公开技术说明）；不越界（纯机器序列化归 B1）；不捏造来源，抓不到写"未核"；不预设"人可读"是必要的或不必要的。
