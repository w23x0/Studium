## 0 一句话结论

xAPI/IEEE 9274.1.1 把"学习记录"定义为不可变 statement 事件流：statement 一经接收即不可修改（同 id 重复提交 MUST NOT 改动已有记录；撤回的唯一合法途径是 voiding"作废声明不销毁"），检索按 stored 时间逆序、支持 since/until 时间窗；但"物理存储是否 append-only"规范明确不指定（ADL 与 IEEE 全文检索 "append-only" 命中 0），可变层是 State / Activity Profile / Agent Profile 三个 document API（覆盖写 + ETag 乐观并发）——即先例是"事件层不可变 + 作废声明、状态层可覆盖"的双层模型，与红线甲/丁在事件层高度同构；"不可变"是 API 契约而非物理存储保证（append-only 判定=C，见 KF22）。

## 1 逐条回答

### 1.1 xAPI 规范（IEEE 9274.1.1）对 statement 不可变性的规定原文

（原文来源：ADL xAPI 1.0.3 规范 xAPI-Data.md §2.3/§2.3.1/§2.3.2 与 xAPI-Communication.md §2.1；IEEE 9274.1.1 开源素材 §4.2.4。IEEE 正式 PDF 全文未到手，见未决 1。）

- 生命周期（ADL §2.3）："Statements are expected to be permanent. The only way to undo a Statement within this specification is to void it. Voiding does not destroy a Statement, rather indicates the evidence in the Statement is to be disregarded."（statement 预期永久；规范内唯一"撤销"方式=voiding；作废不销毁、仅表示该证据应被忽略。）
- 不可变（ADL §2.3.1）："Statements are immutable (they cannot be changed)." 例外清单：LRS 处理时指派属性（id/authority/stored/timestamp/version）；被引用的 Activity Definition（不属 statement 本身）；Verb 的 display；Timestamp 序列化（如时区表示）；无序列表（Group 内 Agent 顺序）；Attachments；大小写。明确"不是例外、受本规则约束"者包括 Result Duration（比较时按字符串处理）。
- statement id（ADL §2.4.1）："Statement ids MUST be generated by the LRS if a Statement is received without an id. Statement ids SHOULD be generated by the Learning Record Provider."；id 用 UUID（RFC 4122）。id 是幂等/冲突判定与 voiding 引用的键，即"身份锚点"。
- 冲突处理（ADL Communication §2.1.1/§2.1.2）："An LRS MUST NOT make any modifications to its state based on receiving a Statement with a statementId that it already has a Statement for. Whether it responds with `409 Conflict` or `204 No Content`, it MUST NOT modify the Statement or any other Object."；内容与已有记录不匹配时 SHOULD 返回 409；同一批次内重复同 id 的 statement 应 400 拒绝。
- IEEE 素材（§4.2.4）："Statements are expected to be unique and to be immutable. In this regard they are unchangeable and should not be deleted."（IEEE 用 should 级"不应删除"，弱于 ADL 的"预期永久"，见 3.2 张力。）

等级 A（ADL 1.0.3 与 IEEE 素材原文均在手；IEEE 正式 PDF 未核）。

### 1.2 LRS 存储模型：statement 流如何按 actor/activity 检索，是否天然 append-only

- 检索：Statement Resource GET（Communication §2.1.3）过滤参数 agent/verb/activity/registration/since/until/limit/format/ascending；返回 "a list of Statements in reverse chronological order based on 'stored' time"。actor 与 activity 是 statement 的一等字段（actor 必填、object 多为 activity），"按 actor/activity 检索"是规范内建查询维度；另有 X-Experience-API-Consistent-Through 一致性水位头。
- append-only 判定：对 ADL 三篇规范 + IEEE 素材全文检索 "append-only" 命中 0 次。API 契约层面只有 PUT/POST 写入 statement、无 statement 的 UPDATE/DELETE 端点、同 id 幂等 MUST NOT modify、撤回必须 voiding——"契约强制不可覆盖"成立；但 IEEE §4.2.4.2 明确 "the storage mechanism is not [specified]"，物理存储是否 append-only 由实现自定。因此"LRS 天然 append-only"定级 C（推断）：报告口径为"API 契约强制不可覆盖，物理存储机制规范不指定"。
- 例外通道：IEEE §4.2.4.1 "an LRS can reject Statements for many reasons not specified in this document and does not have to perpetually keep data beyond normal processes. This specification is not intended to usurp security, authority, or data management processes."（数据管理/安全流程可清除或迁移数据，规范不禁止。）

等级 A（条文原文）+ C（append-only 结论）。

### 1.3 voiding statement 机制：撤回不物理删除的规范原文

- 保留动词（ADL §2.3.2）：`http://adlnet.gov/expapi/verbs/voided`；voiding statement 以 StatementRef 为 object 指向被作废 statement 的 id。
- 不可再作废："Any Statement that voids another cannot itself be voided."
- 作废判定："An LRS MUST consider a Statement it contains voided if and only if the Statement is not itself a voiding Statement and the LRS also contains a voiding Statement referring to the first Statement."
- 授权与撤回语义：未获授权发起 voiding 的请求 SHOULD 以 403 拒绝；"unvoid" 语义 = "A Learning Record Provider that wants to 'unvoid' a previously voided Statement SHOULD issue that Statement again under a new id"（重新发布新 id，而非复活/改写旧记录）。
- IEEE 素材 §4.2.5 同构："Not all Statements are perpetually valid once they have been issued. Mistakes or other factors could dictate that a previously made Statement is marked as invalid. This is called 'voiding a Statement' and the reserved Verb 'http://adlnet.gov/expapi/verbs/voided' is used for this purpose. Any Statement that voids another cannot itself be voided."；空的 voiding statement（仅 id/actor/verb/StatementRef）可接受。

对应本项目"不物理删除"红线：xAPI 是"作废声明替代删除"的成熟标准级先例——原记录保留、仅语义作废，作废本身也是不可变事件。等级 A。
### 1.4 对"学习者掌握状态"的建模：事件流 vs 状态文档

- 事件流（statements）：掌握/进度以 statement 事件表达。cmi5（AICC 联盟规范）Best Practice #11 原文："For recording progress during a session, it is recommend to use a cmi5 allowed statement with the progressed verb (http://adlnet.gov/expapi/verbs/progressed) and a progress extension in the result ... Progress statements should not be sent for progress value of 100% as that indicates completion. Once the learner reaches 100% it is recommended that a cmi5 defined 'completed' statement be issued instead."；#13 建议以 satisfied verb statement 表达达标。事件只追加、可 voided、带 timestamp，天然含时间版本语义。
- 状态文档（State API / Agent Profile / Activity Profile）：ADL xAPI-Data.md §2.3 State Resource 原文——"Generally, this is a scratch area for Learning Record Providers ... need to persist state across devices."；单文档语义 "Stores, changes, fetches, or deletes"（覆盖写，DELETE 即物理删除），多文档按 since 拉取、可整批 DELETE；§3.1 ETag/If-Match 仅用于这三个 document 资源（乐观并发控制）。
- 版本语义差异：事件流=不可变、作废=voiding、查询按 stored 时间；document=可变当前值、覆盖即丢旧值、无内建版本链（除非客户端自存版本）、DELETE 物理删除。
- 边界：基础标准（IEEE 9274.1.1 / ADL 1.0.3）没有把"掌握状态"定义为规范级 MUST 数据模型；cmi5 属 profile/联盟规范级。对 M09 而言，"掌握状态"应建模为事件流中的派生量或显式版本化文档，二者版本语义完全不同。

等级 A。

### 1.5 对 M09"个人学习记录+时间版本"的可借鉴点

1. 事件不可变：statement 一经写入不可改、同 id 幂等不覆盖——M09 个人学习记录可采用"事件只追加 + 同 id 幂等"（对应红线甲/丁）；
2. 作废声明：错误/过时记录用 voiding statement 而非物理删除（对应"不物理删除"红线）；unvoid=以新 id 重新发布而非复活旧记录；
3. 按时间查询：since/until + stored 逆序 + 一致性水位——M09 的"按时间版本查询/回溯"可直接借用这套查询语义；
4. 双层模型：事件层（不可变）+ 状态层（可覆盖 document）——xAPI 先例不提供 document 版本链，M09 若需"掌握状态=版本化"须自行叠加（事件流重算或显式版本表）；
5. 冲突处理：同 id 冲突 MUST NOT modify + 409/204 幂等语义，可作为 M09 多端提交的并发底线；
6. 不可照搬：xAPI 的"不可变"是 API 契约，物理存储/清理由实现自定（IEEE 数据管理例外）——M09 若要求字节级防篡改须自行加固（哈希链/事件溯源理论归 B4，本分支不展开）。

### KF13. IEEE 数据管理例外：不必永久保存、不 usurp 数据管理流程
- 来源: https://opensource.ieee.org/xapi/xapi-base-standard-documentation（IEEE9274.1.1_LRSs.md §4.2.4.1 LRS Rejection Cases）

- 机构: IEEE LTSC / xAPI Working Group
- 日期: 访问 2026-08-12

- 映射启示: 标准允许数据管理/安全流程清除或迁移数据——"不物理删除"是默认语义而非绝对禁令；M09 需自行声明清理/迁移策略并在红线中显式化。

### KF14. IEEE 存储机制不指定 + 不可变等价比较规则

## 3 冲突与张力

1. **IEEE 正式版年份（2023）vs 开源素材 README（2024）**：IEEE SA/Xplore 与 Wikipedia 均指向 IEEE 9274.1.1-2023；但官方开源仓库 README 自述 "These open source artifacts were source material for IEEE 9274.1.1-2024"。两个编号并存（tier 4 project release 面向 2024 修订），本报告以 2023 正式版为准、素材作正文代理，冲突如实记录。
2. **ADL "cannot be logically changed or deleted" 语义 vs IEEE "should not be deleted" + 数据管理例外**：ADL 1.0.3 用 "expected to be permanent / the only way to undo is to void"，IEEE 素材用 "unchangeable and should not be deleted" 并附 "does not have to perpetually keep data beyond normal processes" 例外——即"不可删除"从强预期降为 should 级、且允许数据管理流程清除。对"不物理删除"红线：先例支持"默认不删、作废替代"，但不提供绝对禁令。
3. **"不可变"≠字节级不可变**：§2.3.1 例外清单（LRS 指派字段、Activity Definition、Verb display、时间戳序列化、无序列表、附件、大小写）较大，且 format=ids/canonical 会改变返回序列化——"不可变"指等价比较下的语义不可变，不是存储字节不可变。
4. **"天然 append-only" vs 存储机制不指定**：行业/搜索常把 LRS 描述为 append-only，但规范全文无 append-only 字样且 IEEE 明确 "the storage mechanism is not [specified]"——"天然 append-only"只能作为 API 契约层面的推断（KF22=C），不能写成规范要求。
5. **日期口径混用**：IEEE SA 元数据 designation=IEEE 9274.1.1-2023、Status=Active Standard；ADL 官方公告称 2023-10-10 开源化、3 月 30 日正式批准、公告 2023-11-22 发出；Wikipedia 写 "released 10 October 2023"；Veracity 写 "published ... on October 6th, 2023"。10-06/10-10/3-30 三个日期并存，本报告以"2023-10 发布（IEEE SA）"为准、其余如实标注。
6. **State API 的内部弱化**：§3.1 为 document 资源规定了 ETag/If-Match 乐观并发，但同一规范又允许无并发头的 PUT（覆盖写）——即"状态层可覆盖"是规范内建事实，版本化依赖客户端自觉；事件层与状态层的不对称正是 M09 最需要警惕的复制对象。

## 4 未决

1. **IEEE 9274.1.1-2023 正式 PDF 全文未到手**：IEEE Xplore 文档页（10273185）返回 202 机器限制页，仅 og:title/og:description 元数据到手；正文以 ADL 1.0.3 + IEEE 开源素材为代理，正式 PDF 标"未核"。
2. **LRS 物理存储是否 append-only**：规范明确不指定（KF14/KF22），任何 LRS 实现是否真的 append-only 需逐实现验证；本报告不评测具体产品。
3. **"掌握状态"无规范级 MUST 建模**：基础标准未定义掌握状态数据模型；cmi5 只是 profile/联盟级。M09 采用"事件流重算"还是"版本化文档"需自行决策。
4. **Personal Data Locker 无标准协议**：Wikipedia 提及个人 LRS/数据保险柜概念，但 xAPI 生态无统一"个人记录随人迁移"的标准协议；对 M09"个人学习记录"是方向性参考，非可复制规范。
5. **IEEE "normal processes"（数据管理例外）边界未定义**：什么算"normal processes"、什么场景可物理清除数据，规范未给出判定标准。
6. **Learning Locker 官方文档正文未核**：docs.learninglocker.net 为 Confluence 站点，正文抓取需 JS/登录，仅 README 到手；LRS 实现层面的检索/存储细节（如索引与归档）不在本报告证据范围内。
