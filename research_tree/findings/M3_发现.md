### 问题 2：影子读验证（新旧并行比对）如何落地，差异如何暴露

**落地方式**（Scientist 语义，B8c 已查证）：旧路径（old）= 真实 JSONL 记录 + Python 脚本查询；新路径（new）= 重建 RDF + SPARQL。6 个逻辑查询在两条路径上各实现一遍，逐条比对：
1. q_node_type_counts 节点类型计数
2. q_rel_counts 关系计数
3. q_node_inventory 节点全量清单（node_type/name_en/name_zh/statement/sections/aliases/anchors/parent/atomic 逐条规范化成行）
4. q_edge_inventory 边清单多集 (src,rel,dst)
5. q_edge_provenance 边证据多集 (src,rel,dst,origin,evidence.file,evidence.quote,rel_note)
6. q_dangling 悬空引用

**clean 基线（实测）**：真实 522/1433 上 6 查询**全部 MATCH，diff rows 0**（stdout 第 75–81 行）——新旧载体语义等价。

**差异如何暴露——四类偏离的实测行为**（stdout 第 87–148 行）：

| 偏离 | 暴露的查询 | 暴露层级 | 关键数字 |
|---|---|---|---|
| M1 丢一条边 | q_rel_counts、q_edge_inventory、q_edge_provenance | 计数级 + 行级 | requires 707→706；边清单 1 行 old=1/new=0 |
| M2 反向一条边（src/dst 对调） | q_edge_inventory、q_edge_provenance | **仅行级** | **q_rel_counts 仍 MATCH**（总数不变）；边清单 2 行：旧方向 1→0、新方向 0→1 |
| M3 篡改一个节点 statement | q_node_inventory | 字段级 | 1 行差异，diff 里能直接看到 append 的 "TAMPERED."；计数类全 MATCH |
| M4 丢一个被 22 条边引用的节点 | q_node_type_counts、q_node_inventory、q_dangling | 计数级 + 清单 + 悬空 | theorem 173→172；节点清单 1 节点 new='<absent>'；新侧悬空 1（in_new_only）；边清单/边证据仍 MATCH（边还在，只是端点悬空） |

**关键实测结论**：
- **计数级检查对"总量不变的对称变更"失明**：M2 反向边让边数不变，q_rel_counts 骗过，只有行级多集比对（q_edge_inventory/q_edge_provenance）能抓到。影子读若只比对计数，会漏掉方向性错误。
- **M4 暴露一个 RDF 实现陷阱**（本原型第一版就踩中）：RDF 里"节点存在"必须按 **rdf:type 判定**，不能按"作为 subject 出现"判定。被丢的节点仍是 22 条边的端点、其中 15 条以它为 src（于是它的 URI 以 subject 身份出现在 30 条三元组里：直连 rel + hasEdge），只要还有出边，其 URI 就继续存在于图里，按 subject 判定会把悬空漏报。修复 `new_dangling`（改用 `"node_type" in props[s]` 判节点集）后，q_dangling 才在 M4 下从 MATCH 变 MISMATCH。这正是"新侧实现"最容易写错的语义细节，影子读对照真实数据时应纳入这类悬空查询。

**结论**：影子读可落地为"同一组逻辑查询的双实现 + 规范化结果逐条比对"；差异暴露分计数级/行级/字段级三层，M2 证明必须做行级比对才能捕获方向性错误，M4 证明悬空判据要用类型判定而非 subject 出现。

### 问题 3：双写 vs 影子读 vs 从源重建三者的成本结构（实测数字）

（单进程可行性数字，非正式基准；微观操作 3 次重复取最小以压低噪声。全部来自 m3_cost_structure.py 的 stdout，第 156–187 行。）

| 路线 | 实测成本 | 数据结构 |
|---|---|---|
| 从源重建（一次性/次） | build 0.0986 s + NT 0.0468 s = **0.1454 s**；Turtle 0.8409 s | 每次全量 0.145 s，**确定性/幂等（字节一致）** |
| 双写（写时边际） | RDF 每节点 0.1085 ms、每边 0.0693 ms；JSONL 每节点 0.0120 ms、每边 0.0036 ms；合计**每节点 0.1205 ms、每边 0.0728 ms** | 写时边际极小，但**每笔写入都要付** |
| 影子读（每轮验证） | old 0.0021 s + new（6 SPARQL）1.1118 s + compare 0.0024 s = **1.1162 s/轮** | 成本大头在 RDF 侧 SPARQL |
| 批量：100 条新边 | 双写 0.0099 s vs 全量重建 0.1454 s vs 影子读 1.1162 s | 重建/双写 = **14.75×**；影子读/双写 = **113.18×** |

**结构性结论（由数字支撑）**：
1. **一次全量重建（0.145 s）比一轮影子读（1.116 s）便宜约 7.7×**——且重建是确定性、幂等的，重建这条路**根本不需要影子读**（重建产物与源的一致性由构造保证，本实验用字节一致验证）。
2. **双写边际（约 0.07 ms/边）虽小但是永久性成本**（每次写入都付）；重建是每批次一次性付 0.145 s。
3. 在本规模（1433）下，"JSONL 单真源 + 按需全量重建"的一致性维护成本最低。双写+影子读只有在 RDF 成为**线上服务载体**、写频高到"每批次全量重建太慢"时才划算——从实测看阈值远在百级边批次之上（100 边批次的重建只是双写写入本身的 14.75×）。
4. 与 B8 结论（"JSONL 崩溃安全是实测优势，任何迁移不得以丧失它换取语义完整性"）一致：从源重建以 JSONL 为真源、RDF 完全可派生，不牺牲 JSONL；影子读只在迁移验证期用来证明"新载体语义 == 旧脚本语义"，验证通过后即可停用。

## 5. 未决与风险

1. **数字波动**：build 0.09–0.34 s、Turtle 序列化 3.5–3.75 s 随运行波动，均为单机单进程可行性数字，不是性能基准；换机器/负载会变。
2. **内存口径**：tracemalloc 只计 Python 层分配（17.30 MiB），不含 OS RSS；rdflib 底层的实际驻留可能更高。
3. **影子查询集是我定义的最小覆盖**：6 个查询覆盖了本数据的关键语义，但 `x:` 节点专用字段（apostol_ids/strang_ids/divergence）与 `rel_note` 未进影子比对清单（只在 §1 的逐字段回读里验过）。影子读覆盖面取决于查询设计，不能据此宣称语义全等。
4. **RDF 集合语义丢顺序**：sections/aliases 在 RDF 中是无序多值；回读按排序多集比对 100% 通过，但若业务要求保持原顺序，需要额外 index 建模（本原型 anchor 已带 index，可推广）。
5. **4 个零锚点节点**：若按 SPEC 需补锚点或标 `origin: model` 豁免，否则是既存数据违规。
6. **未测场景**：真实并发/多版本/增量回放未测；影子读只验证了"重建自同一份 JSONL"与"偏离 JSONL"两类，未验证"JSONL 自身被篡改"（哈希链在 B8 其他分支）。

## 6. 建议的下一步

1. 数据侧：修复或标注 4 个零锚点节点（补锚点或按 SPEC 标 `origin: model`）。
2. 迁移设计：以 **"JSONL 单真源 + 按需全量重建（0.145 s、幂等）+ 迁移期影子读"** 为主路线；把影子查询集扩展到 `x:` 节点专用字段与 `rel_note`，并保留**行级多集比对**（M2 证明计数检查对方向性错误失明）。
3. 若需 RDF 作线上服务载体：测"写一批→重建→影子读"端到端循环，量化重建频率与双写边际的真实权衡（本实验给出 100 边批次重建≈双写写入的 14.75× 的起点数据）。
4. 若需顺序语义：把 anchor 的 index 建模推广到 sections/aliases，再跑一轮 round-trip 验证。
