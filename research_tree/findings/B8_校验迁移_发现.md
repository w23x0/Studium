# B8 校验、互操作与迁移路径 — 发现

## 0 一句话结论
现状"append-only JSONL + Python 校验脚本"的每一个薄弱点都有成熟替代件可单独或组合替换（配套 schema 文件、行内 provenance、哈希链防篡改、声明式校验规则版本化、RML/YARRRML 机械转换、双写/影子读迁移），其中"校验规则本身可版本化可审查"是程序式脚本当前最缺乏、且各先例一致支持的增益；但"JSONL 崩溃安全"（磁盘上任何时刻都是合法文件）是该组合的实测优势，任何迁移方案不得以丧失它换取语义完整性。

## 1 逐条回答
### Q1 现状隐式信息盘点（基于项目真实文件，非臆测）
见第 7 节表格。要点：边词表、状态机、四图边界、时间版本、处置单全部是"脚本/流程文档/目录命名里隐式存在、数据行内不显式存在"；锚点判等规则部分显式（audit-nodes.md 记录 grep -qF -f 方法）。

### Q2 校验技术谱系
- JSON Schema 2020-12（json-schema.org，社区规范非正式标准）能表达 enum/required/additionalProperties:false，即"封闭词表+引用完整"的声明式部分；规则本身是数据，可随 schema 文件版本化。
- SHACL/ShEx（见 B5）是图约束的声明式载体；SHACL-SPARQL 层可表达任意校验。
- 程序式脚本可表达任意校验但规则不可审查（规则在代码里、无版本标识）；本项目事故史（--help 清空）证明程序式校验自身也需要被审计。
- 查询式校验（SPARQL 否定/Datalog 否定谓词，见 B3）把"违规即查询结果"，规则即查询，可版本化。
- 可审计性结论：声明式/查询式 > 程序式；程序式可通过"规则文件+版本号+哈希"增强。

### Q3 JSONL 演进化强化路径（与替换路径同等查证）
- 配套 schema 文件：Frictionless Data Package / Tabular Data Resource 是真实先例——表格数据 + JSON Schema 描述（data resource 内嵌 schema 属性、RFC 2119 语言、CSV 须遵循 RFC 4180）。
- 行内 provenance：PROV-JSON 是 W3C 推荐标准（2013-04-30），可在行内嵌入 PROV 序列化；但"逐行 PROV 注解"作为整体没有找到标准先例（未核）。
- 逐行 JSON-LD：JSON-LD 1.1 是 W3C 推荐标准，且任何合法 JSON 文档都可用 JSON-LD 语义解释（推断 C）；名为"JSONL-LD"的权威规范未找到（未核）。
- 行哈希链：Crosby & Wallach（USENIX Security 2009）给出防篡改日志的数据结构先例；B4 已覆盖 RFC 6962。
- JSON Lines 自身定义三条要求：UTF-8、每行一个合法 JSON 值、\n 行分隔。

### Q4 互操作转换
- RML（rml.io 规范 v1.1.2）自述"This document is a draft of a potential specification. It has no official standing of any kind"——成熟但非标准；YARRRML 是人可读映射语言，参考实现 YARRRML Parser 生成 [R2]RML 规则，支持 R2RML/RML/RMLT 等 profile。
- "开放字段必须可稳定查询审查"的最小要求清单（推断 C，依据各语言能力证据）：字段名稳定且枚举可机检、引用可解析（id 可解析到行）、时间可排序、开放字段有类型标签。

### Q5 迁移模式
- 双写/影子读：常见工程实践，未找到权威规范级来源（B 级，未核）。
- Transactional Outbox（microservices.io）：解决"数据库更新与消息发布必须原子"的双写问题——本项目的迁移原子性先例。
- Schema 演化：Avro schema resolution 允许 reader 用不同 schema 读取 writer schema 写的数据（向前兼容机制）；Protobuf Editions 以 edition 2023 合并 proto2/proto3 定义格式、计划每年一版、以最小破坏为原则——"格式内嵌演进"的行业级先例。
- 规模量级：未找到公开的 500 节点级个人图谱迁移报告（未核）；本项目数据 522/1433/921 为本地文件，迁移成本主要由转换器与审计重跑决定（推断 C）。

## 2 关键发现
1. **JSON Lines 是事实格式，非标准**；三条要求（UTF-8/每行合法 JSON 值/\n 分隔）
   - URL: https://jsonlines.org/ | 标题: JSON Lines | 机构: JSON Lines 项目页 | 日期: 持续维护
   - 摘录: "The JSON Lines format has three requirements: 1. UTF-8 Encoding ... JSON Lines is a convenient format for storing structured data that may be processed one record at a time."
   - 等级: A
2. **JSON Schema 2020-12 是社区规范，非 W3C/ISO/IETF 正式标准**；json-schema.org 2026-07-06 有《JSON Schema and IETF》博客（Greg Dennis）
   - URL: https://json-schema.org/draft/2020-12/json-schema-core | 标题: JSON Schema Core 2020-12 | 机构: json-schema.org 社区 | 日期: 2020
   - 摘录: "$schema": "https://json-schema.org/draft/2020-12/schema"（文档以 draft 版本 URI 自标识）
   - 等级: A
3. **PROV-JSON 是 W3C 推荐标准（2013-04-30）**，提供 PROV 数据模型（实体/活动/代理与派生）的 JSON 序列化
   - URL: https://www.w3.org/TR/prov-json/ | 标题: PROV-JSON: JSON Serialization of PROV | 机构: W3C | 日期: 2013-04-30
   - 摘录: 见原文（W3C Recommendation 状态页）
   - 等级: A
4. **RML 规范自述无官方地位**（draft of a potential specification），YARRRML 是其上的可读映射语言并有参考实现
   - URL: https://rml.io/specs/rml/ | 标题: RML: A Generic Language for Integrated RDF Representations of Heterogeneous Data | 机构: RML 社区 | 日期: v1.1.2
   - 摘录: "This document is a draft of a potential specification. It has no official standing of any kind and does not represent the support or consensus of any standards organization."
   - 等级: A
5. **Avro 的 schema resolution**：数据必须携带 writer schema，reader 可用不同 schema 读取——"文件自描述+兼容演化"先例
   - URL: https://avro.apache.org/docs/1.11.1/specification/ | 标题: Apache Avro Specification | 机构: Apache | 日期: 1.11.1
   - 摘录: "A reader of Avro data, whether from an RPC or a file, can always parse that data because the original schema must be provided along with the data. However, the reader may be programmed to read data into a different schema."
   - 等级: A
6. **Protobuf Editions**：edition 2023 合并 proto2/proto3 为单一定义格式，计划每年一版、以最小破坏为原则——"格式内嵌演进"行业先例
   - URL: https://protobuf.dev/editions/overview/ | 标题: Protobuf Editions Overview | 机构: Google (protobuf.dev) | 日期: 2023-2024
   - 摘录: "Edition 2023 was as minimally disruptive as possible. It established the baseline and combined proto2 and proto3 definitions into a new single definition format."
   - 等级: A
7. **Event Sourcing（Fowler）**：所有状态变更以事件对象按序存储，可完整重建状态——M09 版本语义的经典表述
   - URL: https://martinfowler.com/eaaDev/EventSourcing.html | 标题: Event Sourcing | 机构: martinfowler.com | 日期: 2005-12-12
   - 摘录: "The fundamental idea of Event Sourcing is that of ensuring every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied for the same lifetime as the application state itself."
   - 等级: A
8. **Transactional Outbox**：数据库更新与消息发布必须原子，2PC 不可用时的模式——迁移原子性先例
   - URL: https://microservices.io/patterns/data/transactional-outbox.html | 标题: Pattern: Transactional outbox | 机构: microservices.io (Chris Richardson) | 日期: 持续维护
   - 摘录: "The command must atomically update the database and send messages in order to avoid data inconsistencies and bugs. However, it is not viable to use a traditional distributed transaction (2PC) that spans the database and the message broker."
   - 等级: A
9. **防篡改日志数据结构**（Crosby & Wallach）：用哈希链/树实现高效可验证的 append-only 日志
   - URL: https://www.usenix.org/conference/usenixsecurity09/technical-sessions/presentation/efficient-data-structures-tamper-evident | 标题: Efficient Data Structures for Tamper-Evident Logging | 机构: USENIX / Rice University | 日期: USENIX Security 2009
   - 摘录: "Efficient Data Structures for Tamper-Evident Logging, Scott A. Crosby and Dan S. Wallach, Rice University"（论文页，摘要级）
   - 等级: A（论文元数据原文到手；正文未全文核读，摘要级）
10. **Frictionless Tabular Data Resource**：CSV/表格数据 + JSON Schema 描述的配套 schema 先例
    - URL: https://specs.frictionlessdata.io/tabular-data-resource/ | 标题: Tabular Data Resource | 机构: Frictionless Data (Open Knowledge Foundation 系) | 日期: 2017-12-15
    - 摘录: "A single tabular data resource such as a CSV file. It includes support both for metadata such as author and title and a schema to describe the data, for example the types of the fields/columns in the data."
    - 等级: A
11. **本项目现状存储决策原文**：append-only JSONL（崩溃安全）、独立校验脚本+退出码、暂不选图数据库（触发条件：三跳以上遍历或实时交互查询）、graveyard 不物理删除
    - URL: 本地 docs/图工程调研/06-M08技术选型.md §7 | 标题: M08 技术选型 | 机构: 项目内文档 | 日期: 2026
    - 摘录: "数据格式 append-only JSONL：崩溃安全：磁盘上任何时刻都是合法文件；实测两次中断事故都靠这个止损"
    - 等级: A（本地原文）
12. **锚点校验实测方法原文**：grep -qF -f 固定字符串匹配、无空 pattern/多行 pattern
    - URL: 本地 docs/图工程调研/M08实验-Apostol微积分卷1/data/audit-nodes.md | 标题: M08 节点审计报告 | 日期: 2026-07-26
    - 摘录: "将每条 quote 逐字写入临时 pattern 文件，用 grep -qF -f <pattern> source/ch10/<file> 固定字符串匹配验证"
    - 等级: A（本地原文）
13. **"JSONL-LD 逐行 JSON-LD"未找到权威标准先例**（未核；推断：任何合法 JSON 行均可按 JSON-LD 语义解释，等级 C）
    - 等级: C（推断）/ 未核

## 3 冲突与张力
- 崩溃安全（JSONL 每条独立可解析）vs 语义完整性（跨行引用、版本、词表需要上下文）：两者可兼得——上下文进"配套文件+行内引用"，而不是塞进单行。
- 程序式校验的任意表达力 vs 声明式校验的可审查性：本项目红线"开放字段必须可稳定查询审查"倾向声明式，但锚点逐字判等（需访问源文件）不在 JSON Schema 表达能力内，须保留程序式或 SHACL-SPARQL/查询式。
- RML/YARRRML 成熟度（有参考实现）vs 非标准状态（自述无官方地位）：工程可用，标准承诺弱。
- 现有"图数据库暂不选"决策（基于无查询需求）与 B2"GQL 未定义交换格式"结论互洽：属性图语言标准成熟度不足反而不构成迁移障碍的消除。

## 4 未决

2. 行哈希链的个人密钥/签名锚点管理（无服务器场景）。
3. 双写/影子读在本项目的具体形态（源 markdown ↔ 图谱 JSONL 是否双写、以谁为真）。
4. 迁移后"崩溃安全"性质如何保持（目标格式是否仍是每行独立可解析）。
5. 500 节点级迁移公开报告：未找到，需本项目自测。
