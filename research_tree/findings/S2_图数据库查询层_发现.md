## 1. 父会话问题逐条回答（每问：结论+依据+等级）

### Q1 触发条件（三跳以上遍历 / 实时交互图查询的真实产品需求）现在是否已出现？M07 检索、M08 导航、学习过程图上游走逐项核对。

**结论：未出现，逐项不成立。**

- **M07 检索**：审查单原文需求为「按结构、文本、标签或问题查找」「可浏览资料目录」「来源引用与原文跳转」——这是文档级检索（目录/结构/标签/全文），不是图遍历；「跨资料检索标签与重复线索」是「找同标签、同来源或高度相关的资料」的检索线索，等价 1 跳标签匹配，不是 3 跳模式匹配。【A：本地 M07 审查单】
- **M08 导航**：「结构浏览与关系解释」原文为「查看节点、上下游、来源、状态和关系理由；基础实验可采用类似 Obsidian 的关系图，但图形界面只是查看方式」——「上下游」是 1–2 跳邻域；「图只是查看方式」明言图形不是查询引擎。【A：本地 M08 审查单】
- **学习过程中图上游走**：M05 路线规划是「比较通用结构与个人已形成知识、决定下一目标」的批量决策，不在用户直接等待路径；「上下文工程把 M07 结果按图节点组织给 Agent」属 §9 刻意不决定的运行时/上下文工程（红线段：运行时/向量检索刻意不决定），且上下文装配是批量步骤，不是实时交互图查询。【A：本地 M05 审查单、06-M08 §9】
- **对照业界判定框架**：LDBC SNB Interactive 用「复杂读=访问给定节点邻域（IC1 = ≤3 跳）＋短读＋连续更新」定义交互式图负载——本项目已知需求（按 id 取、按边遍历一两跳、全表校验）全是 SNB「短读/简单读」形态，**没有一个等价 SNB 复杂读（≤3 跳模式匹配）**。【A：LDBC SNB，T1 F2/F3 已核】
- 上一轮 T1 的判定清单（四条全不成立）仍然成立；本次未发现任何新需求改变任一条件。【A：T1 轨道发现；C：跨时点复核】

### Q2 组合方案形态：L0 JSONL + L1 RDF + 图数据库查询层（只读物化索引）——数据同步用双写/影子读/物化视图的成本与先例。

**结论：形态可行且有先例；但同步的正确选择是「从源重建的只读派生索引」，不是双写/outbox。**

- **双写**：B8c 已证——双写跨两个独立存储无原子保证（Stripe 4 步双写用于在线迁移；microservices.io 明言无 2PC 则「不保证事务提交」；Two Generals 证明理论不可解边界）。对本项目，双写意味着图引擎进入**写路径**，一旦两写不一致，引擎可能瞬间被当作真相——直接威胁「L0 是唯一真相」与三条红线。**对只读查询层是错误同步手段。**【A：B8c 全套（Stripe / microservices.io / AWS / Two Generals B 级）；C：应用到本场景】
- **影子读**：GitHub Scientist 语义=并行跑新旧读路径比对、差异告警。用于**查询层上线时的验收**（图索引查询结果 vs JSONL+脚本结果逐条比对）完全合适；它不是持续同步机制，是验证机制。【A：GitHub Scientist / Stripe，B8c K9/K10】
- **物化视图**：PostgreSQL 官方语义=「把查询结果持久化成表状；REFRSH 重建；数据不总是最新——但有时不需要最新」。这正是「只读派生索引 + 可接受陈旧窗口 + 按需重建」的直接先例。【A：PG rules-materializedviews】
- **从源重建（本项目推荐形态）**：L0 JSONL 是 append-only 事件日志（近似事件溯源），图索引是派生状态——Fowler Event Sourcing 的 Complete Rebuild「丢弃状态、从事件日志重放重建」、Azure「rehydration=重放事件得到当前状态」直接适用；CQRS 读模型「查询侧是派生的、写侧才是真相、可用 EagerReadDerivation 简化」同样适用。【A：Fowler EventSourcing / Azure / Fowler CQRS，均 B8c 或本次核】
- **成本结构（推断 C）**：不需双写/outbox（省掉一致性协议与 CDC 基建），只需 (a) 重建作业（解析 L0/L1 → 载入引擎），(b) 可接受的陈旧窗口（L0 append 与索引刷新之间），(c) 验收比对（复用 check_graph.py 结果做影子验证）。**代价远低于双写，且引擎永不进写路径。**
- **产业先例（查询层不移动数据）**：Neo4j Aura Virtual Graph「既不移动也不抽取数据湖的数据、把 Cypher 翻译成 SQL」；GraphAr「把属性图存成文件（parquet）、供多引擎读写」；ElasticGraph「以 ES/OpenSearch 为底、schema 驱动 GraphQL 查询层」。三者证明「源数据留在原地、另建只读图查询面」是成熟架构方向。【A：本次核】
- **本任务边界内**：当前未触发（Q1），故只把形态与同步方案写清、不落地实现。

### Q3 图数据库查询层能带来什么、不能带来什么：审计晋升状态机、时间版本回溯、开放字段稳定审查是否仍需应用层自建？

**结论：查询层只买「多跳遍历 + 交互延迟」两件事；三件应用层能力全部仍需自建。**

- **能带来**（业界共识）：图遍历（≤3 跳邻域/模式匹配）与交互式查询——LDBC SNB 定义的交互负载正是图引擎主业。【A：LDBC SNB / T1】
- **不能带来 1——审计晋升状态机**：候选隔离、审计 A/B 双轴、检测并行/处置单点、晋升——是**工作流状态机 + 人工裁定环节**，任何图引擎都不内建（T1 已结论「候选池/审计状态机 图引擎不专门解决」；06-M08 §4 用「候选池+审计晋升」作为独立规程）。【A：T1 / 06-M08；C：引擎能力归并】
- **不能带来 2——时间版本回溯**：图引擎默认只有当前状态，不做结论对象级版本链；时态属性图（B2c）与 SPARQL 版本化（B1c）都是「自建 + 非标准」；「旧结论不覆盖、可回溯」必须应用层在 L0/L1 层建模（版本字段/墓碑），查询层顶多把版本字段作为属性镜像出来，不能代管版本语义。【A：B2c/B1c 既有结论（前轮）；C：应用到查询层】
- **不能带来 3——开放字段稳定审查**：M08 的「9+other 封闭关系词表、节点字段开放、other 频率统计决定何时扩」是**校验规程**，由 check_graph.py 对 L0/L1 执行；图引擎的 schema 灵活性能容忍开放字段，但「稳定审查」= 审计规程，属应用层；若把审查对象从 L0/L1 挪到图索引，审查就不再对着真相跑——这恰恰是红线风险。【A：06-M08 §3；C：审查对象定位】
- **推论**：即使将来触发上图查询层，审计/版本/开放字段审查仍以 L0/L1 + 脚本为准，图索引只服务查询面。这与 T1「图引擎只补遍历、不整体迁移」一致。【A：T1】

### Q4 在查询层方案下，锚点 grep -F、不物理删除、四图不合并三条红线是否不受影响（原文仍留在 L0，引擎只读）？

**结论：在「引擎严格只读、L0 唯一真相、索引可丢弃可重建」前提下不受影响；风险集中在「引擎是否被放进写路径」这一点上。**

- **锚点 grep -F**：不受影响。锚点文本的**权威校验**永远对着源 markdown 文件跑 `grep -qF -f`（B7 已证该流程直接作用于源文件）；图引擎若镜像锚点文本只是副本，不改变校验对象。安全条件=节点身份（锚点集合）由 L0 决定、引擎不定义身份。【A：B7 本地 audit-nodes.md / 06-M08 §2；C：引擎定位】
- **不物理删除**：不受影响。判死写 graveyard（append-only），永远在 L0 侧；引擎若需反映判死状态，是索引从 L0（含墓碑）重建的副产品，引擎本身可丢弃，不存在「引擎里的物理删除」。安全条件=引擎永不接收删除请求。【A：06-M08 §7；C：索引可丢弃性】
- **四图不合并**：不受影响但**要求作用域纪律**。引擎只索引知识关系图（四图之三）；重建作业必须只喂 M08 数据，不导入产品模块图/执行工作流图/学习者状态图。【A：06-M08 §9；C：重建作业范围】
- **风险点（C）**：B7 已给出警示——Logseq DB 版「standard Markdown 导出无法捕获全部数据」证明「一旦图侧数据进 DB，正文不再是完整真相，锚点判等被间接化」。本项目只要保证 **引擎从不进写路径**（不做双写保索引新鲜，改为从源重建），该风险不成立；若未来有人为「实时性」引入双写，红线即被破坏——这是最需要写进决策约束的一点。【A：B7 Logseq db-version.md；C：风险推导】

## 5. 未决与风险

1. **Kuzu「something new」具体是什么未核**：README 只写「working on something new!」，org 内无后继仓库，官网/博客未见新项目名。风险=若后续有新嵌入式引擎上市需重做健康度核查；当前以「无可用后继」为准。【未核 + C】
2. **「从源重建索引」的陈旧窗口与重建成本无实测**：522/1433 规模重建必然秒级（T1 F14 DuckDB 4.4M 行秒级佐证），但「L0 append 与索引刷新之间查询面滞后多久可接受」是产品决策，未实测。【C】
3. **AGE 的只读约束**：AGE 是完整写能力（K2），若作查询层，只读须应用层/权限保证，AGE 自身不强制只读——与「引擎严格只读」约束存在实现张力。【C】
4. **Virtual Graph 是云 + Public Preview**：其「不移动数据」理念是强先例，但产品形态（Aura 云）与本项目本地自托管不匹配，只能借理念不能借实现。【C】
5. **中文权威来源抓取受限**：WebSearch 对中英文关键词全部返回空，中文站点（jiqizhixin/juejin）反爬或 404——本任务中文证据主要来自本地项目文档（A 级），外部中文文献未能补充，须在合成阶段知晓这一覆盖盲区。【未核】
6. **「查询层」命名歧义**：ElasticGraph 是 GraphQL 查询层（非图遍历）、Fuseki 是 SPARQL 查询层（RDF 侧）——与「图数据库查询层」不是同一物；引用时已分别标注，避免合成阶段混用。【C】
