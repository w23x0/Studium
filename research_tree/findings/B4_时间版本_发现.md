## 0 一句话结论

把 M09 的"复检/遗忘/重新掌握"建模为**位时（valid time + transaction time）的 append-only 事实流**（每次处置=追加一条事件，旧状态不物理删除），配快照/物化视图做性能回放，并用内容寻址（trusty URI / IPLD CID）对"锚点-节点-版本"链做自验证，即可同时满足可重放审计与可验证出处；**防篡改做到"逐行哈希链 + 定期签名锚点"是个人级最小机制，Merkle 树是对数级证明与规模化审计的效率升级，不是"必须/不必"的预设前提**（证据 F1-F17）。

## 1 逐条回答

### Q1. Bitemporal 数据模型的权威定义与最小实现要求？M09 的"复检/遗忘/重新掌握各成新版本"是单时间轴还是双时间轴问题？

- **权威定义**：时态数据库文献公认两个时间维（Kulkarni & Michels, SIGMOD Record 2012）：
  - *valid time*：该行被数据库用户认为正确反映现实的时间段（事实"何时为真"）；
  - *transaction time*：该行被提交/记录进数据库的时间段（"何时被记录"）。
  - 同一行的两个时间可任意不同（如保险单先入库、后生效）。两轴都有即 bitemporal；SQL:2011 用 *application-time period*（valid time）+ *system-versioned table / SYSTEM_TIME*（transaction time）分别实现，二者组合即 bitemporal 表（A 级：Kulkarni PDF 原文摘录见 F1/F3；B 级：Wikipedia Bitemporal model）。
- **最小实现要求**（据 A 级原文归纳）：
  1. 每行至少带"起-止"时间段且语义明确（SQL:2011 采用 closed-open 区间）；
  2. 至少一个轴由系统自动维护且用户不可改（system-versioned：GENERATED ALWAYS，用户不能改 Sys_start/Sys_end）；
  3. 对当前行的 UPDATE/DELETE 不覆盖旧值，而是把旧状态保留为历史行（UPDATE/DELETE 只关闭旧时间段、插入新行）——即"不物理删除、追加新状态"；
  4. 查询需要时间切片原语（AS OF / FOR PORTION OF / 区间谓词）。
- **M09 是单轴还是双轴？** 取决于需求粒度（分析性结论，非原文）：
  - 若系统只要求"现在知道什么/曾知道什么"（事实状态随时间演进），记录 valid time 即可——**单时间轴（valid time）**；
  - 若还要求"系统里当时记录下来的样子 vs 后来纠正后的样子"可对照审计（如"复检"发生在事实变化之后、"重新掌握"修正先前记录），就必须再加 transaction time——**双时间轴（bitemporal）**。
  - 语义映射：复检=对既有断言追加"新的掌握状态"事件（valid time 变化）；遗忘=结束某断言的 valid 区间（不是物理删除，见 Q5）；重新掌握=开启新的 valid 区间。三者都是**交易时间的追加动作**，其产物是 **valid time 上的新版本行**——这正是 bitemporal 表的典型形态（F4：SQL:2011 位时表可记录"知识状态的复杂曲折变化"）。

### Q2. 事件溯源用于个人学习记录的先例与已知陷阱？"审计晋升、处置单单点"与 append-only 事件日志是否同构？

- **先例**：事件溯源（event sourcing）= "把所有对应用状态的变更捕获为事件序列"（Fowler, 2005, A 级）。核心能力：完整重建（complete rebuild）、时态查询（temporal query）、事件重放（event replay）。应用状态可由事件日志派生，因此可任意缓存/建快照（Fowler 的 snapshot 段落；Azure 文档的 materialized view/rehydration，A 级）。工程上 git 就是典型事件溯源/版本化先例（IPFS 文档明确说 git 用 Merkle DAG 存历史，F13）。
- **已知陷阱**（A/B 级）：
  1. 查询/重建成本高，几乎必须配 CQRS + 物化视图（Azure、microservices.io，A）；
  2. 事件模式演进/事件版本化在事件量大后是长期包袱（dev.to 讨论，B）；
  3. 学习曲线、迁移成本、对后续设计选择的约束（Azure "Important" 警示，A）；
  4. GDPR 被遗忘权与不可变日志冲突（event-driven.io，B；dev.to，B）。
- **同构性**：是。事件日志本身就是"系统记录"（Azure：event store 是 system of record；microservices.io：100% 可靠审计日志）；**transaction-time 表本质上就是 append-only**（Snodgrass 原文："A transaction-time table is append-only. Changes to the monitored table, whether insertions, deletions, or updates, are in actuality insertions into the tracking log."，F2）。因此"审计晋升=对事件流的读取/物化视图投影；处置单=追加一条处置事件；处置单单点=对同一事件流的顺序追加与幂等"是天然同构的建模方式。注意：同构不代表"唯一正确"，若处置单需要"事后修正且可追溯修正"，应追加修正事件而非改写原事件（Q1 的 transaction time 语义）。

### Q3. Nanopublication 模型与 trusty URI 机制细节？IPLD/Merkle DAG 对"锚点-节点-版本"链式验证的适用性？

- **nanopublication 三段式**（nanopub.net Guidelines，A 级；Groth et al. 2010 W3C 版，A 级）：由 assertion（断言）、provenance（断言的出处："how this came to be"）、publication info（整个 nanopub 的出处：作者/时间戳）三张 RDF 图组成，外加 head 图把三者链接到 nanopub 自身 URI。最小要求：provenance 图必须链接 assertion 图；pubinfo 的 subject 必须是 nanopub URI 且应含归属与时间戳。
- **trusty URI**（Kuhn & Dumontier, IEEE TKDE 2015, A 级；trustyuri.net 规范 v1，A 级）：URI 末尾 45 个 Base64 字符 = artifact code，前两字符 = 模块标识（FA=纯文件、RA=RDF 图集、RB=带引用树），其余 = SHA-256 哈希。验证=对内容重算哈希与 URI 内哈希比对（"potential trusty URI" vs "verified trusty URI"）；可扩展到"引用树"（依赖对象也纳入验证），从而让引用关系本身可验证。
- **IPLD/Merkle DAG**（IPFS 官方文档 + IPFS merkledag spec + IPLD specs，A 级）：节点 ID = 内容哈希（CID）；"Merkle DAG 节点不可变，任何改动都会改变标识并影响所有祖先"；链接（merkle-link）本身就是目标哈希，因此"每个对象包含其子对象的可认证表示"；支持分支与合并（git 式）。对"锚点-节点-版本"链：每个版本节点的 CID 递归包含其父版本 CID → 只要保存锚点（某版本根 CID），即可沿链重算哈希验证任一节点未被篡改——适用性直接成立（F13）。
- 边界：具体 RDF/属性图序列化归 B1/B2，本分支只确认"时间/不可变/出处"三维机制可行。

### Q4. 透明日志先例：M08/M09 需要 Merkle 树级防篡改，还是逐行哈希链即可？各方案最小机制？

- **CT（RFC 6962 / RFC 9162，A 级）**：公开、可审计、append-only、*untrusted* 日志；用二进制 Merkle Hash Tree；每次追加后日志对树根+树信息签名（Signed Tree Head，STH）；Merkle consistency proof 用于证明 append-only 性质（前后树头一致），Merkle audit/inclusion proof 用于证明某叶在树内。
- **哈希链 vs 树**（Crosby & Wallach, USENIX Security 2009, A 级）："经典哈希链对 8000 万事件的日志证明随机一条事件在日志中，需要约 800 MB 追踪；我们的树结构只需 3 KB 证明，语义相同"。即**两者都能防篡改检测，差别在证明尺寸与审计效率（O(n) vs O(log n)）**。
- **最小机制结论**（据上述原文归纳，不预设）：个人学习记录（M08/M09）的最低可核机制 = **逐行/逐事件哈希链 + 定期把链头签名或锚定到外部（如本地密钥签名、可信时间戳）**；当需要向第三方快速证明"某条记录在历史中未被改动"、或审计频繁/数据量大时，升级为 **Merkle 树 + 签名树头**（Trillian 提供了通用化实现，A 级）。是否升级取决于威胁模型与证明效率需求，不是"需要区块链"或"不需要任何防篡改"的二元问题。

### Q5. "不物理删除（写回收站）"在各机制下的表达？

- **位时表/transaction time**：删除=追加（Snodgrass：insertions/deletions/updates 实际都是对追踪日志的插入）；SQL:2011 系统版本化表里 DELETE 只关闭 SYSTEM_TIME 区间、行转入历史（Kulkarni，A 级）。**没有"删除"，只有"状态终结"**。
- **事件溯源**：删除/更正都表示为追加新事件（补偿事件）；物理删除与不可变日志冲突，GDPR 场景用数据隔离/匿名化/留存策略处理（event-driven.io，B；dev.to，B）。
- **墓碑（tombstone）**：分布式存储中"被删除记录的标记"，查询不返回、之后按策略（如 Cassandra GCGraceSeconds/compaction）清除（Wikipedia Tombstone，B 级）。语义=逻辑删除占位。
- **nanopub 撤回（retraction）**：有。nanopub 文档（A 级）："A nanopublication is persistent, you can never edit nor delete it. You can however retract a nanopublication. This is done by publishing a new nanopublication that states that you retract the original publication."（断言形如 `<作者> npx:retracts <原np URI>`，要求签名公钥匹配）。
- **统一表达**：四种机制共享同一原则——**原记录不可变，变化通过"追加一条新记录/新状态/新声明"表达**；区别在于新记录的位置（同表历史行 / 事件流 / 墓碑位 / 独立撤回 nanopub）。

## 3 冲突与张力

1. **"100% 可靠审计日志" vs 被遗忘权**：事件溯源/不可变日志承诺"一切皆可重放"，GDPR 要求"可删除"；工程讨论的折中是数据隔离、匿名化、留存策略，而非物理删除（F7/F21）。这直接影响 M09"遗忘"语义：**遗忘应建模为状态终结/撤回声明，而非破坏日志**。
2. **哈希链 vs Merkle 树**：两者都能防篡改检测；Crosby 定量显示树在证明尺寸上差 5 个数量级（800MB vs 3KB，F15）。因此"要不要 Merkle 树"本质是"审计/证明的频率与受众规模"问题，不应预设。
3. **"untrusted logs" 的承诺模型**：CT 日志服务器本身不可信，靠任何人可审计+签名树头+一致性证明维持诚实（F14）；这与"把日志托管在自己机器上"的 M08/M09 场景不同——若攻击者掌控存储与密钥，任何哈希结构都能被整体替换，需外部锚定（F14/F15 隐含）。
4. **位时表 vs 事件溯源**：位时表由系统自动维护时间段（F3），事件溯源由业务定义事件语义（F5）；两者都可实现"不物理删除"，但查询模型不同（SQL 时间切片 vs 事件重放/物化视图）。
5. **术语口径不一**：Kulkarni 注明 SQL:2011 正文并未定义"temporal table/bitemporal"术语（其论文脚注）；Wikipedia 称 SQL:2011 提供位时语言构件但 2011 年多数产品未实现。引用时需注意"标准正文 vs 学界解读"之别。
6. **nanopub 撤回 vs 位时遗忘**：nanopub 撤回是"元声明"（新 nanopub 声明撤回旧 nanopub，F11），位时遗忘是"事实状态终结"（关闭 valid 区间，F1/F3）；两者都不可变地保留原记录，但语义层次不同，M09 若混合使用需明确哪一层承载"遗忘"。
