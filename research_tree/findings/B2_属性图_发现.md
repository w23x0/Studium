## 0 一句话结论

属性图在**模型层**原生支持"边挂属性"（节点与边都被形式化为可挂标签集与属性记录的一等实体），而 RDF 1.2 对"三元组的元数据"仍需 reifying triple（rdf:reifies + triple term）这类机制，因此与 RDF 的差异是**模型层差异**而非序列化层差异；GQL（ISO/IEC 39075:2024，2024-04 发布，610 页，付费无免费全文）与 SQL:2023 的 SQL/PGQ（ISO/IEC 9075-16:2023，只读 SQL 扩展）共享 GPML 图模式匹配核心，但 GQL v1 未定义交换格式、无内建图版本化语义（仅有时态值类型），故本卡"锚点=逐字字符串集合 + grep -F 硬校验"目前只能依赖具体引擎导出或社区格式（PG Format/PG-JSON 等），不存在 ISO 级标准文本可作锚点。

## 1 逐条回答

### Q1. 属性图模型对"边挂属性"的原生支持度？与 RDF 相比是模型层差异还是序列化层差异？

- **原生支持，且在模型层**。属性图的正式数据模型把"属性记录"定义在节点与边的并集上：PG-Schema（arXiv:2211.10962）Definition 3.1 定义属性图为元组 G=(N,E,ρ,λ,π)，其中 π : (N∪E)→ℛ 把**节点和边**都映射到"键→值"记录（"the record π(x) collects all properties of x (key-value pairs) and is called the content of x"）。即边是拥有一等身份、可挂任意属性记录的实体，不是派生的关联结构（A 级：F13）。
- openCypher v9 同一立场：属性图是"a directed, vertex-labeled, edge-labeled multigraph with self-edges, where edges have their own identity"；relationship（边）是"an entity that encodes a directed connection between exactly two nodes"，而"An entity is assigned a set of properties"（A 级：F11）。TinkerPop/Gremlin 亦定义属性图为"a directed, binary, attributed multi-graph"（A 级：F24）。
- **对候选池状态、审计晋升记录引用、处置单单点引用**：三者都是"边上的键值对或引用型属性值"，属性图模型层无任何阻碍（属性值是任意标量/引用标识符）。具体到本树的"候选池/审计晋升/处置单"语义映射属设计层内容，标准文献不规定业务语义（不越界，仅陈述模型能力）。
- **与 RDF 的差异是模型层差异，不是序列化层差异**：RDF 数据模型的基本断言是 (s,p,o) 三元组，边（谓词）本身不是可挂属性的实体；要对"一条边"附加元数据，RDF 1.2 需要 reifying triple："A reifying triple is a triple where the predicate is rdf:reifies and the object is a triple term"，以引入额外资源节点承载元数据（A 级：F23）。RDF 1.1 时代则是标准 reification（四元组/语句节点）。属性图把"边挂属性"作为一阶构造内建于数据模型，RDF 需要显式的再加工机制，故差异在**模型层**。

### Q2. GQL（ISO/IEC 39075）的标准化状态、范围？SQL:2023 的 SQL:PGQ 范围与 GQL 的差异？

- **GQL 已发布**：ISO/IEC 39075:2024（Information technology — Database languages — GQL），Edition 1，状态 Published，Publication date 2024-04，610 页，CHF 227，ISO/IEC JTC 1/SC 32 制定（A 级：F1）。JTC1 官方文章注明正式发布日 2024-04-11（A 级：F5）；gqlstandards.org 于 2024-04-17 宣布发布（A 级：F3）。
- **获取性**：ISO 官网页与 iTeh 提供免费"Document Preview"，但仅目录级（A 级：F2 抓到了 iTeh 预览 PDF 全文目录）；正式文本付费（CHF 227），无开源/免费正式文本。权威解读可免费获得：JTC1 News 官方文章（7 页 PDF，A 级：F5）、gqlstandards.org 官方社区页（范围说明，A 级：F3/F4）。
- **范围**：ISO 官方摘要——"This document defines data structures and basic operations on property graphs. It provides capabilities for creating, accessing, querying, maintaining, and controlling property graphs and the data they comprise... This document provides a vehicle for portability of data definitions and manipulation among GQL-implementations"（A 级：F1）。JTC1 解读："GQL is a database language, not just a graph query language"（含 DDL/DML/事务/目录，A 级：F5）。
- **SQL:PGQ 与 GQL 的差异**：SQL/PGQ = ISO/IEC 9075-16:2023（2023-06，Edition 1，269 页，A 级：F6），是 SQL:2023 的新增第 16 部分。据 GQL/SQL:PGQ 联合论文（arXiv:2112.06217）：SQL/PGQ"specifies how to define graph views over an SQL tabular schema, and to run **read-only** queries against them"；两项目由同一 WG3 维护，"the identical core of both PGQ and GQL is a graph pattern matching sub-language, here termed GPML"（A 级：F7）。差异要点：SQL/PGQ 是 SQL 之上的只读图视图+查询扩展（GRAPH_TABLE 中的 GPM），无独立图 DDL/DML；GQL 是完整数据库语言（gqlstandards.org："The draft GQL standard builds on the Graph Pattern Matching language and is a full DB language, including: DML – Create, Read, Update, Delete; DDL – Create Graph Type, Create Graph, Create Graph from Graph Type"）（A 级：F3）。

### Q3. 属性图如何表达"三类结构"（不变量层、各自表示层、对齐边）？PG-Schema 能否表达封闭边词表 9+other？

- **不变量层**：GQL v1 已有 Graph Type（目录 §4.13.2 "Graph types and graph element types"、§12.6 "<create graph type statement>"、§17.3 graph type reference；A 级：F2），即对图施加"节点/边类型、标签、属性类型"约束的有限结构；学术侧 PG-Schema/PG-Keys 提案给出更丰富的形式化（PG-Types 多继承 + PG-Keys 键与参与约束，A 级：F12-F14）。PG-Schema 原文："PG-Schema (Property Graph Schema Language) comprises PG-Types and PG-Keys. PG-Types specify possible combinations of labels and properties in nodes and edges of different types..."（A 级：F13）。
- **各自表示层**：节点/边 = 标签集合 + 属性记录（PG-Schema 模型 λ:(N∪E)→2^ℒ 与 π:(N∪E)→ℛ；A 级：F13）；openCypher v9 同（F11）。
- **对齐边**：就是属性图里普通的有向、有标签、可挂属性的边（"A relationship is an entity that encodes a directed connection between exactly two nodes"，且实体可挂属性，A 级：F11）。"三类结构"为本调研树内部术语，标准文献没有这一命名；标准层能提供的对应物即"Graph Type（不变量）+ 节点/边记录（表示）+ 有向带属性边（对齐）"。
- **PG-Schema 能否表达封闭边词表 9+other**：能表达封闭词表。PG-Schema 显式区分 open/closed 类型："closed types forbid any content that is not explicitly mentioned, whereas open types allow any such content"；节点类型示例："The node type customerType requires nodes to carry both labels Person and Customer, and no other labels"（A 级：F13）。"9 种已知类型 + other 兜底"可用标签表达式（&、|、可选标签 ?）加封闭类型表达"九选一"组合，但标准/提案文本中没有"9+other"字样的现成语法，需自行组合（other 兜底可用开放属性或额外标签判别，属设计层，未核到一字不差的先例）。

### Q4. 时间版本化：GQL/Cypher 标准层是否有内建时间/版本语义？社区建模范式？

- **GQL v1**：值类型层有时态类型（iTeh 目录：§3.10 "Temporal terms and definitions"、§4.16.6 "Temporal types"（含 Introduction to temporal data / Temporal instant types / Temporal duration types / Operators）、§20.26-20.29 datetime/duration 值表达式与函数；A 级：F2），但完整目录检索 valid time / transaction time / bitemporal / version / snapshot 全部 **0 命中**——即只有"时间戳/时段"值类型，没有"图版本化、有效时间、事务时间"语义。
- **openCypher v9**：全文检索 temporal **0 命中**；只有 timestamp() 标量函数（"Returns the difference, measured in milliseconds, between the current time and midnight, January 1, 1970 UTC"），无时标类型、无版本语义（A 级：F11）。
- **社区建模范式**（仅列范式与来源，通用机制归 B4）：
  1. **快照+delta（anchor+delta）**：AeonG（PVLDB 2024）——"we propose a novel anchor+delta strategy, in which we periodically create a complete version (namely anchor) of a graph object, and maintain every change (namely delta) between two adjacent anchors"（A 级：F18）。
  2. **时间戳/有效区间属性法**：VLDB Journal 2021（T-GQL）——"a temporal graph data model, where nodes and relationships contain attributes (properties) timestamped with a validity interval"（A 级：F17）；ADBIS 2022 综述式工作提出时态模型+高层查询语言（A 级：F21）；CAiSE 2022 提出时态属性图演化分析操作符（A 级：F22）。
  3. **双时态（bitemporal）**：Rost 等（arXiv:2111.13499，Oracle/莱比锡大学）提出 bitemporal property graph 模型+时态图查询语言+原型（A 级：F19）；ADBIS 2024 论文在 AeonG 上扩展 valid+transaction time（"we extend the recent graph database AeonG to consider both transaction and valid time"，A 级：F20）。

### Q5. 属性图的标准序列化/交换格式是否存在？锚点校验是否必须依赖具体引擎导出？

- **GQL 未定义交换格式**：GQL v1 完整目录（iTeh Document Preview，含全部章节标题）检索 exchange / serialization **0 命中**；ISO 摘要只承诺"portability of data definitions and manipulation"（语言层可移植性），没有序列化格式条款（A 级：F1/F2）。
- **openCypher 也没有**：官方资源只有规范文档、EBNF/Antlr 语法、TCK 测试套件（"The openCypher specification documents, containing a complete reference for openCypher query language. The TCK (Technology Compatibility Kit) is a Cucumber-based set of tests..."），无交换格式（A 级：F9）。
- **社区有交换格式提案**：PG Format / PG-JSON / PG JSONL（arXiv:1907.03936 "Property Graph Exchange Format"：propose interoperable serialization formats for property graphs；A 级：F15）；pg-format.github.io 提供规范与转换工具（A 级：F16）。
- **结论**：截至 GQL v1，不存在 ISO/标准层的图序列化格式，锚点硬校验（逐字字符串集合 + grep -F）只能锚定到**具体引擎的导出格式**或**社区格式（如 PG-JSON）**；不同引擎导出的文本形态不保证一致，跨引擎锚点不可移植（除非以某社区格式为准绳）。

## 3 冲突与张力

1. **GQL 发布日期的口径差异**：ISO 页面标 "Publication date: 2024-04"；JTC1 脚注 "officially published 2024-04-11"；gqlstandards.org 公告日期 2024-04-17（"The GQL Standard is published!"）。三者月份一致，日级口径不同（正式出版日 vs 官宣日）——引用时应注明口径。
2. **openCypher 的"规范"地位**：opencypher.org 自称 "open source specification"，社区常把它当"事实标准"，但 v9 明确不是 ISO 正式标准（正式标准是 GQL，openCypher 自身定位为"向 GQL 演进"）。锚点若锚到 openCypher 文本，是锚到工程规范而非标准。
3. **GQL v1 的 schema 约束能力存疑**：PG-Schema 提案（学术）宣称支持 STRICT/closed 类型（"CREATE GRAPH TYPE fraudGraphType STRICT" 示例），且 GQL v1 目录确有 graph type DDL；但 GQL v1 正文未到手，无法确认 v1 的 graph type 是否等同 STRICT/封闭标签词表（未核，见未决问题 5）。
4. **"边挂属性"模型层差异 ≠ 表达能力差异**：属性图原生支持边属性，RDF 1.2 用 reifying triple 也能表达同样的语义（只是要多一层机制）；因此"模型层差异"不意味着 RDF 表达不了，只意味着属性图无需额外机制。
5. **"GQL 有时态类型" vs "GQL 无版本语义"**：两者并存且易混淆——GQL v1 有时态**值类型**（datetime/duration/instant），但没有 valid time / transaction time / bitemporal / version 等**时态数据模型语义**；引用时需区分值类型与时态建模。
