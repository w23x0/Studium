# 叶子 L2 版本层选型发现

> 任务：L2 版本层二选一——FHIR _history 式（B6d）vs 时态属性图双区间 assert/retract/correct（B2c），叠加 revlog 分离（B6b）与 L3 本地哈希链审计（B6e）
> 选型综合员：深度调研引擎 v3 L2｜日期：2026-08-13
> 证据等级：**A/B=原文到手或实测（P/M 系列沿用 v1.2 原判）；C=推断/组合推理**。推断一律标 C，不把 C 写成结论。
> 范围：不做性能基准（项目红线）；只做工程形态与语义对照；不代产品裁决"设计待定"项（标"待 M04/M09 边界讨论裁决"）。

## 0 一句话结论

**条件性选 FHIR _history 式**：在叠加 revlog 分离 + L3 哈希链的前提下，FHIR 的资源级版本 id + _history 只追加历史 + verificationStatus 验证状态机（B6d，A 级）与 M09"结论对象 + 证据边 + 复检"的映射成本最低——它可直接落地为 L1 RDF 语义层上的"每资源每版本一个命名图 + 版本元数据三元组"（B1c IC 策略，A 级先例），无需在 RDF atemporal（B1c，A 级）上自建双区间语义；时态图双区间（B2c）语义上最贴合"复检=correct/遗忘=retract/重新掌握=assert"，但其在 RDF 层无标准表达、无统一交换格式、TGMS 仅 2026 预印本无复现（B2c，C 级），工程整合成本更高。**当产品先裁决两个设计待定项（复检后旧结论可见性、单轴/双轴）且结论支持"旧结论按时间可回溯 + 事务时间轴可满足（或双轴用标准词汇补足）"时，FHIR 式胜出；若裁决必须原生双区间 + 旧结论纠正后即不再当前（ZEP 式），需重估时态图路线。**

## 1 Q1–Q4 逐条回答

### Q1 两条路线的技术形态与工程成本（对 M09 的具体需求）

M09 需要：closed 记录、证据边、时间版本（"旧结论不覆盖、可回溯"）、复检后旧结论处理、候选输出。

#### 1.1 FHIR _history 式（B6d）

**形态（全部 A 级原文）**：
- **资源粒度**：结论对象 = 一个资源，`meta.versionId` 随每次内容变更更换、同资源内唯一、无固定顺序（不透明标识，客户端不得假设数值大小即新旧）（B6d Q1）。
- **版本历史**：create/update/delete 都产生历史条目；`_history` 端点（实例/类型/系统三级）只追加不可改写；旧版本"retained for audit/integrity purposes"；delete=墓碑条目（不删历史）；vread 单版本读取；过滤 `_since/_at/_count`（B6d Q2）。**单链、不支持并发版本/多分支**（B6d Q2 明示）。
- **验证状态机**：`verificationStatus`（unconfirmed/provisional/differential/confirmed/refuted/entered-in-error）+ `clinicalStatus`（active/recurrence/relapse/inactive/remission/resolved）；约束 con-5：entered-in-error 时不得有 clinicalStatus（B6d Q4）。对过去版本纠错：用 Provenance 指向旧版本（不覆盖）（B6d Q4）。
- **审计**：Provenance（记录创建/修订/删除某版本的活动、可指向任意版本）/ AuditEvent（安全日志）（B6d Q5）。

**映射到 M09**：
| M09 需求 | FHIR 式映射 | 等级 |
|---|---|---|
| closed 记录 | 每个闭环级个人形成记录 = 一个资源（或复合资源组） | A（形态）+ C（粒度适配） |
| 证据边 | 资源引用（Reference）+ Provenance（谁/何时/基于哪一旧版本/为何变更）；M09"结论由哪个模型、哪个版本得出"可落为 Provenance 的 agent/activity 字段 | A（Provenance 能力）+ C（落法） |
| 时间版本（不覆盖、可回溯） | versionId + _history（追加）+ vread（取指定版本） | A |
| 复检后旧结论处理 | 复检=新版本 + 新 verificationStatus（confirmed/refuted）；写错撤回=entered-in-error（用 Provenance 指向旧版本） | A（语义）+ C（映射） |
| 候选输出 | FHIR 无候选/审计/晋升概念，需自建 | C |

**工程成本**：最小集合（版本 id + 历史端点 + 审计三件套）可直接移植（B6d Q5）。三个注意点：
1. "纯文件存储"无规范条文——FHIR 官方文件形态是 Document/NPM/Downloads/FSH（分发/交换形态），"目录即仓库"属推断性设计（B6d Q3，C 级）。
2. 不支持多分支（B6d Q2，A 级）——M09 若需分支需自建（git/IPLD 等）。
3. 图语义（高层个人结构、复合对象/子图）FHIR 不提供，需在版本之上自建（C 级）——但 M09 的图语义本就要自建（S1 判定图引擎不内建候选晋升，见 Q2 红线丙）。

#### 1.2 时态属性图双区间（B2c）

**形态（全部 A 级原文）**：
- **粒度**：顶点/边/属性各有有效时间 + 事务时间双区间（close-open `[ts,te)`）（TPGM+ F1；TGMS 半开区间 F10）；属性级位时解决"属性变更即复制整元素"的存储爆炸（TPGM+ F1；AeonG 语义/拓扑分开 F8）。
- **写前日志**：所有写（assert/retract/correct）经过 append-only write-ahead event log，日志是状态与审计的事实源，重放复现同一 store digest；失败批次也留日志、重放按原样跳过（TGMS F10）。
- **快照算子**：T-PGQL `FOR TX TIME AS OF/BETWEEN/FROM-TO/ALL`（F2）、T-GQL `SNAPSHOT/BETWEEN`（F4）、TerminusDB time-travel（F13）。
- **语义**：assert=登记新信念并切分重叠区间；retract=关闭有效时间（遗忘/不再为真）；correct=关闭错误版本的事务时间并记录替换（"我们错了，错误记录保留"）；位时不可变性=as-of 过去时间结果在后续纠正后逐字节不变（TGMS F10）。ZEP 用四时间戳、矛盾时置旧边失效而非删除（F11）；Graphiti validity window、失效而非删除（F12）。

**映射到 M09**：
| M09 需求 | 时态图映射 | 等级 |
|---|---|---|
| closed 记录 | 结论对象 = 顶点（或子图） | C（映射） |
| 证据边 | 图边（带双区间） | C（映射） |
| 掌握状态 | 属性（属性级位时，贴合熟悉度/掌握度变化） | C（映射）+ A（机制） |
| 时间版本（不覆盖、可回溯） | 版本行带区间、快照从版本行重建；旧版本关闭区间而非删除 | A（机制）+ C（映射） |
| 复检后旧结论处理 | 复检=correct（发现错误）/ assert（重新掌握同一事实）；遗忘=retract；旧版本永久可查 | A（机制）+ C（映射） |
| 候选输出 | 需自建（TPG 无候选/审计/晋升） | C |

**工程成本**：需要引入/实现双区间版本行 + 快照算子 + 事件日志重放（TGMS 是最直接先例但为 2026-07 预印本、无第三方复现，B2c U5）。三个注意点：
1. 无统一 TPG 交换格式（B2c Q5/冲突 4，C 级）——各方案自定承载（JSON 事件流 / git 式文档），M09 若需交换须自定 schema。
2. 单轴 vs 双轴取舍未定（B2c 冲突 1/未决 1）——若只需"当前掌握状态+历史版本"可单轴（valid time）；若要审计"当时记录 vs 后来纠正"必须双轴。
3. 属性历史必须用属性级位时建模，否则存储爆炸（B2c 冲突 2，C 级分析）。

**两路线关键差异**：FHIR 式是"资源级单链版本 + 独立审计资源"，与 L1 RDF 整合有现成先例（B1c IC）；时态图式是"元素级双区间 + 快照重建"，语义最贴 M09 但工程上多一层自定义区间语义。

### Q2 三条红线满足度（结合 S1/P2/M3 已实测约束）

**红线甲 不物理删除**：
- FHIR：旧版本只审计保留、delete=墓碑不删历史（B6d Q2，A 级）；规范明令无改写/删除过去版本之途（B6d Q2，A 级）。HAPI 的 X-Rewrite-History 是规范外扩展、自认 "not supported by the FHIR specification"（B6d Q3，A 级）——若采纳必须作为显式、可审计、默认关闭的操作（B6d 冲突 1）。
- 时态图：retract/correct 关闭区间而非物理删除（TGMS F10 / T-GQL F4 / ZEP F11 / Graphiti F12，全 A 级）；所有时态方案中物理删除都不是"遗忘"的标准做法（B2c Q4）。
- **与实测约束兼容性**：两者都在存储层保障不物理删除，与 P2 实测（pySHACL 8.48s/522 节点、~108× 于 JSONL+脚本、A 级且经独立审计 PASS）不冲突——P2 确立校验层是只读审计层定位，不物理删除不由校验层保障；与 M3 实测（从 L0 重建 0.145s/522 节点、幂等字节一致，A 级）不冲突——重建不破坏历史，反而为"历史可重放/当前视图可重建"提供实测底数（v1.2 D7.3）。
- 边界提醒：B4c 指出工程界常态是压缩/保留期后物理删除（Kafka、Azure，A 级）与红线冲突；若未来采纳压缩类方案，M09 历史必须视为**不可压缩的键空间**（B4c 冲突 3，C 级推断）。两条路线都要求历史区不可压缩。

**红线乙 可回溯**（无性能基准，只做形态 + M3 数字外推，外推标 C）：
- FHIR：按资源回溯，`_history` 返回该资源全部历史（含墓碑）、vread 单版本读取（B6d Q2，A 级）。成本=每资源历史条目数（版本数），**按资源 O(版本数)、不扫全图**（C 级推断：522 节点规模历史条目数百–数千级；增长到全学科后资源数几千–几万、历史总量随版本数线性增长——FHIR 无内建 delta，_history 条目是完整快照）。全量回溯（系统级 _history）需扫全部资源历史（C 级）。
- 时态图：AS OF 快照从版本行过滤重建（B2c Q2，A 级机制）。522 节点规模重建成本**可参考** M3 实测 0.145s 作为"版本行规模相当"时的量级底数（C 级外推，注意 M3 是 RDF 重建不是 TPG 重建）；增长到全学科后重建随版本行总数增长、双区间判断增加复杂度，可用物化锚点优化（AeonG anchor+delta，F8 A 级）（C 级判断）。
- 结论：两路线都满足可回溯红线；FHIR 按资源回溯天然避免全图重建，时态图 AS OF 是快照重建语义（更贴近"某时刻图状态"查询但成本形态不同）。

**红线丙 审计晋升状态机**：
- S1 判定（v1.2 §3 S1 引用）：图引擎不内建"候选池审计晋升"状态机（NebulaGraph R3/R4 需自建）。**此判定对两条路线都适用**：
  - FHIR 的 verificationStatus 提供的是"结论验证状态"先例（confirmed/refuted/entered-in-error，B6d A 级），**不是**候选→审计→晋升流程；Provenance/AuditEvent 提供审计资源先例（B6d Q5，A 级）。
  - 时态图的 assert/retract/correct 是时间操作，不是晋升流程；TGMS write-ahead 日志提供审计轨迹事实源（F10，A 级），但状态机需自建。
- 推荐表达（B4c Q5，C 级）：状态机=候选→审计→晋升→废弃（墓碑）；每个迁移=追加新行/新事件；废弃=墓碑标记+终止时间；默认视图排除墓碑、审计视图全量可见——与 M08 候选池+审计晋升、M09 时间版本不覆盖互洽。
- 结论：**两条路线的候选池+审计晋升状态机都需自建**（S1 判定 + B4c C 级设计），不构成区分因素；FHIR 多给一个"验证状态"内建先例，时态图多给一个"审计日志内建"先例。

### Q3 revlog 式叠加适配（B6b）

B6b 分离的本质（全部 A 级）：历史流 revlog 追加（id=复习时刻时间戳、INSERT OR IGNORE 幂等）+ 当前状态 cards 覆盖分离（可由完整 revlog 重算的派生量，FSRS S/D）（B6b KF1/KF2/KF3）。叠加注意红线反例：Anki 撤销物理 DELETE revlog 行、v2 迁移批量 UPDATE 历史行（B6b KF4，A 级）——M09 必须把撤销/迁移实现为追加反向事件/新版本，不能物理删/改写；FSRS 参数只有当前值、无参数版本链（B6b 冲突 5，C 级）——M09 复检要"按当时参数重算"须自建参数/模型版本链；身份是自增 cid 非内容锚点（B6b KF3）——M09 身份仍须锚点集合（红线乙）。

**叠加到 FHIR _history 式**：
- FHIR 的 `_history` **天然就是 revlog 式历史流**（每次变更追加一个历史条目）；当前版本=资源最新版本（"新版本即当前"，非覆盖写）。
- 分离的具体化 = M09 审查单方向 3"历史区与现有边缘区"：历史区（_history 追加条目）+ 当前区（各资源最新版本=当前视图，可从历史重放重建）。两路线都支持此方向 3（C 级：FHIR 式是 _history/最新版本，时态图式是事件日志/物化后端）。
- 降规模成本：FHIR `_history` 条目是完整资源快照（无内建 delta），体积随版本数线性增长 → 用 B1c 的 CB 增量补丁策略（只存版本间差异，A 级 K10）做历史压缩，代价是 delta 传播/重建成本上移（B1c K10，A 级）。即 revlog 式叠加 = 历史存变更事件（增量）+ 当前视图从最新版本重建（C 级设计，A 级先例支撑）。

**叠加到时态图双区间**：
- TGMS **天然就是 revlog 式**：append-only write-ahead 事件日志（=revlog）+ 物化后端（=cards，可重放重建同一 store digest）（B2c F10，A 级）。叠加成本为零——它本来就是。
- 降规模成本：日志增量小（事件），物化可丢弃、从日志重建（TGMS digest 概念 + M3 重建幂等底数 0.145s 作量级参考，C 级外推）。
- 需补的：参数/模型版本链同样需自建（B6b 冲突 5）；状态机自建（Q2 红线丙）。

**结论**：revlog 分离对两条路线的适配都是"把历史流（追加）与当前状态（可重建派生）分开存储"——FHIR 式需要把 _history 明确为历史区、当前版本明确为可重建派生物（可配 CB 增量压缩）；时态图式（TGMS 形态）本身即是此结构。叠加收益：历史区保持 append-only 红线、当前区可丢弃重建（M3 底数）、两区都进 L3 哈希链。

### Q4 可判定选型建议

见 §2 对照表、§3 设计待定项、§4 最终工程形态。核心裁决逻辑：

**决定性理由（选 FHIR _history 式，3 条）**：
1. **与 L1 RDF 语义层整合成本最低**：L1 已定为 RDF 1.2 + TriG 命名图（v1.2 D2），RDF 图 atemporal（B1c K3，A 级）。FHIR 资源级版本化在 RDF 上落地 = 每资源每版本一个命名图 + 版本号元数据三元组放默认图（B1c IC 策略，A 级原文）+ PROV-O/OWL-Time 生命周期词汇（B1c K11/K12，A 级），**无需在 atemporal RDF 上自建双区间版本行**；时态图双区间在 RDF 上无标准表达（B2c 冲突 4，无统一 TPG 交换格式，C 级），需自建 reification/版本行或与 L1 分叉。
2. **FHIR 提供"版本 id + 历史端点 + 审计 + 验证状态机"完整最小集合**（B6d Q5，A 级），且 **refuted vs entered-in-error 的区分**（B6d A 级）正好覆盖 M09"复检推翻旧结论" vs "写错撤回"两种不同语义（B6d 冲突 5）；其"旧版本保留仅用于审计、delete=墓碑、单链"（B6d A 级）与红线不物理删除、B6b revlog 事件追加幂等（INSERT OR IGNORE，B6b KF1）、M3 重建幂等（A 级）直接同构。
3. **资源级粒度贴合 M09"每结论对象独立演化 + 按对象回溯"**：复检一个结论不影响其他结论；`_history` 按资源查询、vread O(该资源版本数)、不扫全图（C 级推断），增长到全学科后按对象回溯成本可控；时态图 AS OF 需版本行过滤重建，在 RDF 层无先例（C 级）。

**选时态图（另一条）的代价**：
1. 双区间（valid+transaction）在 RDF atemporal（B1c K3，A 级）上无标准表达，需自建 reification/版本行（C 级）；TPG 无统一交换格式（B2c 冲突 4，C 级）。
2. 若改走属性图层，则与 D2 已定的 L1 RDF 语义层分叉（v1.2 D2）。
3. TGMS 为 2026-07 预印本、无第三方复现（B2c U5），无成熟工程实现可参考；单轴/双轴取舍、复检可见性策略未决使工程上多一层自定义区间语义（B2c 冲突 1/6，C 级）。
4. 需实现快照算子 + 双区间索引 + 事件日志重放，工程成本高于 FHIR 三件套移植（C 级判断）。

**建议表述**：**条件性选 FHIR _history 式，当**：产品在 M04/M09 边界讨论中裁决两个设计待定项（复检后旧结论可见性、单轴/双轴）后，若结论是 (a) 旧结论按时间可回溯（审计视图全量可见）且当前视图只显示最新；(b) 事务时间轴即可满足（或双轴可用 PROV-O/OWL-Time 标准词汇在版本元数据上补足）——则 FHIR 式胜出。若产品裁决必须原生双区间、且旧结论在纠正后即不再当前（ZEP 式失效语义，B2c F11），需重估时态图路线。

## 2 两条路线对照表

| 维度 | FHIR _history 式（B6d） | 时态属性图双区间（B2c） |
|---|---|---|
| 版本粒度 | 资源级（结论对象=资源），meta.versionId 随内容变更、同资源唯一、不透明 | 元素级（顶点/边/属性各有 valid+transaction 双区间，close-open） |
| 历史存储 | `_history` 只追加、旧版本保留仅审计、delete=墓碑；单链不支持分支 | append-only write-ahead 事件日志为事实源 + 物化后端重放重建（TGMS） |
| 版本查询 | `_history` 按资源列历史 + vread 单版本；按资源 O(版本数) | AS OF/SNAPSHOT 快照算子，从版本行重建；可配 anchor+delta 物化锚点 |
| 复检语义 | 新版本 + verificationStatus 状态机（confirmed/refuted/entered-in-error） | correct（关闭错误版本事务时间+记录替换）/ assert（重新掌握） |
| 遗忘语义 | 新版本置 refuted/inactive 或墓碑 | retract（关闭有效时间）/ ZEP 失效（置 tinvalid） |
| 审计 | Provenance（可指向任意版本）+ AuditEvent（A 级先例） | write-ahead 日志本身是审计轨迹（A 级先例）；Provenance 类需自建 |
| 状态机内建度 | verificationStatus 内建先例；候选→审计→晋升**需自建**（S1） | assert/retract/correct 内建先例；候选→审计→晋升**需自建**（S1） |
| L1 RDF 整合 | 直接：每资源每版本一个命名图 + 版本元数据（B1c IC，A 级） | 需在 atemporal RDF 上自建双区间版本行，或无统一 TPG 交换格式（C 级） |
| 红线甲 不物理删除 | 旧版本只审计保留、墓碑不删历史（A 级）；X-Rewrite-History 为规范外扩展须默认关闭 | retract/correct 关闭区间而非删除（A 级） |
| 红线乙 可回溯 | 按资源回溯、不扫全图（C 级推断）；522 节点历史条目数百–数千级 | AS OF 快照重建；522 节点量级参考 M3 0.145s（C 级外推，非基准） |
| 红线丙 审计晋升 | 需自建（S1）；FHIR 提供验证状态 + 审计资源先例 | 需自建（S1）；TGMS 提供审计日志先例 |
| revlog 叠加 | _history 即历史流；当前版本=最新版本；可配 CB 增量压缩（B1c K10） | TGMS 天然是事件日志+物化（revlog 式）；零成本叠加 |
| L3 哈希链叠加 | 每版本写入=一条审计事件进本地哈希链 + 周期签名 checkpoint | 每写事件进哈希链 + 周期签名 checkpoint（TGMS digest 概念可复用） |
| 交换格式 | FHIR 官方文件形态为 Document/NPM/FSH（A 级），但"纯文件存储"无规范条文（C 级） | 无统一 TPG 交换格式（C 级），各方案自定承载 |
| 迁移成本 | 资源/版本文件化 + B1c 命名图映射；可用 M1-M4 迁移四件套（A/B 级） | 事件日志/版本行导入；与 L1 RDF 桥接或分叉（C 级） |
| 主要未决 | 纯文件存储无规范条文（C）；单链无分支；图语义需自建 | TGMS 预印本无复现（B2c U5）；单/双轴取舍（C）；复检可见性策略（C） |

## 3 对设计待定项的输出（哪些必须先裁决）

以下五项必须先由产品裁决，才能落地本选型（不代产品裁决，作为输入列出）：

1. **复检后旧结论的可见性**（B2c 冲突 6；B4c 冲突 5）：TGMS 式（correct 后 as-of 过去时间仍返回旧值，位时不可变性）vs ZEP 式（失效即不再当前）→ 决定 correct/refuted 语义与双视图设计（默认视图排除墓碑、审计视图全量可见）。**FHIR 式两种可见性都能表达**（当前视图=最新版本、历史视图=_history 可查），时态图式的选择影响 correct 语义实现。
2. **单轴 vs 双轴**（B2c 冲突 1/未决 1）：若只需"当前掌握状态 + 历史版本"可单轴（valid time）；若要审计"当时记录 vs 后来纠正"（复检/纠正对照）必须双轴。**FHIR `_history` 天然是事务时间**（何时写入/变更）；若需双轴，在版本元数据上用 PROV-O/OWL-Time 补 valid time（B1c K11/K12，A 级词汇）即可。此裁决决定"FHIR 式是否够用"。
3. **版本粒度**（M09 审查问题 4）：复检/遗忘/提取失败/重新掌握是否都形成新版本而不覆盖旧记录——决定版本条目生成规则。
4. **M09 体积单调增长的三个方向**（M09 审查单末尾）：内部版本化 / 历史移交 M01 / 分两区（历史区+当前边缘区）。方向 3 与 revlog 分离（B6b）、FHIR 式（_history+最新版本）、时态图式（日志+物化）都兼容；但"区划写进数据结构"与否需产品裁决。
5. **候选池→审计→晋升状态机定义**（M09 审查问题 5）：自动生成条件、自动/人工审核、晋升/退回权限。两条路线都需自建（S1 判定图引擎不内建；B4c C 级设计），本选型不区分，但必须先行定义。

注：模型身份版本链（M09 需求：证据引用记录"哪个模型、哪个版本得出"，必须是实际执行模型而非可变别名）也需产品确认保留粒度，但其技术承载两条路线均可（FHIR 用 Provenance agent/activity 字段；时态图用事件日志字段），不构成选型区分项（C 级）。

## 4 建议的最终工程形态（条件性选 FHIR _history 式）

若采纳本建议，叠加 revlog 分离 + L3 本地哈希链审计后的形态：

**存储（L2 版本层落在 L1 RDF 之上）**：
- 每个 M09 结论对象（closed 记录/个人形成记录）= 一个资源，带 `meta.versionId`（不透明、随内容变更更换）。
- 历史 = 每资源每版本一个命名图（B1c IC 策略：版本名=图名 + 版本号元数据三元组放默认图，A 级先例）；旧版本命名图只追加、不可改写；删除=墓碑条目（不删历史）。
- 当前视图 = 各资源最新版本（可重建派生：从历史重放或从 L0 JSONL 重建，M3 幂等底数 0.145s/522 节点，A 级）；历史区与当前区分离（对应 M09 审查单方向 3）。
- 状态字段：verificationStatus 映射（confirmed/refuted/entered-in-error → 已确认/已推翻/录入错误），复检/遗忘/重新掌握作为事件类型标记（借鉴 B6b reset 事件=版本边界，A 级）。
- 证据边 = Provenance 式资源/记录：记录"该结论由哪个模型、哪个版本得出"（M09 模型身份要求）+ wasDerivedFrom（指向被取代的旧版本，B6d A 级）。
- 候选池 = 候选资源 + 自建审计晋升状态（S1 判定需自建）。

**查询**：
- 当前视图：各资源最新版本。
- 历史查询：按资源列全部版本（`_history`）+ 取指定版本（vread）。
- 时间点视图：版本号↔时间戳映射（应用层维护）；若需 valid time，用 OWL-Time/PROV-O 词汇挂到版本元数据（B1c A 级词汇）。
- 若规模增长后历史体积成为问题：对历史命名图启用 CB 增量补丁压缩（B1c K10，A 级先例），代价是 delta 传播/重建上移（C 级判断）。

**L3 审计叠加（B6e）**：每版本写入 = 一条审计事件进本地哈希链（`Ci = H(Ci−1 ∥ Xi)`，Crosby & Wallach，A 级），事件内容=版本 hash + 操作（create/update/tombstone）+ 时间戳 + 状态变化 + 模型身份；周期签名 checkpoint（ssh-keygen -Y / GPG，A 级组件），可选外部时间戳锚定（OpenTimestamps/RFC 3161，A 级组件）。逐行哈希链在千条级完全可行（B6e 未决 6 附注，C 级）；规模增长后升级 Merkle 历史树（B6e KF-02 对数级证明，A 级）。

**迁移**：复用 M1–M4 迁移四件套（v1.2 D7）：从 L0 JSONL 映射资源/版本（yaml-ld 管 frontmatter + RMLMapper 管结构化，含前置归一化与去重）；重建幂等校验（M3）；canonical SHA-256（内容）+ 文件字节 SHA-256（字节）双判据（M4）；影子读只作迁移期验收（M3）。

**不采纳时的备选形态（时态图式）**：append-only write-ahead 事件日志（assert/retract/correct）+ 物化后端（顶点/边/属性带双区间，可从日志重放重建）+ AS OF 快照查询 + 事件日志进哈希链。此形态在语义上最贴 M09，但需在 RDF atemporal 上自建双区间表达或与 L1 分叉（C 级），工程成本更高。

## 5 未决与风险

1. **纯文件存储无规范条文（C 级）**：FHIR 官方文件形态（Document/NPM/FSH/Downloads）是分发/交换形态，不是"目录即仓库"的存储模式；把 FHIR 版本语义落到文件系统属推断性设计，落地前需原型验证（B6d Q3）。
2. **FHIR 单链无分支（A 级 + C 级）**：M09 若出现"同一结论对象的多分支修订"（如并行假设的复检），FHIR 无先例，需自建或转向 git/IPLD（B6d Q2/Q5；B4b）。
3. **时态图路线未彻底封死**：若产品裁决必须原生双区间 + ZEP 式失效语义（B2c F11），或 M09 需要"某时刻全图状态"查询为主，需重估时态图路线——本选型是条件性的。
4. **TGMS 预印本无第三方复现（B2c U5）**：若最终改走时态图，其"位时不可变性"仅属性测试验证、未见独立复现，需原型验证。
5. **历史体积单调增长**：红线"不物理删除"意味着历史区不可压缩（B4c 冲突 3，C 级）；FHIR `_history` 完整快照体积随版本数线性增长，CB 增量压缩会把 delta 重建成本上移（B1c K10，A 级），是否启用需规模实测（当前禁基准，C 级判断）。
6. **pySHACL 校验层定位（A 级）**：P2 实测校验 8.48s/522 节点、~108× 于 JSONL+脚本，校验层必须保持只读审计层定位、不进版本写路径；版本写入不得触发全量校验。
7. **L1/L2 词表统一未做（v1.2 §4.1，C 级）**：L1 `node_type` vs L2 `kind` 两套键名映射到不同谓词；版本层落地前需先定正式 `@context`。
8. **交换格式缺失（C 级）**：RDF 命名图版本语义无标准图命名约定/标准版本元数据词汇（B1c Q2，C 级）——需项目自定约定并写入契约。
