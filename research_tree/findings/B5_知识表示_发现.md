# B5 知识表示语言与词表治理 — 发现报告

分支：本体/约束语言与封闭词表的形式化载体
调研员：B5 分支调研员 | 环境：Windows + PowerShell + 网络抓取 | 日期：2026-08-12

## 0 一句话结论

本案的"9 类+other 封闭边词表""锚点存在""引用完整"等校验需求本质是封闭世界下的数据完整性校验，SHACL（sh:in + sh:closed）与 ShEx（valueSet + CLOSED）是最贴近的形式化载体，OWL 2/SKOS 因其开放世界语义只能表达声明性约束而不能完成"只有这些值"的封闭判定，KIF/Common Logic/Topic Maps 属于历史替代路线，本案结论为不采用。

## 1 逐条回答

### Q1 "封闭边词表 9 类+other"的五种形式化载体对比

| 载体 | 可机器校验性 | 可演化性（加第 10 类成本） | 与数据格式耦合度 |
|---|---|---|---|
| OWL 2 ObjectOneOf（oneOf 枚举） | 可表达"恰好这些个体"的类，但开放世界+无唯一名假设，不能断言"只有这些值"（缺失≠假）；不提供校验协议 | 低：改类表达式即可，但"新增第 10 类"需同时处理旧实例一致性；且封闭语义与 OWL 开放世界冲突 | 低耦合：声明于本体层，不绑定序列化 |
| SKOS ConceptScheme | 可声明"X,Y,Z 属于方案 A"，但规范明言"无法封闭 scheme 边界"（no way to close the boundary）；本身无校验机制 | 中：加概念零成本，但正因为无法封闭，不能作为词表封闭校验载体 | 低耦合：数据模型即 OWL Full 本体 |
| SHACL sh:in（+sh:closed） | 可机器校验：W3C 推荐标准，sh:in 定义"每个 value node 是 SHACL list 成员"，字面量精确匹配；sh:closed 限定"只能有显式枚举的谓词" | 高（最友好）：改 SHACL list 加一项即可；校验时精确匹配新值 | 中耦合：校验图与数据图分离，但 SHACL 自身是 RDF 图 |
| ShEx valueSet + CLOSED | 可机器校验：社区组最终报告，valueSetValue 支持枚举+stem/通配，CLOSED 关键字 | 高：改 schema 的 value set 即可；CLOSED 形状加属性需同时加 extra | 中耦合：schema 独立于数据，有 ShExJ(JSON)/ShExC(紧凑) 双语法 |
| JSON Schema enum | 可机器校验：enum 要求值等于数组元素之一（可含 null），const 为单元素 enum | 高：加枚举项即可，最直接 | 高耦合：只对 JSON 数据；若数据是 RDF/图，需先转换，且丢失 RDF 语义 |

结论：若数据侧是 RDF/图，SHACL sh:in 或 ShEx valueSet 是"封闭词表"最合适的载体；纯 JSON Schema enum 仅在数据本就以 JSON 承载时适用；OWL oneOf 与 SKOS 均不提供封闭校验语义。

### Q2 不变量层/表示层/对齐边的三分结构：本体层还是数据层？OWL 2 能否表达"对齐边只能跨层"？

- 类层级、属性 domain/range 属本体层：RDFS/OWL 2 可用 rdfs:subClassOf、rdfs:domain/rdfs:range 声明"对齐边的端点必须是某两类"，这是本体层的类型约束。
- 但"只能跨层、不能同层"是一个**完整性/封闭性**断言：OWL 2 开放世界语义下，未声明的同层边只是"未知"而非"非法"。要判定"不允许出现同层对齐边"，需要封闭世界校验（如 SHACL sh:closed 排除同层谓词、sh:in 限定端点类型），这属于数据校验层。
- 分区/命名图/标签是数据层组织手段：OWL 2 本体层不原生表达命名图（RDF 1.1 命名图属数据层语法，归 B1/B7 边界）；若"层"以命名图或标签实现，则"只能跨层"的约束需要校验语言（SHACL 可借助 SPARQL 约束检查 $this 所在图/谓词路径）或外部图结构检查。
- 结论：类型声明放本体层（OWL/RDFS），封闭性/跨层性放数据校验层（SHACL/ShEx/自定义脚本），两者职责不同，不能互相替代。

### Q3 OWL 2 profiles（EL/QL/RL）在 522 节点/1433 边规模下的推理必要性

- 规模：522 节点/1433 边极小。OWL 2 EL/RL 的推理问题是多项式时间，QL 的 CQ 回答可 LOGSPACE（相对数据量）；在如此规模下推理复杂度不是工程瓶颈，但也不因此构成"需要推理"的理由。
- 项目三类校验需求逐项判断：
  - 锚点存在（锚点是否出现在源文本中）：**不在 OWL 表达能力内**——这是字符串/全文级、且依赖文本内容的事实，属开放世界之外的逐字校验（OWL 可声明"锚点类存在个体"，但不能校验"该个体的字面值逐字出现在某文本串中"，除非把文本片段建模为个体并用 SHACL-SPARQL/外部全文检索）。
  - 词表封闭（边类别限于 9 类+other）：OWL 可声明类与枚举（ObjectOneOf），但**不能**在开放世界语义下完成"只有这些值"的封闭判定；需 SHACL/ShEx 封闭校验。注意 oneOf 声明"恰好这些个体"在推理上表达的是类的外延恰好等于枚举——OWL 语义下若数据中出现枚举外个体且声明其为该类成员则产生不一致，这其实是**能**表达的，但"其他类别"（other）与"出现未声明值即校验失败"的体验更接近数据校验；且无唯一名假设使枚举成员同一性需显式声明（DifferentIndividuals）。
  - 引用完整（引用目标存在）：可建模为对象属性+domain/range，OWL 推理可做类型与存在性的一致性检查（如 SomeValuesFrom 约束），但"每个引用必须解析到存在的节点"这类完整性断言同样属于封闭世界校验（需 SPARQL/SHACL 对数据图做完整性查询）。
- 结论：三类需求中，只有少部分（类层级一致性、子类型/逆关系/传递性推导、不一致检测）是 OWL 推理能做的；封闭词表、锚点逐字、引用完整性本质上都是封闭世界数据校验。**不预设需要或不需要本体推理**：若本体层需要类层级推导/不一致检测，EL 或 RL 足以覆盖 522 节点规模；若只是校验数据，则 SHACL/ShEx 即可。

### Q4 SHACL vs ShEx：差异、工具生态、状态约束表达能力

- 设计理念（来自《Validating RDF Data》第 7 章对比）：ShEx 设计为"RDF 图的文法/schema"，受 Yacc、RelaxNG、XML Schema 启发，目标是描述图结构并据此校验；SHACL 设计为"约束语言"，延续 Schematron 思路，依赖 SPARQL 表达约束。
- 规范地位：SHACL 是 W3C 推荐标准（2017）；ShEx 是 W3C 社区组最终报告（CG-FINAL，2019），未升级为推荐。
- 语义：ShEx 语义有数学基础（递归 shape 有定义）；SHACL Core 用自然语言+非规范 SPARQL 模板定义，SHACL 递归形状语义在推荐中未定义（学术文献已给出补充语义，如稳定模型语义）。
- 封闭形状：ShEx 有 CLOSED 关键字；SHACL 有 sh:closed+sh:ignoredProperties；两者机制相似但语义细节不同。
- 工具生态：ShEx 实现语言多样（Jena/Ruby/JS/Haskell/Python 等）；SHACL 多数实现基于 Jena+TopBraid，含成熟商业实现（TopBraid SHACL API 等）。
- 状态约束（候选→审计→晋升/淘汰）：两种语言都能表达"某节点必须处于某状态集合"（SHACL sh:in、ShEx valueSet），但"状态机迁移规则"（谁可以从候选到审计、历史轨迹）不是两者的设计目标：SHACL-SPARQL 可写任意 SPARQL 约束（需状态已作为数据存在），ShEx 可组合形状描述当前状态，但**迁移/历史/时序约束**需要额外数据模型（状态字段、审计记录、时间版本——与 B4 时间/版本分支相关），两者都只是"状态字段值约束"载体，不是工作流引擎。

### Q5 KIF/Common Logic/Topic Maps：解决过什么、对本案的启示

- KIF（Knowledge Interchange Format，dpANS NCITS.T2/98-004）：为"异质计算机系统间交换知识"设计，类比 PostScript——不做内部表示、不面向人机交互，只做交换中介。后来 Common Logic（ISO/IEC 24707:2007）以 CLIF/CGIF/XCL 三种方言将其标准化，并声明 RDF/OWL 也可视为 CL 的子语言。问题："纯逻辑知识交换"在 Web 语义栈兴起后大部分被 RDF/OWL + 序列化标准取代；且 CL 标准正文未能抓到（未核）。
- Topic Maps（ISO/IEC 13250:2003）：以 topic/association/occurrence 编码知识并连接信息资源，与 RDF 同期竞争"知识表示与索引"生态位；WG3 解散、维护移交 WG8，实际生态萎缩。启示：同为"图式知识组织"方案，RDF/OWL 系因 Web 生态与标准链完整胜出。
- 对本案启示：不采用 CLIF/Topic Maps 是合理结论——本案需要的是"可机器校验的图数据约束"，而 CLIF 是纯逻辑交换语言（无约束校验协议），Topic Maps 是索引式知识组织（无封闭词表/校验语义）。但其历史教训（交换用最小逻辑核心、标准要配工具生态）可佐证：选 SHACL/ShEx 这类"标准+工具+校验语义"齐全的载体。

## 3 冲突与张力

1. **SHACL 名义上提供"封闭"约束，但其推荐文本并未声明全局封闭世界语义**：sh:closed/sh:in 是逐 shape 的封闭校验；SHACL 推荐正文未出现"closed world assumption"字样（基于本次抓取检索，未找到——若存在则属漏检，标未核）。实践中的"封闭词表"是每个形状上局部声明的结果，不是语言级 CWA。
2. **SKOS 专为词表/叙词表设计，却明确不能封闭方案边界**：这是"描述性词表"与"规范性封闭词表"的定位冲突——SKOS 适合描述，不适合强制。
3. **OWL 可表达枚举（ObjectOneOf），但开放世界+无唯一名假设使"枚举外即非法"的校验体验落空**：要么用不一致来"表达"封闭（代价高、语义别扭），要么放弃 OWL 做校验。
4. **ShEx 语义更严谨（递归、数学语义），但只是社区组最终报告；SHACL 是 W3C 推荐、生态（尤其商业）更强，但递归语义留白**：标准地位与语义完备性二选一的张力。
5. **JSON Schema enum 简单直接但深度耦合 JSON 数据格式**：若本项目数据是 RDF/图或需同时服务多种表示，纯 JSON Schema 会丢失 RDF 语义且无法覆盖锚点逐字/引用完整等跨表示校验；若数据本就是 JSON，它是最低成本的方案。
