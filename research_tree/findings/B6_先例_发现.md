## 0 一句话结论

五个先例领域都不约而同地把"知识/记录单元"做成不可变（immutable）+ 显式版本或追加式历史 + 机器可读的身份与校验：mathlib 用源文件+编译产物+import 依赖图与 hash trace，MML 用版本化目录与文章内标签引用；Anki 用 SQLite 表记录复习历史但 revlog 并非强制 append-only；xAPI/FHIR 把不可变陈述/版本化资源定为规范级要求（FHIR 甚至给出"无 REST、纯文件存储"时把版本放进资源自身的官方做法）；审计日志领域则给出 Merkle 树、内容寻址、哈希链等可机械校验的最小实现——因此"节点身份=锚点集合 + 不可覆盖 + 可机械校验"在技术上都有成熟先例支撑，且"先例做法"仅是存储格式选项，须结合本案红线自行裁决，不能直接照搬。

## 1 逐条回答

### 1.1 数学知识库：mathlib（Lean 4）与 MML

**mathlib 的存储：** mathlib4 是 Lean 4 定理证明器的用户维护库（mathlib4 README）。构建系统 Lake 规定：**模块是构建系统可见的最小代码单元**，一般由一个 Lean 源文件（.lean）+ 一组二进制库（Lean 的 .olean 与 .ilean，如开启 precompileModules 还有系统共享库）表示；模块间通过 import 互相依赖；Lake 对每个模块产出 olean/ilean/c/o 等 facet（Lake README）。依赖关系以**显式文本形式**写在源文件头部：mathlib 根文件 Mathlib.lean（约 453KB）开头就是 public import Std、public import Batteries、public import Mathlib.Algebra.AddConstMap.Basic 等约数千条 public import；每个具体模块文件（如 Mathlib/Algebra/AddConstMap/Basic.lean）同样在文件头列出 public import/import。上游依赖（batteries、Qq、aesop 等）在 lakefile.lean 中声明（require "leanprover-community" / "batteries" @ git "main"），Lean 工具链版本固定在 lean-toolchain 文件（当前 leanprover/lean4:v4.34.0-rc1）。增量构建的"过时判定"由 **trace（一般是 hash）** 完成：目标 trace 由其 inputs（源文件、Lean 工具链、imports 等）推导，用于验证目标是否最新（Lake README）。

**MML 的存储与演化：** MML 由 **Mizar 文章（.miz 文本文件）** 组成，全部文章经 Mizar 校验系统验证为两条基础文章（built-in notions 与 tarski.miz 的 Tarski-Grothendieck 集合论公理）的正确推论（mizar.uwb.edu.pl/library）。存储按**版本化目录**组织：https://mizar.uwb.edu.pl/version/ 下列出 7.11.01_4.117.1046/ 至 8.1.15_5.94.1493/ 与 current/（2025-05-30），版本号形如"系统版本_数据库版本_修订号"；current/mml/ 下是数千个 .miz 文件（文件名+日期+大小）。MML 官方修订页给出三类演化：**authorized revision**（写新文章时推广/改进旧文章的定理定义，连带修改依赖它的旧文章）、**automatic revision**（新校验软件出现，如定理等价性检查工具，可删去等价定理；或 Mizar 校验器增强）、**reorganization**（改变文章处理顺序，即重建 Mizar Data Base 时发生，罕见）。

**知识单元身份：** mathlib 中一个知识单元（定理/定义）的标识 = **模块路径 + 模块内名字**（Lean 的 fully-qualified name），模块路径即文件路径（Mathlib/Algebra/AddConstMap/Basic.lean 对应 Mathlib.Algebra.AddConstMap.Basic）。MML 中一个知识单元（定理/定义/模式）的标识 = **文章文件名 + 文章内标签/编号**，例如 tarski.miz 中 "theorem :: Extensionality ... by TARSKI_0:2" 即以 TARSKI_0:2 引用其它文章的定理。二者都是"命名空间内名字"式身份，依赖文件内容之外的名字约定，改名/重构会破坏引用稳定性（mathlib 有 --deprecated_module 之类的废弃模块机制，说明改名真实存在）。与本案"节点身份=锚点集合"的**关系**：先例做法 X（名字/路径身份）与红线乙（身份=锚点集合）的关系是——X 说明主流数学库以"名字"而非"内容锚点"定义身份，锚点集合式身份没有直接先例，但 X 的依赖（import/引用）是可机械解析的文本，为"锚点到引用解析"提供了实现基础；X 的身份脆弱性（改名失效）恰好反衬锚点集合身份在稳定语义上的价值，但锚点方案需自证机械判定性。

### 1.2 间隔重复：Anki 与 FSRS

**Anki SQLite schema（schema11.sql，官方源码）：** 单文件 SQLite 数据库，表有 col（集合配置，conf/models/decks/dconf/tags 都是 JSON 文本列）、notes（id PK、guid、mid、flds 文本、sfld、csum、data）、cards（id PK、nid、did、type/queue/due/ivl/factor/reps/lapses/left/odue/odid、data 文本）、revlog（id PK、cid、usn、ease、ivl、lastIvl、factor、time、type；索引 ix_revlog_usn、ix_revlog_cid）以及同步用 graves 表。复习历史即 revlog 行：一条复习产生一行 ease/ivl/factor/time/type 记录。

**revlog 是否 append-only：否（默认实现不是）。** 官方 Python 源码（2.1.54 tag）中撤销操作（undo）会执行 "select id from revlog where cid = ? order by id desc limit 1" 后 "delete from revlog where id = ?"，即**删除最后一条 revlog**（除非处于预览不计分场景）。因此"复习历史不可变"不是 Anki 的承诺；但正常复习流程下 revlog 只增不删（没有 update 语句改旧行），schema 也没有版本字段区分"重新掌握成新版本"——一次重新掌握表现为 type 变化（重新学习/复习类型）与随后的 ivl/ease 序列，不产生新的"卡片版本快照"。先例做法 X（revlog 可被撤销删除）与红线甲/丁（不可覆盖、可追加）的**关系是**：X 证明"复习记录"在主流实现里是**可变**的，本案若要求不可变，须比 Anki 更严（本案红线是目标，Anki 是反例参照，不能当作满足红线的先例）。

**FSRS 参数与状态的存储：** Anki 源码（card.rs）显示卡片扩展状态含 memory_state: Option<FsrsMemoryState>（stability: f32、difficulty: f32）、desired_retention、decay、last_review_time，序列化在 cards 表的 data 文本（JSON）列中（custom_data 亦然）；deck 配置（deckconfig.rs）含 fsrs_params_4/5/6: Vec<f32>、desired_retention: 0.9（默认）、historical_retention、ignore_revlogs_before_date 等，存于 col 表的 dconf JSON 中。fsrs-rs（FSRS 官方 Rust 实现）README 明确：优化参数从复习日志（FSRSReview { rating, delta_t } 序列）计算，调度时调用方需把 MemoryState { stability, difficulty } 自己存起来（"Replace previous_state/elapsed_days with a stored MemoryState"）。即 **FSRS 不规定状态存哪，只规定状态值形态**；Anki 的落点是"卡片当前状态 + 复习历史日志"，参数本身是当前值的覆盖式更新（fsrs_params_4/5/6 是 Vec 而不是版本化历史）。先例做法 X（状态=当前值+日志，参数可覆盖）与红线甲（旧结论保留）的**关系是**：X 满足"日志可重建历史"（若有 revlog 且不删），但不保留"参数每次变更的版本"，本案若要"参数变更可审计"需自己加版本/追加记录。

### 1.3 学习记录：xAPI / IEEE 9274.1.1 / SCORM / Caliper

**xAPI statement：** 规范（ADL xAPI-Data.md 2.3.1 节）原文 "Statements are immutable (they cannot be changed)."，例外仅是 LRS 处理时指派的 id/authority/stored/timestamp/version、Activity/Verb 的 display 定义、时区序列化、附件、组员顺序、大小写等。撤销唯一方式 = **voiding**：不销毁原 statement，而是发一条含 http://adlnet.gov/expapi/verbs/voided 的新 statement 指向被 void 的 statement，声明其证据应被忽略；voiding 语句本身不可被 void；"unvoid" = 用新 id 重发。JSON 结构为 actor-verb-object（+ result/context/timestamp/stored/authority/version/attachments），object 可以是 Activity/Agent/Group/StatementRef/SubStatement。

**LRS 存储与查询语义（xAPI-Communication.md）：** REST 资源有 statements（PUT/POST/GET/HEAD）、agents、activities、agent profile、activity profile、activity state、about。核心不可变语义：LRS "MUST NOT make any modifications to its state based on receiving a Statement with a statementId that it already has a Statement for"，重复 id 内容不一致应返回 409 Conflict，批量中含重复 id 应 400 Bad Request。**IEEE 9274.1.1-2024**（开源材料，opensource.ieee.org）把同一要求写进标准正文："Statements are expected to be unique and to be immutable. In this regard they are unchangeable and should not be deleted."，并给出 409/If-Match/format=exact 等保持不可变性的机制。**SCORM**：xAPI 的交互类型与响应格式源自 "SCORM 2004 4th Edition Run-Time Environment"（xAPI 规范正文明确写出），SCORM 本身是共享内容对象 RTE，xAPI 是其学习记录层的演进。**Caliper Analytics 1.2**（IMS 官方规范原文）：Event 的 actor、action、object 构成类似 RDF 三元组的结构（"resembles an RDF Triple linking a subject to an object via a predicate"），JSON-LD 序列化，经 Sensor API/Envelope 发送到 Event Store；规范全文未出现 immutability 要求（检索 immutable 0 次），即 Caliper 规范**未规定事件不可变**。

**能否映射 M09"个人学习记录"：** xAPI 的 actor-verb-object + 时间戳/上下文与"谁在何时对什么做了什么学习行为"一一对应，LRS 的按 id 幂等/409 语义可直接作为"个人学习记录"的写入协议；但其不可变性靠"每个 statement 一个全局唯一 id + LRS 不修改"实现，**没有版本链/修订机制**（voiding 是另发新语句而非版本化更新），与红线甲（旧结论保留为可追溯版本）的关系是：X 提供"永不覆盖"的最小语义（id 幂等、void 替代删除），但"同一学习事实的更新/更正"在 xAPI 里表现为新的 statement + void，**没有"同一实体多版本"的建模**，M09 若需要"同一知识节点的修订历史"须自行加实体-版本层；Caliper 连不可变都未规定，作对照说明"不可变"是 xAPI 系的规范选择而非学习记录域的普遍默认。

### 1.4 健康档案：FHIR R5 的版本、Provenance、AuditEvent

**版本机制：** FHIR R5 http.html 原文：update 交互 "creates a new current version for an existing resource or creates an initial version if no resource already exists for the given id"；"If the server supports versions, it SHALL populate the meta.versionId and meta.lastUpdated with the new correct values"；**"there is no support for updating past versions"**。每次更新产生新 meta.versionId，旧版本经 GET [base]/[type]/[id]/_history/[vid]（vread）或 _history 读取；版本支持级别分 no-version / versioned / versioned-update；"Servers that do not support versioning SHALL ensure that Resource.meta.versionId is not present"。HTTP 映射：Logical Id 对应 URL、meta.versionId 对应 ETag（weak，如 W/"3141"）、meta.lastUpdated 对应 Last-Modified。这就是"不覆盖旧结论"的标准实现：**旧版本保留、新版本叠加**。

**文件/无 REST 场景：** versioning.html 原文：确定版本有四种方式（CapabilityStatement.fhirVersion、mime type 的 fhirVersion 参数、资源内 meta.profile、以及仅 R4+ 的版本无关识别），并明确 "The most obvious circumstance [where the version must be in the resources itself] is when resources are stored in files"——此时把版本放进资源自身，例：{ "resourceType": "Patient", "meta": { "profile": ["http://hl7.org/fhir/3.0/StructureDefinition/Patient"] } }，且 "The same technique can be used in a database, or any other kind of storage - just store the mime type (or just the version) alongside the resource."。即 **FHIR 官方明确支持把版本语义剥离 REST/服务器，落成"文件+资源内版本标识"**——这直接回答了问题 4 的"单文件/文件库模式是否可剥离"：**可剥离，且官方给了做法**。

**Provenance / AuditEvent：** Provenance "tracks information about the activity that created, revised, deleted, or signed a version of a resource"；"may be provided about any resource or version, including past versions"；"There may be multiple provenance records for a given resource or version"；基于 W3C PROV，与 AuditEvent 信息重叠。AuditEvent "A record of an event relevant for purposes such as operations, privacy, security, maintenance, and performance analysis"，基于 IHE-ATNA / RFC 3881 / DICOM / ASTM E2147 / NIST SP800-92 / ISO 27789；"All actors involved in an auditable event should record an AuditEvent"，重复条目是预期且有用的。JSON 序列化（json.html）：基于 RFC 8259，resourceType 必须是第一个属性。

**与本案红线的关系：** X（versionId 递增 + 旧版本保留 + 无过去版本更新）与红线甲（不可覆盖）的关系是 Z=**同构**——FHIR 提供了"整资源复制-改-新版本号"的最小版本模型，且官方允许在纯文件模式下把版本放资源自身，可作为 M08/M09 文件库模式的直接参照；但 FHIR 的"不可变"是**服务器语义**（旧版本由服务器保留，文件模式下需要自己保证旧文件不覆盖），Provenance/AuditEvent 是**独立资源**而非内嵌字段，M09 若单文件内嵌历史需另行设计。

### 1.5 审计日志先例：不可变/可追加/可机械校验的最小实现

- **RFC 6962（Certificate Transparency）**："publicly auditable, append-only, untrusted logs"；"The append-only property of each log is technically achieved using Merkle Trees, which can be used to show that any particular version of the log is a superset of any particular previous version."——Merkle 树给出**逐项可证明的追加**（audit path）与**版本包含关系证明**（consistency proof），不依赖信任日志服务器。
- **Log-structured file system（Rosenblum & Ousterhout, SOSP 1991）**：磁盘上只有"日志"，所有修改顺序写入日志，靠索引信息读回；针对写主导负载。这是"日志即存储"的底层先例。
- **Git 对象库**（Git Pro Book 10.2）：content-addressable filesystem，git hash-object 把内容哈希（SHA-1，内容+头）作为对象键，内容不变则键不变、内容一变键即变——"逐内容哈希"的可机械校验最小实现。
- **Bitcoin 白皮书（2008）**："The network timestamps transactions by hashing them into an ongoing chain of hash-based proof-of-work, forming a record that cannot be changed without redoing the proof-of-work."——哈希链把"前一条记录的哈希"卷入后一条，形成防篡改的追加链（时间戳服务器）。
- **Event Sourcing（Martin Fowler, 2005）**："Event Sourcing ensures that all changes to application state are stored as a sequence of events."——状态变化作为事件序列存储，事件日志可重建过去任意状态。
- **NIST SP 800-92（2006）**：日志管理指南，建议日志写入者使用 **append-only 权限**（"users should have append-only privileges and no read access if possible. Users should not be able to rename, delete, or perform other file-level operations on log files"），并建议为归档日志创建**消息摘要**（"creating and securing message digests for the files"）。
- **WORM（write once, read many）术语：** NIST CSRC glossary 页面抓取失败（404/JS 重定向），**未核**；WORM 概念可由 NIST SP 800-92 的 append-only 权限建议替代支撑。

与本案红线的**关系**：这些先例给出"可机械校验的追加式存储"的成熟谱系——逐行/逐内容哈希（Git）、哈希链（Bitcoin）、Merkle 一致性证明（RFC 6962）、事件序列（Event Sourcing）、append-only 权限（NIST）——均为红线丙/丁的最小实现选项；"逐行哈希 + 链式哈希"在单文件场景可直接落地，成本与校验复杂度都可控。

- 原文摘录: "Git is a content-addressable filesystem. ... at the core of Git is a simple key-value data store... you can insert any kind of content into a Git repository, for which Git will hand you back a unique key you can use later to retrieve that content."
- 证据等级: A
- 对 M08/M09 的映射启示: 内容寻址把"身份=内容哈希"与"校验=比对键"合一；与红线乙（身份=锚点集合）的关系是 Z=**近邻但不同**：Git 用整内容哈希做键，锚点集合是"内容的一部分（引用点）"，可把锚点集合序列化后哈希作为节点键，Git 证明该路线在大规模版本库中可行（40 字符 SHA-1 键+增量对象存储）。

**KF23. Bitcoin 白皮书：哈希链使记录不可改（除非重做工作量证明）**
- 来源: https://bitcoin.org/bitcoin.pdf
- 标题: Bitcoin: A Peer-to-Peer Electronic Cash System
- 机构: Satoshi Nakamoto（白皮书，2008）
- 日期: 2008-10
- 原文摘录: "The network timestamps transactions by hashing them into an ongoing chain of hash-based proof-of-work, forming a record that cannot be changed without redoing the proof-of-work."
- 证据等级: A
- 对 M08/M09 的映射启示: 逐条哈希链是最小防篡改结构：每条记录携带前条哈希，改动任一条即破坏后续全部校验；M08 单文件逐行哈希链可低成本实现"行级不可变"，无需工作量证明（其防篡改强度依赖外部副本与审计，而非算力）。

**KF24. Event Sourcing：所有状态变化存为事件序列，事件日志可重建任何过去状态**
- 来源: https://martinfowler.com/eaaDev/EventSourcing.html
- 标题: Event Sourcing
- 机构: Martin Fowler（个人技术写作）
- 日期: 2005-12-12
- 原文摘录: "Event Sourcing ensures that all changes to application state are stored as a sequence of events."
- 证据等级: A
- 对 M08/M09 的映射启示: "状态=事件序列的折叠"与红线甲（旧结论保留）的关系是 Z=**直接支撑**：只要事件序列完整，任意时点状态可重算，天然不覆盖；M09 学习记录若以事件溯源建模，则"当前掌握状态"只是派生视图，底层只有追加事件。

## 3 冲突与张力

1. **"不可变"在规范之间级别不一**：xAPI/IEEE 9274.1.1 明文 immutable（但 IEEE 正文允许 LRS 因数据管理流程删除，是 should 级）；Caliper 1.2 全文无 immutability；Anki revlog 可由撤销删除；FHIR 旧版本由服务器保留但"不可变"是服务器语义而非文件格式保证。M08 若把"不可变"定为红线，须自选等级（MUST 级）并定义例外集，不能默认某规范替我们承诺。
2. **名字式身份 vs 锚点式身份**：mathlib（模块路径）与 MML（文章名+标签号）都是名字身份，改名/重构会破坏引用；本案红线乙=锚点集合身份无直接先例。张力在于：锚点集合身份更稳但更贵（需定义锚点语法、冲突消解、机械判定），名字身份便宜但脆。
3. **"修订=改旧文章"（MML authorized revision）与"不覆盖旧结论"（红线甲）直接冲突**：MML 靠整体版本目录兜底，Anki 靠 revlog 可删（更弱），xAPI 靠 voiding（不删只标注作废），FHIR 靠新版本叠加。四者给出从"允许改旧+目录快照"到"只增不改"的光谱，M08 须选一点并写明取舍。
4. **状态存储 vs 历史保留**：FSRS/Anki 的"当前状态+日志"模式中参数（fsrs_params_4/5/6）是覆盖式更新，无参数版本历史；而红线甲要求旧结论保留。张力在于"算法当前值"是否算"结论"：若算，则参数每次变更也须版本化/追加化，Anki 先例不满足。
5. **可剥离性结论的边界**：FHIR 官方允许文件模式把版本放资源自身，但 Provenance/AuditEvent 在 FHIR 中是独立资源（外键式），单文件模式若要内嵌历史需自行压缩；"REST/JSON 可剥离"不等于"版本机制可内嵌单文件"，两者是不同层的问题。
