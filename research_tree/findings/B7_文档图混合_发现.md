# B7 文档-图混合与人可读写载体 — 发现

## 0 一句话结论
在"人可读写优先"的载体谱系里，Obsidian 式（文件=节点、frontmatter=属性、wikilink=边）与 Logseq 文件版把"节点身份=文件路径/块 id"而非"锚点集合"，因此对"锚点逐字 grep -F 硬校验"工作流，纯文本文档侧天然契合（锚点即正文，grep 直接作用于源文件）；但 Logseq 官方把"文件版"与"数据库版"拆成两个产品并明言 DB 版面向同步/协作/性能，且 DB 版的"standard Markdown 导出无法捕获全部数据（时间戳/属性）"说明——一旦图侧数据进入数据库，Markdown 就不再是完整真相，锚点判等被间接化；文档-图共存的标准化路径（RDFa REC、JSON-LD REC、YAML-LD WD、语义 wiki）均已存在，但"节点身份=锚点集合"在文档载体中没有权威先例（未核），须应用层自建模。

## 1 逐条回答
### Q1 Obsidian（文件+frontmatter+wikilink）与 Logseq（大纲块引用）的数据模型
- Obsidian：节点=文件（vault 是本地文件夹，笔记是 Markdown 纯文本文件）；边=正文中的内部链接 `[[...]]`（vault 内局部）+ frontmatter 属性（Properties 页面：属性含 text/links/dates/checkboxes/numbers 等结构化数据）。节点身份=文件路径（vault 内唯一），不是锚点集合；锚点逐字串是正文内容本身，grep -F 直接作用于源文件即可，无需任何图谱序列化。
- Logseq：DB 版节点=page 或 block 的统一（db-version.md 原文 "A node is a new term for a page or block because the two now behave similarly"）；文件版块引用依赖解析器（`(())`/`[[]]`），DB 版块身份由数据库管理，不是文本内逐字串。
- "节点身份=锚点集合"：文档载体中身份层=文件路径/块 id，锚点=内容层，两者不在同一抽象层；把锚点集合作为身份需要应用层绑定，未找到标准载体先例（未核）。
### Q2 Logseq 从 Markdown 文件迁向 DB 版本的官方理由
- 官方公告（2026-04-24，logseq.io）：Logseq 拆分为两个产品——Logseq OG（文件版，面向"偏好本地 Markdown 文件"的用户，转入维护模式：安全修复+依赖升级）与 Logseq（数据库图，面向"增强图同步、协作与性能"的用户）。
- db-version-changes.md 明列 DB 版收益："loading faster, handling larger graphs and large tables"；"All blocks and pages have created-at and updated-at timestamps! With this built-in dimension of time, time powered features are possible."
- 即：官方认为纯文本 Markdown 文件在同步/协作/性能/内建时间戳需求上不够，但并未否定文件版价值，而是拆成两个产品分别服务。
- 完整性警示：db-version.md 的导出选项里，EDN 是"唯一完整捕获图数据且可编辑"的导出；"Export as standard Markdown"因不可能导出时间戳与全部属性而"无法捕获图内全部数据"——进入 DB 模型后 Markdown 不再完整。
### Q3 Semantic MediaWiki 存储模型与版本历史 vs M09 版本语义
- SMW：页面=文档，页面内语义注解（属性）=图数据（"SMW adds semantic annotations that allow a wiki to function as a collaborative database"）；数据存于 wiki 页面，可从外部经 API 或 RDF triplestore 查询；"All data created within Semantic MediaWiki can easily be exported or published via the Semantic Web"。
- 版本机制：MediaWiki 每页修订历史（Help:Page history："The page shows the newest changes first, followed by older ones. To view a specific version, click its date."）——粒度为"页面任意编辑快照"，可被回退/按权限删除，不承诺"旧结论不覆盖、不物理删除"。
- 与 M09 差异：M09 需要"结论对象级"版本化（复检/遗忘/重新掌握=新版本、旧结论保留），MediaWiki 修订只是页面级时间维度，语义映射须应用层自建模；且 wiki 修订可删除，与本项目红线"不物理删除"冲突，须自写 MUST。
### Q4 文档与图共存的标准化路径
- RDFa Core 1.1（W3C REC 2015-03-17）："a specification for attributes to express structured data in any markup language"，底层抽象模型是 RDF——文档内嵌图的成熟标准化路径之一。
- JSON-LD 1.1（W3C REC 2020-07-16）：JSON-based 序列化 Linked Data，"provides a smooth upgrade path from JSON to JSON-LD"，可内嵌 HTML（script type application/ld+json，B8 已涉）。
- YAML-LD 1.0（W3C Working Draft 2026-07-28）："a set of conventions on top of YAML which specify how to serialize Linked Data as YAML based on JSON-LD syntax, semantics, and APIs"；约束 YAML 使任何 YAML-LD 文档可表示为 JSON-LD——面向文档友好的 YAML 载体的 Linked Data 序列化正在标准化（未达 REC）。
- 语义 wiki 本身=文档+图共存先例（页面=文档、注解=图、可导出 RDF）。
- nanopub 的 Markdown 人可读序列化尝试：未找到权威原文（未核）。
### Q5 对"锚点逐字 grep -F + 人审"工作流的增益与代价
- 增益：锚点定义=源文本逐字串；文档-图混合中"文档侧"保留纯文本可 grep 层，锚点硬校验可直接作用于源文档，与图侧存储解耦；本地 522 节点实验的 `grep -qF -f` 校验正是作用于源 markdown（audit-nodes.md 原文），该流程在文档载体下不需要中间层。
- 代价：图侧（节点身份/属性/边/时间戳）一旦进入数据库（Logseq DB 版模式），正文虽仍是 Markdown，但"锚点→节点"绑定要经解析器/导出器间接化；DB 版 standard Markdown 导出丢失时间戳与属性即为证。
- 结论（推断 C）：对锚点逐字 grep + 人审工作流，人可读文档载体（Markdown/org + 显式属性）最契合；越往数据库端走，越需要"先从存储还原正文再 grep"的中间层，硬校验被间接化。

## 3 冲突与张力
- "文档即真相"（Obsidian/org-roam/Logseq 文件版）vs "图即真相"（Logseq DB 版/SMW）：DB 版官方导出说明证明 Markdown 无法承载全部图数据（时间戳/属性/块 id），文档派则要求一切可 grep 可人读；两种承诺不可兼得于同一载体。
- 官方二分（Logseq 拆分两产品）证明"人可读本地 Markdown"与"同步/协作/性能"是真实取舍，不是同一载体的两种视图。
- MediaWiki 页面修订（可回退、按权限删除、页面粒度）vs 本项目红线（不物理删除、结论对象级版本、旧结论不覆盖）：先例机制不足以直接承接，须应用层自建版本语义。
- 文档载体的"锚点=正文可 grep"优势 vs DB 载体的"时间戳/属性/查询"能力：锚点硬校验越贴合文档侧，结构化查询越弱（反之亦然）。
