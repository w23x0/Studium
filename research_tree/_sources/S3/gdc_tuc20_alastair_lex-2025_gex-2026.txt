TEXT2GRAPHQUERY includes LEX and "openGQL"

GDC is moving LEX and GQL Implementation activities into the TEXT2GRAPHQUERY
project, which is a defining use case, and one which needs strong schema. LEX is an
existing project, running so far from Nov 22 to Feb 25, and restarting this August. GQL
Implementation covers ANTLR grammar, GQL code editor etc., starting 2024.

The charter defines LEX output as a PG schema definition language
  Extends GQL graph types (compatible with GQL and SQL/PGQ)
  Concrete and definite, not speculative or exploratory ("Will, not could")
  Ensure PG users are broadly level with SQL and SHACL users
  Connects to the pre-existing world of conceptual data modelling (ERA)

Assumes RDF languages/vocabularies cannot be used directly with GQL graphs
      That's a defining condition of our charter (and has been there since we started)

RDF BONUS 1: Schema languages with formal semantics that LLMs like

The lack of proper schema language in LPG is a major limitation for GraphRAG - you
have nothing to pass to the LLM to help it understand the data in the graph and be
able to query it. Both precision and recall will suffer when arbitrary information is
placed on nodes and edges without formal schemes.

All major LLMs know and "understand" RDF, RDF Schema, OWL SKOS and SHACL. One of the most efficient retrieval
methods in GraphDB's Talk-to-you-graph tool is the SPARQL one - you only need to tell the model where your ontology is and
it generates decent SPARQL queries, sets the parameters using vector-based entity retrieval, executes the query and
combines the results with those from other retrieval methods. Overall, the RDF stack offers the most efficient method for
passing domain knowledge to an LLM.

There are many things that can be said and done at the level of schema, that are
simpler, more efficient and more comprehensible than things said and done at the
level of the instance. GraphAr yet another reminder.

      It is not an accident that SQL is schema-centric
      And SQLite is also not an accident: data is often chaotic

Property graphs are an opening for the full spectrum (water to ice)

LEX can be the first manifestation of that concept, which is explored in
PG-Schema. This could take the form of OPEN and CLOSED element types.
The "Ontology Gaps"

What SQL/PGQ and GQL can do that Cypher can't
       Define a graph schema (node and edge types), and define keys for them

What SQL can do that GQL can't
       Keys, domains, CHECK constraints, FKs, Information Schema, typed DML

What JSON Schema can do that GQL can't
       Intra-record constraints
       (X-field validations, ranges, string formats ~ SHACL Core Constraints)

What RDFS/SHACL and PG-Schema can do that GQL can't
       Sub-classing, sub-graph shapes

What EERM/UML can do that GQL can't
       Cardinality constraints on elements and relations, N-ary relations, sub-typing(classing)
