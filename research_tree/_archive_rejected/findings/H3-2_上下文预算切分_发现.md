# 叶子 H3-2 上下文预算与切分 调研发现
> ⚠ **已归档（2026-08-15 产品裁决）**：本卡属老旧范式（agent 记忆/RAG/知识库/上下文工程，临床办公场景），与「个人多教材理科学习」项目不匹配，已移入 _archive_rejected/，仅作历史参考，不再作为 Studium 设计依据。

> 任务 H3-2 / A=原文到手 B=二手转引 C=推断
> 调研主题：无界/长上下文下按预算切分代理、成本-质量权衡、prompt caching 命中率边界
> 时间锚定：全部证据 2024-01 之后（vCache 2025-02、Auditing 2025-02 均达标）

## 0. 一句话结论
**prompt caching/上下文预算是「策略敏感」而非「普适存在或普适无效」**：500+ 真实 agent 会话实证表明，得当的缓存策略（动态内容置末、防前缀断裂、按预算切分）可降成本 41–80%、TTFT 13–31%；但缓存收益不是自动的——缓存的创建与读取本身主导了输入侧成本，token 减少 ≠ 成本减少（压缩 38.4% 送达 token 反而使成本 +6.8%）。既有 memory「网关命中率 6%、不值得缓存」是特定负载下的局部实测，**不能一般化**成「不做缓存」的普适结论。

## 1. 父会话问题逐条回答

**Q1. 文献如何对无界上下文做预算/切分？「按上下文预算切分代理，不按任务语义」有何佐证或反例？**
- 结论：文献支持「缓存连续性」是切分的首要约束，与「按任务语义切分」需协调。TokenPilot 明确指出：文本裁剪/记忆淘汰会改布局→前缀不匹配→整段缓存失效，揭示 **text sparsity（文本稀疏）与 prompt cache continuity（缓存连续性）的 trade-off**。其解法是双粒度管理：Ingestion-Aware Compaction（在摄入门稳定前缀、消除环境噪声）+ Lifecycle-Aware Eviction（按段残余效用保守卸载），降成本 61–87%。Don't Break the Cache 佐证：动态内容放末尾、排除动态工具结果，比「naive 全量缓存」更稳（naive 全量缓存甚至可能反向增延迟）。这**支持**「按预算/缓存连续性切分」优先，而任务语义切分需与缓存结构对齐才不冲突。
- 依据：2606.17016 TokenPilot abstract；2601.06007 Don't Break the Cache abstract
- 等级：A

**Q2. 上下文随输入增长的延迟/成本超线性是否有量化实证？prefill 量对首 token 延迟？**
- 结论：文献证实 prompt 缓存对 TTFT 的收益是**线性且普遍**的（500–50k token 的消融、3–50 次工具调用，均线性收益），但「缓存 token 下限」是门槛（provider caching token minimum,低于则不命中）。缓存命中比未命中处理显著快（Auditing Prompt Caching 正是利用这一点做时序侧信道）。成本侧：Don't Break the Cache 量化 41–80% API 成本降幅。/Token Reduction 指出成本被 **prompt-cache 创建和读取主导**，只有有限小比例可被输出端压缩触及——所以「输出少 token」不解决输入侧主导成本。PI-Mem 展示长上下文极限（3.6M token）靠 parallel-iterative memory 而非无限 prefill。
- 依据：2601.06007（线性收益+token 下限）；2607.12161（缓存成本主导）；Auditing(时序差异)；2608.03048（长上下文极限）
- 等级：A

**Q3. prompt caching 的命中率/收益边界——何时值得缓存、何时不值得？**
- 结论（结合实证与既有 memory，C/A 混）：值得缓存的条件 = 前缀稳定 + 请求重复 + 达到 provider token 下限；(a) 长程会话反复提交相同 transcript 前缀 → 值得（TokTier 指出 coding agent 反复提交长 transcript 是最痛场景）；(b) 前缀频繁被动态内容打断 → naive 缓存低效甚至增延迟（Don't Break the Cache）；(c) 缓存创建/读取本身成本占大头时，压缩输出端省不到钱（Token Reduction）。2024 年后缓存语义从「严格前缀」走向「位置无关」（MiniPIC：非相同前缀也可复用 K 向量，prefill 吞吐 +49%、缓存 span TTFT 降两个数量级；vCache：语义缓存复用相似 prompt）。既有 memory「6% 命中率」适用前提 = 前缀频繁变化的通用网关负载；在该类负载下缓存收益确实有限，但这与「长程会话稳定前缀」场景有本质区别。
- 依据：2607.29678 TokTier、2606.13126 MiniPIC、2502.03771 vCache、2601.06007、既有 memory（gateway-no-prompt-caching）
- 等级：A（文献）+ C（既有 memory 的一般化作法）

## 2. 关键发现

**F1. 【Don't Break the Cache：500+ agent 会话实证 prompt caching 降成本 41–80%、TTFT 13–31%】**
- 论断：首次量化跨 OpenAI/Anthropic/Google 三家、DeepResearch Bench 500+ 会话；战略缓存块控制（动态内容置系统提示末尾、避免动态传统 function calling、排除动态工具结果）比 naive 全量缓存更一致获益；naive 全量可能反向增延迟；线性成本/TTFT 收益普遍，但有 provider token 下限。
- 来源：arXiv 2601.06007v2，abs 页 arxiv_abs_2601.06007.html；Elias Lumer 等；published 2026-01-09
- 原文摘录：「prompt caching reduces API costs by 41-80% and improves time to first token by 13-31% across providers」；「naive full-context caching, which can paradoxically increase latency」
- 等级：A

**F2. 【Token Reduction Is Not Cost Reduction：token 减 ≠ 成本减，缓存成本主导输入侧】** 
- 论断：压缩 38.4% 送达工具输出 token 反而使账单成本 +6.8%；token 减少与成本弱相关（Pearson r=0.15）；成本分解显示 prompt-cache 创建/读取主导输入侧成本，仅有限比例可被输出压缩触及；压缩还会改变 agent 轨迹（更多检索/诊断/测试轮）抵消局部节省。
- 来源：arXiv 2607.12161v5，abs 页 arxiv_abs_2607.12161.html；Sarel Weinberger, Amir Hozez；published 2026-07-13
- 原文摘录：「The largest compression setup reduced delivered tool-output tokens by 38.4% but increased billed cost by 6.8%」；「prompt-cache creation and reads dominate the measured input-side cost」；「token reduction is not a reliable proxy for cost reduction」
- 等级：A

**F3. 【TokenPilot：缓存连续性 trade-off，双粒度上下文管理降成本 61–87%】**
- 论断：文本裁剪/记忆淘汰改布局→前缀不匹配→缓存失效，是文本稀疏与缓存连续性的根本 trade-off；Ingestion-Aware Compaction（稳定前缀）+ Lifecycle-Aware Eviction（段残余效用保守卸载）双粒度，PinchBench/Claw-Eval 降成本 61%/56%(isolated)、61%/87%(continuous)；集成进 LightMem2。
- 来源：arXiv 2606.17016，abs 页 arxiv_abs_2606.17016.html；Buqiang Xu 等(ZJU)；published 2026-06-15
- 原文摘录：「unconstrained sequence mutations alter layouts, introducing prefix mismatches and cache invalidation. This reveals a critical trade-off between text sparsity and prompt cache continuity」
- 等级：A

**F4. 【缓存语义演进：前缀缓存 → 位置无关缓存（PIC）】**
- 论断：前缀缓存(vLLM 等)须请求共享相同前缀才复用 KV；MiniPIC 用无位置编码 K 缓存 + 用户可控缓存复用原语（block-aligned padding/SSep/PDep），<100 行实现 Block-Attention/EPIC/Prompt Cache 多种 PIC；2WikiMultihopQA prefill 吞吐 +49%、缓存 span TTFT 降两个数量级、线性 prefill 扩展保持、最坏 5.7% 开销。
- 来源：arXiv 2606.13126，abs 页 arxiv_abs_2606.13126.html；Nathan Ordonez, Thomas Parnell(IBM)；published 2026-06-11
- 原文摘录：「prefix caching in engines such as vLLM cannot reuse their KV entries unless they share identical prefixes with another request」
- 等级：A

**F5. 【KVEraser：局部编辑有全局后果，KV 层上下文擦除需刻意导流】**
- 论断：post-hoc 上下文擦除难在一个 span 被处理后其影响会全局扩散；需学习性导流在 KV cache 上做局部擦除。与 H3-1 的「重构不破坏副作用」在上下文形态层同构。
- 来源：arXiv 2606.17034v2，published 2026-06-15（API summary 到手）
- 原文摘录：「a local edit has a global consequence: once a span has been processed, its influence begins to diffuse across the entire sequence」
- 等级：A

**F6. 【PI-Mem：长上下文极限的对照——3.6M token parallel-iterative memory】**
- 论断：长上下文推理是瓶颈；recurrent-memory 有两大固有挑战；PI-Mem 用 parallel-iterative memory 把长上下文推理推到 3.6M token——提供『无限 prefill 撞墙』之外的退化路径参考（记忆外置而非全量进窗口）。
- 来源：arXiv 2608.03048，published 2026-08-04（API summary 到手）
- 等级：A（标题+摘要，正文未核）

## 3. 对决策点的输入
- **「按上下文预算切分代理」获文献强支持**，且切分的第一约束是缓存连续性（前缀稳定），不是任务语义分区。Studium 若在 proxy 层切分长程上下文，应让「稳定前缀」优先、动态片段置末，与缓存结构对齐。
- 缓存该不该做的判定=看负载形态：稳定长前缀会话=值得；前缀多变的通用负载=收益有限（呼应既有 memory 6%）。
- 成本度量应以 cost-per-successful-task 而非 token 数（Token Reduction 强论据）。

## 4. 与范围/红线的冲突张力
- 无红线冲突。切分边界：不评估具体缓存产品定价策略（聚焦机制与边界），已遵守。
- 与既有 memory「网关不做 prompt caching」表面张力：本叶澄清为负载形态差异，不推翻 memory，但标注其适用前提（避免 memory 被误读成普适断言）。
